# 오프라인 OCR SOTA 5종 — 한국 보험약관 표 벤치마크 계획

- 작성: 2026-08-03 18:50 KST
- 범위: `2열짝짓기` 보류 고유 109,192개 중 업무 관련 표의 회수 가능성 검증
- 장비: `x600`(RTX 4070 SUPER 12GB), 필요 시 `runpod-gpu`
- 안전 원칙: 신규 결과는 이 계획에서 **절대 serving/citation에 연결하지 않는다.** 별도 실험 산출물로만 저장한다.
- 선행 계획: [표 추출 한계 5종 해결 계획](2026-08-03_1200_표추출_한계5종_해결계획.md)

## 1. 목표와 질문

최신 오프라인 문서 OCR/파서가 현재 좌표 추출기보다 다음 실패군을 실제로 더 살리는지 잰다.

1. 무테두리 3열 이상 표
2. 다단·병합 헤더 표
3. 자기부담금의 금액↔행↔열 축 결합
4. KCD 코드의 영문자/숫자 혼동(`I00`↔`100`)
5. 페이지 분할 표

이번 실험의 질문은 "표 HTML이 예쁜가"가 아니다.

> **같은 원문에서 업무 fact의 값·축·근거를 더 정확하게 회수하는가?**

### 후보 선정 원칙

- API 전용 제품은 제외한다. 가중치를 내려받아 네트워크 없이 재실행할 수 있어야 한다.
- 전역 SOTA 4개와 **한국어 목적 SOTA 1개**를 함께 둔다.
- MOSS-OCR 0.3B는 작고 빠르지만 공식 지원 언어가 영어·중국어·일본어라 이번 5종에서 제외한다.
- 35B급 Infinity-Parser2-Pro는 x600 12GB에서 동일 조건 비교가 불가능해 제외한다.

## 3. 과거 Paddle 실험과 다른 점

기존 실측은 PaddleOCR-VL-1.6 페이지 파이프라인이 22개 표에 약 11,066초, 12GB OOM,
KCD `I00~I02`를 `100~102`로 오독해 탈락했다. 그 결과를 지우지 않는다.

이번에는 다음을 분리해 잰다.

1. **page-level**: OvisOCR2·MinerU·BizOnAI의 공식 전체 페이지 경로
2. **table-region**: 동일 표 영역을 Paddle `task=table`, GLM `Table Recognition:` 등으로 입력
3. **공통 후처리**: 모델별 Markdown/HTML을 동일 정규화기로 fact 후보화

Paddle은 전체 페이지 파이프라인을 다시 3시간 돌리지 않는다. 공식 문서가 명시한
Transformers element-level 경로로 표 영역만 처리해 모델 자체의 표 인식 능력을 분리한다.

## 4. 평가셋

### P0 — 연결·설치 smoke

- 1쪽: 흥국화재 KCD 특정질병분류표 `ff0521a99902`, PDF p109
- 합격: 프로세스 정상 종료, 비어 있지 않은 UTF-8 출력, 실행시간·VRAM 기록

### P1 — 비교 표본

최소 5쪽, 보험사·표 유형을 겹치지 않게 고른다.

| 표본 | 용도 |
|---|---|
| 흥국화재 KCD p109 | 기존 22행 정답, `I`↔`1` 오독 검출 |
| NH농협생명 자기부담금 p26~27 | 다단 헤더·금액·급여/비급여 관계 |
| 삼성화재 자기부담금 p40~41 | 3열 이상 무테두리·페이지 분할 |
| 롯데손해보험 자기부담금 후보 | 다른 조판 일반화 |
| DB손해보험 자기부담금 후보 | 용어정의/금액 표 구분 |

원문은 `data/raw/`에서 읽되 원격에는 `sha12_pNNN.png`만 보낸다. DB 자격증명·매니페스트는 보내지 않는다.

### P2 — 확장

P1에서 하나라도 기존 좌표 방식보다 나은 모델만 30쪽→100쪽으로 확대한다.
5종 모두를 109,192개에 바로 돌리지 않는다.

## 5. 지표

### 자동 지표

| 지표 | 정의 |
|---|---|
| `process_success` | 정상 종료하고 구조화 출력 생성 |
| `latency_s/page` | 모델 로드 제외 warm latency와 cold latency 분리 |
| `peak_vram_mb` | `nvidia-smi` 실측 |
| `kcd_pair_exact` | 질병명↔KCD 코드 22쌍 exact match |
| `kcd_letter_digit_error` | `I`↔`1`, `O`↔`0` 오류 수 |
| `amount_exact` | `8천원`, `1만5천원`, `2만원`, `%` exact match |
| `header_binding` | 값이 올바른 행·열 헤더에 연결됐는지 |
| `table_structure` | 행/열/병합 구조 관계 보존 |
| `source_grounding` | 결과를 원문 페이지/영역으로 되짚을 수 있는지 |

### 채택 게이트

- `kcd_letter_digit_error = 0`
- 자기부담금 금액 오연결 **0건**
- 기존 좌표 방식보다 fact recall이 높을 것
- 오류·누락을 숨기지 않고 실패로 기록할 것
- 최소 P1에서는 페이지당 실사용 가능한 시간일 것

평균 점수보다 **치명 오류 0건**을 우선한다. 게이트 미통과 결과는 candidate fact에도 자동 승인하지 않는다.

## 6. 원격 실행 구조

```text
local repo
  ├─ docs/plans/...
  ├─ data/eval/ocr_sota5/{manifest, gold, images}
  └─ scripts/eval/ocr_sota5_*.py
          │ scp: sha12_pNNN.png + 실행 스크립트만
          ▼
x600 F:\ocr_sota5_20260803
  ├─ env/
  ├─ models/          # Hugging Face cache
  ├─ input/
  ├─ output/{model}/
  └─ logs/
```

- 모델은 한 번에 하나만 GPU에 올린다.
- 첫 모델의 smoke가 끝나기 전 다음 대형 모델을 받지 않는다.
- 각 실행은 model id·revision·패키지 판·GPU·입력 SHA256을 기록한다.
- 원격 원본과 산출물은 벤치 종료 후 바로 삭제하지 않는다. 삭제는 별도 승인 전까지 하지 않는다.

## 7.1 실행 결과와 채택 결정

- 결과 리포트: [오프라인 OCR SOTA 5종 x600 실측](../reports/2026-08-03_2010_오프라인_OCR_SOTA5_x600_실측.md)
- 동일 KCD 22행 exact: OvisOCR2 21/22, MinerU2.5-Pro 21/22, GLM-OCR 3/22,
  PaddleOCR-VL 1.6 0/22, BizOnAI-OCR 0/22. Paddle/BizOnAI에서 핵심 `I→1` 오독을 확인했다.
- 자기부담금 P1 7쪽에서 MinerU는 전부 HTML 표를 만들고 중국계 문자 혼입·중복 라인 0을 기록했다.
  Ovis도 표는 만들었으나 페이지별 중국계 문자 8~66자, 중복 라인율 33~96%였다.
- **1차 채택: MinerU2.5-Pro를 고가치 업무 후보의 shadow page parser로 사용한다.**
  기존 109,192개를 자동 승인하거나 전수 serving으로 전환하지 않는다.
- OvisOCR2는 보조 비교군, GLM-OCR은 빠른 region 재검 후보로 남긴다.
  PaddleOCR-VL 1.6과 BizOnAI-OCR은 이번 x600/KCD 조건에서는 확대하지 않는다.
- Paddle NF4 4bit 후속은 VRAM 2,162.5→1,173.4MB로 감소했지만 81.425→84.225초로 느려졌고
  `I00→100` 오독이 유지됐다. 공식 GGUF는 x600 Windows 정책에서 llama.cpp 실행 전 차단됐다.
- 다음 게이트는 48개 원문 3쪽 창 층화 평가와 자기부담금 전용 axis binder다.
  MinerU의 공식 cross-page table merging이 아직 없고, 실제 p26→p27 연속 표의 부모 셀도 p27에서는 비어 있었다.

## 8. 중단 조건

- 공용 GPU 사용자가 나타나면 새 추론 시작 중단
- 모델 라이선스가 업무 사용과 충돌하면 다운로드 전 제외
- VRAM OOM 2회 후 임의 설정 변경을 반복하지 않고 `resource_incompatible`로 기록
- 한 표에 30분을 넘기면 timeout 처리
- 원문/근거가 없는 출력은 정확해 보여도 `ungrounded` 처리
