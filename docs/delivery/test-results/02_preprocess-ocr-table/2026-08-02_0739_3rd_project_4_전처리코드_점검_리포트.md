## 2. 우리 기준을 어기는 것 — 고쳐야 함

### 2.1 조용한 조항 소실 + 인용 오귀속 ★ (RULE 3장 / CLAUDE.md 0장)

`doc_processor.py:194` 가 헤더를 **순차 문자열 일치**로 본문 줄에 되찾는다.

```python
if hi < len(headers) and headers[hi].raw == ln.strip():
```

그런데 `headers[].raw` 는 `clause_detector.py:154` 의 `clean_line()` 을 거친 값이고,
거기서 **NBSP(`\xa0`) → 일반 공백**으로 바뀐다. `lines[]` 는 안 바뀐다.
→ 헤더 줄에 NBSP 가 **하나만** 있어도 그 헤더는 영영 매칭되지 않고, `hi` 가 멈춰
**그 뒤 헤더 전부**가 위치를 못 찾는다.

재현했다(3개 조항, 2번째 헤더에만 NBSP 삽입):

```
검출된 헤더: ['제1조(목적)', '제2조(용어의 정의)', '제3조(보상하지 않는 사항)']
생성된 청크 조번호: [1, 1, 1, 1]        ← 2·3조 본문이 제1조로 흡수됨
n_clauses(리포트값) = 3  /  실제 청크가 나온 조 = 1
```

**두 가지가 동시에 나쁘다.**
1. 제3조 본문이 `citation="제1조(목적) 제1항"` 을 달고 나간다 — **틀린 근거**다.
2. `quality_report.csv` 의 `n_clauses` 는 여전히 3이다. 분모가 안 줄어 **지표가 좋아 보인다.**

**실제 코퍼스에서 몇 건이 이 증상을 겪었는지는 이 산출물로 셀 수 없다** — §2.2 참조
(`chunks_clean.jsonl` 과 `quality_report.csv` 가 서로 다른 코드 버전의 산출물이라
교차 대조가 성립하지 않는다). 확정된 것은 **결함의 존재와 재현 절차**까지다.

세는 방법 자체도 간단하지 않다. 조 번호는 특약마다 1로 리셋되므로
`distinct(article_no)` 로는 소실을 잴 수 없다(처음에 그렇게 셌다가 틀렸다).
gid 순서로 런(run)을 세는 방법도 분권 병합 문서에서 `n_clauses` 를 역전해 신뢰할 수 없었다.
**제대로 세려면 `unmatched_headers` 를 코드에 심고 재실행해야 한다.**

**고침:** 매칭을 `raw` 비교 대신 `clean_line(ln)` 비교로 바꾸고, `hi` 가 멈추면
**세어서 보고**한다(`unmatched_headers`). 못 찾은 헤더 수가 0이 아니면 `suspect`.

### 2.2 산출물이 코드와 어긋나 있다 — chunk_id 중복 15,429건 (RULE 1.2)

`chunks_clean.jsonl` 전수 검사:

```

최다: '50908#00003::제4조(보상하지 않는 사항)' 9회
```

`check_quality.py` 가 스스로 **"`chunk_id 중복: 0` 이면 통과"** 로 정의한 기준을
프로젝트 폴더에 놓인 산출물이 못 넘긴다.

**★그런데 지금 배포된 `batch_runner.py` 는 이 중복을 만들 수 없다.**
`chunk_id=f"{doc_id}#{gid:05d}::…"` 의 `gid` 는 문서 내 전역 순번이라 구조상 유일하다
(`doc_processor.py:226`). README 도 `fix_ids.py` 를 *"구버전 batch_runner 로 만든 기존
chunks_all 의 충돌 재부여 — 처음부터 새로 돌리는 사람은 필요 없음"* 이라 적었다.

→ **`chunks_clean.jsonl`(240MB)은 폐기된 구버전 코드의 산출물이다.**
   `quality_report.csv` 는 신버전 산출물이다. **둘은 같은 실행의 결과가 아니다.**

결과적으로:
- 이 jsonl 을 그대로 임베딩하면 벡터DB에서 같은 id 가 9개까지 겹친다.
- **jsonl 과 CSV 를 교차 대조한 지표는 전부 무효다.** (§2.1 의 피해 건수, 조항 길이 분포 등)
- 폴더에 최신 산출물이 없으므로 **검증 가능한 상태가 아니다.** 재실행이 선행돼야 한다.

### 2.3 보조 PUA ⑩ 이상 매핑 — 우리가 렌더링으로 반증한 부분

`clause_detector.py:124`

```python
_PUA_CIRCLED = {chr(0xF02B1 + i): '①②③④⑤⑥⑦⑧⑨⑩⑪⑫⑬⑭⑮⑯⑰⑱⑲⑳'[i] for i in range(20)}
```

**20개를 전부 산술로 매핑한다.** 우리 `to_page_json.py:107` 은 `range(1, 10)` — **1~9만** 한다.
이유는 주석(:102-106)에 있다: 코덱스가 PDF 를 직접 렌더링해 확인한 결과
**`⑩` 은 `U+F02BA` + `U+F02C3` 두 문자가 같은 자리에 겹쳐** 나온다.
`U+F02B0+n` 산술식을 10 이상으로 늘리면 **틀린다.**

→ `_3rd_project_4` 는 `U+F02BA` 를 `⑩`, `U+F02BB` 를 `⑪` 로 확정 치환한다.
제10항 이상이 있는 조항에서 **항 번호가 틀린 인용**이 나갈 수 있다.
(스캔 결과 산출물에 보조 PUA 잔재는 0 — 전부 치환된 상태다. 즉 틀렸다면 조용히 틀려 있다.)

**고침:** 1~9만 매핑, 나머지는 지우지 말고 `unmapped_glyphs` 로 세어 남긴다.

## 3. 우리보다 나은 것 — 가져와야 함

> **정정.** 초판에서 이 절의 3.1·3.3 을 *"우리에게 없는 발상"* 으로 썼다. 틀렸다.

### 3.1 조 → **항(①) → 호(1./가./1))** 단위 청킹 ★ 가장 큰 수확

`_3rd_project_4` 는 항 단위로 자르고 호 라벨까지 메타에 박는다.

```json
{"article_no": 4, "article_title": "보상하지 않는 사항",
 "paragraph_no": 1, "item_no": "3", "item_list": "1;2;3;4;5;6;7",
 "citation": "제4조(보상하지 않는 사항) 제1항 제3호"}
```

**우리 쪽 실제 상태는 이렇다 — 세 문서가 서로 다른 말을 하고 있다.**

| 문서 | 9단계(계층형 청킹)에 대해 |
|---|---|
| `2026-07-31_전처리_파이프라인_현황.md:24` | **`❌ 없음`** — 팀 11단계 목록에 있고 미착수로 기록 |
| `to_clauses.py:18` (독스트링 "하는 일") | *"9 계층형 청킹 : 부 → 조 → (긴 조는 항 단위) 로 나눈다"* |
| 실제 코드 (`to_clauses.py:299,318`) | `paras` 를 **`paragraph_count` 계산에만** 쓰고 버린다. 항 청크 없음 |
| `2026-08-02_전처리_v4_중간리포트.md` §7 남은 한계 | **언급 없음** |

★**독스트링이 코드보다 앞서 있다.** "하는 일"에 적힌 것을 안 하고 있다 — RULE 1.1 위반이다.
그리고 v4 리포트의 "남은 한계"가 이 항목을 빠뜨려, **읽는 사람은 끝난 줄 안다.**
`docs/handoff/` 로 팀에 넘어간 문서라 더 위험하다.

즉 격차는 *"저쪽이 우리가 생각 못 한 걸 했다"* 가 아니라
**"우리가 하겠다고 적어 놓고 안 한 단계를 저쪽이 먼저 구현했다"** 이다.

### 3.2 추출 2모드 자동 선택 — 이건 계획에도 없다

`doc_processor.py:47` — `get_text(sort=False)` / `sort=True` 를 둘 다 뽑아
**조항 헤더 수 + 번호 순차성**으로 점수를 매겨 이긴 쪽을 쓴다.
우리는 `to_page_json.py:164` 에서 `page.get_text()` 단일 모드다.

docs 전체를 검색해도 추출 모드 선택에 관한 계획·검토가 없다. 가장 가까운 것은
`2026-07-31_약관보관형식_결정.md:109` 의 *"★미검증·과도한 단정. **좌표 포함 word/block 추출**,
레이아웃 텍스트, 규칙 복원 등 반론이 가능하다"* — 좌표 기반 추출이라는 **대안의 존재만 인지**하고
검증하지 않은 상태다. **세 항목 중 유일하게 계획에도 없던 것.**

### 3.3 용어 정의 분해 (`make_term_chunks.py`)

용어 1개 = 1청크, `term_key` 정규화, 별도 컬렉션.

**"우리에게 대응물이 없다"는 과장이었다.** 기능·평가 계약은 이미 서 있다.

| 위치 | 내용 |
|---|---|
| `2026-08-01_보험비서_전환_계획서.md:80` | `terms.py` — 약관 검색·**용어 설명** |
| 〃 `:126` | `POST /v1/terms/explain` 용어 설명 |
| 〃 `:171` | P1 조건부 — *"용어 챗봇 — `AnswerQuestion` 재사용이라 저비용"* |
| `handoff/10_계약_모델_평가.md:164` | 평가셋 층화에 **용어 5문항** (모델팀과 계약된 수치) |

없는 것은 **그 API 와 평가셋을 뒷받침할 전처리**다. 용어 정의를 조항 본문에서 분리해
검색 가능한 단위로 만드는 코드가 없다. `_3rd_project_4` 는 그 칸을 채웠다.
*"저비용"* 이라 P1 로 분류한 근거가 사실은 **전처리 미구현 위에 서 있었다.**

### 3.4 비조항 블록 차단 (`NONCLAUSE_MARKERS`)

'약관 요약서'·'쉽게 이용할 수 있는 팁'·'Q&A'·'QR코드' 등 22종을 만나면 조 본문 파싱을 끊는다.
우리는 목차만 걸러낸다. 요약서가 조에 섞이는 문제를 우리는 아직 안 봤다.

### 3.5 겹침-글리프 중복 정제 (`collapse_glyph_dup`)

`'담보종목 담보종목 담보종목'` 같은 렌더링 아티팩트를 1회로 축약하고 **횟수를 리포트에 남긴다**.
정직성 규칙에 맞는 방식이다.

## 무효 처리한 측정 (기록)

정직성을 위해 남긴다. 아래 두 지표를 냈다가 **둘 다 틀려서 버렸다.**

1. **`distinct(article_no)` 로 헤더 소실 측정** — 조 번호가 특약마다 1로 리셋되는 걸
   빠뜨렸다. "1,581개 헤더가 45개로 소실"은 소실이 아니라 **번호 반복**이었다.
2. **gid 런(run) 으로 재측정** — 분권 병합 문서에서 런 수(1,613)가 리포트 헤더 수(543)를
   역전했다. 원인을 파다가 §2.2(두 산출물이 다른 코드 버전)를 찾았다.

두 번 다 **"그럴듯한 수"가 먼저 나왔다.** 교차 대조 전제를 확인하지 않은 탓이다.
