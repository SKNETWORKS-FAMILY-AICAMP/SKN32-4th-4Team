- 대상: `_unified_mall_3`
- 분석 범위: 애플리케이션 구조, 보험 사전점검 로직, 데이터·릴리스, 전처리 파이프라인, API, 테스트, 보안, 운영, 문서
- 분석 방식: 소스·설정·산출물·매니페스트·프로세스에 대한 읽기 전용 점검
- 변경 사항: 본 보고서 파일 추가 외 애플리케이션 코드와 데이터는 수정하지 않음

## 0. 결론

현재 프로젝트는 **보험 약관 PDF 수집·구조화 플랫폼과 KCD 기반 면책 사전점검 서비스를 결합한 운영 전 단계 시스템**이다.

보험 코어는 fail-closed 원칙, 포트·어댑터 경계, 승인 릴리스 고정, 독립 인용 검증 등 좋은 안전 설계를 갖추고 있다. PDF 전처리도 1,367개 고유 대상 문서를 처리할 수 있는 배치·재개·버전 관리 체계를 확보했다.

그러나 현재 상태에서 핵심 사전점검 기능을 서비스 가능하다고 보기는 어렵다.

1. 기본 설정에서 판정에 사용할 수 있는 확정 약관은 **0건**이다.
2. 실제 엔진은 보장 가능성 전체가 아니라 **면책 및 면책 예외만 판정**한다.
3. 수집·식별·전처리·용어집·색인이 하나의 파이프라인으로 연결되지 않았고, 일부 스크립트는 폐기된 매니페스트 경로를 참조한다.
4. 상품명 불일치, 약관 occurrence 소실, 조항 인용 적격성 누락처럼 확정 데이터 투입 후 오판으로 이어질 수 있는 P0 문제가 남아 있다.
5. readiness, CI, 의존성 선언, 개인정보 보호 상태가 실제 운영 준비도를 정확히 보증하지 못한다.

따라서 현재 병목은 추출 알고리즘 자체보다 **문서 확정·서비스 승격·단일 진실원 연결·운영 검증**에 있다.

## 1. 분석 시점과 주의사항

본 보고서는 2026-08-03의 작업 디렉터리 상태를 기준으로 한다.

- 프로젝트는 상위 Git 저장소의 하위 디렉터리다.
- 작업 트리에는 기존 수정·미추적 파일이 다수 존재했다. 해당 변경은 사용자 작업으로 보고 수정하거나 정리하지 않았다.
- 분석 당시 PID 28468에서 `python -u -m scripts.extract.run_all --jobs 0`가 실행 중이었다.
- 해당 작업은 모든 CPU 코어를 사용하는 전처리 배치이므로, 최신 s5/s6 산출물 수와 성능 측정값은 분석 중에도 변할 수 있다.
- 리소스 경합 때문에 전체 테스트의 신뢰 가능한 최종 pass/fail 결과는 확보하지 못했다. 따라서 이 보고서는 전체 테스트 통과를 주장하지 않는다.

## 3. 애플리케이션 아키텍처

### 3.1 실행 진입점

| 역할 | 실행 대상 | 기본 포트 | 실행 스크립트 |
|---|---|---:|---|
| 통합 개발 앱 | `app.main:app` | 8080 | `scripts/run_dev_server.py` |
| 고객 앱 | `app.main:customer_app` | 8080 | `scripts/run_customer_server.py` |
| 관리자 앱 | `app.main:admin_app` | 8081 | `scripts/run_admin_server.py` |

`app/main.py`의 `create_app(role)`이 공통 FastAPI 인스턴스를 만든다.

- 공통/고객 경로: health, auth, precheck, cohort, terms, chat, voice, face
- 통합/관리 경로: rag, lab, bounty, workflow, admin

다만 분리는 라우트 테이블 수준이다.

- `app.main` import 시 운영 라우터까지 모두 import한다.
- 모듈 import 시 `app`, `customer_app`, `admin_app` 세 인스턴스를 모두 생성한다.
- 고객 프로세스도 운영 코드와 무거운 의존성을 불러온다.
- `role` 값의 유효성 검사가 없어 `customer` 오타는 운영 라우터를 포함하는 fail-open 동작이 될 수 있다.

### 3.2 보험 핵심 요청 흐름

```text
POST /v1/prechecks
  → app/routers/precheck.py
  → app/workflow/precheck_graph.py
  → app/core/usecases/precheck.py
  → app/core/ports/precheck.py
  → app/adapters/manifest_policy_resolver.py
  → app/adapters/file_clause_store.py 또는 pg_clause_store.py
```

좋은 점은 다음과 같다.

- `core/domain`, `core/ports`, `core/usecases`는 FastAPI, DB, adapter에 역으로 의존하지 않는다.
- 도메인 결과는 순수 dataclass이고 HTTP Pydantic DTO 변환은 라우터가 담당한다.
- 실제 약관 저장소는 포트를 통해 file/PG 구현으로 교체된다.
- 최신 버전을 자동 선택하지 않고 승인 릴리스 포인터를 명시적으로 사용한다.
- 판정 후 인용 근거를 저장소 원문과 독립적으로 대조한다.

그러나 클린 아키텍처 적용은 보험과 일부 RAG 수직 슬라이스에 한정된다. auth, face, voice, admin, workflow와 일부 RAG 라우터는 DB·ML·서비스를 직접 호출한다. 또한 `workflow.precheck_graph`와 라우터가 각각 의존성·그래프 객체를 캐시해 단일 composition root라고 보기는 어렵다.

### 3.3 실제 API 표면

고객 앱의 주요 API:

- `POST /v1/prechecks`
- `GET /v1/support-manifest`
- `POST /v1/observations`

고객 앱에도 얼굴 라우터 전체가 포함되므로 관리자 성격의 face backend 변경·benchmark API가 인증된 상태로 물리적으로 존재한다. 고객 포트에서 운영 API를 완전히 404로 격리한다는 목표와는 다르다.

## 4. 보험 사전점검 로직 분석

### 4.1 실제 판정 범위

현재 판정은 규칙 기반이며 주 판정 경로에서 LLM을 사용하지 않는다.

1. 보험사·가입일·상품명으로 약관 버전을 선택한다.
2. 문서 식별·세대 검수·날짜 신뢰도를 확인한다.
3. 선택된 약관의 모든 조항에서 KCD 범위 표현을 찾는다.
4. 면책 선언과 예외 문구를 규칙으로 판정한다.
5. 근거 인용을 생성하고 다시 검증한다.

실제 결과 생성 규칙은 다음과 같다.

| 조건 | 결과 |
|---|---|
| 면책 범위에 포함 | `UNLIKELY` |
| 면책 예외에 해당 | `NEEDS_DOCUMENTS` |
| 그 밖의 경우 | `NEEDS_EXPERT` |

`LIKELY_COVERED`와 `COVERED_BY_CLAUSE`는 enum/UI/테스트에는 있으나 실제 production 유스케이스가 생성하지 않는다. 즉 이 시스템은 현재 **보장 판정기보다 면책 사전점검기**다.

### 4.2 fail-closed 설계

다음 원칙은 일관되게 잘 구현돼 있다.

- 증거가 없으면 긍정 판정을 만들지 않는다.
- 최신 약관을 임의로 선택하지 않는다.
- 문서가 확정되지 않으면 판정을 중단한다.
- 인용 검증에 실패하면 재시도 후 기권한다.
- `NEEDS_EXPERT`를 오류가 아닌 정상적인 200 응답으로 취급한다.
- 실제 코호트와 합성 데모 코호트를 분리한다.
- 미검증 관측 데이터는 실제 통계에서 제외한다.

### 4.3 현재 서비스 가능 상태

매니페스트 실측 결과:

| 항목 | 수량 |
|---|---:|
| 전체 발생 행 | 2,121 |
| 고유 SHA | 1,703 |
| 제외 | 336 |
| 전처리 대상 고유 SHA | 1,367 |
| `identification=unidentified` | 2,117 |
| identification 값 누락 | 4 |
| `generation_review=unreviewed` | 1,394 |
| generation_review 값 누락 | 727 |

기본 설정은 `identification=confirmed`, `generation_review=reviewed|partial` 등 확인 조건을 요구한다. 이에 따라 `manifest_policy_resolver.load_versions()`의 현재 결과는 **0건**이다.

따라서 `/v1/support-manifest`의 지원 약관 수 역시 0이며 `/v1/prechecks`는 안전하게 기권한다. 데이터는 많이 확보됐지만 **serving manifest로 확정·승격된 문서가 없다**.

### 4.4 판정 로직의 주요 위험

#### P0-A. 상품명 불일치가 기권되지 않음

`app/adapters/manifest_policy_resolver.py`에서 입력 상품명과 일치하는 후보가 없을 경우 오류나 기권 대신 기존 후보 목록을 유지한다. 이후 상품명이 입력됐다는 이유로 동일 시작일 복수 후보 검사도 우회할 수 있다.

영향: 확정 약관이 투입되는 순간 다른 상품의 약관을 선택해 오판할 수 있다.

권고: 상품명이 주어졌다면 정규화된 exact/명시적 alias 일치가 없을 때 즉시 `NEEDS_EXPERT`로 기권한다.

#### P0-B. 파일 SHA와 상품 occurrence 혼동

동일 SHA를 먼저 `seen` 처리해 후속 발생 행을 제거한다. 그러나 동일 PDF가 서로 다른 판매개시일이나 상품 occurrence에 재사용될 수 있다.

실측상 239개 SHA가 여러 행에 재사용되고, 79개 SHA는 서로 다른 판매개시일을 가진다.

영향: 가입일에 대응하는 올바른 상품 발생이 사라질 수 있다.

권고: PDF 아티팩트 중복 제거와 상품 occurrence 모델을 분리한다. resolver 입력은 occurrence를 보존해야 한다.

#### P1-A. 혼합 KCD 입력의 최상위 결과

일부 코드가 invalid여도 다른 코드가 면책이면 전체 결과가 `UNLIKELY`가 된다. per-code 결과에는 오류가 남지만 소비자가 최상위 상태만 읽으면 부분 입력 오류를 놓칠 수 있다.

권고: invalid code가 하나라도 있으면 명시적 partial/invalid 플래그를 최상위 응답에 포함한다.

#### P1-B. trace 체계 분리

- HTTP 미들웨어: 요청마다 UUID `X-Trace-ID`
- 사전점검 응답: 보험사·가입일·KCD 등을 SHA-256으로 만든 결정적 `trace_id`

두 값은 연결되지 않으며 판정 결과 감사 이벤트도 없다. KCD는 가능한 값의 공간이 작아 비밀키 없는 결정적 해시는 dictionary 공격으로 역추론될 수 있다.

권고: 요청 ID와 판정 run ID를 연결하고, KCD는 keyed HMAC 또는 비가역 토큰화 정책을 사용한다. 릴리스·규칙 버전·근거 hash를 감사 이벤트에 포함한다.

#### P1-C. 릴리스 hot-swap과 캐시 불일치

릴리스 모듈은 요청 단위 snapshot을 의도하지만 precheck graph는 최초 호출 시 versions를 클로저에 저장하고 라우터가 graph를 전역 캐시한다.

영향: 약관 확인 상태나 릴리스 변경이 프로세스 재시작 전까지 반영되지 않을 수 있다.

## 5. 전처리 작업 코드파일

### 5.1 대표 실행 파일

보험 약관 PDF 전처리의 대표 배치 오케스트레이터는 다음 파일이다.

> **`scripts/extract/run_all.py`**

담당 범위:

- 현행 보험사별 split manifest 로드
- SHA 기준 대상 dedupe 및 제외 문서 필터링
- PDF → 페이지 JSON 호출
- 페이지 JSON → 조항 JSON 호출
- 병렬 실행
- 기존 산출물 재사용과 중단 후 재개
- 임시 파일을 이용한 원자적 저장
- 실패 보고서 생성

### 5.2 실제 변환 엔진

#### `scripts/extract/to_page_json.py`

PDF를 페이지 단위 JSON으로 변환한다. 현재 페이지 스키마 버전은 5다.

- 제어문자, BMP PUA, surrogate 정리
- PyMuPDF 기반 페이지 텍스트 추출
- `find_tables()` 기본 표 추출
- 좌표 기반 표 복원기 호출
- 원본 PDF, SHA, 페이지 수, 정규화 통계 기록

#### `scripts/extract/to_clauses.py`

페이지 JSON을 조항·항·호·별표·붙임 구조로 변환한다. 현재 조항 스키마 버전은 6이다.

- 목차 페이지 판정
- 부·법령 구간 및 `제N조`/번호형 머리 복원
- 조 → 항 → 호 계층 구조화
- `locator`, `qualified_no`, `content_hash` 생성
- 별표·붙임·질병분류표를 `annexes[]`로 분리
- 표를 같은 페이지 근거로 연결
- 문서 `parse_status`와 조항별 `citation_eligible` 생성

### 5.3 보조 전처리·후처리 파일

| 단계 | 파일 | 역할 |
|---|---|---|

## 6. 전처리 데이터 흐름

```text
보험사 웹사이트/API
  → data/raw/insurance_terms/<보험사>/*.pdf
  → data/raw/manifests/<보험사>.jsonl
  → classify_documents / set_generation / 식별 검수
  → scripts.extract.run_all
      ├─ to_page_json
      │    ├─ PyMuPDF 본문·기본 표
      │    └─ table_coords → table_signals
      └─ to_clauses
           ├─ 목차·부·조·항·호
           ├─ annexes·tables
           ├─ content_hash

  → data/extracted/<보험사>/<page_tag>/<sha12>.json
  → data/structured/<보험사>/<clause_tag>/<sha12>.clauses.json
      ├─ build_glossary → data/glossary/*
      └─ build_clause_index → PostgreSQL/pgvector
```

현재 수집부터 색인까지 한 번에 실행하고 단계별 불변식을 검사하는 최상위 오케스트레이터는 없다. 각 단계는 별도 수동 명령으로 연결된다.

## 7. 전처리·릴리스 상태

### 7.1 승인 릴리스와 최신 생성 코드

`config/accepted_extraction.json`의 승인 serving 릴리스:

- release: `r2026-08-02-clause-s5`
- page tag: `s4_pymupdf-1.28.0`
- clause tag: `s5_pymupdf-1.28.0`
- document count: 1,367
- embed profile: 미승인/비어 있음

현재 소스가 생성하는 버전:

- page schema/tag 계열: s5
- clause schema/tag 계열: s6

즉 최신 s5/s6은 shadow 산출물이며 승인 포인터가 변경되기 전에는 서비스에 자동 노출되지 않는다. 이 구조는 올바른 릴리스 안전장치다.

### 7.2 색인 상태

점검 시 PostgreSQL에는 s6, s5-mixed generation 데이터가 존재했으나 승인 generation인 s5와 일치하는 공식 occurrence/chunk는 준비되지 않았다. `embed_profile`도 비어 있어 PG clause index가 ready가 아닌 것은 의도된 상태다.

문제는 애플리케이션 최상위 readiness가 이 상태와 확정 약관 0건을 핵심 준비 조건으로 반영하지 않는다는 점이다.

### 7.3 용어집 상태

`data/glossary/passages.jsonl`과 metadata가 존재하며 승인 s5 기준 1,367문서를 대상으로 생성돼 있다.

다만 metadata에 다음 한계가 기록돼 있다.

- `appendix_not_found`: 89
- `documents_with_pointer_only`: 1,118

또한 `build_glossary.py`가 승인 릴리스 포인터 대신 s4/s5 경로를 하드코딩해, 다음 승인 변경에서 drift가 발생할 수 있다.

## 8. 전처리 파이프라인의 핵심 결함

### P0-1. 수집 전체 실행기가 현행 manifest와 단절

`scripts/crawl/update_all.py`는 현재 존재하지 않는 `data/raw/fetch_manifest.jsonl`을 읽고 쓴다. 현행 진실원은 `data/raw/manifests/*.jsonl`이다.

### P0-2. 식별 스크립트도 구 manifest를 사용

`scripts/identify/build_document_manifest.py`와 `build_review_queue.py`도 폐기된 단일 manifest 경로를 참조한다. 결과를 catalog/reports에 만들 뿐 현재 serving manifest의 `identification` 값을 갱신하지 않는다.

이는 2,121행 대부분이 아직 `unidentified`로 남아 있는 직접적인 구조적 원인이다.

### P0-3. 브라우저 수집기의 manifest 기록 누락 가능성

`browser_collector.py`의 `_append_manifest()`가 정의돼 있지만 실제 정상 수집 경로에서 호출되지 않는 분기가 있다. 계단식 사이트는 최종 batch 기록 전에 반환할 수 있어 PDF는 생기고 manifest는 빠질 수 있다.

### P0-4. PDF 읽기 실패 시 fail-open

`classify_documents.py`는 PDF 읽기 예외 시 기본값으로 정상 약관을 반환한다.

영향: 손상되거나 비약관인 파일이 제외되지 않고 전처리 대상에 포함될 수 있다.

권고: `unreadable`을 명시적으로 기록하고 기본 제외한 뒤 사람 검수로만 해제한다.

### P0-5. s6의 `citation_eligible`이 file store에서 무시됨

`to_clauses.py` s6은 문서 `parse_status`와 별도로 각 조항의 `citation_eligible`을 만든다. 그러나 `app/adapters/file_clause_store.py`는 문서 parse 상태와 page fallback만 gate하고 조항의 `citation_eligible=false`를 제외하지 않는다.

영향: s6을 file serving에 승인하면 인용 부적격 조항이 판정 근거에 들어갈 수 있다.

권고: s6 승인 전 file/PG store 양쪽에 동일한 조항 eligibility 불변식을 적용한다.

### P1-1. 용어집 버전 하드코딩

`build_glossary.py`는 s5 조항과 s4 페이지 경로를 직접 사용한다. 현재 승인판과 우연히 같지만 승인 릴리스가 변경되면 자동으로 따라가지 않는다.

### P1-2. 배치 보고 정보 부족

`run_all._report()`는 `clause_tag`를 받지만 결과 JSON에는 page extractor tag만 기록한다. dry-run도 페이지 산출물 누락만 계산하고 clause 산출물 누락은 별도로 보여주지 않는다.

### P1-3. 임베딩 모델·차원 하드코딩

`shard_embed.py`, `gpu_embed.py`는 `jhgan/ko-sroberta-multitask`와 768차원을 하드코딩한다. 승인 embed profile과 단일 진실원으로 연결할 필요가 있다.

## 9. 코호트·관측 데이터

`POST /v1/observations`는 사용자 관측을 append-only 파일로 저장한다. 그러나 다음 단계가 없다.

- 제출물을 문서 근거와 대조하는 검증 파이프라인
- `unverified`를 `document_backed` 또는 `confirmed`로 승격하는 writer/API
- 검증 완료 자료를 `data/cohort/verified_real`로 옮기는 흐름

현재 `data/cohort/` 디렉터리도 없어 실제·데모 코호트 모두 n=0이다.

관측 endpoint는 비인증 상태에서 건강 관련 KCD와 결과를 평문 파일에 저장한다. rate limit, 보존기간, 암호화, 접근통제, 삭제 절차를 명시해야 한다. 중복 방지 역시 check-then-write 형태라 동시 요청 시 중복 event가 기록될 가능성이 있다.

## 10. 운영·보안 점검

### 10.1 Readiness 오판

`app/obs/readiness.py`의 필수 DB 테이블 목록은 비어 있다. 현재 `data/mall.db`에 테이블이 없어도 DB ready가 true가 될 수 있다.

기본 file clause store 환경에서는 다음 상태에서도 최상위 ready가 true가 될 수 있다.

- 확정 지원 약관 0건
- 승인 embed profile 없음
- PG clause index generation 불일치
- SQLite auth/admin 테이블 없음

반대로 사용하지 않는 PG clause index도 항상 probe하고 접속 timeout이 명시되지 않아 readiness가 오래 지연될 수 있다.

권고: 다음을 분리해 보고한다.

- process liveness
- 고객 보험 기능 readiness
- auth/admin DB readiness
- 현재 선택된 clause store readiness
- 승인 릴리스 및 확정 약관 수
- glossary/cohort와 같은 선택 기능 readiness

### 10.2 인증·개인정보

- 비밀번호 최소 길이가 4자로 낮다.
- 데모 프론트는 토큰을 localStorage에 저장한다.
- 로그인·관측 제출에 명시적 rate limit이 없다.
- 얼굴 challenge/attempt 상태가 프로세스 메모리에 있어 다중 프로세스에 안전하지 않다.
- 음성 STT/TTS는 비인증으로 호출 가능해 비용·남용 제어가 필요하다.
- KCD, 얼굴 특징, 관측 결과에 대한 암호화·보존·삭제·감사 정책이 부족하다.

### 10.3 고객/운영 표면

잘못된 `role` 문자열이 운영 라우터를 포함할 수 있고 일부 운영 성격의 face API가 고객 앱에도 물리적으로 존재한다.

권고: role을 enum으로 제한하고 예상값이 아니면 앱 생성을 실패시킨다. 고객·관리자 라우터 모듈과 배포 엔트리포인트도 명시적으로 분리한다.

### 10.4 API 계약

전역 `AppError`는 `{ok, error_code, message}` 형식을 사용하지만 precheck, terms, chat, cohort 일부는 `HTTPException`으로 다시 감싸 `{detail: ...}`를 반환한다.

권고: 모든 API가 공통 error envelope와 trace 필드를 사용하도록 통일한다.

## 11. 테스트와 품질 검증

### 11.1 강점

- 도메인 규칙 및 KCD 범위 파싱 테스트
- 릴리스 고정과 최신 자동 선택 방지 테스트
- 인용 검증과 응답 정직성 테스트
- 정적 UI 링크·API 경로 테스트
- core 계층 의존성 경계 테스트
- 실제 코호트와 합성 데이터 격리 테스트

### 11.2 부족한 영역

다음 핵심 모듈을 직접 검증하는 정규 unit/golden/integration 테스트가 부족하다.

- `to_page_json.py`
- `to_clauses.py`
- `table_coords.py`
- crawler와 split manifest 기록
- identify → human review → serving manifest 승격
- 전체 PDF → clause → index → precheck E2E
- finetune split/eval 파이프라인

현재 표 관련 정답 데이터는 약 3개 표·22개 논리 레코드이며 2열 표 신호 샘플도 positive 3, negative 4 수준이다. 이 데이터에서 얻은 F1 1.000은 12개 보험사와 다양한 PDF 조판에 대한 일반화 성능으로 해석할 수 없다.

### 11.3 필요한 검증 세트

1. 보험사별 최소 표본을 가진 page extraction golden set
2. 목차, 중복 조번호, 부록, 법령 인용, OCR, 깨진 글꼴을 포함한 clause golden set
3. 표 false positive/false negative 및 병합 셀 평가 세트
4. `citation_eligible=false`가 모든 serving store에서 제외되는 계약 테스트
5. 상품명 불일치와 동일 SHA 다중 occurrence resolver 테스트
6. 승인 release pointer 변경 전후 hot-swap 테스트
7. 빈 DB·PG 장애·확정 약관 0건 readiness 테스트

## 12. CI·패키징·재현성

### 12.1 GitHub Actions 위치

현재 Git 저장소 루트는 프로젝트의 상위 디렉터리이며 `.github/workflows/ci.yml`은 `_unified_mall_3` 하위에 있다. GitHub Actions는 저장소 루트의 `.github/workflows`만 발견하므로 이 workflow는 현재 토폴로지에서 실행되지 않을 가능성이 높다.

workflow 명령도 `requirements.txt`, `pytest`를 프로젝트가 저장소 루트라고 가정하고 실행한다.

### 12.2 의존성 선언

- `pyproject.toml`의 `[project]`에 dependencies가 없고 build-system도 없다.
- `pip install .`로 실행 의존성이 설치되지 않는다.
- 전처리 코드가 직접 사용하는 PyMuPDF(`fitz`), Playwright, scikit-learn이 `requirements.txt`에 직접 고정돼 있지 않다.
- PyYAML, NumPy도 직접 사용하지만 주로 전이 의존성에 기대고 있다.
- 보험 런타임, 커머스 레거시, 얼굴·음성, 전처리, ML, 테스트 도구가 한 requirements에 섞여 있다.

권고 디렉터리/extra 구분:

- core runtime
- preprocessing/crawling
- vector/ML
- voice/face optional
- dev/test
- legacy commerce

## 15. 권장 실행 순서

### P0: 핵심 기능 개통과 오판 방지

1. **문서 확정 파이프라인 완성**
   - 식별 후보 생성
   - 사람 검수
   - generation/date 검토
   - split manifest 원자적 갱신
   - support manifest 재생성

2. **Policy resolver 수정**
   - 상품명 불일치 시 기권
   - 파일 SHA와 occurrence 분리
   - 동일 시작일 복수 후보를 항상 보수적으로 처리

3. **전처리 SSOT 통합**
   - 모든 crawler/identify 스크립트를 `data/raw/manifests/*.jsonl`로 이전
   - PDF 저장과 manifest append를 하나의 원자적 작업으로 구성
   - unreadable 문서를 기본 격리

4. **s6 serving 안전성 확보**
   - file/PG store에 `citation_eligible` 필터 적용
   - 다보험사 golden test 작성
   - 품질 리포트와 승인 포인터 갱신을 한 절차로 통합

5. **Readiness 재작성**
   - 현재 활성 store만 검사
   - 확정 약관 수, 승인 release, auth DB, glossary/cohort 상태를 분리 표시
   - 외부 DB probe에 짧은 timeout 적용

6. **CI와 의존성 복구**
   - workflow를 실제 Git 루트로 이동하거나 working-directory 명시
   - 런타임/전처리/개발 extras 분리
   - 직접 의존성 고정

### P1: 운영 신뢰성과 제품 정의

7. 관측 제출 인증·rate limit·암호화·보존기간·삭제 정책 도입

11. 관측 검증·승격·코호트 집계 파이프라인 구현

### P2: 구조 단순화와 성능

## 16. 최종 평가

| 영역 | 평가 | 요약 |
|---|---|---|
| 보험 도메인 안전성 | 양호 | 근거 없을 때 기권하는 원칙이 잘 반영됨 |
| 코어 아키텍처 | 양호 | domain/ports/usecases 경계가 실제로 지켜짐 |
| PDF 전처리 구현 | 중상 | 대규모 배치·재개·버전 관리가 구현됨 |
| 전처리 품질 근거 | 보완 필요 | golden set과 다보험사 회귀검증이 부족함 |
| 서비스 데이터 준비 | 미완성 | 판정 가능한 확정 약관 0건 |
| 파이프라인 통합 | 미완성 | 수집·식별·승격·색인이 분리되고 구 경로가 남음 |
| 운영 readiness | 취약 | 핵심 보험 준비 상태를 정확히 반영하지 않음 |
| 보안·개인정보 | 보완 필요 | KCD·관측·얼굴·토큰 취급 정책 강화 필요 |
| 테스트·CI | 보완 필요 | 도메인 테스트는 좋으나 추출 E2E와 실제 CI가 부족함 |
| 문서 일치성 | 취약 | 보험 현행 코드와 커머스 문서 간 drift가 큼 |

최종적으로 이 프로젝트에서 가장 성숙한 부분은 **보험 도메인의 안전한 기권 원칙과 PDF 전처리 기반**이다. 가장 먼저 해결해야 할 부분은 **확정 문서 0건 문제, resolver 정확성, 현행 manifest 단일화, s6 인용 적격성, readiness/CI**다.
