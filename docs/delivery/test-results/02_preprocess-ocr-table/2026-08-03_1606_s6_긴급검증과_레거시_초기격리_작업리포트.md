## 2. s6 검증 중 발견·수정한 결함

### 2.1 manifest sidecar가 실제 파일 해시와 달랐음 — 수정 완료

재현값:

```text
실제 manifest SHA-256  c39ffb1bec3ca16300fd0588106fd91b29ee398fc30585e79fd7b122eb6ebfcf
기존 sidecar 기록       060d0f21b7cd7a59cec4b96b8b517fd8be13c6e56f053a9b17d189c27bae5331
CRLF 쌍                 38,760
```

원인은 쓰기 전 LF 문자열을 해시한 뒤 Windows가 파일을 CRLF로 쓴 것이다. `--verify`도 sidecar를 검사하지 않았다.

수정:

- manifest를 명시적 LF로 쓴다.
- 쓴 뒤 `sha256_file(out)`으로 실제 파일을 다시 해시한다.
- `--verify`가 sidecar 부재·형식 오류·불일치를 실패 처리한다.
- 기존 sidecar를 실제 해시 `c39ffb…`로 정정했다.

상세: `docs/reports/debugs/2026-08-03_1556_s6_manifest_sidecar_무결성_검증누락.md`

### 2.2 mutable 승인 포인터를 전처리 입력으로 해시 — 수정 완료

기존 manifest는 `accepted_extraction.json`을 config snapshot에 포함했다. s6를 승인해 포인터를 바꾸면
s6 manifest 검증이 실패하는 순환 의존이었다.

수정:

- 새 manifest config snapshot에서 `accepted_extraction.json`을 제외한다.
- 과거 manifest의 해당 키는 NOTE를 남기고 전처리 무결성 검증에서 제외한다.
- 제외 규칙과 과거 manifest 호환 테스트를 추가했다.

상세: `docs/reports/debugs/2026-08-03_1602_s6_manifest가_승인포인터를_입력으로_해시함.md`

### 2.3 부록의 file·PG 근거 집합 불일치 — 수정 보류

file store는 `clauses[]`만 읽어 부록을 제외하지만 index builder는 `annexes[]` 9,342개를 넣는다.
부록의 eligibility와 locator 계약이 먼저 필요하므로 임의로 한쪽에 맞추지 않았다.

상세: `docs/reports/debugs/2026-08-03_1602_s6_부록_file_pg_근거집합_불일치.md`
