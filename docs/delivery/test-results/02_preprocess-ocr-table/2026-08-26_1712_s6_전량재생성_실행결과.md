# s6(조항 구조화) 전량 재생성 — 실행 결과

## 1. 작업 목표

`scripts/extract/to_clauses.py`(조항 구조화, 스키마 태그 `s6_pymupdf-1.28.0`)에 오늘 세션 동안
총 15건의 수정이 들어갔다(A-B-A 재진입 오탐 감소용 13건 + S3/S4 정밀도 수정 2건). 모든 수정은
`to_clauses.build()`를 코드에서 직접 호출해 전량(1,367문서) 검증됐으나, 디스크의
`data/structured/*/s6_pymupdf-1.28.0/*.clauses.json`은 여전히 **오늘 아침의 옛 코드**로 만든
옛 산출물이었다. 이 작업은 그 산출물을 오늘 수정된 코드로 **전량 재생성**하고 검증하는
순수 재생성 작업이다(코드 수정 없음 — 별도 계획서 없이 작업 지시 자체가 범위를 규정).

## 2. 수행 내용

1. **백업** — 기존 `data/structured/*/s6_pymupdf-1.28.0/*.clauses.json` 1,367개를
   `data/backup/s6_pymupdf-1.28.0_backup_20260826_1702.tar.gz`(147,640,369 bytes, 약 141MiB)로 백업.
   - tar 안 파일 수 1,367 = 원본 파일 수 1,367 (전량 일치)
   - 담긴 항목 전부가 `s6_pymupdf-1.28.0/*.clauses.json` 패턴에만 일치(다른 산출물 섞임 없음, 검증 완료)
   - 샘플 1건(`dbins/s6_pymupdf-1.28.0/02aaee47b190.clauses.json`)을 추출해 원본과 `diff` — **바이트 단위 일치**
2. 백업 검증 후 기존 1,367개 파일 삭제(잔여 0건 확인).
3. `python -m scripts.extract.run_all --stage clauses --jobs 0` 로 전량 재생성.
4. 재생성된 파일 수·집계값을 검증(§3).

## 3. 검증 방법과 결과

### 3.1 소요 시간

배경 실행 로그(`[exited with code 0]` 는 뒤에 붙인 `date` 명령의 종료코드이며 python 자체의
종료코드가 아님 — §3.3 참조)의 시작·종료 타임스탬프 기준:

```
시작 Wed Aug 26 17:06:15 2026
종료 Wed Aug 26 17:07:50 2026
```

**총 95초** (8프로세스 병렬, 1,355건 — 페이지 JSON이 이미 로컬에 있고 조항 구조화는
순수 텍스트 처리라 가볍다는 사전 설명과 일치).

### 3.2 파일 수

- 재생성 후 `data/structured/*/s6_pymupdf-1.28.0/*.clauses.json` 개수: **1,355개**
- `run_all.py --dry-run` 재대상 확인: 대상 1,355건, 페이지 JSON 없는 것 0건
- **독립 대조**(`_targets()`로 뽑은 대상 1,355건 각각에 대해 대응 `.clauses.json` 존재 여부 직접 확인):
  **누락 0건** — 모든 대상이 산출물을 갖고 있음(§3.3의 크래시가 파일 손실로 이어지지 않았음을
  집계 로직과 독립적으로 확인)
- 백업 전 1,367개 → 재생성 후 1,355개로 12건 감소한 것은 **격리 반영**(오늘 세션 중 진행된
  문서 확정·격리 작업으로 대상 모집단이 줄었기 때문)이지 재생성 실패가 아니다.
  CLAUDE.md §5 상태표에 이미 "판정 대상 1,355(2026-08-26 갱신)"로 기록돼 있어 이 수치와 일치한다.

### 3.3 실패·이상 기록(조용히 스킵하지 않음)

재생성 실행 중 **이미 알려진 결함**(`docs/reports/debugs/2026-08-26_1330_run_all_진행바가_cp949_콘솔에서_전체를_죽인다.md`)이
그대로 재현됐다:

```
UnicodeEncodeError: 'cp949' codec can't encode character '█' in position 2: illegal multibyte sequence
```
(`run_all.py:194`, 진행률 표시줄 출력 중 25/1355 지점에서 발생)

- 이번엔 `PYTHONUTF8=1` 우회를 걸지 않고 지시된 명령(`python -m scripts.extract.run_all --stage clauses --jobs 0`)을
  그대로 실행해 동일하게 재현됨을 확인했다.
- **그러나 파일 손실은 없었다** — 원인을 코드로 확인: `_run_parallel()`(`run_all.py:182-198`)은
  `with ProcessPoolExecutor(...) as ex:` 블록 안에서 `ex.submit()`으로 **1,355건을 한꺼번에** 제출한 뒤
  `as_completed()`로 결과를 소비하며 25건마다 진행률을 출력한다. 25번째 출력에서 예외가 나
  루프가 끊겼지만, 예외가 `with` 블록을 벗어나며 `ProcessPoolExecutor.__exit__`가 `shutdown(wait=True)`를
  호출해 **이미 제출된 나머지 1,330건의 워커 실행을 끝까지 기다린 뒤** 트레이스백을 출력하고 종료됐다
  (배경 실행 로그의 `date` 종료 시각이 크래시 출력 *뒤*에 찍힌 것으로 확인 — stderr 트레이스백은
  즉시 출력되지만 최종 `date` 프린트는 셸이 python 종료를 기다린 뒤 나온다).
  각 워커(`_process_one()`, `run_all.py:112-157`)는 **성공 시에만** `_write_atomic()`으로 파일을 쓰고
  실패는 파일을 쓰지 않은 채 `failures` 리스트로 반환하는 구조라, 파일 존재 여부만으로
  성공/실패를 신뢰성 있게 판별할 수 있다.
- **단, 이 크래시로 인해 `run_all.py` 자체의 실패 집계·요약 리포트(`_report()`, `run_all.py:240-241`)는
  호출되지 못했다** — `_run_parallel()`이 정상 반환하기 전에 예외가 나 `main()`의 `_report()` 호출까지
  못 갔다. 그래서 run_all.py가 만드는 공식 실패 목록 파일은 이번엔 생성되지 않았다.
  이를 보완하기 위해 §3.2의 "대상 1,355건 vs 산출물 존재 여부" 독립 대조를 직접 수행해
  **파일 단위 실패 0건**을 확인했다(위 참고).
- 코드 수정은 이번 작업 범위 밖이라 하지 않았다(이미 문서화된 결함이므로 새 디버그 리포트는
  추가하지 않고, 이 리포트에 재현 사실만 남긴다).

## 3.6 부수 발견 — `manifest_s6.json`의 불변 보증이 깨졌다(★중요, 별도 디버그 리포트)

`docs/handoff/README.md:115-131`이 안내하는 표준 확인 명령을 재생성 후 그대로 돌려 봤다:

```bash
python -m scripts.extract.build_manifest --schema s6 --verify
```

**1,367건 대조 중 1,367건 전부 해시 불일치**로 실패(종료코드 1). 원인은 `SCHEMA_VERSION`이
안 바뀐 채 같은 경로에 새 내용을 썼기 때문 — 매니페스트가 정확히 설계된 대로 이 상황을
잡아낸 것이지 새로운 결함은 아니다. 다만 이 사실을 모르는 사람이 `--verify`를 돌리면
"산출물이 오염됐다"고 오판할 수 있어 별도 디버그 리포트로 남기고 `docs/handoff/README.md`
인덱스에도 걸었다 →
`docs/reports/debugs/2026-08-26_1715_s6_전량재생성으로_manifest_s6_불변보증_깨짐.md` (내부 원본 참조: `debugs/2026-08-26_1715_s6_전량재생성으로_manifest_s6_불변보증_깨짐.md`).
매니페스트 재기준선화(`--force`)는 팀 결정이 필요하다고 판단해 이번 세션에서는 하지 않았다.

## 4. 미해결 이슈·다음 작업 제안

- **`run_all.py`의 cp949 진행률 크래시는 여전히 미수정**이다. 이번 세션도 우회(`PYTHONUTF8=1`)
  없이 지시된 명령을 그대로 돌려 동일 결함을 다시 만났다 — 코드 수정은 이번 작업 범위 밖이라
  손대지 않았다. 근본 수정 제안은 기존 디버그 리포트(§3.3 링크)에 이미 있다: `_bar()`를 ASCII로
  바꾸거나 `run_all.py` 시작부에서 `sys.stdout.reconfigure(encoding="utf-8")`.
  ★**추가로 발견한 위험**: 이 크래시가 나면 `_report()`가 호출되지 않아 **run_all.py 자체의
  실패 집계 파일이 통째로 안 만들어진다** — 파일이 실제로는 정상 생성돼도(이번처럼) 공식 실패
  리포트가 없어 "실패 0건"이라고 자동으로 믿을 수 없다. 이번엔 독립 대조로 메꿨지만, 다음
  세션이 코드를 고칠 때 이 부분도 함께 감안하면 좋겠다.
- **`data/manifests/preprocess/manifest_s6.json`이 옛 산출물 해시를 그대로 갖고 있어 `--verify`가
  1,367/1,367 전건 실패한다.** §3.6·별도 디버그 리포트 참조. 재기준선화 여부는 팀이 정해야 한다.
- 디스크 산출물은 갱신됐지만 **DB·라이브 조항 벡터 인덱스는 과거 s6 스냅샷 그대로**다(CLAUDE.md
  기준 별도 재색인 단계 필요). 이번 작업 범위 밖이라 손대지 않았다.
- `data/structured/*/s5_pymupdf-1.28.0/`, `data/extracted/`는 이번 작업에서 건드리지 않았다.
