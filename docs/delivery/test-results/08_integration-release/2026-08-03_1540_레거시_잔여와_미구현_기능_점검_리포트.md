# 레거시 잔여와 미구현 기능 점검 리포트

- 작성 시각: 2026-08-03 15:40 KST
- 대상: 현재 작업트리의 보험 사전판정 프로젝트 전체
- 점검 방식: 코드·설정·계획·핸드오프·산출물 대조 및 읽기 전용 실측
- 주의: 작업트리에 다른 세션의 미커밋 변경이 많으므로, 이 리포트는 **현재 디스크 상태의 스냅샷**이다.

---

## 0. 결론

현재 프로젝트는 **보험 사전판정 코어를 기존 커머스/RAG 실습 플랫폼 위에 올려 전환 중인 상태**다.
상품·주문·결제 고객 라우터와 일부 화면은 이미 격리됐지만, 기본 앱·readiness·CLI·DB·관리자·문서에는
구형 커머스/RAG가 아직 현행 기능처럼 남아 있다.

보험 기능은 API와 도메인 뼈대가 있으나, 서비스 관점의 가장 큰 차단점은 다음 두 가지다.

1. 판정 조건을 만족하는 **확정 약관이 0건**이어서 `/v1/prechecks`가 실제 상품을 판정할 수 없다.
2. 현재 판정기는 보장 전체가 아니라 **면책·면책 예외 중심의 사전 점검**이며 운영 경로에서
   `LIKELY_COVERED`를 생성하지 않는다.

s6는 1,367문서 생성이 끝났지만 **생성 완료와 품질 승인 완료는 다르다.** 따라서 이번 작업은 s6를
승인 포인터로 올리지 않고, 기존 불변 manifest와 구조 검사를 먼저 재검증한다.

> **16:06 후속 실행 반영** — RAG UI와 Lab API를 `v6`·`v7` zip으로 격리했고,
> s6 manifest 검증기 결함 2건을 수정했다. 실행 근거는
> `docs/reports/2026-08-03_1606_s6_긴급검증과_레거시_초기격리_작업리포트.md`에 있다.

## 1. 이미 정리된 범위

- 상품·주문·결제 고객 라우터는 `app/main.py`에서 제거됐다.
- 삭제된 쇼핑 화면(`shop`, `index`, `orders`, `video`, `mcp`)은 활성 static 경로에 없다.
- `app/agent`, `app/mcp`, `app/a2a` 패키지는 현재 활성 트리에 없다.
- 구형 `rag.html`·`rag.js`는 활성 static에서 빠졌고, 이번 차수에 원본 경로를 유지한
  `legacy/v6_rag_ui.zip`으로 압축 격리했다.
- 현행 코드가 `legacy/`를 import하거나 파일 경로로 읽지 못하게 하는 ARCH-004 테스트가 있다.

이 범위는 다시 살리는 것이 아니라 압축 보관 규칙에 맞게 마무리하면 된다.

## 2. 덜 정리된 레거시

### P0 — 런타임·운영 기준을 흐리는 항목

| 항목 | 실측 상태 | 정리 방향 |
|---|---|---|
| 구형 운영 API | 점검 당시 `/api/rag`, `/api/lab`, `/api/bounty`, 커머스 ticket workflow, 주문 admin 등 18개. 후속 작업에서 Lab 6개를 제거해 **현재 잔여 12개** | 보험 앱에서 unmount 후 필요 시 압축 보관 |
| 기본 앱 export | 일반적인 `uvicorn app.main:app`이 `full` 앱을 띄워 구형 운영 API까지 노출 | 기본 export를 보험용으로 고정하고 role을 fail-closed로 검증 |
| readiness | `data/vector_store/index.faiss`, `index.pkl`이라는 환불정책 RAG 인덱스를 전체 준비 조건으로 사용 | 승인 보험 릴리스·지원 약관 수·활성 clause store 기준으로 교체 |
| 운영 CLI | `scripts/manage.py`의 `seed`·`ingest`가 상품·재고와 환불정책 FAISS를 초기화 | 보험 전용 validate-release/build-index 명령만 활성 유지 |
| 문서 | 루트 README와 `docs/architecture.md`가 커머스·MCP·A2A를 현행 기능으로 설명 | 보험 정본으로 교체하고 과거 설명은 history/archive 처리 |
| CI | 실제 Git 루트는 상위 `llm_workspace`인데 workflow는 하위 프로젝트에 있음 | 저장소 루트 기준으로 재배치하고 작업 디렉터리 명시 |

### P1 — 코드 계층과 데이터 모델에 남은 항목

- `app/application/` 전체: 구형 RAG 질의, 커머스 ReAct, 바운티, 자기검증 계층.
- `app/composition.py` 전반부: FAISS/Graph/Hybrid RAG와 커머스 agent builder가 보험 조립과 혼재.
- 구형 RAG 어댑터: FAISS, fusion, lexical, GraphRAG, reranker, LLM gateway 등.
- `app/adapters/react_agent_adapter.py`: 존재하지 않는 `app.agent.react`를 동적 import하는 죽은 경로.
- `app/db/models.py`: Product, Inventory, Order, OrderItem, Payment, KnowledgeGap 등 커머스 모델.
- `app/db/seed.py`, `app/services/admin_report.py`, `app/static/admin.*`: 상품·주문·매출·지식갭 중심.
- `app/adapters/pg_graph.py`: 보험 그래프가 아니라 환불·오배송·배송비 관계를 하드코딩.
- `scripts/demo.py`, MCP 캡처·실키 테스트, 구형 MCP parity 테스트: 현재 존재하지 않는 API/패키지를 참조.
- `requirements.txt`: 현행 보험 런타임, 전처리, ML/index, 개발, 레거시 demo 의존성이 한 파일에 혼재.

단, `pgvector_index.get_conn()`은 보험용 clause store/index도 공유하므로 구형 PG 어댑터를 바로 삭제하면 안 된다.
보험용 연결 모듈로 옮긴 뒤 커머스 RAG 부분을 격리해야 한다.

### 제품 범위 결정이 먼저인 항목

인증·음성·얼굴 기능은 커머스 잔재라고 단정할 수 없다. 보험 제품 요구사항에 남길지 별도 optional demo로
분리할지 결정한 후 움직여야 한다. A2A는 기존 계획에서도 선택·시간 제한 기능이므로 MVP 누락으로 세지 않는다.

## 3. 구현하기로 했지만 부족한 기능

### P0 — 서비스 개통 전 필수

#### 3.1 확정 약관 승격 파이프라인

raw manifest는 2,121행이지만 현재 식별 상태는 사실상 전부 `unidentified`이고, 세대 검토도
`unreviewed` 또는 비어 있다. `REQUIRE_CONFIRMED=true` 조건에서 `load_versions()` 결과는 0건이다.

자동 후보·검토 큐를 생성하는 코드는 있으나, 사람이 확인한 결과를 current split manifest에 기록하고
serving 대상으로 승격하는 writer/API가 없다. 이 기능이 없으면 s6 품질을 승인해도 실제 판정 상품은 0건이다.

#### 3.2 약관 버전 resolver의 fail-closed 계약

`app/adapters/manifest_policy_resolver.py`에는 다음 위험이 남아 있다.

- 입력 상품명과 일치하는 후보가 없어도 전체 후보를 유지한다.
- 동일 PDF의 여러 상품·판매기간 occurrence를 SHA 중복으로 합친다.
- `date_confidence`가 없으면 `exact`로 간주한다.
- 상품명이 들어왔다는 이유로 일부 동일 시작일 모호성 검사를 건너뛴다.

확정 데이터가 들어오기 전에 occurrence 보존과 상품 불일치 기권을 회귀 테스트로 고정해야 한다.

#### 3.3 조항 eligibility 필드 계약

전처리 조항은 법령성 여부를 `statute`에 기록하지만 eligibility·파일 저장소·색인 코드는 `is_statute`를 본다.
또 PG 스키마에는 `citation_eligible`, `chunk_type`, `is_statute`가 없어 공통 게이트를 만족하지 못한다.
스키마·전처리·file/PG store·색인의 필드 이름을 하나로 통일해야 한다.

#### 3.4 LangGraph·인용 검증

현재 `PrecheckGraph`는 5단계 trail을 남기지만 운영 경로는 단일 use case 실행에 가깝고, 실제 LangGraph builder는
3노드다. 인용 실패 뒤 표적 재검색·재설명 retry도 조립되지 않았다.

추가로 `citation_guard.by_path`의 중복 덮어쓰기와 정상 인용문 안 준용 조항을 미선언 인용으로 잡는 오탐이 남아 있다.
상세 완료 조건은 `docs/handoff/17_LangGraph_인용검증_MCP_결함수정_의뢰.md`를 따른다.

#### 3.5 보험 DB·감사로그 수직 슬라이스

핵심 DDL 초안은 있으나 보험 ORM/Alembic/조항 적재기/판정 감사로그/관측 검수 경로가 완성되지 않았다.
`docs/handoff/16_DB_스키마_적재_의뢰.md`의 완료 조건을 기준으로 작은 수직 슬라이스부터 구현해야 한다.

### P1 — 핵심 기능 확장

| 계약/기능 | 부족한 부분 |
|---|---|
| AI1 검색 | 상품·세대 범위를 고정한 embedding 검색, 최대 3단계 준용 조항 해소, `EvidenceBundleV1`, unresolved/truncated 표현 없음 |
| AI2 판정 | 공제액·한도·대기기간, 구조화 설명, 20~30개 golden scenario, 모델 비교 리포트 없음 |
| 긍정 보장 판정 | 운영 코드가 면책·예외 외에는 `NEEDS_EXPERT`를 반환. 제품이 coverage precheck라면 `LIKELY_COVERED` 경로가 부족함 |
| s6 승인·색인 | s6 구조화 완료, 사람 품질 승인·공식 embed profile·승인 세대 index는 미완료 |
| 관측→코호트 | `/v1/observations` append는 있으나 `unverified`를 `document_backed/confirmed`로 승격하는 검수 파이프라인 없음 |
| 전처리 품질 | 표 층화 라벨링, 부록 recall, 조항-span P/R/F1, D4 사전 기준, D6 결함 fixture, s7 2모드 검증이 남음 |
| 보험 MCP/Agent | 보험용 도구·resource, API key scope, rate limit, idempotency, audit, demo client 없음 |
| UI/운영 | 원문 보기, 보험 화면 시각 QA 캡처, 지원 약관·승인 릴리스 중심 admin 화면이 부족함 |

## 4. 권장 실행 순서

s6 검증이 시급하다는 요청을 반영해 기존 우선순서를 다음처럼 조정한다.

1. **s6 불변 manifest·구조·표 회귀 재검증** — 승인 포인터는 바꾸지 않는다.
2. **의존성 없는 레거시 1차 격리** — 이미 활성 static에서 빠진 loose RAG 화면을 zip으로 보관. ✅
3. **확정 약관 승격 + resolver/eligibility 계약 수정** — 실제 지원 약관 0건 해소의 선행 작업.
4. **LangGraph 5노드·retry·인용 검증 통합**.
5. **보험 DB·감사로그·관측 검수 수직 슬라이스**.
6. **s6 사람 검수·embed profile 확정·shadow index 평가 후 승인**.
7. **구형 18개 API, application/RAG/DB/admin/CLI를 묶음별 압축 격리**.
8. **보험 MCP·원문 보기·선택 기능** 순으로 확장.

## 5. 이번 리포트의 한계

- s6의 1,367건 생성 완료는 확인됐지만 사람 라벨 기반 품질 승인을 뜻하지 않는다.
- 얼굴·음성·인증의 제품 생사는 문서만으로 확정하지 않았다.
- 다른 세션의 미커밋 변경이 많아 체크박스 상태만으로 완료 여부를 판단하지 않았다.
- 실제 격리와 s6 재검증 결과는 별도 작업 리포트와 계획서 진행 기록에 남긴다.
