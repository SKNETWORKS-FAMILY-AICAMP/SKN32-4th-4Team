## 0. ★반대 의견부터 — 지금 상태로는 전환하면 안 된다

**DB를 합치는 결정 자체에는 반대하지 않는다.** 두 DB는 이미 같은 PostgreSQL 클러스터와 같은 디스크를 쓰므로 CPU·shared buffers·WAL·checkpoint·I/O 장애영역은 지금도 공유한다. 같은 DB 안에서 원장과 색인을 FK·조인·한 트랜잭션으로 묶을 수 있는 이점은 실재한다.

그러나 **현재 초안과 현재 실행 상태로 cutover 하는 것에는 반대한다.**

P0 차단 사유는 다음과 같다.

1. 감사 도중, 내가 시작하지 않은 이관이 이미 진행 중이었다. `017_vec_clause_index.sql`은 2026-08-26 12:56:47 KST에 `postgres`로 적용됐고, 13:07 KST에도 별도 세션이 `COPY public.policy_clause_chunk TO STDOUT` → `COPY vec.policy_clause_chunk FROM STDIN` 중이었다.

2. 현재 복사 도구의 occurrence `COPY`는 **확정적으로 실패한다.** 원본과 목적지의 열 순서가 다르다.

   - 원본 9~15열: `index_generation text`, `source_kind text`, `citation_eligible bool`, `chunk_type text`, `is_statute bool`, `parse_status text`, `ordinal int`
   - 목적지 9~15열: `citation_eligible bool`, `chunk_type text`, `is_statute bool`, `parse_status text`, `ordinal int`, `index_generation text`, `source_kind text`

   열 목록 없는 binary `COPY`는 원본 9열의 `text`를 목적지 9열의 `boolean`에 넣으려 한다.

3. 런타임·운영 SQL은 `vec.`를 쓰지 않는다. 맨이름 `policy_clause_*`가 **활성 파일 14개, 문자열 위치 111곳**에 있다. 기본 `search_path`는 `"$user", public`이고 DB/role별 보정도 0건이라 DSN만 바꾸면 `relation does not exist`로 깨진다.

4. 새 `vec` 테이블 3개 소유자는 문서가 말하는 `insurance_owner`가 아니라 **`postgres`**다. `insurance_owner`와 그 멤버인 `insurance_admin`은 현재 이 테이블을 변경·복구할 수 없다.

5. 되돌리기 문구의 `DROP SCHEMA vec CASCADE`는 단독으로 성립하지 않는다. migration ledger에는 017이 이미 기록됐다. 스키마만 지우면 적용기는 017을 `skip`하여 테이블을 다시 만들지 않는다.

6. 운영 템플릿 `config/production.env.example`에는 `CLAUSE_STORE=pg`는 있지만 **`PGVECTOR_DSN`이 없다.** `docker-compose.yml`은 `.env`를 읽으며, 현재 루트 `.env`에도 키가 없다. 그러면 코드 기본값인 `127.0.0.1:5433/postgres/mall_vec`를 계속 쓴다. 컨테이너 안에서는 주소 자체도 틀리다.

7. GitHub CI는 PostgreSQL service가 없고 `not pg`로 PG 시험을 모두 제외한다. 현재 schema cutover를 잡아 줄 CI 관문은 **0개**다.

결론은 **“통합 가능, 현 cutover 중단”**이다.

## 3. 맨이름 SQL — `vec`로 옮기면 어디가 깨지나

측정 방법: 활성 `app/`, `db/`, `scripts/`, `tests/`의 Python AST에서 `policy_clause_content|chunk|occurrence`가 `vec.`/`public.` 없이 나오고 SQL 동사가 함께 있는 문자열 위치를 셌다. 동적 f-string의 같은 줄은 한 번으로 셌다.

결과는 **14파일 / 111문자열 위치**다. 문자열에는 도움말·검사 정규식도 일부 포함하므로 “실행 횟수”가 아니라 수정·검토 분모다.

`db/migrations/postgres/017_vec_clause_index.sql`과 `scripts/db/migrate_vec_to_insurance_real.py`는 이미 `public.`/`vec.`를 명시하므로 위 분모에서 제외했다.

현재 두 DB의 세션 `search_path`는 모두 `"$user", public`; `pg_db_role_setting`의 DB/role별 설정은 0행이다.

해결책은 다음과 같다.

- 권고: 모든 SQL을 `vec.policy_clause_*`로 명시한다.
- 임시 호환: DSN options나 role 설정으로 `search_path=vec,pg_catalog`를 둔다.

**search_path만으로 영구 해결하지 않는 편이 낫다.** `ensure_schema()`가 맨이름 DDL을 실행하므로 잘못된 search path에서 다시 `public` 테이블을 만들 수 있고, 시험도 `public` namespace를 직접 검사한다. 민감한 `app` 데이터가 있는 DB에서 동일 이름 탐색 규칙에 권한 경계를 기대해서도 안 된다.

## 4. 두 DB를 동시에 여는 코드

### 4-1. 명시적으로 두 연결을 동시에 lease하는 곳

`scripts/db/migrate_vec_to_insurance_real.py:86-87` 한 곳뿐이다. `SRC=mall_vec`와 `DST=insurance_real`을 같은 `with`에서 연다. 정상 런타임이 아니라 이관 도구다.

### 4-2. 정상 런타임의 실제 경계

판정 요청은 색인을 읽은 뒤 연결을 닫고, 그 다음 `app/routers/precheck.py:_persist_precheck_if_enabled()`에서 `PgInsuranceRepository` 트랜잭션을 연다.

즉 한 요청에서 두 DB를 순차 사용하지만 한 트랜잭션이 아니다. process-local pool은 DSN별로 남으므로 프로세스 수준에서는 두 DB 물리 연결이 동시에 열려 있을 수 있다.

합친 뒤에도 자동으로 한 트랜잭션이 되지는 않는다. `get_conn()`과 `PgInsuranceRepository._connect()`는 별도 진입점이다. 검색 SELECT와 판정 저장을 한 트랜잭션으로 묶으려면 repository/connection 경계를 명시적으로 합쳐야 한다.

반대로 현재 코드가 “반드시 서로 다른 DB여야 한다”고 가정하는 정상 런타임 로직은 발견하지 못했다.

추가로 `get_settings()`는 LRU cache이고 precheck dependency도 `_DEPS`에 cache된다. 환경변수만 바꾸는 것은 실행 중 프로세스의 cutover나 rollback이 아니다. customer/admin/worker를 재시작하고 기존 pool을 닫아야 한다.

## 5. 권한·역할 — 약관 원문을 넓게 열지 않는 최소안

### 5-1. 현재 실측

- `insurance_owner`: NOLOGIN
- `insurance_app`: NOLOGIN
- `insurance_runtime`: LOGIN, `insurance_app` 멤버
- `insurance_admin`: LOGIN, `insurance_owner` 멤버
- `core` 12테이블: `insurance_owner` 소유, `insurance_app` SELECT만
- `vec` schema: `insurance_owner` 소유
- `vec` 테이블 3개: **`postgres` 소유**
- `insurance_app`: vec 테이블 3/3에 SELECT만
- vec 테이블 RLS: 3/3 모두 꺼짐
- `insurance_owner`와 `insurance_admin`: 현재 vec 테이블 SELECT/INSERT/UPDATE/DELETE 권한 없음
- 017의 default ACL: `postgres`가 앞으로 만드는 vec 테이블에만 적용됨

### 5-2. 유지해야 할 최소 권한

| 주체 | 필요한 권한 | 주면 안 되는 것 |
|---|---|---|
| `insurance_owner` | schema/table/index 소유; migration·복구 | LOGIN, 앱 트래픽 |
| `insurance_app` | `USAGE ON SCHEMA vec`, 3테이블 `SELECT` | INSERT/UPDATE/DELETE/TRUNCATE/CREATE |
| `insurance_runtime` | `insurance_app` 상속만 | 직접 테이블 grant, owner membership |
| 별도 `vec_ingest` NOLOGIN + 전용 LOGIN | 검증된 적재에 필요한 SELECT/INSERT/UPDATE, 필요한 경우 제한된 DELETE | core/app/ops 권한, schema CREATE, TRUNCATE |
| `insurance_admin` | 승인된 migration/maintenance 경계에서 owner 역할 상속 | 일반 HTTP 트래픽의 PGVECTOR DSN |

현재 적재 스크립트들은 `ensure_schema()`에서 `CREATE EXTENSION/TABLE/INDEX`, `ALTER TABLE`까지 하고 그 뒤 DML을 한다. 단순 writer 권한으로는 그대로 돌지 않는다.

해결은 앱 role을 넓히는 것이 아니라 다음을 분리하는 것이다.

- DDL 보장: migration/owner 경계
- 데이터 적재: 전용 writer
- 런타임 검색: read-only `insurance_runtime`

가장 위험한 선택은 기존 기본값에서 dbname만 바꿔 `user=postgres dbname=insurance_real`로 두는 것이다. 그러면 검색 경로가 보험 실제 사례·동의·감사 원장 전체에 슈퍼유저 권한을 얻는다.

## 6. pgvector·인덱스와 재생성 비용

### 6-1. 확장

`insurance_real`에는 이미 다음 확장이 있다.

- `vector 0.8.3`
- `pg_trgm 1.6`
- `pgcrypto 1.3`

`mall_vec`의 vector/pg_trgm 버전과 일치한다. 확장 설치는 선행조건이 아니다.

### 6-2. 무엇이 따라오고 무엇이 재생성되나

| 이관 방식 | 테이블 데이터 | PK/보조/HNSW/GIN |
|---|---|---|
| 현재 Python binary COPY | 데이터만 | 안 따라옴. 목적지 PK는 DDL 때문에 이미 존재; HNSW/GIN/보조 2개는 별도 생성 |
| `pg_dump -Fc` + `pg_restore` | 따라옴 | 정의는 포함되지만 restore 때 **재구축**됨 |
| 물리 base backup/동일 DB 복원 | 따라옴 | 물리 인덱스 페이지도 포함되지만 두 DB를 merge하는 방식은 아님 |
| CTAS/논리복제/FDW/INSERT-COPY | 데이터 | 목적지 인덱스 별도 생성 필요 |

원본 인덱스 실측:

| 인덱스 | 크기 |
|---|---:|
| HNSW `policy_clause_chunk_hnsw` | 975,740,928 B, 930.5 MiB |
| GIN `policy_clause_chunk_text_trgm` | 275,324,928 B, 262.6 MiB |
| chunk PK | 74,293,248 B, 70.9 MiB |
| occurrence PK + gen + sha | 170,704,896 B, 162.8 MiB |
| content PK | 8,855,552 B, 8.4 MiB |

원시 float32 벡터 하한은 다음과 같다.

`164,977행 × 1,024차원 × 4 B = 675,745,792 B = 644.4 MiB`

최종 세 테이블+인덱스의 추가 공간 하한은 원본 실측 기준 **3.23 GiB**다. HNSW+GIN만 다시 써도 약 **1.17 GiB**이며 WAL·임시공간·동시 원본 보존은 별도다.

**시간은 모른다.** 저장소에는 164,977행/1024차원 HNSW 실제 build 시간이 기록돼 있지 않고, 이번 감사는 DDL 실행 금지라 측정하지 않았다.

현재 서버 설정은 다음과 같다.

- `maintenance_work_mem=64MB`
- `max_parallel_maintenance_workers=2`
- `max_wal_size=1GB`
- `checkpoint_timeout=5min`

이 값과 완성 인덱스 크기만으로 신뢰할 elapsed time을 만들 수 없다. restore rehearsal에서 HNSW·GIN 각각의 시작/종료와 peak disk/WAL을 기록해야 한다.

보수적 공간 preflight로는 **최종 추가분 3.23 GiB의 2배 이상, 약 6.5 GiB + dump 보관분**을 임시 여유로 잡을 수 있으나 이는 측정값이 아니라 운영 headroom 제안이다. 현재 디스크 free는 sandbox에서 신뢰할 값으로 읽지 못했다.

## 7. 현재 이관 초안에서 추가로 깨지는 것

`scripts/db/migrate_vec_to_insurance_real.py`와 017을 실행하지 않고 읽어 확인했다.

1. **occurrence binary COPY 열 순서 불일치**
2. **부분 커밋**: 테이블마다 commit한다. content 성공 후 chunk/occurrence가 실패하면 반쪽이 남는다.
3. **재시도 자기 차단**: 목적지 어느 테이블이든 행이 있으면 스크립트가 재시도를 거부한다.
4. **ledger와 DROP 모순**: schema를 DROP해도 017 ledger가 남아 apply가 재생성을 skip한다.
5. **검증이 행수뿐**: 같은 행수의 열 오배치·본문·벡터 손상을 잡지 못한다.
6. **메모리 비상한 없음**: 테이블 전체를 `io.BytesIO`에 받은 뒤 `getvalue()`하여 보낸다. chunk의 데이터+TOAST만 1,247,625,216 B다.
7. **`--indexes`에 완전성 gate 없음**: 빈 occurrence나 행수 불일치 상태에서도 인덱스를 만들 수 있다.
8. **소유권 오류**: schema owner는 자식 table owner로 자동 상속되지 않는다.
9. **“인덱스를 데이터 뒤에”가 절반만 맞음**: HNSW/GIN은 뒤지만 PK 3개는 DDL에서 먼저 생겨 COPY 중 유지 비용을 낸다.

검증은 명시 열 목록과 source/destination binary stream digest 또는 PK별 정렬 digest까지 필요하다.

## 8. 되돌리기 — 옛 DB를 안 지우는 것만으로는 부족하다

옛 DB 보존은 **필수지만 충분하지 않다.**

추가로 필요한 것은 다음과 같다.

1. **cutover 기준점**: 원본 행수·스키마·constraint·index·세대/모델 분포와 dump SHA-256 기록
2. **writer 정지**: build/load/shard/backfill/reconcile 도구 quiesce
3. **단일 snapshot**: 세 테이블을 같은 repeatable-read 또는 한 `pg_dump` snapshot에서 읽기
4. **cutover 후 old DB freeze**: 새 DB에만 write가 생긴 뒤 단순 DSN rollback을 하면 새 write가 사라짐
5. **환경변수 변경 + 전 프로세스 재시작**
6. **ledger 처리**: 017을 삭제·변조하지 말고 새 번호의 forward repair migration 사용
7. **복구 리허설**: 현재 S3 `pg_dump -Fc` restore 시험은 문서상 **0회**

권고 rollback 관문:

| 단계 | 실패 시 |
|---|---|
| DDL/복사 전 | 아무 변경 없음 |
| staging 복사·검증 전 | staging만 폐기; 운영 DSN 불변 |
| 검증 후 cutover 전 | staging 유지/폐기; old DB 계속 정본 |
| cutover 직후, writer 동결 중 | DSN 복귀 + 전 프로세스 재시작 |
| 새 DB write 허용 후 | old DB와 차이 대조·역반영 전에는 단순 DSN 복귀 금지 |

현재 계획의 `DROP SCHEMA vec CASCADE`는 특히 위험하다. 향후 `core`와 vec 사이 FK나 view가 생기면 `CASCADE`가 예상보다 넓게 객체를 제거할 수 있다.

## 9. 백업·복구와 워크로드 관점의 찬반

### 합쳐도 되는 근거

- 두 DB는 이미 같은 PostgreSQL instance/data directory다.
- 한 DB면 `core`→색인 계보 FK/조인과 consistent snapshot을 만들 수 있다.
- schema별 logical dump로 `core/app/ops`와 vec의 백업 주기를 나누는 것은 한 DB 안에서도 가능하다.

### 합치지 않거나 별도 cluster를 고려할 근거

- 운영 원장과 3.23 GiB 검색색인을 한 physical restore 단위로 두면 원장 RTO가 HNSW/GIN 재구축에 끌려간다.
- HNSW build·VACUUM·logical backup이 connection budget과 lock 관찰 범위를 함께 쓴다.
- 진짜 장애·성능·PITR 격리가 필요하면 **다른 DB가 아니라 다른 PostgreSQL cluster/스토리지**가 필요하다.

가장 중요한 백업 판단은 다음이다.

문서에는 vec가 “파생 색인”이라고 적혀 있지만 현재 `core→vec` ETL/계보는 없다. 따라서 지금 vec는 **재생성 가능한 파생물이라고 버릴 수 없다.** 계보와 재생성 시험이 생기기 전까지 원문·벡터를 원장급으로 백업해야 한다.

그 뒤에야 다음 정책 분리가 가능하다.

- `core/app/ops`: 고빈도, 짧은 RPO
- vec: 저빈도 백업 또는 재생성 중심

## 10. 스키마 이름 의견

둘 중에는 **`vec`가 `index_a`보다 낫다.** `index_a`는 내부 프로젝트 단계명이라 의미가 없고 다음 사람이 B가 있는지 묻게 된다.

다만 최선은 **`clause_index`**다. 이 스키마에는 vector뿐 아니라 원문 content, occurrence, trigram GIN, 인용 gate가 함께 있어 `vec`도 실제 책임보다 좁은 이름이다.

이미 017과 부분 복사가 `vec`로 적용된 지금 이름 변경은 P0가 아니다. 먼저 안전하게 멈추고 결함을 고친 뒤 최종 이름을 한 번 정해 SQL을 전부 schema-qualified해야 한다.

## 0. ★반대 의견부터 — 지금 상태로는 전환하면 안 된다

**DB를 합치는 결정 자체에는 반대하지 않는다.** 두 DB는 이미 같은 PostgreSQL 클러스터와 같은 디스크를 쓰므로 CPU·shared buffers·WAL·checkpoint·I/O 장애영역은 지금도 공유한다. 같은 DB 안에서 원장과 색인을 FK·조인·한 트랜잭션으로 묶을 수 있는 이점은 실재한다.

그러나 **현재 초안과 현재 실행 상태로 cutover 하는 것에는 반대한다.**

P0 차단 사유는 다음과 같다.

1. 감사 도중, 내가 시작하지 않은 이관이 이미 진행 중이었다. `017_vec_clause_index.sql`은 2026-08-26 12:56:47 KST에 `postgres`로 적용됐고, 13:07 KST에도 별도 세션이 `COPY public.policy_clause_chunk TO STDOUT` → `COPY vec.policy_clause_chunk FROM STDIN` 중이었다.

2. 현재 복사 도구의 occurrence `COPY`는 **확정적으로 실패한다.** 원본과 목적지의 열 순서가 다르다.

   - 원본 9~15열: `index_generation text`, `source_kind text`, `citation_eligible bool`, `chunk_type text`, `is_statute bool`, `parse_status text`, `ordinal int`
   - 목적지 9~15열: `citation_eligible bool`, `chunk_type text`, `is_statute bool`, `parse_status text`, `ordinal int`, `index_generation text`, `source_kind text`

   열 목록 없는 binary `COPY`는 원본 9열의 `text`를 목적지 9열의 `boolean`에 넣으려 한다.

3. 런타임·운영 SQL은 `vec.`를 쓰지 않는다. 맨이름 `policy_clause_*`가 **활성 파일 14개, 문자열 위치 111곳**에 있다. 기본 `search_path`는 `"$user", public`이고 DB/role별 보정도 0건이라 DSN만 바꾸면 `relation does not exist`로 깨진다.

4. 새 `vec` 테이블 3개 소유자는 문서가 말하는 `insurance_owner`가 아니라 **`postgres`**다. `insurance_owner`와 그 멤버인 `insurance_admin`은 현재 이 테이블을 변경·복구할 수 없다.

5. 되돌리기 문구의 `DROP SCHEMA vec CASCADE`는 단독으로 성립하지 않는다. migration ledger에는 017이 이미 기록됐다. 스키마만 지우면 적용기는 017을 `skip`하여 테이블을 다시 만들지 않는다.

6. 운영 템플릿 `config/production.env.example`에는 `CLAUSE_STORE=pg`는 있지만 **`PGVECTOR_DSN`이 없다.** `docker-compose.yml`은 `.env`를 읽으며, 현재 루트 `.env`에도 키가 없다. 그러면 코드 기본값인 `127.0.0.1:5433/postgres/mall_vec`를 계속 쓴다. 컨테이너 안에서는 주소 자체도 틀리다.

7. GitHub CI는 PostgreSQL service가 없고 `not pg`로 PG 시험을 모두 제외한다. 현재 schema cutover를 잡아 줄 CI 관문은 **0개**다.

결론은 **“통합 가능, 현 cutover 중단”**이다.

현재 두 DB의 세션 `search_path`는 모두 `"$user", public`; `pg_db_role_setting`의 DB/role별 설정은 0행이다.

해결책은 다음과 같다.

- 권고: 모든 SQL을 `vec.policy_clause_*`로 명시한다.
- 임시 호환: DSN options나 role 설정으로 `search_path=vec,pg_catalog`를 둔다.

**search_path만으로 영구 해결하지 않는 편이 낫다.** `ensure_schema()`가 맨이름 DDL을 실행하므로 잘못된 search path에서 다시 `public` 테이블을 만들 수 있고, 시험도 `public` namespace를 직접 검사한다. 민감한 `app` 데이터가 있는 DB에서 동일 이름 탐색 규칙에 권한 경계를 기대해서도 안 된다.

## 4. 두 DB를 동시에 여는 코드

### 4-1. 명시적으로 두 연결을 동시에 lease하는 곳

`scripts/db/migrate_vec_to_insurance_real.py:86-87` 한 곳뿐이다. `SRC=mall_vec`와 `DST=insurance_real`을 같은 `with`에서 연다. 정상 런타임이 아니라 이관 도구다.

### 4-2. 정상 런타임의 실제 경계

판정 요청은 색인을 읽은 뒤 연결을 닫고, 그 다음 `app/routers/precheck.py:_persist_precheck_if_enabled()`에서 `PgInsuranceRepository` 트랜잭션을 연다.

즉 한 요청에서 두 DB를 순차 사용하지만 한 트랜잭션이 아니다. process-local pool은 DSN별로 남으므로 프로세스 수준에서는 두 DB 물리 연결이 동시에 열려 있을 수 있다.

합친 뒤에도 자동으로 한 트랜잭션이 되지는 않는다. `get_conn()`과 `PgInsuranceRepository._connect()`는 별도 진입점이다. 검색 SELECT와 판정 저장을 한 트랜잭션으로 묶으려면 repository/connection 경계를 명시적으로 합쳐야 한다.

반대로 현재 코드가 “반드시 서로 다른 DB여야 한다”고 가정하는 정상 런타임 로직은 발견하지 못했다.

추가로 `get_settings()`는 LRU cache이고 precheck dependency도 `_DEPS`에 cache된다. 환경변수만 바꾸는 것은 실행 중 프로세스의 cutover나 rollback이 아니다. customer/admin/worker를 재시작하고 기존 pool을 닫아야 한다.

## 5. 권한·역할 — 약관 원문을 넓게 열지 않는 최소안

### 5-1. 현재 실측

- `insurance_owner`: NOLOGIN
- `insurance_app`: NOLOGIN
- `insurance_runtime`: LOGIN, `insurance_app` 멤버
- `insurance_admin`: LOGIN, `insurance_owner` 멤버
- `core` 12테이블: `insurance_owner` 소유, `insurance_app` SELECT만
- `vec` schema: `insurance_owner` 소유
- `vec` 테이블 3개: **`postgres` 소유**
- `insurance_app`: vec 테이블 3/3에 SELECT만
- vec 테이블 RLS: 3/3 모두 꺼짐
- `insurance_owner`와 `insurance_admin`: 현재 vec 테이블 SELECT/INSERT/UPDATE/DELETE 권한 없음
- 017의 default ACL: `postgres`가 앞으로 만드는 vec 테이블에만 적용됨

### 5-2. 유지해야 할 최소 권한

| 주체 | 필요한 권한 | 주면 안 되는 것 |
|---|---|---|
| `insurance_owner` | schema/table/index 소유; migration·복구 | LOGIN, 앱 트래픽 |
| `insurance_app` | `USAGE ON SCHEMA vec`, 3테이블 `SELECT` | INSERT/UPDATE/DELETE/TRUNCATE/CREATE |
| `insurance_runtime` | `insurance_app` 상속만 | 직접 테이블 grant, owner membership |
| 별도 `vec_ingest` NOLOGIN + 전용 LOGIN | 검증된 적재에 필요한 SELECT/INSERT/UPDATE, 필요한 경우 제한된 DELETE | core/app/ops 권한, schema CREATE, TRUNCATE |
| `insurance_admin` | 승인된 migration/maintenance 경계에서 owner 역할 상속 | 일반 HTTP 트래픽의 PGVECTOR DSN |

현재 적재 스크립트들은 `ensure_schema()`에서 `CREATE EXTENSION/TABLE/INDEX`, `ALTER TABLE`까지 하고 그 뒤 DML을 한다. 단순 writer 권한으로는 그대로 돌지 않는다.

해결은 앱 role을 넓히는 것이 아니라 다음을 분리하는 것이다.

- DDL 보장: migration/owner 경계
- 데이터 적재: 전용 writer
- 런타임 검색: read-only `insurance_runtime`

가장 위험한 선택은 기존 기본값에서 dbname만 바꿔 `user=postgres dbname=insurance_real`로 두는 것이다. 그러면 검색 경로가 보험 실제 사례·동의·감사 원장 전체에 슈퍼유저 권한을 얻는다.

## 6. pgvector·인덱스와 재생성 비용

### 6-1. 확장

`insurance_real`에는 이미 다음 확장이 있다.

- `vector 0.8.3`
- `pg_trgm 1.6`
- `pgcrypto 1.3`

`mall_vec`의 vector/pg_trgm 버전과 일치한다. 확장 설치는 선행조건이 아니다.

### 6-2. 무엇이 따라오고 무엇이 재생성되나

| 이관 방식 | 테이블 데이터 | PK/보조/HNSW/GIN |
|---|---|---|
| 현재 Python binary COPY | 데이터만 | 안 따라옴. 목적지 PK는 DDL 때문에 이미 존재; HNSW/GIN/보조 2개는 별도 생성 |
| `pg_dump -Fc` + `pg_restore` | 따라옴 | 정의는 포함되지만 restore 때 **재구축**됨 |
| 물리 base backup/동일 DB 복원 | 따라옴 | 물리 인덱스 페이지도 포함되지만 두 DB를 merge하는 방식은 아님 |
| CTAS/논리복제/FDW/INSERT-COPY | 데이터 | 목적지 인덱스 별도 생성 필요 |

원본 인덱스 실측:

| 인덱스 | 크기 |
|---|---:|
| HNSW `policy_clause_chunk_hnsw` | 975,740,928 B, 930.5 MiB |
| GIN `policy_clause_chunk_text_trgm` | 275,324,928 B, 262.6 MiB |
| chunk PK | 74,293,248 B, 70.9 MiB |
| occurrence PK + gen + sha | 170,704,896 B, 162.8 MiB |
| content PK | 8,855,552 B, 8.4 MiB |

원시 float32 벡터 하한은 다음과 같다.

`164,977행 × 1,024차원 × 4 B = 675,745,792 B = 644.4 MiB`

최종 세 테이블+인덱스의 추가 공간 하한은 원본 실측 기준 **3.23 GiB**다. HNSW+GIN만 다시 써도 약 **1.17 GiB**이며 WAL·임시공간·동시 원본 보존은 별도다.

**시간은 모른다.** 저장소에는 164,977행/1024차원 HNSW 실제 build 시간이 기록돼 있지 않고, 이번 감사는 DDL 실행 금지라 측정하지 않았다.

현재 서버 설정은 다음과 같다.

- `maintenance_work_mem=64MB`
- `max_parallel_maintenance_workers=2`
- `max_wal_size=1GB`
- `checkpoint_timeout=5min`

이 값과 완성 인덱스 크기만으로 신뢰할 elapsed time을 만들 수 없다. restore rehearsal에서 HNSW·GIN 각각의 시작/종료와 peak disk/WAL을 기록해야 한다.

보수적 공간 preflight로는 **최종 추가분 3.23 GiB의 2배 이상, 약 6.5 GiB + dump 보관분**을 임시 여유로 잡을 수 있으나 이는 측정값이 아니라 운영 headroom 제안이다. 현재 디스크 free는 sandbox에서 신뢰할 값으로 읽지 못했다.

## 7. 현재 이관 초안에서 추가로 깨지는 것

`scripts/db/migrate_vec_to_insurance_real.py`와 017을 실행하지 않고 읽어 확인했다.

1. **occurrence binary COPY 열 순서 불일치**
2. **부분 커밋**: 테이블마다 commit한다. content 성공 후 chunk/occurrence가 실패하면 반쪽이 남는다.
3. **재시도 자기 차단**: 목적지 어느 테이블이든 행이 있으면 스크립트가 재시도를 거부한다.
4. **ledger와 DROP 모순**: schema를 DROP해도 017 ledger가 남아 apply가 재생성을 skip한다.
5. **검증이 행수뿐**: 같은 행수의 열 오배치·본문·벡터 손상을 잡지 못한다.
6. **메모리 비상한 없음**: 테이블 전체를 `io.BytesIO`에 받은 뒤 `getvalue()`하여 보낸다. chunk의 데이터+TOAST만 1,247,625,216 B다.
7. **`--indexes`에 완전성 gate 없음**: 빈 occurrence나 행수 불일치 상태에서도 인덱스를 만들 수 있다.
8. **소유권 오류**: schema owner는 자식 table owner로 자동 상속되지 않는다.
9. **“인덱스를 데이터 뒤에”가 절반만 맞음**: HNSW/GIN은 뒤지만 PK 3개는 DDL에서 먼저 생겨 COPY 중 유지 비용을 낸다.

검증은 명시 열 목록과 source/destination binary stream digest 또는 PK별 정렬 digest까지 필요하다.

## 8. 되돌리기 — 옛 DB를 안 지우는 것만으로는 부족하다

옛 DB 보존은 **필수지만 충분하지 않다.**

추가로 필요한 것은 다음과 같다.

1. **cutover 기준점**: 원본 행수·스키마·constraint·index·세대/모델 분포와 dump SHA-256 기록
2. **writer 정지**: build/load/shard/backfill/reconcile 도구 quiesce
3. **단일 snapshot**: 세 테이블을 같은 repeatable-read 또는 한 `pg_dump` snapshot에서 읽기
4. **cutover 후 old DB freeze**: 새 DB에만 write가 생긴 뒤 단순 DSN rollback을 하면 새 write가 사라짐
5. **환경변수 변경 + 전 프로세스 재시작**
6. **ledger 처리**: 017을 삭제·변조하지 말고 새 번호의 forward repair migration 사용
7. **복구 리허설**: 현재 S3 `pg_dump -Fc` restore 시험은 문서상 **0회**

권고 rollback 관문:

| 단계 | 실패 시 |
|---|---|
| DDL/복사 전 | 아무 변경 없음 |
| staging 복사·검증 전 | staging만 폐기; 운영 DSN 불변 |
| 검증 후 cutover 전 | staging 유지/폐기; old DB 계속 정본 |
| cutover 직후, writer 동결 중 | DSN 복귀 + 전 프로세스 재시작 |
| 새 DB write 허용 후 | old DB와 차이 대조·역반영 전에는 단순 DSN 복귀 금지 |

현재 계획의 `DROP SCHEMA vec CASCADE`는 특히 위험하다. 향후 `core`와 vec 사이 FK나 view가 생기면 `CASCADE`가 예상보다 넓게 객체를 제거할 수 있다.

## 9. 백업·복구와 워크로드 관점의 찬반

### 합쳐도 되는 근거

- 두 DB는 이미 같은 PostgreSQL instance/data directory다.
- 한 DB면 `core`→색인 계보 FK/조인과 consistent snapshot을 만들 수 있다.
- schema별 logical dump로 `core/app/ops`와 vec의 백업 주기를 나누는 것은 한 DB 안에서도 가능하다.

### 합치지 않거나 별도 cluster를 고려할 근거

- 운영 원장과 3.23 GiB 검색색인을 한 physical restore 단위로 두면 원장 RTO가 HNSW/GIN 재구축에 끌려간다.
- HNSW build·VACUUM·logical backup이 connection budget과 lock 관찰 범위를 함께 쓴다.
- 진짜 장애·성능·PITR 격리가 필요하면 **다른 DB가 아니라 다른 PostgreSQL cluster/스토리지**가 필요하다.

가장 중요한 백업 판단은 다음이다.

문서에는 vec가 “파생 색인”이라고 적혀 있지만 현재 `core→vec` ETL/계보는 없다. 따라서 지금 vec는 **재생성 가능한 파생물이라고 버릴 수 없다.** 계보와 재생성 시험이 생기기 전까지 원문·벡터를 원장급으로 백업해야 한다.

그 뒤에야 다음 정책 분리가 가능하다.

- `core/app/ops`: 고빈도, 짧은 RPO
- vec: 저빈도 백업 또는 재생성 중심

## 10. 스키마 이름 의견

둘 중에는 **`vec`가 `index_a`보다 낫다.** `index_a`는 내부 프로젝트 단계명이라 의미가 없고 다음 사람이 B가 있는지 묻게 된다.

다만 최선은 **`clause_index`**다. 이 스키마에는 vector뿐 아니라 원문 content, occurrence, trigram GIN, 인용 gate가 함께 있어 `vec`도 실제 책임보다 좁은 이름이다.

이미 017과 부분 복사가 `vec`로 적용된 지금 이름 변경은 P0가 아니다. 먼저 안전하게 멈추고 결함을 고친 뒤 최종 이름을 한 번 정해 SQL을 전부 schema-qualified해야 한다.
