## 2. 커머스 격리 — 지우지 않고 옮겼다

```
app/routers/products.py  →  app/legacy/products.py
app/routers/orders.py    →  app/legacy/orders.py
app/routers/payments.py  →  app/legacy/payments.py
```

`main.py` 에서 `include_router` 만 뺐다. **코드는 그대로 있다.**

- **지우지 않은 이유**: 실습 산출물이라 평가 자료가 될 수 있고, 삭제는 되돌릴 수 없다
- **옮긴 이유**: `app/routers/` 에 두면 OpenAPI 문서에 `/api/products` 가 계속 뜬다.
  보험 API 를 쓰는 사람이 혼란스럽다

앱 제목도 `AI 커머스 에이전트` → `보험 보장 판정 에이전트` 로 바꿨다.
라우트 45개 중 커머스 경로는 `/api/admin/orders` 하나만 남았다(관리자 전용).

## 3. `citation_guard` — 이 프로젝트의 안전장치

### 문제 인식은 팀에서 나온 것이 맞았다

> 근거가 아예 없으면 `knowledge_gap` 으로 막아 놨다. 그런데 근거가 **조금이라도**
> 있어서 판정까지 온 경우엔, LLM 이 나머지를 자기 지식으로 채울 위험이 있다.
> 조항에 "우울증"이 없는데 "정신과 질환이니 비슷하게 보장될 겁니다" 처럼.

실제로 지금 코드가 그 구조다.

```python
evidence = self._retriever.search(q, k=self._top_k)
if not evidence:
    return AnswerResult(answer=NO_ANSWER, sources=[])   # 0건이면 차단
reply = self._model.complete(...)                       # 1건이면 통과, 이후는 프롬프트 소관
```

### 다만 "프롬프트가 유일한 방어선"은 아니다

**코드로 강제할 수 있다.**

```
LLM 이 인용한 조항을 뽑는다 → 넘겨준 근거에 실재하는지 대조 → 없으면 답을 버린다
```

프롬프트를 무시하는 모델이라도 이 검사는 통과하지 못한다.

### 더 위험한 건 지금 구조다

`_citations()` 는 **검색 결과를 그대로 출처로 붙인다.**
LLM 이 지어낸 답에도 근거가 달려 나가서 **오히려 더 그럴듯해 보인다.**
인용한 것과 붙은 출처가 다른 것이다.

### 구현

| 검사 | 위반 시 |
|---|---|
| 인용 조항이 허용 목록(근거)에 있는가 | **폐기** |
| 본문에서 `제N조` 를 말했는데 선언 안 했는가 | 경고 |
| 인용문이 조항 원문의 실제 일부인가 | 경고 |

2번을 폐기 사유로 삼지 않은 이유: 본문의 `제N조` 는 **조항 안의 상호참조**일 수 있다.
(실측: 조항 간 상호참조가 문서당 평균 5.8개)

부 이름은 대조에서 뺐다 — LLM 이 `보통약관/제9조` 를 정확히 쓰길 기대하면
**정답인데 폐기**하는 일이 생긴다. 번호가 근거에 없으면 그건 확실한 오류다.

## 4. `policy_version` — 가입일 → 적용 약관

### 현행 약관 폴백을 만들지 않았다

못 찾으면 `NotResolved` 를 돌려준다.
**"일단 최신 약관으로 답한다"가 가장 위험한 폴백**이다 —
사용자는 자기 계약이 아닌 약관으로 안내받는다.

```python
def test_보유_기간_밖이면_현행약관으로_때우지_않는다():
    r = resolve(insurer="삼성화재", enrolled_on="20100101", versions=_POOL)
    assert isinstance(r, NotResolved)
    assert r.reason_code == "no_version_at_date"
```

### 실데이터로 돌리며 결함 셋을 잡았다

**① `00000000` 이 날짜인 척 후보에 들어왔다**
```
삼성화재 20050101 → 후보: 00000000 실손의료비 보장 무사고자 할인 특별약관(Ⅰ)
```
자리표시자를 날짜로 취급했다. `usable_for_judgment` 에서 걸러냈다.

**② 특별약관이 본약관과 동급으로 경쟁했다**
```
삼성화재 20190501 → [ambiguous] 후보: [갱신형] 무배당 실손의료비 특별약관
                                     무배당 삼성화재 다이렉트 실손의료비보험
```
특약은 본계약에 붙는 것이지 "가입한 상품"이 아니다.
본약관을 먼저 보되, 상품명을 명시하면 특약도 후보로 둔다.

**③ 상품 라인이 갈리는데 조용히 하나를 골랐다**

이게 가장 위험했다. 일반 실손·노후실손·유병력자실손은 **자기부담금 체계가 아예 다르다.**
시작일이 우연히 하나만 최신이면 노후실손을 골라 버려서,
일반 실손 가입자에게 노후실손 기준으로 답하게 된다.

이제 반드시 되묻는다.

```
삼성화재 20190501 → [ambiguous_product_line]
   · standard          무배당 삼성화재 다이렉트 실손의료비보험(1904.3)
   · senior            무배당 삼성화재 노후실손의료비보험(1904.8)
   · simplified_issue  무배당 삼성화재 유병력자 실손의료비보험(1904.3)

삼성화재 20190501 "다이렉트 실손의료비" → 3세대(착한실손) / 20190401
```

판정 가능 약관 **1,361개** (본약관 914 / 특약 447).

## 5. 계획 밖에서 나온 것 — 두 가지 큰 결함

### 5-1. 내가 만든 세대 판정이 틀렸다 (코덱스가 잡음)

`config/generation_profiles.json` 이 **이미 있는데 보지 않고** 경계를 코드에 박았다.

| 항목 | 내 코드 | 기존 설정 |
|---|---|---|
| 5세대 | **없음** | 2026-05-06 시작 (verified) |
| 4세대 종료 | 없음 | 2026-05-05 |
| 노후·유병력자 | 일반과 같은 축 | `applies_to: ["standard"]` — **별도 라인** |

**107행을 4세대로 잘못 판정**했고, 노후실손·유병력자실손에 세대를 붙였다.
설정을 읽도록 다시 썼다. 같은 사실을 두 곳에 두면 반드시 갈라진다.

설정의 `review_status="unreviewed"` 도 존중해 판정 결과에 `generation_review` 를 남긴다.
설정 스스로 *"금융위/협회 원문으로 재확인이 필요하다"* 고 적고 있다.

### 5-2. 실손의료보험이 아닌 문서 159건

세대 판정에서 `product_line=unknown` 184건이 나와 열어 보니:

```
실손·비례보상 주택 풍수해·지진재해보험(Ⅲ)     ← 주택 재해보험
실손보상 온실 풍수해보험(Ⅴ)                  ← 농업시설 보험
KB간편가입아파트화재보험(실손형)               ← 화재보험
자동차사고 변호사선임비용…(실손) 특별약관        ← 자동차 특약
```

여기서 `실손` 은 **"실제 손해를 보상한다"는 방식**을 뜻하지 의료비가 아니다.
수집 필터가 키워드만 봐서 딸려 들어왔다.
**의료비 질문에 풍수해보험 조항을 들이대게 되므로** 격리했다.

## 7. 남은 위험

코덱스 지적을 그대로 옮긴다.

> 가장 큰 불확실성은 기술이 아니라 **데이터**다.
> 안정적인 조항 ID·번호·페이지·약관 버전이 없다면 **판정 API보다 전처리가 먼저**다.

구체적으로:

- **조 번호 충돌이 남아 있다** — 부까지 포함해도 37종.
  `(문서, 특약ID, 조번호)` 식별키가 서야 `citations` 가 신뢰된다
- **표(table) 의미 부착 미착수** — 보장 한도·자기부담금이 표에 들어 있다
- **별표 귀속 미정** — 장해분류표 등이 어느 조항에 속하는지
- **`ambiguous_product_line` 이 자주 뜬다** — 정상 동작이지만
  프론트에서 상품 선택 UI 가 필요하다는 뜻이다
