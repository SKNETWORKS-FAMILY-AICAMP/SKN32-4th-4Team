# 인용 검증기 P0 결함 — 안전장치가 87% 문서에서 작동하지 않았다

작성 2026-08-02 · 코덱스 교차검증 · 대상 `app/core/domain/citation_guard.py`

---

## 0. 왜 이게 P0인가

`citation_guard` 는 이 서비스에서 **제1원칙("모르면 모른다고 한다")을 강제하는 장치**다.

근거가 0건이면 LLM 을 부르지 않는 방어는 이미 있다. 문제는 **근거가 하나라도 있을 때**다.
그때 LLM 은 호출되고, 그 다음은 프롬프트에 맡겨진다. 조항에 "우울증"이 없는데
*"정신과 질환이니 비슷하게 보장될 겁니다"* 처럼 지어낼 위험이 여기 있다.

프롬프트는 지켜지길 **바라는 것**이지 강제되지 않는다.
그래서 코드로 막는다 — LLM 이 인용한 조항을 근거와 대조하고, 없으면 그 답을 버린다.

**그게 작동하지 않고 있었다.**

---

## 1. 결함 1 — 조항 키에서 부(部) 이름을 뗐다

```python
def _clause_key(qualified_no: str) -> str:          # v1
    """`보통약관/제 9 조` → `제9조`. 부 이름은 떼고 번호만 본다."""
```

주석은 이 완화를 **의도적으로** 설명한다.

> *"LLM 이 부 이름까지 정확히 쓰길 기대할 수 없다.
> 부까지 맞추길 요구하면 정답인데 폐기하는 일이 생긴다."*

의도는 타당하다. **결과가 뒤집혔다.**

### 실측 (v4 전량 1,367문서)

| 키 | 중복 | 영향 문서 | 한 키 최대 |
|---|---:|---:|---:|
| `qualified_no` 그대로 | 31,085건 | 1,181 (86%) | 25 |
| **v1 의 키 적용 후** | **71,707건** | **1,191 (87%)** | **96** |

**완화가 충돌을 2.3배로 늘렸다.**

한 문서에서 키 `'1.'` 에 9개가 뭉친 실제 예:

```
보통약관/1.                          p34  '보장종목'
특별약관/1.                          p58  '보장종목'
이륜자동차 운전중상해 부담보 특별약관/1.   p72  '특별약관의 체결 및 효력'
```

### 두 가지가 깨졌다

**① 검증 우회** — LLM 이 **어느 특약의 1조를 인용하든** 허용 목록을 통과한다.

**② 엉뚱한 대조** — `by_key` 가 dict comprehension 이라

```python
by_key = {_clause_key(e.qualified_no): e for e in evidence}
```

**95개가 마지막 것에 덮인다.** 인용문 원문 대조가 **다른 조항 본문**과 이뤄져
틀린 근거가 "검증됨"으로 나온다. 이게 더 위험하다 — 근거가 붙어 있으니
**오히려 더 그럴듯해 보인다.**

## 2. 코덱스가 찾은 결함 다섯 개 더

| # | 결함 | 결과 |
|---|---|---|
| 3 | `ok = not unknown` | **빈 `cited_clauses` 로도 통과**했다 |
| 4 | `quote_mismatches`·`undeclared_mentions` 가 경고 | 틀린 인용문도 통과했다 |
| 5 | `_NUM.search()` | `"아무말 제9조 아무말"` 이 통과했다 |
| 6 | `1.`(호)과 `제1조`를 같은 키로 | 문법 층이 다른데 섞었다 |
| 7 | `quotes` 가 dict | 같은 조항의 복수 인용이 덮였다 |

특히 3·4번은 **검사를 통째로 우회하는 경로**다.

```
cited_clauses=[] 로 두고 본문에만 "제9조에 따르면" 이라 쓰면 → 통과
quote="" 로 두면 대조를 건너뛴다                              → 통과
```

## 3. v2 설계

### 인용 해소 순서

```
① 손잡이(E001)        요청 단위로 근거에 붙여 준다. 가장 확실하다
② 전체 경로            `보통약관/제9조`
③ 번호만               후보가 **정확히 1개일 때만** 해소
    후보 0개  → unknown
    후보 2개+ → ambiguous   ★통과시키지도, 폐기하지도 않고 "모른다"고 한다
    조항 표기가 아님 → invalid
```

**손잡이가 핵심 해법이다.** "LLM 이 이름을 정확히 못 쓴다"는 원래 문제 인식은
맞았는데, 해법이 *"기준을 낮춘다"* 였다. **기준을 낮추는 대신 쉬운 손잡이를 준다.**

### 부를 썼는데 틀리면 번호로 강등하지 않는다

`없는특약/제9조` 는 `제9조` 가 근거에 있어도 통과하면 안 된다.
부까지 썼는데 틀렸다는 것은 **다른 조항을 가리킨 것**이다(코덱스 지적).

### 승인은 fail-closed

```python
ok = (
    not no_citations                      # 인용이 하나도 없으면 실패
    and not any(unknown/ambiguous/invalid)
    and not any(quote_mismatch)
    and not undeclared                    # 본문에서만 말한 조항이 있으면 실패
)
```

### 선언 누락 판정에서 상호참조는 뺀다

조항 본문에는 상호참조가 많다(실측: 문서당 평균 5.8개).
`제9조` 를 인용했는데 그 본문에 "제4조에 따라"가 있다고 폐기하면 과하다.
**해소된 근거 자신의 번호는 선언된 것으로 본다.**

## 4. `clause_id` 충돌도 함께 고쳤다

코덱스가 지적한 별건이다.

```python
def clause_id(self) -> str:                 # 이전
    return f"{self.sha256[:12]}/{self.qualified_no}"
```

`qualified_no` 가 유일하지 않으므로 이것도 31,085건 충돌한다.
그리고 `_dedupe()` 가 이 값으로 인용을 접어 **서로 다른 조항이 조용히 사라졌다.**

원인은 조 번호 재시작이 아니다. **부 탐지 입도가 특약보다 굵어** 서로 다른
특약 여러 개가 한 라벨 아래 뭉친다.

```
p73  보험료 자동납입 특별약관/1.   "보험료 납입"             324자
p73  보험료 자동납입 특별약관/1.   "특별약관의 체결 및 효력"   798자
```

**내용 해시를 덧붙여** 구분한다. `_dedupe` 는 페이지도 함께 본다.

| | 중복 | 영향 문서 |
|---|---:|---:|
| 이전 | 31,085건 | 1,181 (86%) |
| **수정 후** | **8건** | **3 (0%)** |

**99.97% 감소.**

## 5. 검증

테스트 19개를 새로 썼다. **v1 의 결함마다 하나씩** 대응한다.

```
같은 번호가 여러 부에 있으면 기권한다        ← 결함 1
손잡이로 인용하면 충돌이 없다
부를 썼는데 틀리면 번호로 강등하지 않는다
인용이 아예 없으면 폐기한다                   ← 결함 3
본문에서만 말하고 선언하지 않으면 폐기한다     ← 결함 4
인용문이 원문에 없으면 폐기한다               ← 결함 4
빈 인용문은 통과가 아니라 실패다
조항 표기가 아니면 invalid 다                 ← 결함 5
조와 호를 구분한다                            ← 결함 6
같은 조항의 인용문 여러 개를 모두 본다        ← 결함 7
```

전체 **57개 통과** (인용 19 · KCD 17 · 약관버전 11 · 아키텍처 10).

API 응답의 인용도 서로 구분된다:

```
bbbdfd030355/보통약관/4-1.#9389a9ef                  p33
bbbdfd030355/실손의료보험 특별약관/4.#12829d60         p58
bbbdfd030355/비급여 주사료 실손의료보험 특별약관/4.#78ec1f68  p62
```

이전에는 셋이 `4.` 하나로 뭉쳤을 것이다.

## 6. 이 검증기가 **하지 못하는 것** (정직 기록)

코덱스가 짚은 것들이다. 고치지 않았고, 고칠 수 없는 것도 있다.

| 남은 구멍 | 설명 |
|---|---|
| **인용 세탁** | 정확한 조항의 진짜 문장을 인용하면서 **엉뚱한 결론**을 내는 것. 문자열 포함 검사이지 함의(entailment) 검사가 아니다 |
| snapshot 불일치 | 모델에 보낸 본문과 검증기가 읽는 원문이 다를 수 있다. 실제 전송 바이트의 해시를 묶어야 한다 |
| 버전 적용성 | ID 가 맞아도 가입일에 적용되는 약관 버전이 아니면 무효다 |
| 상호참조 | "제9조에 따른다"만 있는 조항은 제9조를 더 따라가야 한다 |
| 목차·표제 오인 | 목차 줄을 본문 조항으로 취급하는 경우 |
| 프롬프트 인젝션 | 근거 본문 안의 지시문 |

### ★그래서 최종 구조는 이렇게 가야 한다

> **규칙 엔진이 판정(verdict)을 소유하고, LLM 은 설명만 만든다.**
> 인용 검증에 실패하면 설명 전체를 폐기한다.

이 검증기로 **LLM 의 판정 자체를 검증하려 하면 안전장치가 완성되지 않는다.**
지금 `precheck` 는 LLM 없이 규칙만으로 판정하므로 그 구조에 이미 맞다.
LLM 을 붙일 때 이 경계를 넘지 않아야 한다.

---

## 7. 남은 일

1. **`ambiguous` 를 판정에 반영** — 지금은 `GuardResult` 가 돌려주기만 한다.
   `precheck` 가 이를 받아 `verdict=NEEDS_EXPERT` · `reason_code=AMBIGUOUS_CITATION`
   으로 기권하는 경로를 붙여야 한다(코덱스 권고).
2. **부 탐지 입도 개선** — 근본 원인이다. 전처리 v5 에서 다루고 있다.
3. **LLM 연결 시 손잡이 주입** — `make_handles()` 로 근거에 `E001` 을 붙여
   프롬프트에 넣고, 그걸로 인용하도록 지시해야 한다.
