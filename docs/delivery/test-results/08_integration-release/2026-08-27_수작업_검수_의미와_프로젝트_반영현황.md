# 수작업·검수의 의미와 프로젝트 반영 현황

현재까지의 수작업은 단순히 데이터를 많이 만드는 작업이 아니라, 자동화 결과를 어디까지 믿고 어디서 차단할지를 정하는 작업이었습니다.

쉽게 말하면 다음 구조입니다.

```text
수집한 원문
  ↓ 사람·기계가 문서 신원 확인
전처리 결과
  ↓ 표·OCR 결과를 사람이 판독
서비스에 써도 되는 근거만 승인
  ↓
검색·보험 판정
  ↓ 사람이 답변 문장과 근거를 검수
평가용 정답지로 보관
```

## 전체 요약

| 수작업 | 규모 | 의미 | 현재 프로젝트 사용 상태 |
|---|---:|---|---|
| 보험사 사이트·PDF 원문 확인 | 최초 1,817건 수집 | 제대로 된 실손 약관을 받았는지 확인 | ✅ 현재 1,355개 판정 대상 문서의 기반 |
| 약관 문서명·상품·버전 확인 | 어려운 문서 109건 검토, 최종 원장 1,355건 | 어떤 상품의 어느 약관인지 확정 | ✅ 실제 약관 선택·DB 적재에 사용 |
| 표 판별 라벨링 | 최초 59건 + 추가 68건, 최종 120쪽 | 표와 일반 문장을 구분 | ✅ 전처리 규칙 개선에 반영 |
| OCR 추출 결과 승인 | 29패턴·1,066개 사실 | OCR이 읽은 숫자와 항목이 맞는지 확인 | ✅ 승인 850건만 검색·인용에 사용 |
| 전처리 600건 검수 | 600건 | 빠진 약관 페이지, 표, 장해율, 지연이자 검증 | ⚠ 병합본은 있지만 아직 본 프로젝트에 완전히 반영되지 않음 |
| 판례·금감원 사례 검수 | 114건 | 잘린 원문·법리 오분류·잘못된 결론 제거 | 🧪 QA·평가 자료로 일부 사용, 실시간 판정에는 미사용 |
| QA 답변 검수 | 파일럿 300건, 평가 정답 221건 | 고객에게 나갈 문장과 근거가 맞는지 확인 | 🧪 모델 평가용, 학습·실서비스에는 직접 미사용 |
| 검수 HTML 사용성 확인 | 선택 표시·앞뒤 문맥·다운로드 점검 | 사람이 잘못 누르는 문제 방지 | ✅ 검수 도구 품질 개선 |
| 얼굴 로그인 모델 실측 | 여러 조건·모델 비교 | 실제 운영 기본 모델 결정 | ✅ AdaFace가 현재 기본값 |

## 1. 보험 약관 수집 과정의 수동 확인

보험사마다 다운로드 방식이 달라 사람이 사이트 구조와 실제 내려받은 파일을 확인했습니다.

예를 들면 다음과 같습니다.

- 삼성화재의 여러 첨부파일 중 어느 것이 진짜 약관인지 표지를 대조했습니다.
- 메리츠화재는 일반 다운로드가 막혀 브라우저 다운로드 이벤트를 확인했습니다.
- 흥국생명은 EUC-KR 인코딩과 이중 인코딩을 찾아냈습니다.
- 삼성생명의 비실손 문서 443건을 실제 상품 종류와 대조해 제거했습니다.
- 잘린 PDF, 중복 파일, HTML 오류 파일을 확인했습니다.
- robots 정책상 수집하면 안 되는 곳은 중단했습니다.

이 작업의 의미는 “데이터가 많다”가 아니라 “출처부터 틀린 문서가 들어오는 것을 막았다”는 데 있습니다.

최초 1,817건을 모았지만 중복·비대상·격리 문서를 제외한 현재 판정 대상은 1,355건입니다. 이 문서들이 이후 전처리·검색·보험 판정의 원재료입니다.

관련 보고서: [실손약관 수집 결과보고](../01_collection-identification/2026-08-01_실손약관_수집_결과보고.md)

## 2. 문서명·상품·버전 확인

PDF 내용은 맞더라도 상품명이나 세대가 틀리면 사용자의 가입일에 맞는 약관을 고를 수 없습니다. 그래서 이름 불일치·경쟁상품 혼동 같은 어려운 문서를 따로 검토했습니다.

작업 결과는 다음과 같습니다.

- 이름 불일치·모호 문서 109건 검토
- 106건 확인
- 잘못 들어간 문서 1건 분리
- 당시 보류 2건은 후속 원문 대조로 처리
- 현재 확정 원장 1,355건

이 원장은 실제로 다음 코드가 읽습니다.

- [`app/adapters/manifest_policy_resolver.py`](../../../../app/adapters/manifest_policy_resolver.py)
- [`app/routers/precheck.py`](../../../../app/routers/precheck.py)
- [`scripts/db/import_insurance_core.py`](../../../../scripts/db/import_insurance_core.py)

즉, 사용자가 가입일과 상품을 입력했을 때 어떤 약관을 찾아야 하는지 결정하는 데 직접 쓰입니다.

다만 중요한 한계가 있습니다. 현재 1,355건은 프로젝트 소유자가 일괄 승인한 것이며, 문서별로 1,355개를 모두 직접 읽은 것은 아닙니다. 특히 945건은 근거가 `name_only`, 즉 이름 위주 확인입니다. 따라서 “1,355개 전부 사람이 개별 검증했다”고 표현하면 안 됩니다.

정본: [`config/confirmed_documents.jsonl`](../../../../config/confirmed_documents.jsonl)

## 3. 표 판별 수작업

좌표가 여러 열로 나뉘었다고 모두 표는 아닙니다. 일반 문장, 코드 목록, 목차가 표처럼 잡히는 문제가 있었습니다.

첫 번째 검수는 다음과 같았습니다.

- 실제 표 5건
- 표가 아님 51건
- 원문 추가 확인 3건

이 라벨로 검사해 보니 기존 표 판별 신호가 참과 거짓을 제대로 구분하지 못한다는 사실이 드러났습니다. 그래서 셀 길이, 문장부호 비율, 긴 문장 비율을 보는 `T9 본문 모양 검사`를 추가했습니다.

후속 68건까지 반영한 최종 페이지 정답은 다음과 같습니다.

- 실제 표 또는 구조가 있는 페이지 37쪽
- 일반 문장·깨진 결과 등 사용 불가 83쪽
- 합계 120쪽

이 수작업 결과는 서비스가 라벨 파일을 매번 읽는 방식은 아닙니다. 사람이 확인한 결과로 전처리 규칙을 고쳤고, 현재 [`scripts/extract/table_signals.py`](../../../../scripts/extract/table_signals.py)의 `T9` 규칙으로 남아 있습니다.

정답 파일: `data/eval/table_labels_s7_human_20260804.jsonl` — 사람 검수 원자료는 공개 저장소 제외 대상입니다.

## 4. OCR 사실 29패턴 승인

OCR이 읽어낸 결과 중 같은 구조를 가진 항목을 패턴으로 묶어 사람이 대표 원문과 대조했습니다.

결과는 다음과 같습니다.

| 판정 | 패턴 | 실제 추출 사실 | 처리 |
|---|---:|---:|---|
| 승인 | 24 | 850 | 검색·인용 가능 |
| 수정 필요 | 5 | 216 | 격리, 서비스 사용 금지 |

이 작업은 현재 서비스에 직접 반영된 가장 중요한 수작업입니다.

승인된 850건만 다음 경로에 들어갑니다.

- 검색 인덱스
- 챗봇 근거 검색
- 페이지·표 위치 인용
- QA 후보 생성

실제 서비스 코드는 [`app/adapters/file_benefit_facts.py`](../../../../app/adapters/file_benefit_facts.py)에서 승인 파일만 읽습니다. 수정 필요로 분류한 216건은 파일로 보존되지만 고객 답변의 근거로 사용할 수 없습니다.

승인 원본: `data/work/s7_1_approved_facts/approved_facts.jsonl` — 승인 원자료는 공개 저장소 제외 대상입니다.

관련 보고서: [S7.1 OCR 승격 결과](../02_preprocess-ocr-table/2026-08-04_S7.1_OCR승격_최종결과.md)

## 5. 전처리 600건 검수

5명이 나눠 검수했던 600건은 다음 내용으로 구성됐습니다.

| 내용 | 검수 수 | 확인한 것 |
|---|---:|---|
| A1 조항 밖 원인 | 240 | 약관 내용이 빠진 것인지, 표지·목차인지 |
| 조항 밖 2차 표본 | 200 | 조항 추출기의 누락률과 누락 원인 |
| 표 정답셋 A | 60 | 좌표 표가 실제 표인지 |
| 표 정답셋 B | 65 | 표·깨진 표·일반 문장 구분 |
| 장해지급률 B8 | 26패턴 | 장해 설명과 지급률 숫자의 짝이 맞는지 |
| 지연이자 F4 | 9쪽 | 기간별 이자율 36개가 정확한지 |

주요 결과는 다음과 같습니다.

- 약관 내용인데 조항에서 빠진 페이지: A1 74쪽, 2차 표본 39쪽
- 장해지급률: 24패턴 승인, 2패턴 수정
- 지연이자: 9쪽 전부 승인
- 표 B: 실제 표 6, 깨진 표 29, 일반 문장 30

이 작업은 전처리기가 어디서 내용을 버리고 있는지, 장해지급률·지연이자 전용 추출기가 믿을 만한지를 확인하기 위한 작업이었습니다.

하지만 현재 가장 중요한 문제는 결과가 아직 서비스 데이터에 완전히 연결되지 않았다는 점입니다.

- 최종 병합본 600건은 별도 작업 폴더에 존재합니다.
- 본 프로젝트 코드에는 이 병합본을 가져오는 반영 절차가 없습니다.
- 장해지급률 26패턴은 여전히 `pending_human_pair_accuracy` 상태입니다.
- 지연이자 9쪽도 `candidate`, 즉 후보 상태입니다.
- 두 데이터 모두 `serving_eligible=false`라서 실제 답변에는 아직 사용되지 않습니다.

최종 병합본: 외부 검수 작업 폴더의 `review600/human_review_600_merged.jsonl` — 사람 검수 원자료는 공개 저장소 제외 대상입니다.

또 Part 4의 141건 중 70건은 사람이 최종 승인한 것이 아니라 Codex가 PDF를 다시 읽고 정정한 결과입니다. 따라서 정확한 표현은 “사람 제출 후 Codex 원문 재검수·정정 완료”입니다.

## 6. 판례·금감원 사례 114건 검수

AI가 처음 정리한 판례에는 다음 문제가 있었습니다.

- 판결문이 중간에서 잘림
- 판결 주문과 이유를 혼동
- 보장 여부 사건이 아닌데 `not_covered`로 단순 분류
- 계약 해지와 계약 무효 혼동
- 절차법·부당이득·정액 암보험을 실손 보장 판정으로 오분류

검수 결과는 다음과 같습니다.

| 결과 | 건수 |
|---|---:|
| 그대로 확인 | 57 |
| 내용 수정 | 30 |
| 사용 거절 | 27 |
| 합계 | 114 |

현재 이 자료는 실시간 보험 판정의 근거로 사용하지 않습니다. 일부가 QA 파일럿의 기권 사례를 만드는 참고자료로 사용됐고, 향후 판례 검색·평가용 정답 후보로 보관돼 있습니다.

정본: `data/legal/legal_case_normalized_final.jsonl` — 법률 검수 원자료는 공개 저장소 제외 대상입니다.

주의할 점도 있습니다.

- `case_100`, `case_94`는 서로 다른 AI 검토 결과가 충돌했지만 실제 담당자가 원문을 다시 확인하지 않은 상태입니다.
- 암 정액보험금·계약무효·자동차보험 등은 실손과 관련은 있어도 실손 담보 판정 정답으로 바로 사용할 수 없습니다.
- 파일에는 114건 모두 `human`으로 표시됐지만 일부는 AI+Codex 교차검증 후 담당자 명의로 귀속한 사례입니다.

따라서 “114건 모두 독립적인 사람 원문 검증 완료”라고 발표하면 과장입니다.

## 7. QA 답변 수작업 검수

QA 검수에서는 엔진 판정을 바꾸는 것이 아니라 다음을 확인했습니다.

- 고객 질문의 날짜가 현실적으로 가능한지
- 사고일이 가입일보다 앞서 있지 않은지
- 근거가 없는데 보장된다고 단정하지 않는지
- `parse_status`, `citation_eligible` 같은 내부 개발자 용어가 고객에게 노출되지 않는지
- 인용한 조항과 답변 내용이 실제로 일치하는지
- 같은 조항을 반복하거나 잘린 문장을 출력하지 않는지

현재 파인튜닝 데이터에는 사람이 확인한 항목 221건이 들어 있습니다.

- 그대로 승인: 118건
- 사람이 문장을 수정: 103건

이 221건은 학습에 넣지 않고 모델을 시험하는 “시험 정답지”로만 사용했습니다. 학습 데이터 2,360건은 규칙으로 만든 데이터입니다.

실제 평가에서는 고객 문장 형식과 사람 답변 유사도는 좋아졌지만, 근거가 정말 옳은지는 충분히 검증하지 못했고 반복 출력도 증가했습니다. 따라서 파인튜닝 모델은 아직 실서비스에 배포되지 않았습니다.

현황: `data/finetune/sft/manifest.json` — 학습·평가 원자료는 공개 저장소 제외 대상입니다.

평가 보고서: [파인튜닝 실행결과 평가](../05_llm-finetuning-qa/2026-08-27_파인튜닝_실행결과_평가.md)

별도 통합 재감사본에서는 300건 중 131건이 아직 `needs_human=true`로 남아 있습니다. 따라서 “QA 파일럿 300건 전부 최종 확정”이라고 말할 수는 없습니다.

## 8. 검수 HTML 자체의 수동 테스트

검수자가 실제로 화면을 사용하면서 다음 문제를 찾아냈습니다.

- 선택한 버튼의 테두리만 바뀌고 체크 표시가 안 보이는 문제
- 현재 페이지만 보여줘서 약관 내용인지 판단하기 어려운 문제
- 앞뒤 페이지·조항 범위가 부족한 문제
- 비전공자가 선택지의 의미를 이해하기 어려운 문제
- 잘못된 선택을 되돌리거나 저장하기 어려운 문제

이 피드백으로 선택 표시, 앞뒤 문맥, 모범 사례, 임시 저장, JSONL 다운로드 기능을 보완했습니다.

이 작업은 보험 판정 로직을 바꾼 것은 아니지만, 사람이 잘못 선택해서 정답 데이터가 오염되는 것을 줄이는 역할을 했습니다.

## 9. 얼굴 로그인 모델 실측

얼굴 로그인은 별도의 사람 라벨 정답셋 작업은 아니지만, 사람이 테스트 조건을 정하고 결과를 비교해 모델을 결정했습니다.

- 흐림
- 저조도
- 저해상도
- 같은 사람과 다른 사람 구분
- CPU·DirectML 속도

이 비교 결과 AdaFace가 ArcFace와 LVFace보다 열악한 촬영 조건에서 상대적으로 안정적이어서 현재 기본 모델이 됐습니다.

현재 사용 상태:

- 기본 모델: AdaFace IR-101
- 환경변수: `FACE_RECOGNITION=adaface`
- 선택 가능: `adaface`, `lvface`, `insightface`
- 모델을 바꾸면 기존 얼굴을 다시 등록해야 함

다만 실제 여러 사용자의 웹캠 분포와 사진 공격을 이용한 라이브니스 검증은 아직 충분하지 않습니다.
