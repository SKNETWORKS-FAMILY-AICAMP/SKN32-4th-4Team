# 서버·클라이언트 동작 검증 + 팀 저장소 반영

- 날짜: 2026-08-04 07:00
- 목표: 고객앱·운영앱이 뜨는지, 화면에서 **값 입력과 버튼**이 실제로 동작하는지 확인하고
  문제를 고친 뒤 팀 저장소 `feature-frontend` → `develop` 에 올린다
- 규칙: RULE.md §2 · §3.4 · §4.0 · CLAUDE.md §4

## 1. 무엇을 어떻게 확인했나

브라우저에서 **실제 마우스 클릭과 키보드 입력**으로 돌렸다. DOM 스크립트로 값을 넣는 것은
핸들러만 확인될 뿐 "사용자가 눌러서 되는가"를 확인하지 못한다.

★**중간에 헛짚었다.** 처음 몇 번의 클릭이 먹지 않아 앱 결함으로 의심했는데,
탭이 앞으로 나와 있지 않으면(`tabs_select` 전) 합성 클릭이 전달되지 않는 것이었다.
그리고 `read_page` 로 좌표를 잡은 뒤 지원범위 패널이 늦게 그려지며 **레이아웃이 밀려**
같은 좌표가 다른 자리를 눌렀다. **도구 사정이지 앱 결함이 아니다.**

## 3. 고친 것 셋

### ① 정적 파일에 `Cache-Control` 이 없었다 — 화면에 옛 브랜드명이 남았다

**위치** `app/main.py:83` (미들웨어 신설)

운영 화면 제목이 `관리자 대시보드 — 옛브랜드명` 으로 떴다. 저장소에는 그 문자열이
**한 곳도 없고**(`grep` 0건) 서버도 올바른 파일을 내보내고 있었다.

```
서버 응답: const BRAND_NAME = "올바른 보험비서";
브라우저:  BRAND_NAME === "옛브랜드명"
```

`/static/*` 응답에 `Cache-Control` 이 없어 브라우저가 `Last-Modified` 로 **제 유효기간을
스스로 정하고**(heuristic caching) 옛 파일을 계속 썼다.

**위험도: 중** — 코드를 고쳐 배포해도 **이미 방문한 사용자 화면은 안 바뀐다.**
이번엔 이름이었지만 판정 문구·경고 배너가 옛 것으로 남으면 같은 방식으로 조용히 틀린다.

조치: `/static/` 응답에 `Cache-Control: no-cache`. 캐시 금지가 아니라 **쓰기 전 재확인**이라
ETag 가 같으면 304 로 끝나 전송량은 그대로다.

검증 — `fetch(..., {cache:'reload'})` 로 캐시를 갱신한 뒤 재접속:

```
전: 관리자 대시보드 — 옛브랜드명
후: 관리자 대시보드 — 올바른 보험비서
헤더: /static/common.js · admin.js · style.css 전부 Cache-Control: no-cache
```

### ② 판정 화면에 `추출` 라벨만 덩그러니 찍혔다

**위치** `app/static/insurance.js:174`

```
규칙엔진 rules-2026.08.02 · 추출  · 추적 c11e9fac028cfb89
```

`extractor` 가 빈 문자열이라 라벨만 남았다. **값이 빈 것은 옳다** — PG 색인 경로에서
`pg_clause_store.stats()` 는 `extractor` 를 돌려주지 않는다. PG 에 그 값이 없기 때문이고,
없는 것을 채우지 않는 것이 이 프로젝트의 규칙이다(CLAUDE.md §1). **화면이 틀렸다.**

조치: 빈 값이면 라벨째 뺀다.

```
후: 규칙엔진 rules-2026.08.02 · 추적 fae097c8613a6570
```

★파일 저장소 경로에는 `extractor: "pymupdf/1.28.0:"` 가 들어 있다(끝의 `:` 는 별건).
**어느 저장소를 쓰느냐에 따라 화면 정보량이 달라진다** — 이건 안 고쳤다(§5).

### ③ 워크스페이스 실행 설정이 고객/운영 분리를 무너뜨리고 있었다

**위치** `.claude/launch.json` (워크스페이스 루트)

`app.main:app`(통합 앱)을 8099 로 띄우는 항목이 있었다. 그러면 **관리자 API 를 포함한
경로 40개가 한 프로세스에 열린다.** 화면에서는 안 보여도 API 는 열려 있다.
프로젝트 자신의 `_unified_mall_3/.claude/launch.json` 이 정확히 이 사고를 적어 두고
"하나로 합치지 말 것" 이라고 쓰고 있었다.

조치: `insurance`(8099, 통합) 항목을 지우고 `insurance-customer`(8080) ·
`insurance-admin`(8081) 둘로 나눴다. 두 서버의 경로 수가 19 / 40 으로 갈리는 것을 확인했다.


디스크 부족이 원인일 가능성이 크다. **원인 미확인 상태로 남긴다.**
