## 3. 이번에 실제로 고친 것

### 3.1 설명 검증 상태를 현행 코드에 맞춤

브리핑에는 `verify_explanation()`이 “실제 호출되지 않는다”고 적혀 있었지만 현행 코드는
그렇지 않았다. `app/workflow/precheck_graph.py`의 `verify_against_store()`가 별도 저장된
원문·쪽수·인용문을 먼저 대조하고, 이어서 `verify_explanation()`을 호출한다.

다음 두 곳을 바로잡았다.

- `app/core/usecases/precheck.py`: 낡은 “호출부 없음” 설명을 실제 호출 흐름으로 수정
- `docs/handoff/19_담당자별_코드범위_및_구현현황.html`: 인용 검증은 연결됐고,
  LLM이 새 설명문을 만드는 기능만 미연결이라고 구분

쉽게 말하면, **인용을 검사하는 안전문은 이미 연결돼 있고, AI가 별도 해설을 새로 쓰는
기능은 아직 연결되지 않은 상태**다.

### 3.2 프론트 계약의 낡은 경로 설명 수정

`docs/handoff/08_계약_프론트.md`는 이미 v2에서 고객 판정과 근거 화면을
`insurance.html/js` 하나로 통합하도록 갱신됐다. 그런데 담당 범위 브리핑에는 여전히
“계약 갱신 필요”라고 적혀 있어 다음처럼 현행화했다.

- 계약 경로 갱신은 완료로 수정
- 사람의 실제 브라우저·모바일·키보드 확인만 남은 것으로 분리
- 고객 서버 시작 주소 `http://127.0.0.1:8080/` 명시
- 관리자 서버 시작 주소 `http://127.0.0.1:8081/` 명시
- 마이페이지 주소 `http://127.0.0.1:8080/static/mypage.html` 명시

기존 계약에 적힌 `/insurance`, `/admin`은 실제 서버에서 각각 404였다. 서버 코드가
다른 트랙과 겹치므로 별칭 주소를 새로 만들지 않고, 현재 정상 동작하는 주소를 계약에
정확히 적었다.

## 7. Claude 별도 구조 검수 결과 (2026-08-25, 별도 세션)

이 보고서 §5가 "이 세션에는 Claude 실행 수단이 없음"으로 남겨 둔 두 가지 — §3.1/§3.2의
주장 재검증과 P1 브라우저 눈검사 — 를 인앱 브라우저를 가진 별도 Claude 세션이 이어서
닫았다.

### 7.1 §3.1 재검증 — `verify_explanation()` 연결 주장

`app/workflow/precheck_graph.py`의 `verify_against_store()`를 직접 읽어 확인했다.
독립 저장된 원문·쪽수·인용문을 먼저 대조(조항ID·발생ID 구분, 인용 가능 여부 재확인,
쪽수 범위·인용문 부분일치 검사)하고, **그 대조를 전부 통과했을 때만**
`app/core/usecases/precheck.py`의 `verify_explanation()`을 호출한다. `build()`에서
`deps["clauses"]`를 주입해 실제로 그래프에 연결돼 있는 것도 확인했다. **§3.1의 주장은
사실이다.**

### 7.2 §3.2 재검증 — 프론트 경로 주장

`app/main.py`를 읽어 `/insurance`, `/admin` 경로가 라우터에 없음을 정적으로 확인했고,
실행 중인 서버에 직접 요청해 두 경로 모두 `{"detail":"Not Found"}`(404)임을 실측으로
재확인했다. `http://127.0.0.1:8080/`, `.../static/mypage.html`, `http://127.0.0.1:8081/`
은 모두 정상 응답했다. **§3.2의 주장도 사실이다.**

### 7.3 P1 브라우저 눈검사 결과

| 화면 | 크기 | 결과 |
|---|---|---|
| 고객(8080) | 데스크톱 1280x720 | 정상. 입력 폼·질병코드 목록·챗봇 사이드바(용어 버튼 24개)·메시지 입력창 모두 렌더. 콘솔 에러 0(실제 페이지 요청은 전부 200) |
| 고객(8080) | 모바일 375x812 | 정상. `document.documentElement.scrollWidth === clientWidth === 375` — 가로 넘침 없음 |
| 관리자(8081) | 데스크톱 1280x720 | 정상. 첫 렌더에서 `{{BRAND}}` 미치환·`net::ERR_CONNECTION_REFUSED` 3건이 잠깐 보였으나, 재확인 시 네트워크 요청 전부 200이고 탭 제목도 "관리자 대시보드 — 올바른 보험비서"로 정상 — 서버 두 개를 연달아 띄운 테스트 환경 자체의 기동 경쟁 상태로 판단(앱 결함 재현 안 됨, 별도 디버그 리포트는 작성하지 않음) |
| 관리자(8081) | 모바일 375x812 (로그인 게이트) | 최소 조치 적용 후 **가로 넘침 해소**(`scrollWidth 1080 → 375`) |
| 관리자(8081) | 인증 후 대시보드 내부 (실제 로그인) | 임시 계정으로 로그인 확인 — 시스템 준비 상태 "정상 운영", 코호트 실제/합성 분리, SSE 실시간 이벤트, 사용자 관리 등 정상 렌더. **모바일에서는 여전히 부분 가로 넘침**(`scrollWidth 1080 → 513`, 2단 grid의 `minmax(380px, ...)`가 원인) |

적용). 되돌리기 쉬운 최소 조치로 `@media (max-width: 1079px) { body { min-width: 0; } ... }`를
추가해 **1080px 이상(데스크톱)은 전혀 건드리지 않고** 로그인 게이트의 넘침만 없앴다

가정하지 않아 여전히 일부 넘치는데, 이건 미디어 쿼리 하나로 못 없애고 실제 레이아웃 변경이
필요해 건드리지 않았다 — 데스크톱 전용이 의도인지, 반응형이 필요한지는 화면 담당
