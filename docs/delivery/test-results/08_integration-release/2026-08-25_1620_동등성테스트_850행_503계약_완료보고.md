## 2. ③ 503 계약 — 계약은 이미 있었고, PG 만 빠져 있었다

`app/core/usecases/precheck.py` 에 이렇게 적혀 있었다:

> ★"산출물이 아직 없다"는 **장애가 아니라 사실**이므로 기권이 맞다.

그런데 판별을 **메시지 문자열**로 하고 있었다(`_MISSING_HINTS`).
PG 저장소는 「이 약관의 조항 기록이 없습니다」라는 **다른 문구**를 써서 걸리지 않았고,
그래서 **같은 상황에서 파일은 200 기권 · PG 는 503** 이었다.

같은 파일 주석이 해법도 이미 적어 두었다 — *"어댑터가 별도 예외 타입을 던지는 편이 낫다.
(DB 적재 때 `ArtifactMissing` 을 만들어 교체한다)"*. 그대로 했다.

| 파일 | 변경 |
|---|---|
| `app/core/errors.py` | `ArtifactMissing(InfraError)` 신설 |
| `app/core/usecases/precheck.py` | `isinstance(e, ArtifactMissing)` 우선, 문자열은 **구 어댑터용으로 남김** |
| `db/postgres/pg_clause_store.py` | "없다" 두 곳만 `ArtifactMissing`. **"읽지 못했다"(장애)는 그대로 `InfraError`** |

검증:

```
색인에 없는 문서 → HTTP 200   (수정 전: 503)
  verdict: needs_expert | abstained: True | reason: no_evidence
```

★**저장소 장애는 여전히 503 이다.** 테스트로 고정했다 —
`_is_missing_artifact(InfraError("PostgreSQL 에 연결할 수 없습니다"))` 는 `False`.

## 3. ② 승인fact 850행

`source_kind='approved_ocr_table_fact'` — `load_s7_1_approved_facts.py` 가 승인 payload 에서
넣는 행이라 **조항 JSON 에 대응이 없다.** 그래서 순번을 JSON 에서 가져올 수 없다.

→ 문서·종류별 **결정적 순위**로 매겼다(§4 와 같은 방식).

```
s6 전체 210,733 · 순번 197,205 (93.6%)
★게이트 있고 순번 없음: 0건        ← 인용 가능한 행은 전부 확보
★순번 충돌: 0건
   clause                   200,881 · 순번 189,305
   annex                      9,002 · 순번   7,050
   approved_ocr_table_fact      850 · 순번     850
```

순번이 없는 나머지 13,528행은 **게이트도 비어 있어 이미 판정에서 배제**된 행이다.

## 4. ★테스트가 잡아낸 결함 2건

### 4-1. 내 백필이 순번 유일성을 깨뜨렸다

처음엔 조항 JSON 의 `ordinal` 을 그대로 넣고, 충돌 키가 같은 항목이 합쳐지면
`LEAST` 로 가장 작은 값을 쓰게 했다. **틀렸다.**

색인의 발생행은 JSON 등장과 **1:1 이 아니다**(로더가 `ON CONFLICT` 로 합친다).
그래서 어떤 행의 번호를 낮추면 **다른 행이 이미 쓰던 번호와 겹친다.**
실제로 한 문서에 `…:clause:1` 이 둘이 됐고,
`test_수록_식별자는_문서_안에서_유일하다` 가 잡았다.

→ **문서·종류별 결정적 순위**로 바꿨다. 정렬 키 `(page_from, qualified_no, content_hash)` 는
로더의 충돌 키와 같은 조합이라 `(sha256, generation)` 안에서 유일하고, 실행마다 같은 값이 나온다.

★그 결과 **file 과 pg 의 순번은 서로 다를 수 있다.** 문제가 되지 않는다 —
인용 검증은 그 인용을 만든 **같은 저장소**와 대조한다. `occurrence_id` 에 요구되는 것은
"정확히 한 행"이지 "JSON 과 같은 번호"가 아니다.

★단일 UPDATE 는 `statement_timeout` 에 걸렸다(210,733행). **문서 단위로 쪼개고
문서마다 커밋**했다 — 공유 DB 에서 긴 잠금을 잡지 않기 위해서이기도 하다.

### 4-2. ★★부록이 조항으로 둔갑하고 있었다

순번을 고쳐도 중복이 남았다. 원인은 다른 데 있었다 —
`pg_clause_store` 의 SELECT 가 **`source_kind` 를 읽지 않았다.**
그러면 `ClauseRow` 기본값 `"clause"` 가 붙어, **부록 행이 조항으로 표시된다.**

`occurrence_id = 릴리스:sha256:source_kind:순번` 이므로 부록 1번이 조항 1번과 **같은 식별자**가
되고, 인용 검증은 중복 키를 「못 쓰는 것」으로 표시해 **그 조항을 근거에서 버린다.**

→ `o.source_kind` 를 SELECT 에 넣고 `ClauseRow.source_kind` 로 전달했다.

★이건 순번 문제와 **별개의 결함**이다. 순번이 없던 시절에는 `occurrence_id` 가 아예 빈 문자열이라
드러나지 않았다.

## 5. ① 동등성 테스트 (`tests/test_clause_store_parity.py`, 마커 `pg`)

| 테스트 | 무엇을 고정하나 |
|---|---|
| `test_두_저장소가_같은_판정을_낸다` | verdict·인용 개수는 **엄격 대조**. `reason_code` 는 양쪽이 같은 것을 가졌을 때만 |
| `test_pg_행은_수록_식별자를_갖는다` | `occurrence_id` 가 비면 인용 검증이 전건 기권한다 |

| `test_색인에_없는_문서는_기권이지_장애가_아니다` | ③ 계약. 문구가 달라도 타입이면 통과, 장애는 통과 못 함 |

실행:
```
pytest tests/test_clause_store_parity.py -m pg   → 4 passed
```

### 5-1. 실측 동등성 (10개사 × 8기호 = 80건)

```
★동등성: 72/80 = 90.0%
불일치 8건 = 전부 동양생명 · verdict 와 인용 수는 같고 **사유만** 다르다
  file: document_not_reliable (산출물은 있으나 parse_status 미심쩍음)
  pg  : no_evidence           (색인에 아예 없음)
```

★**이건 동등성 결함이 아니라 커버리지 격차**다. 두 저장소가 **아는 사실 자체가 다르다.**
그래서 테스트는 verdict·인용 수를 엄격히 보고, 사유 차이는 「가진 것이 다르다」계열끼리만 허용하되
**허용한 건수를 출력한다**(숨기지 않는다).

★표본을 5→10건으로 늘렸다. 5건일 때는 색인 미적재 문서가 안 걸려 **차이를 못 봤다.**
