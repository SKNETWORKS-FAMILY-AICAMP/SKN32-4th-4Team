# Dockerize + EC2(docker-compose) 배포 완료 보고

- 작성: 2026-08-25 KST
- 계획: docs/plans/2026-08-25_1727_dockerize_ec2_배포_계획.md (내부 원본 참조: `../plans/2026-08-25_1727_dockerize_ec2_배포_계획.md`)
- 제외: agent API(8082), TLS/도메인/WAF, `insurance_real.core` 실데이터 채우기,
  ECS/RDS 전환, Django delivery BFF, 리랭커/GPU, 다중 인스턴스, 로컬 LLM 동시성 개선

## 1. 한눈에 보기

EC2 서버 한 대 + docker-compose로 배포할 수 있는 코드·설정·문서 전량을 이번에 새로
만들었다. LLM은 사용자 확정에 따라 OpenAI/Gemini 전환이 아니라 **기존
`scripts/local_model_server.py`(llama.cpp + Gemma GGUF)를 그대로 컨테이너화**했다 —
vLLM은 GPU 없이는 실용적이지 않아 기각했다(계획 문서 Context 참고).

★**이 세션은 실제 AWS 실행을 검증하지 못했다.** 이 환경에 Docker 자체가 없어서
(`docker: command not found`) `docker compose build`/`up`을 직접 돌려볼 수 없었다.
그래서 이번 완료의 의미는 "배포 가능한 코드+런북까지"이지 "실제로 EC2에서 동작을
확인했다"가 아니다 — 계획 문서의 완료 기준을 그대로 지켰다.

## 2. 만든 파일

| 파일 | 역할 |
|---|---|
| `Dockerfile` | customer/admin/migrate 공용 이미지(Python 3.12-slim, runtime.txt만) |
| `.dockerignore` | 저작물·PII·비밀값 이미지 제외(.gitignore 기준 반영) |
| `docker-compose.yml` | postgres·migrate·llm·customer·admin·backup 6개 서비스 |
| `docker/llm/Dockerfile`, `docker/llm/entrypoint.sh` | 로컬 LLM 사이드카(HF 다운로드→기존 서버 실행) |
| `requirements/local-llm-serve.txt` | llama-cpp-python 등 사이드카 전용 의존성(버전 미검증, 하한선만) |
| `docker/postgres/init/01-create-databases-and-roles.sh` | insurance_demo·mall_vec 생성, LOGIN 롤 생성(첫 부팅 1회) |
| `docker/postgres/init-post-migrate/grant-login-roles.sql` | insurance_runtime → insurance_app 멤버십 부여 |
| `docker/backup/Dockerfile`, `entrypoint.sh`, `crontab` | 일 1회 pg_dump→S3 |
| `scripts/ops/pg_backup_to_s3.sh` | 백업 로직 본체(컨테이너 밖에서도 수동 실행 가능) |
| `docs/manuals/ec2-deploy-runbook.md` | 첫 배포 순서, `.env` 채우는 값, 재배포 절차(영어 — `docs/manuals/README.md` 관례) |
| `docs/manuals/backup-restore-procedure.md` | 백업 자동화 설명 + 복원 테스트 절차(영어) |

## 3. 검증한 것 / 못 한 것

### 검증함
- `docker-compose.yml` YAML 문법·서비스/볼륨 목록 파싱 확인(6개 서비스, 2개 volume).
- 신규 셸 스크립트 4개(`docker/llm/entrypoint.sh`, `docker/postgres/init/*.sh`,
  `scripts/ops/pg_backup_to_s3.sh`, `docker/backup/entrypoint.sh`) `bash -n` 문법 검사 통과.
- `python -m pytest -q -p no:randomly -W ignore -m "not llm and not ml and not mcp and not pg and not legacy_data and not delivery"`
  (CI와 동일 마커) 실행 — 실패 2건(`test_admin_method_path_snapshot`,
  `test_rerank_process`)은 **이번 작업 시작 전부터 이미 수정 상태였던 파일**
  (`app/main.py`, `app/routers/admin.py`, `app/adapters/rerank_worker.py`,
  신규 `tests/test_rerank_process.py`)에서 온 것으로, `git status`로 대조해 이번
  Docker 작업과 무관함을 확인했다 — 새로 만든 파일은 모두 `docker/`·루트
  Dockerfile류·`requirements/local-llm-serve.txt`·`docs/`뿐이고 `app/`·기존 `tests/`는
  건드리지 않았다.

### 못 함(이 세션의 한계, 계획서에 명시했던 대로)
- `docker compose build`/`up` 자체 — Docker 미설치 환경.
- `mall_vec` 실제 이관·행 수 대조 — AWS/EC2 접근 없음.
- 백업 1회 수동 실행·S3 업로드 확인, 복원 테스트 — 마찬가지.
- `requirements/local-llm-serve.txt`의 `llama-cpp-python`/`huggingface_hub` 정확한
  버전 확인(PyPI 접속 불가) — 하한선(`>=`)만 넣어 뒀고, 런북에 "실제 설치되는 버전을
  확인해 고정하라"고 남겨 뒀다.

  명시**하고 있음을 다시 읽고 확인했다 — 추측이 아니라 코드 근거로 확정된 사실이라
  `docker/postgres/init/01-create-databases-and-roles.sh`(LOGIN 롤 생성)와
  `docker/postgres/init-post-migrate/grant-login-roles.sql`(`insurance_owner` 멤버십
  부여)에 반영했다. `docker-compose.yml`의 `migrate` 서비스도 이 SQL 파일이 이제
  문장 2개(세미콜론 구분)를 담고 있어, psycopg3 `execute()`가 매개변수 없는 여러 문장을
  한 번에 안전하게 처리한다고 보장하지 않는 점을 고려해 **주석 제거 → 문장 단위 분리
  실행**으로 고쳤다.
- 로컬 LLM 동시성 한계(전역 싱글턴이라 요청 직렬화) — 계획서 §9에서 이미 범위 밖으로
  못박은 그대로, 런북에도 명시(변동 없음).

## 4b. (후속, 2026-08-26) 실제 EC2에 배포해 검증함

`jikimi-ec2`(us-east-2, m7i-flex.large, Ubuntu 26.04, 2vCPU/7.6GB, **루트 디스크 8GB뿐**)에
직접 SSH로 접속해 core 스택(postgres·migrate·customer·admin — llm·backup은 디스크·S3 미비로
보류)을 실제로 띄워 검증했다. 계획 문서·런북을 "쓸 수 있는 코드"에서 "실제로 동작을 확인한
코드"로 올린 것 — 그 과정에서 정적 리뷰로는 못 잡는 버그 2건을 실제로 찾아 고쳤다.

| 버그 | 증상 | 원인 | 수정 |
|---|---|---|---|
| `numpy` 누락 | customer 컨테이너가 `ModuleNotFoundError: No module named 'numpy'`로 즉시 죽음 | `app/ml/face.py`가 모듈 최상단에서 `import numpy as np`를 무조건 실행. insightface/onnxruntime/cv2는 함수 안 지연 import라 괜찮지만 numpy만 예외였음 — 얼굴 기능을 안 쓰는 배포도 numpy 없이는 앱 자체가 기동 못 함 | `requirements/runtime.txt`에 `numpy==1.26.4` 추가 |
| `migrate` 서비스의 인라인 `python -c` `IndentationError` | grant 단계에서 `migrate-1 exited with code 1` | YAML 들여쓰기가 그대로 파이썬 소스 문자열에 들어가 첫 줄부터 들여써짐 | `docker/postgres/apply_grants.py`로 분리, `docker-compose.yml`의 `migrate` command를 그 스크립트 호출로 단순화 |
| `.env` 작성 실수(코드 버그 아님) | customer가 `127.0.0.1:5433`(개발용 기본값)에 붙으려다 계속 실패 | 런북 표에는 `PGVECTOR_DSN` 행이 있었는데 실제 `.env` 작성 때 빠뜨림 | `.env`에 `PGVECTOR_DSN=host=postgres port=5432 ...` 추가 |

수정 후 재검증:

```
customer / -> 200, <title>올바른 보험비서</title>
admin    / -> 200 (127.0.0.1:8081, 루프백만 — 계획대로)
GET /api/health/ready -> {"ready":false,"db_tables_ready":true,"insurance_postgres":true,
                           "ops_postgres":true,"clause_index_ready":false, ...}
```

`ready:false`는 결함이 아니라 **정확히 예상한 상태**다 — `mall_vec` 데이터 이관을 아직
안 했으니 `clause_index_ready:false`가 맞다. 스키마·DB 연결·앱 부팅까지는 전부 정상.

★정정: 이전 세션에서 admin 화면의 `{{BRAND}}` 미치환을 "테스트 하네스 기동 경쟁 상태"로
추정했었는데, 이번에 `curl`로 재현해 보니 **재현성 있게 항상** 미치환 상태였다 — 원인은
경쟁 상태가 아니라 **`{{BRAND}}`는 서버가 아니라 브라우저 JS(common.js)가 치환한다**는
것. `curl`은 JS를 안 돌리니 원본 그대로 보이는 게 정상이다(브라우저로 열면 문제없음).
이전 추정을 여기서 정정한다.

**의도적으로 안 한 것(이번 EC2는 8GB 디스크뿐이라)**: `llm` 서비스(GGUF 모델 다운로드가
디스크를 다 씀), `backup` 서비스(S3 버킷 미생성). 팀이 볼륨을 늘리거나(권장 30GB+) 별도
인스턴스를 쓰면 이어서 검증한다.
