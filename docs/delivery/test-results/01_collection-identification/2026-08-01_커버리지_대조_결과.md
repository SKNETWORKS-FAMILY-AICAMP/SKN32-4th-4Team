## 2. 대조로 드러난 것과 고친 것

### 2-1. 롯데손보 — 진짜 누락 1건

```
https://www.lotteins.co.kr/upload/C/newProduct/sil_contract_conversion_1904_yak3.pdf
```

같은 상품의 `_yak` · `_yak2` 는 있는데 `_yak3` 만 없었다. 재수집해서 받았다(2,883,035B).
**대조를 안 했으면 못 찾았을 것이다.**

### 2-2. 흥국생명 "3건 누락" — 누락이 아니라 **데이터 결함**

대조는 `(상품명, 판매개시일)` 로 맞추는데, 세 행의 상품명이 이랬다.

```
20240909_(무)흥국생명 실손의료비보험(갱신형)
20220101_(무)흥국생명 실손의료비보험(갱신형)
20230401_(무)흥국생명 실손의료비보험(갱신형)
```

**상품명 앞에 날짜가 붙어 있었다.** 기록 유실 후 파일명으로 복구할 때
`날짜_상품명.pdf` 를 통째로 상품명에 넣은 것이다. 그래서 같은 상품이
**다른 상품으로 보였다.** 파일은 멀쩡히 있었다.

같은 결함을 전 보험사에서 찾아 32행 더 정리했다
(`scripts/crawl/fix_name_date_prefix.py`).

| 경우 | 건수 | 처리 |
|---|---:|---|
| 접두어 날짜 = `sale_start` | 3 | 접두어만 뗀다 |
| `sale_start` 가 **비어 있음** | 27 | 접두어를 `sale_start` 로 **옮긴다**(현대해상. 정보 이득) |
| 접두어 날짜 ≠ `sale_start` | 5 | 이름만 정리, 날짜는 `file_date` 로 **보존**(KB손보·롯데손보) |

세 번째는 접두어가 **파일 개정일**이고 `sale_start` 는 **판매개시일**로 뜻이
다를 수 있어서, 판단 근거 없이 덮어쓰지 않고 따로 남겼다.

KB손보는 파일명이 `{날짜}_{상품코드}_{슬롯}_{상품명}` 이라 코드·슬롯도 떼고
`product_code` 가 비어 있으면 거기에 채웠다.

## 3. 현대해상 — 서버가 응답을 끊었고, **오프라인으로 대조했다**

### 3-0. 결론부터 — 누락 0

서버를 다시 두드리지 않고 **카탈로그 ↔ 매니페스트**를 `(상품명, 판매개시일)` 로 맞췄다.

```
카탈로그 실손(여행 제외) 303건 / 매니페스트 337행
이름+개시일로 맞은 것 303 / 안 맞은 것 0
이름만으로도 없는 것    0
```

매니페스트가 303 보다 많은 것(337)은 같은 약관이 여러 상품·기간에 붙기 때문이다(Occurrence).

★이 대조는 URL 이 아니라 **이름+날짜** 기준이다. URL 대조보다 약하다.
  서버가 회복되면 URL 로 다시 맞춰 보는 것이 낫다.

### 3-1. 그 전에 있었던 일 — 오류 메시지가 사실을 잘못 전했다

대조 중 이런 오류가 났다.

```
InfraError: robots가 허용하지 않습니다: https://www.hi.co.kr/ajax.xhi (robots 확인 불가(URLError))
```

**이 메시지는 사실을 잘못 전한다.** robots 를 직접 확인해 보면 허용이다.

```
robots.txt HTTP 200 / 335B
User-agent: *
Allow: /
Disallow: /jsp/bin/CL ... (ajax.xhi 는 금지 목록에 없다)
→ 판정: True / 200 → allow
```

원인은 `_robots_allows` 가 **모든 예외를 거부로 처리**한 것이다.
일시적 통신 실패와 실제 거부가 구분되지 않았다.

재시도(3회, 점증 대기)를 넣었으나 그 뒤로는 아예 응답이 없다.

```
URLError: [WinError 10060] 호스트로부터 응답이 없어 연결이 끊어졌습니다
```

**대조 과정에서 파일 메타를 310건 개별 조회한 것이 원인으로 보인다.**
우리가 부하를 준 결과라면 더 두드리는 것이 옳지 않다. **여기서 멈춘다.**

### 3-2. 대상 조회는 실은 **성공했다** — 다만 숫자를 그대로 쓰면 안 된다

서버가 끊기기 전에 돌던 조회가 끝나 `대상 246건` 을 냈다.
그런데 이 숫자는 카탈로그 303건보다 작다. 코드를 보면 이유가 있다.

```python
try:
    out.add(m.pdf_url(m.file_meta(it.terms_file_id)))
except InfraError:
    continue          # ★실패를 세지 않고 넘어간다
```

메타 조회에 실패한 **57건이 조용히 빠졌다.** "대상 246" 은 사이트의 실제 목록이
아니라 **우리가 URL 을 풀 수 있었던 것의 수**다. 이대로 누락을 계산하면
**분모가 줄어 커버리지가 실제보다 좋아 보인다.**

### 3-3. 남은 개선

- `_t_hyundaimarine` 의 `except InfraError: continue` 는 **실패 건수를 세어
  보고해야 한다.** 조용한 스킵은 커버리지를 부풀린다.
- `_robots_allows` 의 판정은 fail-closed 를 유지하되, **"확인 실패"와 "거부"를
  다른 메시지로** 내야 한다. 지금은 둘 다 "robots가 허용하지 않습니다"로 나와
  사이트가 우리를 막은 것처럼 읽힌다.
- 대조 시 파일 메타 조회에 간격을 둬야 한다(현재는 연속 호출 — 이것이 응답 중단의 원인으로 보인다).

## 4. 브라우저 수집 3곳은 URL 대조가 안 된다

삼성생명·메리츠화재·NH농협손보는 화면 클릭으로 받아서 **PDF 의 원 URL 을 갖고 있지 않다.**
URL 로 맞출 수가 없다. 이들은 **화면 검색 결과 건수**로 대조한다.

| 보험사 | 화면 기준 | 수집 | 비고 |
|---|---:|---:|---|
| 삼성생명 | 223 | 221 | 1건은 서버가 DRM 컨테이너를 내려줌(§5) |
| 메리츠화재 | 157 | 158 | 같은 약관이 상품 2건에 붙음 |
| NH농협손보 | 12 | 12 | 일치 |

## 5. 끝내 못 받은 1건

```
[FAIL] 삼성생명노후실손의료비보장보험2.0(갱신형,무배당)
       PDF가 아닙니다(앞 8바이트=b'<## NASC')
```

`NASCA` 는 국산 DRM 헤더다. 서버가 PDF 대신 DRM 컨테이너를 내려줬고 2회 모두 같았다.
**우회는 하지 않는다는 원칙**이므로 여기서 멈췄다.

## 7. 이 대조가 값어치가 있었나 — 있었다

카탈로그 기준으로는 전부 100% 로 보였다. 사이트를 다시 물어보니:

- **진짜 누락 1건**(롯데손보)을 찾았다
- **데이터 결함 35행**(상품명에 날짜 접두어)을 찾았다 — 이건 버전 매칭을 조용히
  망가뜨렸을 것이다
- **오류 메시지의 거짓말**을 찾았다(통신 실패를 robots 거부로 보고)

- **조용한 스킵**을 찾았다(현대해상 메타 조회 실패 57건이 세어지지 않았다) — 커버리지를 부풀린다

다만 **남의 서버에 부하를 준다.** 현대해상이 응답을 끊은 것이 그 증거다.
정기 점검으로 돌릴 것이 아니라, **큰 변경 뒤에 한 번씩** 돌릴 일이다.
