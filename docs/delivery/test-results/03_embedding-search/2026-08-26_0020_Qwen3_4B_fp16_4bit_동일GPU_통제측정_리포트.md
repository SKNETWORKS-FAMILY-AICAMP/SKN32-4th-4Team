## 1. 결론 — **세 축 모두 「차이를 확인하지 못했다」**

같은 GPU · 같은 스크립트 판 · 같은 가중치 · **같은 배치(4)** 로 정밀도만 바꾼 짝비교:

| 축 | n | fp16 MRR@10 | 4bit MRR@10 | ΔMRR | 95% 구간 | 판정 |
|---|---:|---:|---:|---:|---:|---|
| 제목(title) | 145 | 0.5210 | 0.5352 | **+0.0142** | [−0.0043, +0.0373] | 0 포함 |
| 뒷부분(tail) | 60 | 0.2456 | 0.2653 | **+0.0197** | [−0.0453, +0.0913] | 0 포함 |
| 면책(exclusion) | 16 | 0.1906 | 0.1558 | **−0.0348** | [−0.1332, +0.0429] | 0 포함 |

★**「구간이 0 을 걸친다」는 「같다」가 아니다.** 표본이 작아 못 가린 것일 수 있다.
특히 면책은 **n=16** 이라 구간이 매우 넓다 — 부호(−)만 보고 "4bit 가 나쁘다"고 읽으면 안 된다.

★**벡터무변화는 fp16·4bit 모두 0/60** 이다(세 실행 전부). 브리핑 재측정값과 일치한다.

## 4. ★부수적으로 확인된 것 3가지

### 4-1. **원 fp16 측정과 대조 — 과제마다 다르다** (★2026-08-26 정정)

★**처음에 "소수 넷째 자리까지 일치"라고 썼는데 틀렸다**(`unified-mall-3-ea` 지적).
브리핑 표의 `0.521` 은 **반올림 표시값**이고 원본 JSON 은 `0.5206` 이다.
반올림값과 비교해 "일치"라고 쓰면 재현이 실제보다 깨끗해 보인다.

원본 JSON(`data/eval/embed_bench_results/Qwen__Qwen3-Embedding-4B.json`)과 직접 대조:

| 지표 | 기존 fp16 | 이번 fp16 | 차 |
|---|---:|---:|---:|
| `recall@10` | 0.6759 | 0.6759 | **0** |
| 제목 MRR | 0.5206 | 0.5210 | +0.0004 |
| **뒷부분 MRR** | 0.2530 | 0.2456 | **−0.0074** |
| **면책 MRR** | 0.1854 | 0.1906 | **+0.0052** |

→ *"MRR 은 벡터무변화 공식 결함의 영향을 받지 않는다"*(§5-10)는 **`recall@10` 과 제목에서
확인됐고, 뒷부분·면책에서는 확인되지 않았다.**

★**두 측정의 차이가 어디서 왔는지** — 조건을 대조하면 좁혀진다:

| 조건 | 기존 fp16 | 이번 fp16 | 근거 |
|---|---|---|---|
| GPU | RTX 2000 Ada | **같음** | 양쪽 JSON 의 `gpu` 필드 |
| `blind_eps` | 1e-09 | **같음** | 양쪽 JSON |
| 배치 | ~~16~~ **추정 16** | 4 | ★**기록 없음** — 아래 참조 |
| 스택 판 | 미상 | torch 2.8.0 · ST 6.0.0 · tf 5.15.1 | 기존은 JSON 에 없음 |

GPU 와 공식이 같으므로 남는 후보는 **배치와 스택 판**이다. 어느 쪽인지는 **가르지 못했다.**

★★**`batch` 는 결과 JSON 에 기록되지 않는다**(`unified-mall-3-ea` 발견, 내가 실측 확인).

```
data/eval/embed_bench_results/*.json  21건 ┐
data/eval/runpod_2026-08-25/*.json     3건 ┘ → batch 키 있는 파일 0건 (0/24)
```

`run()` 은 `batch` 를 인자로 받아 쓰지만(`bench_embedders.py:249`) **결과 dict 에 넣지 않는다.**
그래서 "원 측정은 배치 16" 은 재현 명령에 `--batch` 가 없고 CLI 기본값이 `16`(`:724`)이라는 데서 온
**추정**이지 기록된 사실이 아니다. **내 3건도 마찬가지로 파일명에만 배치가 있다.**

→ **배치를 조건으로 말하려면 결과 JSON 에 `batch` 를 남기는 것이 먼저다.**
   그 전까지는 배치 관련 서술을 전부 「추정」으로 읽어야 한다.

### 4-1-★. `blind_eps` 에 대한 정정 — 파일 집합이 둘이다

작업 중 "기존 결과에 `blind_eps` 가 없다 → 옛 판이다"라는 서술이 오갔는데, **저장소 기준으로는 틀렸다.**

| 위치 | 건수 | `blind_eps` |
|---|---:|---|
| 저장소 `data/eval/embed_bench_results/` | **21** | **전부 있음**(없음 0) |
| x600 `F:\bench\data\eval\embed_bench_results/` | 16 | 없음 → 새 스크립트가 「☠무효(옛공식)」로 표시 |

★**두 집합이 다르다.** 저장소 것은 §5-10 의 재측정분이고, x600 에 남은 것은 **재측정 이전 잔존물**이다.
내가 x600 에서 본 「16건 전부 무효」를 저장소·브리핑에까지 적용한 것이 오류의 출발이었다.
**어느 경로의 파일을 보고 하는 말인지 밝히지 않으면 같은 혼동이 반복된다.**

### 4-2. ★**fp16 이 16GB 에서도 배치 16 으로는 안 올라간다**

```
배치 16 (expandable_segments 적용) → CUDA OOM: 664 MiB 할당 실패, 15.58 GiB 중 534 MiB 여유
배치  4 (expandable_segments 적용) → 성공 (적재 25.4초)
```

★**단정하지 않는다.** 원 측정은 같은 GPU 계열에서 성공했고 **배치는 16 으로 추정된다**
(기록되지 않았다 — §4-1 참조). 그렇다면 차이는 VRAM 이 아니라
**스택 판**(torch 2.8.0 / ST 6.0.0 / transformers 5.15.1)일 가능성이 크다.
★배치가 기록되지 않았으므로 **이 추론의 전제부터 확인된 값이 아니다.**
브리핑 1단계-A 조건 ③ *"12GB VRAM 에서 fp16 구동"* 을 인용할 때는
**어느 스택 판 기준인지**를 함께 적어야 한다.

### 4-3. ★**배치가 4bit 지표를 약간 움직인다**

```
4bit 배치 16 → MRR 0.5416 · R@10 0.6966
4bit 배치  4 → MRR 0.5352 · R@10 0.6897
```

★**배치는 조건이다.** 4bit 는 배치 16↔4 에서 제목 MRR 이 0.5416 → 0.5352 로 갈렸다.
(★이 두 값은 **내가 직접 두 번 돌린 것**이라 배치를 안다. 다만 **JSON 에는 안 남는다** —
파일명에만 있다. 다음 사람이 파일만 보고 재현하려면 §4-1 의 기록 누락부터 고쳐야 한다.)
그래서 이 리포트의 짝비교는 **배치를 4 로 맞춘 쌍**만 썼다.

★fp16 쪽은 배치별 재측정을 하지 못했다(배치 16 이 OOM 이라 애초에 못 돌렸다).
§4-1 의 기존 fp16(배치 16) ↔ 이번 fp16(배치 4) 차이에는 **스택 판 차이도 섞여 있어**
배치만의 효과로 읽을 수 없다. **fp16 에서 배치가 얼마나 움직이는지는 모른다.**

## 5. ★도구 한계 — `--compare` 로는 이 비교를 못 한다

`bench_embedders.compare()` 는 결과를 **모델명으로 키**를 잡는다:

```python
rows[r["model"]] = np.array(rk, dtype=float)     # :490
```

fp16 과 4bit 는 `model` 값이 같으므로 **뒤엣것이 앞엣것을 덮어쓴다.** 그래서
`--compare Qwen/Qwen3-Embedding-4B` 는 항상 **「비교 0개」** 를 낸다(`--dtype ''` 로 열어도 같다).

게다가 그 함수에는 이런 주석이 있다:

> ★정밀도가 다른 것을 **같은 구간표에 두지 않는다**(코덱스 지적).
> 4bit 와 fp16 을 섞으면 "이 차이가 모델 때문인지 정밀도 때문인지"를 읽는 사람이 가릴 수 없다.

★**그 규칙은 「여러 모델을 한 표에서 비교할 때」의 것이다.** 이번은 모델·GPU·판·가중치·배치를
전부 고정하고 **정밀도만** 바꿨으므로 그 위험이 없다. 그래서 **도구를 고치지 않고**
(공유 자산이라 생성 블록에 영향이 간다) 같은 방식으로 별도 계산했다:
`data/eval/runpod_2026-08-25/` 와 함께 둔 계산 방식 — 질의 재표집 부트스트랩 2,000회,
`RR = 1/rank (1≤rank≤10) else 0`, seed 20260803 (`compare()` 와 동일 규약).

★**군집 재표집(문서 sha12 단위)은 하지 않았다.** 같은 문서에서 나온 질의들의 상관이
구간에 반영되지 않아 **구간이 실제보다 좁을 수 있다**. `compare(cluster=True)` 에 해당하는 보정이다.

### 5-1. 별건 — `--compare` 가 실패하고도 종료코드 0 이다

```
기준 모델이 결과에 없습니다: Qwen/Qwen3-Embedding-4B
[EXIT compare] 0
```
비교할 짝이 없는 것은 맞는 동작이지만, **자동화가 성공으로 읽는다.** 조용한 실패다.

## 6. 이 결과가 **말하지 않는 것**

- ✗ "4bit 가 fp16 과 같다" — 구간이 0 을 걸친 것은 **못 가린 것**이다
- ✗ "4bit 가 더 낫다" — 제목·뒷부분의 Δ 가 양수지만 구간이 0 을 포함한다
- ✗ "다른 모델도 그렇다" — 통제 실험은 `Qwen3-4B` **하나**다
- ✗ "12GB 에서 fp16 이 불가하다" — 스택 판 교란이 안 갈라졌다(§4-2)
- ✗ x600(RTX 4070 SUPER) 결과와 이 표를 묶는 것 — **판과 GPU 두 조건이 다시 바뀐다**
- ✗ "원 측정은 배치 16 이었다" — **기록이 없다.** CLI 기본값에서 온 추정이다(§4-1)
