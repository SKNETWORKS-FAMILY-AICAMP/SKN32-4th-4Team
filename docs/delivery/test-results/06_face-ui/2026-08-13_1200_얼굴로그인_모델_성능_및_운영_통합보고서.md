## 1. 최종 결론

현재 얼굴 로그인 파이프라인은 다음과 같다.

```text
입력 이미지
  → InsightFace buffalo_l(RetinaFace) 얼굴 검출·랜드마크·자세·정렬
  → 품질 게이팅
  → Silent-Face MiniFASNetV2 라이브니스
  → 저조도 조건부 CLAHE
  → AdaFace IR-101 임베딩
  → 저장 임베딩과 코사인 비교
  → 임계값 0.30 통과 시 얼굴 2차 인증 성공
```

AdaFace를 기본으로 선택한 이유는 일반 고품질 벤치마크의 1위라는 뜻이 아니라, 이 프로젝트의
웹캠 로그인 조건인 흐림·저조도·저해상 입력에서 동일인 유사도가 가장 안정적이었기 때문이다.
LVFace-S는 고품질 일반 인식과 CPU 지연에는 강했지만, 합성 저품질 조건에서는 AdaFace와
`buffalo_l`보다 낮았다.

## 2. 모델 역할과 현재 설정

| 역할 | 현재 모델/설정 | 비고 |
|---|---|---|
| 검출·랜드마크·정렬 | InsightFace `buffalo_l` / RetinaFace | 모델팩 이름이며 기본 임베딩 모델이라는 뜻이 아님 |
| 얼굴 임베딩 | AdaFace IR-101 WebFace12M | `FACE_RECOGNITION=adaface` 기본값 |
| 선택 가능한 임베딩 | `adaface`, `lvface`, `insightface` | 기존 등록 임베딩과 공간이 달라 모델 변경 후 재등록 필요 |
| 라이브니스 | Silent-Face MiniFASNetV2 | live 클래스 확률 index 1 사용, CPU 고정 |
| 얼굴 매칭 임계값 | `0.30` | AdaFace 기준 시작값, 실사용 분포 튜닝 전 |

## 3. 모델 선정 과정

### 3.1 InsightFace 기준선에서 AdaFace로 교체

초기 기준선은 `buffalo_l`의 ArcFace r50 임베딩이었다. 동일 정렬 crop에 합성 열화를 적용해
비교한 결과 AdaFace가 모든 저품질 항목에서 더 높았다.

| 조건 | `buffalo_l` ArcFace r50 | AdaFace IR-101 | 차이 |
|---|---:|---:|---:|
| 블러 k21 | 0.578 | **0.665** | +0.087 |
| 저조도 ×0.12 | 0.869 | **0.923** | +0.054 |
| 저해상 0.25배 | 0.711 | **0.772** | +0.061 |
| 저해상 0.15배 | 0.299 | **0.389** | +0.090 |
| 타인 분리 | -0.030 | -0.032 | 유사 |

따라서 검출·정렬은 검증된 InsightFace를 유지하고, 인식 임베딩만 AdaFace ONNX로 교체했다.

### 3.2 LVFace 재검토

LVFace가 최신 고품질 벤치마크에서 강하다는 지적을 반영해 LVFace-S/B를 같은 입력으로 다시
실측했다. 결과는 아래와 같다.

| 조건 | `buffalo_l` | AdaFace | LVFace-S | LVFace-B |
|---|---:|---:|---:|---:|
| 블러 k21 | 0.578 | **0.665** | 0.379 | 0.279 |
| 저조도 ×0.12 | 0.869 | **0.923** | 0.881 | 0.880 |
| 저해상 0.25배 | 0.711 | **0.772** | 0.579 | 0.456 |
| 저해상 0.15배 | 0.299 | **0.389** | 0.120 | 0.057 |
| 타인 분리 | -0.030 | -0.032 | -0.020 | 0.056 |
| CPU 임베딩 지연/장 | 103ms | 553ms | **96ms** | 171ms |

판정은 “LVFace가 나쁜 모델”이 아니라 “현재 사용 조건에 AdaFace가 더 맞다”이다. LVFace-S는
선택 가능한 백엔드로 남겨 두었다.

### 3.3 DirectML 가속

Windows 11 Intel Iris Xe에서 워밍업 후 측정했다.

| 모델 | CPU | DirectML | 배속 |
|---|---:|---:|---:|
| AdaFace 112×112 | 530.8ms | **74.3ms** | **7.1×** |
| LVFace-S 112×112 | 90.6ms | 64.3ms | 1.4× |
| MiniFASNet 80×80 | 3.4ms | 6.4ms | 느려짐 |

결론적으로 인식 임베딩은 DirectML 우선, 라이브니스는 CPU 고정으로 적용했다. 실제 장치·드라이버가
다르면 지연은 달라질 수 있다.

## 4. 전처리와 인증 게이트

`analyze_face()`는 다음 순서를 강제한다.

1. 이미지 디코드
2. 여러 얼굴이면 bbox 면적이 가장 큰 앞쪽 얼굴 선택
3. 얼굴 크기·검출 신뢰도·흐림·밝기·자세 품질 게이트
4. 라이브니스 판정
5. 112×112 정렬
6. 저조도일 때만 CLAHE
7. 임베딩 생성

등록은 여러 장을 받아 엄격 품질 게이트와 라이브니스 통과 샷의 임베딩 평균을 저장한다.
검증은 저장 임베딩과 코사인 비교를 수행한다. 실패 시 비밀번호만으로 통과시키는 폴백은 없다.

라이브니스 출력은 Silent-Face의 `[2D-spoof, live, 3D-spoof]` 순서를 사용한다. 과거 `prob[0]`
을 live로 읽던 오류를 수정했고, 현재 live 클래스는 index 1이다.

## 5. API·ENV 설정

### ENV 설정

코드는 `.env` 및 환경변수로 다음 값을 바꿀 수 있다.

```dotenv
FACE_RECOGNITION=adaface
FACE_EMBED_MODEL=buffalo_l
FACE_MATCH_THRESHOLD=0.30
FACE_LIVENESS_THRESHOLD=0.50
FACE_ADAFACE_ONNX=C:/path/to/adaface_ir101_webface12m.onnx
FACE_LVFACE_ONNX=C:/path/to/LVFace-S_Glint360K.onnx
FACE_ANTISPOOF_ONNX=C:/path/to/minifasnet_v2.onnx
FACE_RECOG_PROVIDERS=["DmlExecutionProvider","CPUExecutionProvider"]
FACE_LIVENESS_PROVIDERS=["CPUExecutionProvider"]
```

ENV 변경은 서버 재시작 후 적용된다. 관리자 전용 `PUT /api/face/backend`는 프로세스가 실행 중일
때만 임시로 백엔드를 바꾸며, 재시작하면 ENV 설정으로 돌아온다. 현재 경로는
`app/routers/face.py:66`, `app/routers/face.py:76`이다.

모델을 `adaface`·`lvface`·`insightface` 사이에서 바꾸면 임베딩 공간이 달라지므로 기존 등록 얼굴을
재등록해야 한다. 모델 다운로드는 `scripts/fetch_face_model.py:69`에서 활성 백엔드에 따라 처리한다.

## 6. 인증 적용과 운영 연결

- 일반 로그인은 비밀번호 인증 뒤 등록된 사용자에 대해 얼굴 2차 인증을 수행한다.
- 얼굴 등록은 인증된 세션에서만 가능하다.
- `/api/face/backend` 조회는 현재 백엔드와 선택 가능 백엔드를 반환한다.
- `/api/face/benchmark`는 관리자 전용이며 세 백엔드의 코사인·지연을 비교한다.
- 모델 로드 실패·라이브니스 실패·매칭 실패는 조용한 다른 모델 전환 없이 명시적으로 실패한다.
- 라이브니스와 매칭 실패의 사용자 메시지는 일반화하고, 내부 감사 이벤트에는 실패 원인을 남긴다.

## 8. 아직 검증하지 않은 것

다음 항목은 구현되어 있거나 테스트된 것과 별개로, 실사용 정확도 관점에서는 미완료다.

1. 실제 웹캠 사용자 모집단의 FAR/FRR, ROC/DET, EER
2. 실제 조명·카메라·마스크·안경·각도별 genuine/impostor 분포
3. 실 사진·영상 공격에 대한 라이브니스 정량 정확도
4. `FACE_MATCH_THRESHOLD=0.30`의 실제 사용자 분포 기반 최종 튜닝
5. 다중 장치·다중 프로세스 환경의 얼굴 인증 부하 및 지연
6. AdaFace·InsightFace 가중치의 상용 라이선스 검토

따라서 현재 문서에서 “인식률이 운영 환경에서 확정됐다”거나 “라이브니스가 검증됐다”고 표현하면
안 된다. 현재 결론은 **합성 저품질 비교와 코드·단위 테스트에 근거한 프로토타입 기본값 선정**이다.

## 9. 다음 권장 순서

1. 실제 웹캠 수집 동의와 보관 정책을 먼저 확정한다.
2. 동일인 다중 촬영 및 타인 쌍을 분리해 genuine/impostor 평가셋을 만든다.
3. AdaFace·LVFace-S·InsightFace를 동일 파이프라인으로 평가한다.
4. FAR 고정 기준으로 임계값을 다시 정하고 FRR·지연을 함께 기록한다.
5. 라이브니스는 실제 공격 유형별 데이터로 별도 평가한다.
6. 결과가 바뀔 때만 ENV 기본값과 본 통합 보고서를 함께 개정한다.
