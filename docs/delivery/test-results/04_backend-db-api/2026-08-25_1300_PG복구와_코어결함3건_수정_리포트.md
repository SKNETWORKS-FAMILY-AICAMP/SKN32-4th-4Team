## 3. 코어 결함 3건 (내 담당)

### 3.1 `CLAUSE_STORE=pg` 에서 판정 API 전부 500 — **수정**

- 원인: PG 조항 색인이 `parse_status=None`("모른다")을 정직하게 돌려주는데
  **응답 스키마에 "모름"을 담을 자리가 없었다**(`str`).
- 수정: 도메인이 이미 쓰던 규약(`None` = 모른다)에 응답 계층을 맞췄다.
  `app/core/domain/precheck_result.py`(`AppliedPolicyInfo`)·`app/schemas/precheck.py` → `str | None`
- ★**내 초안 권고를 정정했다** — 처음엔 `"unknown"` 문자열(안 B)을 권했으나,
  `app/core/ports/precheck.py:143` 과 `eligibility.check()` 가 이미 `None` 을 "모른다"로 쓰고 있었다.
  새 어휘를 만들지 않고 기존 규약을 따르는 것이 맞다.
- 회귀 테스트: `tests/test_parse_status_unknown.py` **7건**
- 검증: 같은 요청이 **500 → 200**

★★**그 뒤에 더 깊은 문제가 드러났다** — pg 경로는 **판정을 하나도 못 한다**.
5개사 전부 `citations=0` · `document_not_reliable` 로 기권한다.
PG 가 `parse_status` 를 저장하지 않아 모든 조항이 인용 불가가 되기 때문이다.
동작은 정직하지만(§0) **쓸 수는 없다.** → 결함 리포트 §10

### 3.2 `support_manifest` 가 요청마다 원장을 다시 파싱 — **수정**

- 실측: 요청당 **JSON 6,739회 파싱 · 파일 27개 읽기 · ~180ms**
- 원인: 같은 모듈에서 `_versions()` 만 캐시돼 있고 `_confirmation_stats()` 는 없었다.
  게다가 요청당 **2번** 불렸고, **판정 핫패스에서도** 불린다.
- 수정: `load_versions_cached()` 와 **같은 파일 지문**으로 캐시(TTL 아님, 실패는 캐시 안 함)
- 검증: **180ms → 2.9ms (약 62배)**, 값 불변(확정 1,248 / 수집 1,362)
- → `docs/reports/debugs/2026-08-25_1230_support_manifest가_요청마다_원장을_다시_파싱했다.md`

### 3.3 커넥션 풀이 **설치돼 있지 않아 무력화**돼 있었다 — **수정**

- 다른 세션이 `db/postgres/pool.py` 를 만들고 어댑터 6곳을 전부 이관해 두었으나,
  **`psycopg_pool` 이 venv 에 없어** `_pool_for()` 가 `None` 을 돌려주고
  **요청마다 `psycopg.connect()` 로 떨어지고 있었다.** 내 부하 시험이 DB 를 죽인 직접 조건이다.
- 조치: `pip install "psycopg[pool]==3.3.4"` → `psycopg_pool 3.3.1` 설치
  (`requirements/runtime.txt` 는 이미 `psycopg[pool,binary]` 로 선언돼 있었다 — 선언과 실환경이 어긋나 있었다)
- ★**남는 지적**: `pool.py` 는 `psycopg_pool` 이 없으면 **조용히 직접 연결로 떨어진다.**
  `RULE.md` §3.2(폴백 금지) 관점에서 이 폴백은 감사 신호가 필요하다.
  실제로 이 침묵이 "풀을 넣었는데도 DB 가 죽는" 상황을 만들었다. **다른 세션 소유 파일이라 건드리지 않았다.**

## 6. 미해결 — L0 재측정은 **아직 못 한다**

| 막는 것 | 상태 |
|---|---|
| 여유 메모리 < 4GB | 현재 3.27GB. **가드가 막고 있다**(정상 동작) |
| pg 경로 전건 기권 | `parse_status` 미적재 — L3 측정이 의미를 못 가진다(§3.1) |

앞선 L0 수치 중 **`cohorts` 는 무효**다(DB 가 죽어 가는 중에 잰 값).
`noop_async`/`noop_sync`/`health` 는 유효하고, `support_manifest` 는 **이제 다시 재야 한다**(62배 개선).

**유효한 L0 소견 하나** — 동기 핸들러가 async 보다 p50 **87% 느리다**
(22.61ms vs 12.05ms · rps 298 vs 524). 이 앱은 엔드포인트 **45/51 이 동기**다.
