# 외부·개념·내부 스키마가 실제로 어디에 구현돼 있나 — 실측

기준 **2026-08-05 실측** · 문서화 2026-08-25 · 두 데이터베이스를 직접 조회

> ★**이 리포트가 늦게 저장된 경위.** 처음엔 아티팩트(웹 페이지)로만 만들어 두었다.
> 그러면 **git 에 없어서 저장소를 받은 사람에게 안 보이고, 버전이 안 붙어 코드가 바뀌어도

> 옮겨져 아티팩트의 경로 인용이 낡았다. 리포트는 저장소에 둔다(`CLAUDE.md` §7).

## 한 줄 결론

세 계층이 다 있다. 다만 **설계된 곳과 가동 중인 곳이 서로 다른 데이터베이스**다.
정규화된 3-스키마는 `insurance_real` 에 있고 **약관 본문이 한 행도 없으며**,
실제로 답을 내는 `mall_vec` 는 `public` 한 층에 평평하게 놓여 있다.

| 계층 | `insurance_real` — 설계 | `mall_vec` — 가동 |
|---|---|---|
| **외부** | 역할별 권한 + 뷰 `app.cohort_stats` 1개 | **뷰 0 · 구체화뷰 0 · 역할 권한 0** → 앱이 대신함 |
| **개념** | `core`/`app`/`ops` 3스키마 · 테이블 **32** · 외래키 **44**<br>★`core` 12테이블 합계 **0행** | `public` 6테이블 · 외래키 **0**<br>발생 368,919 · 조각 122,772 · 내용 64,607<br>★고아 발생 **38,326행** |
| **내부** | `003_embedding.sql` 이 HNSW·GIN 지정 | **실제로 구축됨** — HNSW 753MB · GIN trgm 255MB · `vector(1024)` |

**내부 스키마만 설계와 가동이 일치한다.**

## 1. 개념 스키마

### 설계 — `insurance_real` · 외래키 44개

```
core.insurer
  └ core.product
      └ core.policy_version ──┐
core.confirmed_policy_document┤   ← 어느 파일이 어느 상품의 어느 판본인가
      └ core.document_extraction┘
            └ core.policy_clause
                  ├ FK content_hash → core.clause_content   (본문 한 벌)
                  └ core.clause_chunk → 벡터
```

정본: `db/migrations/postgres/001_core.sql`

★그런데 **`core` 12테이블 합계가 0행**이다. 데이터가 있는 것은
`app`(합계 14행)과 `ops`(합계 53행)뿐 — 약관 도메인은 설계만 서 있고 채워지지 않았다.

### 가동 — `mall_vec.public` · 외래키 0개

| 테이블 | 행 | 기본키 | 뜻 |
|---|---:|---|---|
| `policy_clause_content` | 64,607 | `(content_hash)` | 조항 본문 — 내용이 같으면 한 행 |
| `policy_clause_occurrence` | 368,919 | `(content_hash, sha256, qualified_no, page_from, index_generation)` | 그 조항이 **어느 문서 어디에** 실렸나 |
| `policy_clause_chunk` | 122,772 | `(content_hash, chunk_ix, embed_model)` | 검색용 조각 + `vector(1024)` |

★**정체성과 발생을 나눈 설계가 기본키에 그대로 박혀 있다.** 본문 64,607 ↔ 발생 368,919 —
한 조항이 여러 문서에 실리기 때문이다. 발생 기본키에 `index_generation` 이 들어 있어
**같은 조항의 여러 색인 세대가 한 테이블에 공존**한다(`s6` 210,733 · `s5-mixed` 158,186).
세대를 지우지 않고 게이트로 가리는 설계다.

## 2. 내부 스키마 — 유일하게 설계와 가동이 맞는 층

| 인덱스 | 종류 | 크기 | 무엇을 빠르게 하나 |
|---|---|---:|---|
| `policy_clause_chunk_hnsw` | **hnsw** | 753 MB | 벡터 최근접 — `vector_l2_ops` |
| `policy_clause_chunk_text_trgm` | **gin** | 255 MB | 낱말·오타 — `gin_trgm_ops` |
| `policy_clause_occurrence_pkey` | btree | 148 MB | 같은 발생 중복 적재 차단 |
| `policy_clause_occurrence_gen` | btree | 7.5 MB | 세대 필터 — **이 값이 게이트다** |
| `policy_clause_occurrence_sha` | btree | 7.3 MB | 약관 범위 좁히기(`scope_sha256s`) |

### 저장 배치

| 테이블 | 전체 | 본체(heap) | 비고 |
|---|---:|---:|---|
| `policy_clause_chunk` | 2,039 MB | 317 MB | 차이는 대부분 **인덱스 1,008 MB** + TOAST |
| `policy_clause_content` | 523 MB | 109 MB | 긴 조항 본문이 **TOAST 로 밀려남** |
| `policy_clause_occurrence` | 307 MB | 144 MB | **기본키가 본체의 절반보다 크다** |

본체보다 인덱스·TOAST 가 큰 것은 이 도메인에서 자연스럽다 —
조항은 3만 자까지 가고, 검색은 본문이 아니라 1024차원 벡터로 하기 때문이다.

## 3. 외부 스키마 — 누가 무엇까지 보는가

### 설계 — DB 권한으로 (`insurance_real`)

| 역할 | `core` | `app` | `ops` |
|---|---|---|---|
| `insurance_app` (런타임) | **SELECT 만** | SELECT·INSERT·UPDATE·DELETE | SELECT·INSERT·UPDATE |
| `insurance_owner` (소유자) | 전권 — 마이그레이션 전용 | | |

★**권한이 곧 도메인 규칙이다.** 약관(`core`)은 런타임이 못 고친다 — 판정의 근거이기 때문이다.
감사 로그는 `INSERT` 만 주고 `UPDATE·DELETE·TRUNCATE` 를 회수해 **append-only** 로 만들었다.
함수도 `PUBLIC` 에서 회수한 뒤 특정 역할에만 `EXECUTE` 를 준다.
정본: `db/migrations/postgres/002_grants.sql` · `005_integrity_and_privileges.sql`

### 가동 — 애플리케이션이 대신 (`mall_vec`)

`mall_vec` 에는 뷰도 역할 권한도 없다. 그래서 외부 스키마를 **세 겹의 코드**가 만든다.

**① 프로세스를 갈라 경로 자체를 없앤다**
고객 앱(`:8080`) 경로 33개 중 관리자 **0** · 운영 앱(`:8081`) 60개 중 관리자 21.
인증으로 막는 게 아니라 **존재하지 않게** 한다.

**② 필드를 투영해 약관 원문을 감춘다**

```
내부(개념)  content_hash · chunk_ix · text · distance · sha256 · insurer
           qualified_no · section · title · page_from · page_to · full_text
           └ 파생: citable_text · clause_id

외부(응답)  clause_id · insurer · section · qualified_no · title
           page_from · page_to · distance · sha256
           ← text · full_text · content_hash · chunk_ix 는 나가지 않는다
```

`ClauseHit` 12필드 + 파생 2 → `/api/admin/clause-search` 응답은 **9필드**.
약관 원문은 저작물이라 보이면 안 되는 것이고, 그 규칙이 응답 투영에 박혀 있다.

**③ 행을 게이트로 거른다**
`citation_eligible` 과 `index_generation` 이 사실상 **행 수준 뷰**다.
발생 368,919 중 승인 세대(`s6`)는 210,733이고 나머지는 게이트 값이 비어 검색에 안 걸린다.
뷰를 안 만들고 `WHERE` 로 같은 일을 한다.

## 4. 질의 하나가 세 층을 지나가는 길

「치과치료 보철료는 보상하나요」 실측(2026-08-05).

| 층 | 하는 일 |
|---|---|
| 외부 | 승인 프로필로 질의를 벡터화 — `query: ` 접두사를 붙인다. 없으면 **오류 없이 틀린 조항**이 올라온다 |
| 외부 | 범위 강제 — `scope_sha256s` 없이 전역으로 찾으려면 `allow_global=true` 를 따로 줘야 한다 |
| 내부 | HNSW 로 최근접 20건 · 세대 게이트가 함께 걸린다 |
| 개념 | `content_hash` 로 `policy_clause_content` 조인 — 조각에 **조 전체**를 붙인다 |
| 외부 | **9필드만** 응답 + `provenance`(어느 색인·프로필로 찾았는지) |

## 5. 정직하게 적는 간극

- ★**개념 스키마가 두 벌이다.** 정규화된 `insurance_real.core`(FK 44)는 비어 있고,
  실제 데이터는 FK 0인 `mall_vec.public` 에 있다. **둘을 잇는 적재 경로가 없다.**

- ★**가동 DB 에 참조 무결성이 없고, 이미 깨져 있다.**
  `s6` 고유 해시 **72,723 중 8,206건(11.3%)** 이 `policy_clause_content` 행 없이 있다 —
  전 세대로는 고아 발생 **38,326행**. 외래키가 있었다면 **적재 시점에 막혔을** 것들이다.
  다만 조각(`chunk`) 쪽은 본문 없는 행이 **0** 이라 검색 경로 자체는 온전하다.

- **두 DB 를 잇는 배선은 있으나 꺼져 있다.** `INSURANCE_PG_DSN`·`INSURANCE_ADMIN_PG_DSN`
  이 정의돼 있지만 값이 **빈 문자열**이라 런타임은 `insurance_real` 에 붙지 않는다
  (`readiness` 가 `configured=false` 로 보고). 자리는 있고, 켜지지 않았을 뿐이다.

- **외부 스키마가 DB 밖에 있다.** 앱을 우회해 `mall_vec` 에 직접 붙으면 원문이 그대로 보인다.
  지금은 `listen_addresses=localhost` 가 사실상의 마지막 방어선이다.

## 재현

```bash
# 스키마·뷰·외래키·권한
psql "$PGVECTOR_DSN" -c "SELECT schemaname, count(*) FROM pg_tables
  WHERE schemaname NOT IN ('pg_catalog','information_schema') GROUP BY 1"
psql "$PGVECTOR_DSN" -c "SELECT count(*) FROM pg_constraint WHERE contype='f'"

# 인덱스 종류·크기
psql "$PGVECTOR_DSN" -c "SELECT i.indexrelid::regclass, am.amname,
  pg_size_pretty(pg_relation_size(i.indexrelid))
  FROM pg_index i JOIN pg_class c ON c.oid=i.indexrelid JOIN pg_am am ON am.oid=c.relam
  WHERE c.relnamespace='public'::regnamespace ORDER BY pg_relation_size(i.indexrelid) DESC"

# 고아 발생(참조 무결성이 없어서 생긴 것)
psql "$PGVECTOR_DSN" -c "SELECT count(*) FROM policy_clause_occurrence o
  WHERE NOT EXISTS (SELECT 1 FROM policy_clause_content t
                    WHERE t.content_hash=o.content_hash)"
```
