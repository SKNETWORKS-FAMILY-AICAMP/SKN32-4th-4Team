# 외부 에이전트 API 기반 구현 완료 보고

- 작성: 2026-08-04 KST
- 상태: **로컬 기술 구현·PostgreSQL 통합 검증 완료**
- 범위: 실제 인터넷 배포나 실제 제휴 에이전트 발급 전 단계
- 계획: `docs/plans/2026-08-04_2052_외부에이전트_API_기반구현계획.md`

## 1. 결론

기존 `scripts/simulate_agents.py`의 합성 에이전트와 별도로, 등록된 외부 에이전트가
우리 판정·용어·코호트 API를 호출하고 실제 결과를 미검증 사례로 돌려줄 수 있는 보호 REST
기반을 구현했다.

기존 고객 앱의 공개 `/v1/*`는 호환성을 위해 그대로 두었고, 신뢰 가능한 기계 채널은 별도
프로세스·포트의 `/v1/agent/*`로 분리했다. 따라서 “외부 에이전트가 API로 데이터를 주고받는
구조”는 이제 코드와 DB에 있다. 다만 DNS·TLS·WAF·키 전달을 하지 않았으므로 아직 인터넷에
공개된 운영 서비스는 아니다.

## 2. 구현 구조

| 경계 | 구현 |
|---|---|
| 전용 앱 | `app.agent_main:agent_app`, 기본 `127.0.0.1:8082` |
| 인증 | `Authorization: Bearer <agent-key>` |
| 사용자 축 | 개인정보가 아닌 `X-Agent-Subject` opaque 참조, DB에는 HMAC만 저장 |
| 권한 | endpoint별 4개 scope 강제 |
| 요청 제한 | PostgreSQL advisory lock 기반 `client + subject + operation` 분당 한도 |
| 쓰기 멱등 | `Idempotency-Key` 필수, HMAC 원장·payload 충돌 409·lease token CAS |
| 감사 | 요청·응답·trace HMAC과 판정 메타데이터만 append, 원문 의료정보 제외 |
| 사례 상태 | 항상 `unverified`; 외부 입력만으로 검증·코호트 승격하지 않음 |
| 데이터 격리 | `insurance_agent` DB 및 `submissions/registered_agent/` 원본 채널 |
| 장애 정책 | 인증·DB·감사 장애 시 파일/무인증 경로로 폴백하지 않고 503 |

## 3. 보호 API

| Method | Path | scope | 용도 |
|---|---|---|---|
| GET | `/v1/agent/support-manifest` | `precheck:read` | 지원 보험사·판본 계약 확인 |
| POST | `/v1/agent/prechecks` | `precheck:read` | 약관 근거 사전판정 |
| POST | `/v1/agent/terms/explain` | `terms:read` | 약관 용어 근거 설명 |
| GET | `/v1/agent/cohorts` | `cohort:read` | 검증된 실제 코호트만 조회 |
| POST | `/v1/agent/observations` | `observations:write` | 사후 결과를 미검증 사례로 접수 |

전용 앱에는 고객 정적 파일, 관리자 API, 합성 `/v1/demo/*` 라우터를 싣지 않았다.
`AGENT_API_ENABLED=false`가 기본이며, 직접 uvicorn으로 ASGI 앱을 불러도 인증 의존성이
비활성 플래그를 다시 검사한다.

## 4. 보안·정합성 구현

### 클라이언트와 권한

- 서버가 256-bit 난수 API key를 생성하며 원문은 생성·회전 때 한 번만 출력한다.
- DB `ops.agent_client`에는 key의 SHA-256만 남기고 상수시간 비교한다.
- `insurance_agent_runtime`, `insurance_agent_admin`, `insurance_agent_owner` 역할을 분리했다.
- runtime은 client·audit 원장을 수정/삭제하거나 인증 로그를 truncate할 수 없다.

### 멱등·동시성

- 호출자가 보낸 멱등키 원문 대신 `AGENT_HASH_SECRET` HMAC을 DB 기본키로 쓴다.
- 같은 client·key·payload 재시도는 기존 `submission_id`를 돌려주고 다시 쌓지 않는다.
- 같은 key의 다른 payload는 409로 실패한다.
- 5분 이상 stale인 작업은 새 lease로 재개하되, 이전 worker의 늦은 완료/실패 갱신은
  compare-and-set에서 거부된다.
- raw 파일 작성 뒤 event append가 실패한 부분 기록은 동일 payload 재시도로 복구한다.

### 감사·보존

- API 감사 DB와 telemetry에는 질병기호, 가입일, 질문, subject 원문을 남기지 않는다.
- 인증 30일, rate 2일, 감사·멱등 90일 보존기한과 admin 전용 prune 함수를 두었다.
- 실제 observation 원본과 정규화 사건에는 업무상 필요한 의료 입력이 남는다. 현재 로컬 파일
  저장은 애플리케이션 수준 암호화가 없으므로 운영 배포 전 디스크 암호화·접근권한·백업·파기
  정책이 필요하다.

## 5. DB·운영 도구

- migration track: `scripts/db/agent/001_agent_api.sql`,
  `002_agent_security_hardening.sql`
- 초기화: `python -m scripts.pg init-agent`
- 관리: `python -m scripts.agent_clients create|rotate|disable|list|prune`
- 실행: `python -m scripts.run_agent_server`
- 계약 확인: `/openapi.json`, `/llms.txt`, `/api/health/ready`

이미 적용된 001·002는 수정하지 않는 forward-only 정본이다. 추가 변경은 003 이상의 보정
마이그레이션으로만 해야 한다. 공통 마이그레이션 적용기의 dry-run 체크섬 충돌도 이제 종료코드
1로 고정했고 정상 `would/skip`은 0으로 시험한다.

## 8. 운영 전 남은 일

이번 요청의 “필요한 기술 구현”에는 아래를 포함하지 않았다.

- DNS, TLS 종료, reverse proxy/WAF, 네트워크 allowlist, 비밀 저장소와 안전한 키 전달
- 원격 Streamable HTTP MCP, OAuth 2.1, A2A Agent Card, webhook
- 실제 제휴 클라이언트 발급·부하/침투 시험·장애 대응 runbook
- 사용자 계정과 장기 대화 세션, 동의·철회·삭제 요청 처리
- 외부 사례의 자동 진위 확인 또는 판정 근거·실제 코호트 자동 승격
- 보호 API를 호출하는 데모/SDK 클라이언트

운영 공개 전에는 위 항목 중 최소 TLS·비밀 전달·저장 암호화/권한·보존 파기 검증을 완료해야 한다.
