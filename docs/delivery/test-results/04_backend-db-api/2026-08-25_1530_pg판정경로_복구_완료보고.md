## 3. 3층 조치 상세 — ★**재임베딩 없이** 끝냈다

사용자 제안("368,919 그냥 지우고 다시 쓰면 되지 않나")을 검토한 결과,
**지울 필요조차 없었다.** 근거:

| 테이블 | 행수 | 재생성 비용 |
|---|---|---|
| `policy_clause_occurrence` | 368,919 | 메타데이터 — 싸다 |
| `policy_clause_content` | 64,607 | 중간 |
| **`policy_clause_chunk`** | 122,772 | ★**임베딩 4~5시간** |

368,919 는 **벡터가 아니라 메타데이터**다. 그래서:

1. `ALTER TABLE policy_clause_occurrence ADD COLUMN ordinal integer`
   — nullable·기본값 없음이라 **PG11+ 에서 메타데이터만 바꾸는 즉시 작업**(테이블 재작성 없음)
2. `scripts/index/backfill_occurrence_ordinal.py` **신규** — s6 조항 JSON 을
   **한 파일씩 흘려보내며** 순번만 UPDATE. 임베딩·대용량 dict 없음
3. `db/postgres/pg_clause_store.py` — `o.ordinal` 을 SELECT 에 넣고 `ClauseRow.ordinal` 로 전달

★**전체 로더(`build_clause_index.py`)를 돌리지 않았다.** 그쪽은 임베딩까지 하는 경로이고,
같은 날 다른 세션이 고치고 있어 **건드리지 않았다**(§5).

★**검증**: 조각 수 **122,772 불변** — 재임베딩이 일어나지 않았음을 수치로 확인했다.

### 순번 충돌 처리

로더의 `ON CONFLICT (content_hash, sha256, qualified_no, page_from, index_generation)` 때문에
JSON 항목 여럿이 한 행으로 합쳐진다. 그때 **나중 값이 이기게 두면 처리 순서에 따라 식별자가 달라진다.**
그래서 `LEAST(COALESCE(ordinal, %s), %s)` 로 **가장 작은 순번에 고정**했다 — 순서와 무관하게 같은 값이 나온다.
(20문서 시험에서 갱신 2,579 → 실제 행 2,576. 차이 3이 합쳐진 중복이다.)

## 5. 다른 세션과의 관계

같은 저장소에서 동시에 작업 중이었다. **충돌은 없었다** — 다음을 지켰다:

- 다른 세션이 같은 날 고친 `build_clause_index.py`·`pgvector_clause_index.py` 를 **건드리지 않고**,
  새 스크립트 + 내 담당 파일(`pg_clause_store.py`)만 고쳤다
- 그쪽이 `drop_incomplete()` 를 고쳐 **본문을 지우며 고아를 만들던 문제**를 막아 둔 덕에
  이 작업의 위험이 줄었다(→ `2026-08-25_1500_고아발생_38326행_...md`)

★**발견한 조율 문제 2건**

1. **두 세션이 서로 다른 파이썬을 쓴다** — 나는 `.venv`, 다른 쪽은 anaconda.
   그래서 `django`·`sentence_transformers` 가 한쪽에만 있고, 상대 테스트가 **수집 단계에서 터진다.**
2. **회귀검사 중 상대가 소스를 고치면 거짓 실패가 난다.** 오늘 두 번 겪었다
   (`test_config`·`test_retrieval` 3건 / `test_rerank_worker` 4건 — 전부 단독 실행 시 통과).
