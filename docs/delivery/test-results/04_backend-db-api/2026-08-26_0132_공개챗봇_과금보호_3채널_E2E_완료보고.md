# 공개 챗봇 과금 보호 3채널 E2E 완료보고

## 결론

작업자 2 패치를 그대로 적용하지 않고 현재 프로젝트 계약에 맞게 통합했다. 공개 REST,
등록 에이전트 REST, MCP가 같은 챗봇 응답 계약을 유지하고 동일한 fake provider 결과를
공유하는 E2E가 통과했다. 실제 외부 LLM과 PostgreSQL은 호출하지 않았다.

## 원본 패치에서 수정한 핵심 결함

| 항목 | 원본 상태 | 통합 결과 |
|---|---|---|
| 등록 에이전트 응답 | strict 스키마에 `source`가 없어 검증 실패 | 선택적 Literal 필드 추가 |
| 설정 | 라우터 안 `Settings` 하위 클래스 | 중앙 `app.core.config.Settings`로 이동 |
| 등록 에이전트 429 | façade에서 503으로 변환 | 429·`Retry-After` 보존 |
| 유료 시험 안내 | 클라이언트 rate limit만 해제 | 전역 예산·캐시까지 시험 목적별 명시 |
| 호출 수 해석 | `source=call`을 과금 수로 단정 | gateway 관측값을 진실 원장으로 명시 |
| 완료 표식 | status 누락 | coordinator 통합 status 별도 작성 |

## 3채널 E2E 실측

동일한 `통원 뜻` 요청을 순서대로 보냈다.

| 채널 | HTTP/도구 결과 | `llm.source` |
|---|---:|---|
| 공개 `POST /v1/chat` | 200 | `call` |
| 등록 에이전트 `POST /v1/agent/terms/explain` | 200 | `cache` |
| MCP `explain_term` | 성공 | `cache` |

세 응답의 message·provider·model은 같고 fake provider 호출은 1회였다. 별도 시나리오에서
LLM 예산을 1회로 설정한 뒤 다른 용어를 요청했을 때 등록 에이전트는 429와
`Retry-After`, MCP는 `http_status=429` 구조화 오류를 반환했다.

이 1회 수치는 같은 테스트 프로세스에서 세 인터페이스가 동일 라우터 함수를 재사용하는 계약을
검증한 결과다. 실제 배포의 customer·agent·MCP는 별도 프로세스이므로 메모리 캐시와 호출 예산을
서로 공유하지 않는다.

## 회귀 결과

총 149개의 고유·인접 테스트 묶음이 통과했고, 동시 20건 핵심 시험은 별도로 5회 반복해
모두 통과했다. 모든 시험은 `--noconftest`로 실행해 PostgreSQL 공통 픽스처를 타지 않았다.
공개 `POST /v1/chat`의 기존 OpenAPI operationId도 유지됨을 확인했다.

## 운영 판단

현재 customer 컨테이너는 uvicorn 단일 worker이므로 프로세스 메모리 기반 보호를 적용할 수
있다. 향후 worker/replica를 늘리면 한도가 인스턴스별로 배가되므로 공유 제한이 필요하다.
실제 유료 부하 시험에서는 전용 드라이버 하드 상한을 켠 상태에서 애플리케이션의 client
limit·전역 예산·TTL 캐시를 시험 목적에 맞춰 일시 해제해야 한다.

백업 위치는 `backups/chat_cost_guard_integration_20260826_011858/`이다.
