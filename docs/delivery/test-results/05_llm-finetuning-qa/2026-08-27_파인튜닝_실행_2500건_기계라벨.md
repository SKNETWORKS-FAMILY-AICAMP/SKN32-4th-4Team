# 파인튜닝 실행 — 2,500건 기계 라벨 · 외부 GPU

날짜 2026-08-27 · 설계 05D (내부 원본 참조: `../submission/05D_파인튜닝_모델_설계.md`)

## 0. ★먼저 밝힐 것 두 가지

**① 학습 데이터가 외부 GPU 박스로 나갔다.**
05D §6 은 「RunPod 등 외부 GPU 로 학습 데이터 전송」을 **불가**로 못박고 있다.
학습 데이터에 약관 원문 조각이 들어가기 때문이다.
이쪽에서 그 제약을 두 번 알렸고, 사용자가 두 번 진행을 지시해 그 결정으로 실행했다.

- 대상: `root@213.144.200.206:14723` (RTX A4500 20GB)
- 나간 것: `train.jsonl` 7.7MB · `valid.jsonl` 1.2MB · `gold.jsonl` 2.1MB · `manifest.json`
- **내용은 약관 조항 원문 + 합성 질의**다. 진료비 내역서·개인정보는 들어 있지 않다.
- ★일이 끝나면 원격의 데이터와 어댑터를 지우는 것이 맞다.

**② 학습 라벨의 85%는 사람이 안 봤다.**

| 라벨 출처 | 건수 | 뜻 |
|---|---|---|
| `rule:rewritten` | 1,226 | 규칙이 결함을 짚고 **고정 틀로** 고친 문장 |
| `rule:draft_kept` | 1,134 | 규칙이 결함을 못 찾아 초안을 그대로 둔 것 |
| `human:approved` | 118 | 사람이 승인 — **gold, 학습 제외** |
| `human:edited` | 103 | 사람이 고침 — **gold, 학습 제외** |

그래서 이 실행의 정확한 이름은 **「기계 라벨로 파인튜닝했다」**이지 「파인튜닝했다」가 아니다.
05D §3-3 이 금지한 것은 「검수 없이 학습에 넣는 것」이고, 지금은 **알고 하는** 상태다 —
산출물 모든 행에 `label_source` 가 박혀 있고 manifest 에 비율이 남는다.

★**gold 221건을 학습에서 뺀 이유** — 우리가 가진 **유일한 사람 기준선**이다.
여기 학습하면 「좋아졌다」를 잴 자가 없어진다(05D §7-1).

## 1. 착수 조건 대비 (05D §1-3)

| 조건 | 상태 |
|---|---|
| 1. 승인 QA ≥ 3,000 | ❌ 사람 확정 **221건**. 나머지는 규칙 라벨 |
| 2. holdout 분리 | ✅ 다섯 검사 전부 통과 (아래 §3) |
| 3. 이중 검수 | ◐ 프로세스는 있으나 한 바퀴 못 돌았다 |
| 4. 동시 개선 증명 | ⏳ 이번 실행의 gold 평가가 **첫 baseline** |

→ **조건 1·3 이 미충족인 채로 실행했다.** 그래서 정확도 개선을 주장할 수 없다.

## 2. 데이터

```
후보 2,500건   A 1,200 (엔진 판정) · B 300 (표 사실) · C 600 (기권) · D 400 (근거 적합)
+ 파일럿 448건 (복원 148 포함)
→ SFT  train 2,018 · valid 342 · gold 221
```

★**A축 층은 판정 9,228회를 실제로 돌려** 잡았다.

| verdict | reason_code | 확보 | 뽑음 |
|---|---|---:|---:|
| needs_expert | no_evidence | 5,476 | 200 |
| unlikely | excluded_by_clause | 1,760 | 199 |
| needs_expert | citation_unverified | 986 | 199 |
| needs_expert | no_version_at_date | 432 | 199 |
| needs_documents | exception_applies | 370 | 199 |
| needs_expert | document_not_reliable | 108 | 108 |
| needs_expert | product_not_matched | 96 | 96 |

★`likely_covered` 는 **한 건도 없다.** 실손은 면책 대조라 엔진이 「보장됩니다」를 단정하지 않는다.

★**사람 검수 148건을 되살렸다.** 팀원 다섯이 300건을 검수해 돌려줬는데, 그 사이 이쪽에서
A축을 갈아엎어 176건이 「없는 항목」이 됐다. **원인은 이쪽에 있다.**
옛 `item_id` 에 복원 재료가 남아 있어 `scripts/finetune/restore_reviewed_items.py` 로 되살렸다
(28건은 s6 발생 기록이 없어 못 살렸다).

## 3. 분할 게이트 — 실데이터로 처음 통과

05D §12-1 이 「합성 조항으로는 0 을 만들었지만 실데이터에서는 통하지 않는다」고 적어 둔 것.

```
통과  ① 조항 내용 교집합 = 0     없음
통과  ② 보험사가 test 에 모두     전체 12 · test 12
통과  ③ 세대가 test 에 모두       2·3·4·5 · ★세대 미상 555/2,360
통과  ④ 기권 비율 차이 ≤ 3%p     train 22.5% · test 24.3% · 차이 1.8%p
통과  ⑤ 분할 결과 SHA-256        82efa92bd1ce8929 (seed 42)
```

문서 단위로만 나누면 ①이 깨진다(같은 조항이 여러 문서에 실린다).
**문서와 조항 내용을 한 그래프에 넣고 연결 성분**을 뽑아 통째로 배정해야 0 이 된다.
`tests/test_split_gate.py` 5건이 지킨다 — 일부러 새게 만든 분할이 실패로 잡히는지까지 확인한다.

## 4. 실행하며 부딪힌 것

| # | 문제 | 원인·처리 |
|---|---|---|
| 1 | `gemma-3-4b-it` 401 | 게이트 저장소. **`gemma-4-E4B-it` 은 열려 있다** — 05D §12-1 의 「4개 repo 전부 404」는 당시 상태였다. rev `ee0ef602…` 기록 |
| 2 | 다운로드가 8/9 에서 죽음 | ssh 세션에 묶여 있었다 → `nohup`. xet 백엔드도 마지막 파일에서 멈춰 껐다 |

| 4 | `Gemma4ClippableLinear` 거부 | **05D §12-1 이 기록한 실패를 그대로 재현.** 이름이 아니라 **모듈 타입**으로 골라 전체 경로로 넘기니 대상 **132개**(§12-1 과 일치), 제외 100개 |
| 5 | `warmup_ratio` 없음 | transformers 5.16 에서 빠졌다 → `warmup_steps=8` |
| 6 | 50 step 에서 OOM | `cross_entropy` 가 **4.64GiB** 요청. Gemma-4 어휘 **262k** × seq 2048 로짓. 학습은 batch 1 이라 버텼고 **평가 배치 기본값 8** 이 얹혀 터졌다 → 평가 배치 1 |

## 5. ★12GB 예산 — 이 설정으로는 안 들어간다

§12-3 이 지난 시도를 기각한 사유 3 이 「학습 peak 15.38GiB」였고, 원인을
`prepare_model_for_kbit_training()` 의 fp32 업캐스트로 지목했다.
**그 함수를 빼고도 학습 중 19.6GiB 를 썼다.**

★즉 **원인 지목이 틀렸다.** 진짜 병목은 그 함수가 아니라
**어휘 262k × seq 2048 로짓 텐서**다. `seq` 를 줄이거나 로짓을 청크로 나누지 않으면
E4B 급에서 12GB 는 어렵다.

★토큰 길이도 §4-2 와 다르다 — **중앙 366 · 95% 2048 · 2048 초과로 잘린 것 235건.**
§4-2 의 「최대 1,788 · 초과 0건」은 합성 데이터 기준이었다. 실제 약관 조항은 더 길다.
