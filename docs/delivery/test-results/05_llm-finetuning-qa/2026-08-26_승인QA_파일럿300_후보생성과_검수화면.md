## 1-2. ★A축을 다시 만들었다 — 검색 정답셋 → **엔진 판정**

처음엔 A축을 검색 정답셋(`retrieval_probes.json`)에서 뽑아 「이 조항이 근거로 맞나」를 물었다.
그건 **검색 평가**이지 우리가 학습시킬 것이 아니다. 05D §3-2-1 이 요구한 층은
`verdict × reason_code` 인데 검색 정답셋에는 **엔진 판정이 붙어 있지 않아** 그 층을 못 만들었다.

`/v1/prechecks` 를 **실제로 1,248회 돌려** 층이 어떻게 갈리는지 먼저 쟀다:

| verdict | reason_code | 확보 |
|---|---|---|
| needs_expert | no_evidence | 723 |
| unlikely | excluded_by_clause | 257 |
| needs_expert | citation_unverified | 147 |
| needs_documents | exception_applies | 49 |
| needs_expert | no_version_at_date | 36 |
| needs_expert | document_not_reliable | 24 |
| needs_expert | product_not_matched | 12 |

★**`likely_covered` 는 한 건도 없다.** 실손은 면책 대조라 엔진이 「보장됩니다」를 단정하지 않는다.
없는 층을 만들어 내지 않는다.
★밑비율대로 뽑으면 `no_evidence` 가 60%를 먹는다 — **층을 고르게** 채웠다(29·29·29·29·28·24·12).

과업도 바뀌었다(코덱스 결론): **엔진 판정을 입력으로 준다.**
`verdict`·`reason_code`·`citations` 는 이미 정해진 것이고, 사람이 보는 것은
**그 위에 얹힌 고객 문장이 맞는가**다. 그래야 규칙엔진의 한계가 결함이 아니라 설계가 된다.
화면도 엔진 판정 블록을 **결정 전에도** 보여 준다 — 이건 숨겨야 할 기계 의견이 아니라 전제다.

★첫 판에서 **중단 조건을 도달 불가능하게** 잡았다(층 8개 × 상한 40 = 320 < 목표 360).
  16,260회를 다 도는 30분짜리 루프가 됐다. 상한과 목표를 같은 자로 맞춰 고쳤다.

★인용 창은 **정확히 300자**로 잘린다. 인용 있는 58건 중 **52건**이 질문의 질병기호를
담는다(직접 30 · 범위 22 — 약관은 `F04~F99` 처럼 범위로 적는다). 나머지 6건은
검수자가 판단할 진짜 사례라 **남겼다.**

## 3. 검수 화면이 하는 일

600건 라벨링이 **건당 43.2초**를 낸 동작을 그대로 살렸다 — **한 화면, 한 키.**

| 요구 (05D §3-2-1) | 구현 | 확인 |
|---|---|---|
| 질문·초안·근거 본문·출처를 한 화면에 | 상단 고정 헤더 + 본문 | ✔ DOM 확인 |
| 질의 어절을 근거 본문에 강조 | `<mark>` — 표본 항목에서 28곳 | ✔ |
| 출처 표기(회사·조항·쪽·sha12·parse) | 근거 위 모노스페이스 줄 | ✔ |
| `parse_status != ok` · 인용불가 경고 | 빨간 박스 | ✔ 코드 경로 확인 (이번 표본엔 해당 0건) |
| **기계 의견은 결정 전 숨김** | `decision` 이 있을 때만 `<details>` | ✔ 결정 전 숨김 / 후 노출 |
| `[A]승인 [E]수정 [N]기권 [R]반려` | 키보드 + 버튼 | ✔ |
| 사유 단축키 `1`~`9` | 결정별 사유 목록 | ✔ R축 4종 표시 확인 |
| 승인은 사유 없이 바로 다음 | `decide()` 자동 이동 | ✔ `1/60 → 2/60` |
| 자동저장 | 입력마다 `localStorage` | ✔ |
| 중단 후 위치 복귀 | `cursor` 저장·복원 | ✔ 새로고침 후 같은 항목 |
| Undo | `Ctrl+Z`, 결정 스택 | ✔ |
| 작업 잠금 | `--parts N` 로 **겹치지 않게 분할** | ✔ 5×60 |
| 감사 로그 | `state.log` 에 결정·시각 | ✔ |
| 내보내기 | JSONL 내려받기 | ✔ 60줄 |

추가로 넣은 것(600건 검수판과 맞춤): **검수자 이름** · 필터(전체/미완료/완료/보류·수정) ·
**다음 미완료** · **이전 결과 불러오기**(다른 파트 항목은 세어서 무시) · 안내 문서 링크.

확인 방법: 꾸러미를 정적 서버로 띄우고(`.claude/launch.json` 의 `review`, 8093)
DOM·`localStorage` 를 직접 읽어 동작을 검사했다. **콘솔 오류 0건.**
압축을 다시 풀어 **팀원이 실제로 밟는 경로**로도 열어 확인했다.

## 3-2. ★「기권」과 「보류」를 갈랐다 — 팀원이 실제로 물었다

검수 화면을 보고 팀원이 바로 물었다: **「승인=맞다, 반려=틀리다, 기권=보류. 이게 맞나요?」**
앞의 둘은 맞고 **세 번째가 틀렸다.** 그리고 그렇게 읽힌 것은 **화면 탓이다** — 보류 버튼이 없었다.

| | 뜻 | 누구의 상태인가 |
|---|---|---|
| **기권** | 근거를 댈 수 없으니 **서비스가 답하면 안 된다** | 검수자는 **확신한** 상태 |
| **보류** | **내가** 판단을 못 하겠다 | 다른 사람이 봐야 한다 |

고친 것 셋:

1. **`S` 판단 보류를 넣었다.** 사유 2종(`원문만으로 확실히 못 정하겠다` · `전문 지식이 필요하다`).
2. **버튼 라벨을 축에 맞게 바꿨다.** C축 초안은 그 자체가 기권이라
   `승인 = 기권이 맞다` · `반려 = 기권이 틀렸다(근거가 있다)` 이고, **C축에는 `N` 이 없다.**
   같은 키에 다른 뜻을 두면 잘못 찍는다.
3. **`00_먼저읽기.html` §4 에 표로 못박았다.**

## 3-3. ★근거가 제목 한 줄뿐인 항목 14건을 없앴다

검수 화면 스크린샷에서 근거 본문이 **「제4조(보상하지 않는 사항)」 15자**뿐인 항목이 보였다.
「이 조항이 근거로 맞나?」를 물어 놓고 **볼 것을 안 준 셈**이다. 실측 240건 중 **14건(5.8%)**.

지어내지 않고 고쳤다 — **같은 질의의 다른 gold 조항** 중 본문이 가장 긴 것을 쓰고,
전부 120자 미만이면 그 질의를 **버린다**(A축 6건 버림, 조용히 넘기지 않고 세어 출력).
결과: 근거 본문 **최소 101자 · 중앙 7,877자**. 120자 미만 8건은 전부 B축 표 사실이고 **내용이 온전하다.**

## 4. 만들면서 고친 결함 4건

1. **`E`(수정)에 고친 문장을 적을 곳이 없었다.** 결정만 남고 정정본이 없으면
   학습 데이터로 못 쓴다. 입력란을 넣고, **비어 있으면 헤더에 「미완성 수정 n」** 을 띄운다.
2. **자동저장 실패가 조용했다.** `file://`·`data:`·시크릿창에서 `localStorage` 가 막힌다.
   조용히 실패하면 60건을 다 찍고 나서야 안다 — 시작할 때 확인해 **빨간 배너**를 띄운다
   (CLAUDE.md §0, 신호 없는 실패 금지).
3. **보험사 표기가 두 갈래였다** — 조항 색인은 한글(`현대해상`), 승인 OCR 사실은
   슬러그(`hyundaimarine`). 검수자가 같은 회사를 다른 회사로 읽는다.
   `data/raw/manifests/<슬러그>.jsonl` 안의 **실제 한글값을 세어** 대응표를 만들었다.
4. **B축 층이 안 나뉘었다.** `category` 가 850건 **전부 `missed`** 다.
   실제로 갈리는 `plan`(5종)×`service`(3종)로 바꾸고 층별 라운드로빈으로 뽑았다
   — 안 그러면 618/850 인 `표준형`이 층을 다 먹는다.

- **~~A축 층화가 05D 명세와 다르다~~ — 해결.** `/v1/prechecks` 를 실제로 돌려
  `verdict × reason_code` 7개 층으로 다시 만들었다(위 §1-2).
- **~~경고 박스 경로가 안 밟혔다~~ — 해결.** DB 실측으로 `citation_eligible=false` 발생 265 ·
  `parse_status IS NULL` 발생 7,045 를 찾아 C축 30건에 **실제 조항**을 붙였다.
  화면에서 두 경고가 다 뜨는 것을 확인했다(정상 항목에는 안 뜬다).
  ★`parse_status` 가 **`ok` 가 아닌 행은 하나도 없다** — 있는 것은 `ok` 아니면 NULL 이다.
    처음엔 JS 가 null 을 falsy 로 걸러 15건이 **아무 표시 없이** 나갔다. 고쳤다.
- **C축 절반은 여전히 합성이다.** `no_evidence` · `ambiguous_product` 30건은
  결손을 인위적으로 만든 것이다(나머지 30건은 실제 조항을 붙였다).
- **A축 180건 중 인용이 있는 것은 58건뿐이다.** 나머지 122건은 엔진이 근거를 못 댄
  기권 계열이다. 그게 실제 분포이고, 검수자가 볼 것은 「문장이 단정하지 않는가」다.
- **B축 초안 문장이 OCR 원문 그대로다** — 띄어쓰기가 깨진 것이 있다

- **원자료 표기 흠 2건**(이번 작업 범위 밖, 고치지 않고 적어만 둔다):
