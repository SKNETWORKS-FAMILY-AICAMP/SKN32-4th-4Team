# LLM 설명문 생성 모델 비교 — gpt-4o-mini vs gpt-5-nano (gpt-5.6-luna 검토 포함)

- 작성: 2026-08-26
- 배경: EC2 배포 중 로컬 LLM(GGUF)이 디스크 8GB 제약으로 못 올라가서 `LLM_PROVIDER=openai`로
  전환. 현재 실사용 모델은 `gpt-4o-mini`. 사용자가 "gpt-5.6-luna가 4o보다 싸다"는 것을 보고
  교체를 검토해 달라고 요청 → 실제 가격 조회 결과 luna는 4o-mini보다 **더 비싸** 제외하고,
  대신 4o-mini보다 싸거나 같은 후보(`gpt-5-nano`, `gpt-4.1-nano`)를 실측 비교했다.
- 예산: 500원 이내(사용자 지정). **실제 사용: $0.0542(약 79원, raw API 1~4차 합계)** —
  예산 내(421원 남음). gpt-5.6-luna는 Codex CLI 경유(달러 비용 0원, §4.5)와 raw API
  경유(§4.8) 두 가지로 다 실측했다.

## 1. 왜 gpt-5.6-luna가 아니라 gpt-5-nano를 비교했나

OpenAI 공식 pricing 페이지(`developers.openai.com/api/docs/pricing`) 실측(1M 토큰당):

| 모델 | 입력 | 출력 | 비고 |
|---|---:|---:|---|
| gpt-4o-mini(현재) | $0.15 | $0.60 | — |
| gpt-5.6-luna | $0.20 | $1.20 | 4o-mini보다 **비쌈**(입력 33%↑, 출력 2배) |
| **gpt-5-nano** | **$0.05** | **$0.40** | 4o-mini보다 **쌈**(입력 3배↓, 출력 1.5배↓) |
| gpt-4.1-nano | $0.10 | $0.40 | 4o-mini보다 쌈 |

"luna가 4o보다 싸다"는 맞는 말이지만, 비교 대상을 잘못 잡은 것이었다 — 우리가 실제 쓰는 건
`gpt-4o`가 아니라 그보다 훨씬 싼 `gpt-4o-mini`다. luna는 그 기준으로는 더 비싸 제외했고,
대신 진짜로 4o-mini보다 싼 후보 중 가장 최신 세대인 `gpt-5-nano`를 실측했다.

## 2. 테스트 방법

`app/adapters/llm_assessment_explainer.py`의 **실제 프로덕션 프롬프트·JSON 스키마를 그대로
재현**했다(별도 스크립트, 앱 코드는 안 건드림). 실제 약관 조항 데이터
(`data/structured/dbins/s6_pymupdf-1.28.0/02aaee47b190.clauses.json`)에서 크기가 다른
조항 5개를 골라, 5가지 판정 시나리오(likely_covered·unlikely×2·needs_documents·needs_expert)
로 두 모델에 동일 입력을 주고 비교했다.

측정 항목: 실제 `response.usage`(prompt/completion 토큰 — 추정 아님) → 실제 비용,
응답 시간, `verdict`가 입력 `rule_verdict`와 일치하는지, **`citations[0].quote`가 실제
`evidence.text`(원문)에 문자 그대로 포함되는지**(이 프로젝트의 핵심 안전 기준 —
CLAUDE.md §0 "근거 조항을 못 대면 판정하지 않는다"와 직결).

## 4. 발견 — 가격표만 봐서는 안 보이는 것

### 4.1 `gpt-5-nano`는 추론 모델이다 — completion 토큰이 숨은 "reasoning tokens"로 폭증

스모크 테스트 하나(`{"x":"hello"}`만 출력)에서도 **completion_tokens=1105 중 1088개가
`reasoning_tokens`**였다. 실제 5건에서도 completion 토큰이 1720~3069(4o-mini는 60~107)로
**20~40배** 많다. 그 결과:

- **응답 시간이 4o-mini의 6~19배**(평균 3.0초 → 19.5초). 실시간 사용자 응답에는 부담스러운
  지연이다.
- **1M 토큰당 가격은 nano가 3배 싸지만, 실제 호출당 비용은 nano가 평균 4.5배 더 비싸다**
  (합계 $0.0011 vs $0.0050). 추론 토큰이 "싼 단가 × 훨씬 많은 토큰"으로 가격 이점을
  상쇄하고도 남는다.

**결론: "1M 토큰당 단가"만 보고 비용을 비교하면 틀린다.** 실제 워크로드로 측정해야 한다 —
이번처럼.

### 4.2 인용 정확도는 gpt-5-nano가 눈에 띄게 우세했다 (4/5 vs 2/5, n=5로 작음)

★이 저장소의 원칙(CLAUDE.md §4)대로 표본이 작다고 명시한다 — 5건으로 "5-nano가 더
정확하다"고 확정할 수 없다. 다만 이번 실측에서 나온 **실패 패턴의 성격 차이**는 기록해 둘
가치가 있다.

- **gpt-4o-mini의 실패 3건은 전부 같은 패턴**이다 — `citations[0].quote`에 실제
  `evidence.text`(약관 원문)가 아니라 **입력으로 준 `per_code[].note` 문구를 그대로
  복사**했다(예: case2에서 quote="건강검진은 면책 조항에 해당" — 이건 내가 테스트 입력에
  넣은 note 필드 문자열이지 약관 원문이 아니다). 즉 "그럴듯해 보이지만 실제로는 원문을
  인용하지 않은" 패턴 — 이 프로젝트가 가장 경계하는 실패 유형과 정확히 일치한다.
- **gpt-5-nano의 실패 1건(case5)은 다른 패턴**이다 — 원문에서 앞부분("계약자(보험금
  지급사유 발생 후에는...)는 회사의 사업방법서에서 정한 바에 따라")을 자른, 근접하지만
  완전 일치는 아닌 인용이었다. 없는 내용을 지어낸 게 아니라 절삭에 가깝다.

### 4.3 verdict 필드는 두 모델 다 5/5 정확 — 이건 약한 신호다

시스템 프롬프트가 "rule_verdict를 그대로 반환하라"고 명시하므로 이건 사실상 그대로
베끼는 것에 가깝다. 모델 판단력을 테스트하는 지표가 아니다 — 인용 정확도(§4.2)가
진짜 비교 기준이다.

## 4.4 (후속) gpt-4.1-nano 추가 + 추론 끄고 재측정 — "인용 정확도"의 진짜 원인을 찾음

사용자 요청으로 두 가지를 더 실측했다: ① `gpt-4.1-nano`(추론 없는 모델), ②
`gpt-5-nano`를 `reasoning_effort="minimal"`로 강제해 추론을 끈 경우. 비용 $0.00187
(약 2.7원) 추가 — 누적 총 11.5원, 예산(500원) 안.

| 모델 | 5건 합계 비용 | 평균 응답시간 | 인용 원문 일치 |
|---|---:|---:|:---:|
| gpt-4o-mini | $0.0011 | 3.0초 | 2/5 |
| **gpt-4.1-nano** | **$0.0009** | **2.0초** | **3/5** |
| gpt-5-nano(추론 끔) | $0.0010 | 3.1초 | 2/5 |
| gpt-5-nano(추론 켬, 기본) | $0.0050 | 19.5초 | 4/5 |

**핵심 발견: gpt-5-nano의 인용 정확도 우위는 "추론" 그 자체 때문이었다.** 추론을 끄자
(`reasoning_effort=minimal`) 인용 정확도가 4/5 → 2/5로 떨어져 gpt-4o-mini와 동률이
됐다 — 모델 자체의 우위가 아니라 **"충분히 생각하고 답하는 과정"이 정확한 원문 인용을
만들어낸 것**이다. 추론을 끄면 속도(3.1초)·비용($0.0010)은 저렴한 모델 수준으로
돌아오지만 정확도 이점도 같이 사라진다.

`gpt-4.1-nano`는 이번 4개 구성 중 **비용 최저·속도 최고이면서 정확도도 4o-mini보다 나음
(3/5 vs 2/5)** — 추론 없이도 4o-mini보다 나은 결과라 새로운 유력 후보다. 다만 이것도
n=5라 확정은 아니다.

## 4.5 (후속) gpt-5.6-luna를 Codex CLI로 실측 — 달러 비용 0원, Codex 쿼터만 소비

앞서 §1에서 raw API 가격만 보고 luna를 후보에서 뺐었는데, 사용자가 "Codex CLI로 돌리면
API 과금이 아니라 Codex 구독 쿼터로 되는 거 아니냐"고 물어서 실제로 테스트했다.

- **`codex exec --model gpt-4o-mini`/`gpt-5-nano`는 거부된다** — 실측 에러:
  `"The 'X' model is not supported when using Codex with a ChatGPT account."`
  (raw API 모델은 ChatGPT 구독 인증에서 원천 차단)
- **`codex exec --model gpt-5.6-luna`는 된다** — Codex 계열 모델이라 ChatGPT 구독 인증으로
  정상 호출됨. **`OPENAI_API_KEY` 과금 없이 Codex 구독 쿼터만 소비.**

같은 5개 케이스로 재현(별도 스크립트, `codex exec` 표준입력으로 프롬프트 전달 — Windows에서
CLI 인자로 멀티라인 프롬프트를 넘기면 `.cmd` 셸 래퍼가 깨트려서 stdin 파이프로 우회했다):

| case | verdict 일치 | 인용 원문 일치 | Codex tokens(쿼터) |
|---|:---:|:---:|---:|
| case1 | ✓ | ✓ | 6,768 |
| case2 | ✓ | ✓ | 5,662 |
| case3 | ✓ | ✓ | 5,019 |
| case4 | ✓ | ✓ | 4,022 |
| case5 | ✓ | ✓ | 1,880 |
| **합계/평균** | **5/5** | **5/5(100%)** | **23,351 tokens(쿼터, 달러 비용 아님)** |

**gpt-5.6-luna(Codex 경유)가 이번 비교에서 인용 정확도 1위(5/5)를 기록했다** — gpt-5-nano
추론 켠 것(4/5)보다도 나았고, **API 비용은 0원**(Codex 구독 쿼터 23,351토큰 소비)이다.
다만:

- ★n=5로 여전히 작은 표본이다.
- **Codex 쿼터도 무한이 아니다** — 이 쿼터는 코딩 작업(Codex CLI로 하는 다른 모든 작업)과
  공유되는 자원이라, 프로덕션 트래픽만큼 반복 호출하면 코딩 작업용 쿼터를 깎아먹는다.
  "이 방식은 확장 가능한 프로덕션 아키텍처가 아니라 이번 비교 테스트에 한해 유효한
  절약 수단"이라는 점을 분명히 해 둔다 — 실제 서비스에서 사용자 요청마다
  `codex exec`를 호출하는 설계는 제안하지 않는다.
- Codex CLI는 코딩 에이전트 인터페이스라 raw API의 `response_format=json_schema`(구조적
  강제) 같은 보장이 없다 — 프롬프트만으로 JSON 형식을 지키게 해야 했다(처음 시도는 모델이
  input을 그대로 복사해 버려 프롬프트를 다시 써야 했다).

## 4.6 (후속) 25건으로 확대 — n=5 결론이 뒤집혔다

사용자 요청으로 4개 raw API 구성(gpt-4o-mini·gpt-4.1-nano·gpt-5-nano 켬/끔)을 **같은
문서에서 뽑은 25개 실제 조항**(짧은 것부터 긴 것까지 균등 샘플링, verdict/KCD 코드는
4종류를 순환 배정)으로 재측정했다. 총 100회 호출, 비용 $0.0367(약 53.2원) — 지금까지
누적 총 $0.0446(약 65원), 500원 예산 중 435원 남음.

| 구성 | n=25 비용 | 평균 응답시간 | 인용 정확도 | (참고) n=5였을 때 |
|---|---:|---:|:---:|:---:|
| gpt-4o-mini | $0.0038 | 1.6초 | **2/25(8%)** | 2/5(40%) |
| **gpt-4.1-nano** | **$0.0034** | **1.9초** | **11/25(44%)** | 3/5(60%) |
| gpt-5-nano(추론 켬) | $0.0259 | 20.9초 | 8/25(32%) | 4/5(80%) |
| gpt-5-nano(추론 끔) | $0.0036 | 3.1초 | 9/25(36%) | 2/5(40%) |

**★정정한다 — §4.4의 "인용 정확도는 추론 유무가 갈랐다"는 n=5에서 나온 착시였다.**
표본을 25로 늘리자:

1. **모든 구성의 정확도가 큰 폭으로 낮아졌다**(4o-mini 40%→8%, 5-nano-켬 80%→32%).
   n=5는 우연히 쉬운 케이스가 몰려 있었던 것으로 보인다 — CLAUDE.md §4가 경고하는
   정확히 그 상황이다.
2. **추론 켠 gpt-5-nano가 더 이상 최고 정확도가 아니다** — 추론 끈 것(36%)이 오히려
   추론 켠 것(32%)보다 근소하게 나았다. 그런데도 추론 켠 쪽은 **7배 더 비싸고 7배 더
   느리다.** n=5에서 봤던 "추론이 정확도를 끌어올린다"는 관계가 n=25에서는 사라졌다.
3. **`gpt-4.1-nano`가 4개 구성 중 정확도·비용·속도 전부 최상위다**(44%, $0.0034,
   1.9초) — n=5 때도 1등이었는데 표본을 늘려도 그대로 유지됐다. 지금까지 나온 것 중
   가장 일관된 신호다.

여전히 낮은 절대 정확도(최고가 44%)는 이 테스트의 합성 케이스 구성(조항과 판정문구를
실제 판정 로직 없이 순환 배정) 때문일 수 있어 실제 프로덕션 파이프라인의 절대 수치로
그대로 옮기면 안 된다 — 다만 **네 구성이 완전히 동일한 입력을 받았으므로 구성 간
상대 비교는 유효하다.**

## 4.7 (후속) gpt-5.6-luna도 25건으로 확대 — 정확도 1위 유지, 단 100%는 착시였다

§4.6과 완전히 같은 25개 케이스로 luna도 확대했다(Codex CLI, `codex exec --model
gpt-5.6-luna`, 25회 순차 호출). 파싱 실패 0건.

| 지표 | n=5 | **n=25** |
|---|:---:|:---:|
| verdict 일치 | 5/5(100%) | **25/25(100%)** |
| 인용 원문 일치 | 5/5(100%) | **15/25(60%)** |
| 비용 | $0(쿼터) | $0(쿼터, 누적 116,871 토큰) |

n=5의 "100% 정확"은 역시 작은 표본의 착시였다(다른 모델들과 같은 패턴). 그래도 **n=25
기준으로도 60%로 5개 구성 중 압도적 1위**(2위 gpt-4.1-nano 44%)이고, verdict는 25/25
전부 일치했다 — 정확도만 보면 gpt-5.6-luna가 가장 낫다. 다만 §4.5에서 이미 밝혔듯
Codex 쿼터는 프로덕션 트래픽에 반복 호출하는 용도가 아니다.

**소요 시간**: n=5는 약 1분(콜당 평균 12초), n=25는 약 4분(콜당 평균 9.6초) — 결과
파일 타임스탬프로 역산.

**raw API 환산 비용 추정(참고용, 정확한 값 아님)**: Codex CLI는 입력/출력 토큰을
나눠 보고하지 않고 합계(`tokens used`)만 준다. n=25 합계 116,871토큰을 luna 가격표
($0.20/1M 입력, $1.20/1M 출력)로 전부 입력이라 가정하면 하한 $0.023, 전부 출력이라
가정하면 상한 $0.140 — **실제 값은 이 사이(약 33~203원)** 다. medium reasoning
effort라 completion/reasoning 쪽 비중이 커서 상한에 더 가까울 가능성이 높다.

## 4.8 (후속) gpt-5.6-luna를 raw API로 실측 — Codex CLI 결과와 갈렸다

사용자가 "Codex CLI 말고 실제 API로 5.6-luna를 돌려서 정확한 금액·시간·결과를 보라"고
요청해 §4.6·§4.7과 완전히 같은 25개 케이스·같은 프로덕션 스키마로 `client.chat.completions.create()`를
직접 호출했다(`response_format=json_schema strict`, `temperature=1`, 다른 4개 raw API
구성과 동일한 측정 코드). 비용 $0.0096(약 13.9원) — 누적 총 $0.0542(약 79원), 예산 남음 421원.

| 지표 | Codex CLI 경유(§4.7) | **raw API 직접(신규)** |
|---|:---:|:---:|
| verdict 일치 | 25/25(100%) | 25/25(100%) |
| **인용 원문 일치** | **15/25(60%)** | **11/25(44%)** |
| 비용 | $0(쿼터), raw 환산 추정 $0.023~$0.140 | **$0.0096(실측, 정확)** |
| 평균 응답시간 | 9.6초/건 | **3.0초/건** |
| 평균 토큰(건당) | 4,675(입출력 합계, 추정) | **prompt 621 + completion 217 = 838**(실측) |
| reasoning_tokens | 미공개(Codex는 합계만 보고) | 평균 78/건(25건 중 22건에서 0 초과, 3건은 0) |

**raw API 실측 비용은 애초 추정 하한($0.023)보다도 낮았다** — Codex CLI가 실제로 훨씬
많은 토큰(건당 평균 4,675 vs raw API 838, **약 5.6배**)을 썼다는 뜻이다. Codex CLI의
`medium` reasoning effort가 raw API 기본값보다 훨씬 무겁게 동작하는 것으로 보인다
(raw API 25건 중 3건은 `reasoning_tokens=0`, 나머지도 대부분 두 자릿수~200 미만 —
§4.1에서 본 `gpt-5-nano`의 수천 토큰짜리 추론과는 규모가 다르다).

**핵심 발견: raw API 경유는 Codex CLI 경유와 품질이 다르다.** 인용 정확도가 60%→44%로
떨어져 **`gpt-4.1-nano`와 정확히 동률**이 됐다 — §4.4에서 확인한 "추론을 많이 쓸수록
인용이 정확해진다"는 패턴이 여기서도 재현된다(Codex CLI의 무거운 추론이 정확도를
끌어올렸을 뿐, raw API 기본 설정의 `gpt-5.6-luna` 자체가 더 정확한 모델은 아니었다).
이것으로 §6 option (C)의 미확인 전제("raw API 응답이 Codex 경유와 같은 품질일지는
별도 확인 필요")가 **아니다로 확인됐다** — raw API로 붙이면 Codex CLI가 보여준 60%가
아니라 44%를 기대해야 하고, 그마저도 `gpt-4.1-nano`보다 **2.8배 비싸고(​$0.0096 vs
$0.0034) 1.5배 느리다**(3.0초 vs 1.9초). 정확도가 동률인데 비용·속도가 둘 다 밀리므로
raw API `gpt-5.6-luna`는 프로덕션 후보에서 **탈락**시킨다.

## 4.9 (후속) 로컬 Gemma4(GGUF)도 같은 25건으로 실측 — 원래 결정이었는데 비교에서 빠져 있었다

비교가 전부 OpenAI 계열끼리만 이뤄져 **원래 후보였던 로컬 모델이 비교표에서 빠져 있었다** —

   원격 프로세스 목록을 직접 확인해 `kill -9`로 잡는 방식으로 고쳤다. **이 결함이 있던
   동안 내려진 "부적격" 판정 일부는 모델 자체 문제가 아니라 오염된 환경 때문이었을 수
   있다** — 실제로 `solar-10.7b`는 좀비 프로세스를 다 정리하고 **완전히 깨끗한 환경에서
   재실행**했더니 처음보다 훨씬 빠르게(15분에 19건) 진행되다가, **case13에서 다시
   독립적으로 멈췄다** — 이건 오염 때문이 아니라 이 모델 자체(또는 이 케이스)의 진짜
   문제라는 뜻이다. `gemma4:12b`·`gemma4:26b`·`qwen3.5:9b`·`kanana-a3b`는 시간 제약상
   깨끗한 환경에서 전부 재검증하지 못했다 — **이 네 모델의 "부적격" 판정은 오염된 조건
   아래에서 내려졌을 가능성을 배제할 수 없다**는 점을 명시해 둔다(재검증하면 결과가
   달라질 수 있음).
2. **로그 파일 tail이 실제 진행 상황보다 지연됐다.** `/workspace`(네트워크 마운트 볼륨)에
   redirect한 로그 파일은 실제 결과가 이미 JSON에 기록된 뒤에도 한참 늦게 나타났다 —
   그래서 진행 상황 확인은 로그 tail이 아니라 결과 JSON 파일의 건수를 직접 세는 방식으로
   바꿨다.

**타임아웃 규칙(사용자 확정, §계획서 4)**: 한 케이스가 15분 넘게 응답 없으면 강제 종료하고
"응답성 부적격"으로 기록 — 응답 지연 자체가 프로덕션에 못 쓴다는 유효한 판단 근거이므로
조용히 건너뛰지 않고 결과로 남긴다.

**결론**: 오늘자 기준으로 찾은 10개 로컬 후보(일반 SOTA급 4 + 한국어 특화 6) 중
**완료된 6종의 최고 인용 정확도는 12%**로, 이 프로젝트가 원래 쓰던 `gemma4:e4b`(40%)를
단 하나도 넘지 못했다 — "더 새롭다"·"한국어 특화"라는 타이틀이 이 태스크(약관 원문
그대로 인용)에서의 실제 성능을 보장하지 않는다는 걸 실측으로 확인했다. 응답성 문제(4종
부적격)까지 감안하면, 로컬 후보 중 지금 프로덕션에 쓸 만한 선택지는 여전히 **`gemma4:e4b`
하나뿐**이다.

## 4.11 (후속) 도메인 인접 파인튜닝 모델 2종 추가 — "10개 다 체크한 거 맞냐"는 지적에 대한 재검색

사용자가 §4.10의 10개가 정말 다 체크한 것인지 되물었다 — 정직하게 답하면 **아니었다**.
원래 10개는 "일반 SOTA급" + "잘 알려진 한국 빅테크 모델" 위주였고, 리서치 중 발견했지만
후보에서 뺀 것(HyperCLOVA X SEED)과 애초에 검색조차 안 한 카테고리(법률 도메인 파인튜닝)가
있었다. 재검색해 2개를 더 찾아 추가로 실측했다.

- **`K-intelligence/Midm-2.0-Base-Instruct`(KT 믿:음 2.0, 11.5B)** — [LegalMidm 논문](https://arxiv.org/abs/2604.25297)이
  이 모델을 베이스로 한국 법률 도메인 특화 파인튜닝을 한 사례라 발견했다. LegalMidm 자체의
  파인튜닝된 가중치 공개 여부는 확인 못 했고(연구 방법론 논문으로 보임), **공개된 베이스
  모델**을 테스트했다.
- **HyperCLOVA X SEED(네이버) 계열** — 원래 리서치에서 찾았지만 최종 10개에서 뺐던 것.
  순정 `HyperCLOVAX-SEED-Text-Instruct-1.5B`는 GGUF 변환이 마땅치 않아(hf.co 직접 pull
  시도 실패, "realm host" 오류), 커뮤니티가 이 계열을 파인튜닝한
  `HyperCLOVA-X-HyperClever-V2`(1.59B, Q8_0 GGUF)로 대체 실측했다 — 순정 SEED가 아니라는
  점은 명시해 둔다.

**보험/법률 도메인 자체에 직접 파인튜닝된 공개 모델**(예: 실손보험 약관 전용)은 재검색으로도
찾지 못했다 — 공개된 게 없는 것으로 보인다.

| 모델 | 분류 | n | 인용 정확도 | verdict 일치 | 평균 응답시간 |
|---|---|---:|:---:|:---:|---:|
| **Midm-2.0-Base-Instruct(KT, 11.5B)** | 법률 도메인 인접 | 25/25 | **16%(4/25)** | 25/25 | 10.2초 |
| HyperClever-V2(HyperCLOVA X SEED 파인튜닝, 1.59B) | 한국어 특화(순정 아님) | 15/25(부분) | 13%(2/15) | 14/15 | 7.7초, case16에서 15분+ 무응답으로 중단 |

`Midm-2.0-Base-Instruct`가 **이번에 테스트한 12개 로컬 모델 전체 중 최고 인용 정확도(16%)를
기록했다** — §4.10의 6종(최고 12%)보다도 낫다. 다만 여전히 `gemma4:e4b`(40%)에는 크게
못 미친다. 법률 도메인 베이스 모델이라는 점을 감안하면 자체 데이터로 이 모델을 추가
파인튜닝(LegalMidm 논문 방법론 참고)했을 때 격차가 좁혀질 가능성은 있으나, 이는 **이번
리포트 범위 밖의 별도 R&D 결정**이다.

## 5. 최종 결론 (n=25 기준 — n=5 결과는 §4.6·§4.7에서 정정됨)

| 구성 | n=25 비용 | 평균 응답시간 | 인용 정확도 |
|---|---:|---:|:---:|
| gpt-5.6-luna(Codex CLI 경유, 프로덕션 불가) | $0(쿼터) | 9.6초 | 60% |
| **gpt-4.1-nano(raw API)** | **$0.0034** | **1.9초** | **44%** |
| gpt-5.6-luna(raw API) | $0.0096 | 3.0초 | 44% |
| gpt-5-nano(추론 끔, raw API) | $0.0036 | 3.1초 | 36% |
| gpt-5-nano(추론 켬, raw API) | $0.0259 | 20.9초 | 32% |

**Codex CLI 경유 luna의 60%는 raw API로는 재현되지 않는다**(§4.8) — raw API 직접 호출
결과는 44%로 `gpt-4.1-nano`와 동률이면서 비용은 2.8배, 응답시간은 1.5배 더 든다.
Codex CLI의 무거운 추론(건당 평균 토큰 4,675, raw API의 5.6배)이 정확도를 끌어올린
것이지 모델 자체의 우위가 아니었다 — §4.4에서 이미 본 "추론량이 인용 정확도를
좌우한다"는 패턴과 일치한다. **실제로 `.env`에 넣어 프로덕션에 쓸 수 있는 구성
중에서는 `gpt-4.1-nano`가 정확도·비용·속도 세 축 모두 1등**이다 — n=5·n=25 양쪽에서
일관됐고, raw API `gpt-5.6-luna`를 새로 넣어 봐도 순위가 바뀌지 않았다. `gpt-5-nano`의
"추론을 켜면 더 정확하다"는 n=5에서만 보였던 착시로 정정됐다 — n=25에서는 추론 켠 쪽이
오히려 근소하게 더 부정확하면서 7배 비싸고 7배 느렸다. `gpt-4o-mini`(현재 프로덕션 모델)는
raw API 구성 중 정확도 최하위(8%)였고, 실패 패턴(원문이 아니라 입력 메타데이터를
인용문으로 재사용)도 이 프로젝트 안전 원칙과 직접 충돌하는 유형이라 재검증 가치가 있다.
**원래 이 프로젝트가 쓰기로 했던 로컬 `gemma4:e4b`(§4.9)도 정확도 40%로 `gpt-4.1-nano`와
거의 동률이고 비용은 0원** — EC2 디스크 제약만 아니면 여전히 유력한 선택지지만, 속도는
`gpt-4.1-nano`의 5배 느리다.

## 6. 다음 결정이 필요한 지점 (사용자 판단 필요)

- (A) `gpt-4.1-nano`로 전환 — **프로덕션에 바로 쓸 수 있는 구성 중 가장 근거가 탄탄한
  선택지.** n=5·n=25 양쪽에서 정확도·비용·속도 전부 1등. 추천.
- (B) 지금은 `gpt-4o-mini` 유지 — 바꾸는 리스크를 피하고 싶다면. 다만 정확도가 raw API
  구성 중 최하위(8%, n=25)라는 게 이번에 확인된 약점이다.
- (C) `gpt-5.6-luna`를 raw API로 프로덕션에 붙이는 안 — **§4.8 실측으로 기각됐다.**
  raw API 직접 호출 시 정확도가 44%로 떨어져(Codex CLI의 60%는 재현 안 됨)
  `gpt-4.1-nano`와 동률이면서 비용은 2.8배($0.0096 vs $0.0034), 응답시간은 1.5배
  (3.0초 vs 1.9초) 더 든다 — 어느 축으로도 (A)를 이기지 못한다.
- (D) `gpt-5-nano`(추론 켬/끔 둘 다) — 이번 결과로는 다른 구성 대비 우위가 없어
  **추천하지 않음**
- (E) 로컬 `gemma4:e4b`로 되돌아가는 안(원래 결정) — §4.9 실측 결과 정확도 40%로
  `gpt-4.1-nano`와 거의 동률, 비용 0원. 다만 **EC2 디스크 8GB 제약이 여전히 유효**해
  지금 구조로는 EC2에 못 올린다 — x600처럼 별도 GPU 호스트에서 서빙하도록 아키텍처를
  바꾸거나 EC2 볼륨을 늘리는 결정이 먼저 필요하고, 속도도 5배 느리다(9.7초 vs 1.9초).
  **인프라 결정이 선행돼야 하는 안이라 이번엔 채택하지 않음.**
- (F) 오늘자 SOTA급/한국어 특화 로컬 모델로 교체 — **§4.10·§4.11 실측으로 기각됐다.**
  12종(10종 + 재검색 2종) 전부 테스트한 결과 최고 인용 정확도가 `Midm-2.0-Base-Instruct`
  (KT, 법률 도메인 인접 베이스)의 16%로, `gemma4:e4b`(40%)에 크게 못 미쳤다. 6종은
  응답성 자체가 부적격(15분+ 무응답)이었다. "더 새롭다"·"한국어 특화"·"법률 도메인
  베이스"가 이 태스크에서의 실제 성능을 보장하지 않음을 확인 — 로컬 후보를 쓴다면
  여전히 `gemma4:e4b`가 유일한 선택지다.
