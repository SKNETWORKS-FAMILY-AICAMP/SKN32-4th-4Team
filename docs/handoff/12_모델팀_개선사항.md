## 1. 먼저 — 잘한 것

점검 결과가 모두 수정 요구인 것은 아니다. 유지해야 할 설계와 검증 태도가 분명하다.

- `rag_config.py`를 단일 출처로 둔 것이 좋다. 모델·경로·접두사가 한 파일에만 있고 나머지가
  참조하므로 모델 교체는 한 줄 변경으로 끝난다.
- 모델 선정(`2_model_select/`)·확정(`rag_config.py`)·사용을 분리했다. 실험 코드와 운영 설정이
  뒤섞이지 않는다.
- **README 수치는 원본 CSV에서 정확히 재현된다.** `embedding/results/*.csv` 480행을 직접
  재계산한 결과, 6모델 모두 hit@5·hit@1·MRR이 README 값과 일치했다.
- 결론의 한계를 스스로 기록했다. README에는 소표본으로 결론 내리지 말 것이라는 경고와 함께
  8→12→18문항까지 선두가 계속 바뀐 사실, 유료 API가 당연히 낫다는 가정이 실측으로
  반박된 사실, 알려진 이슈 5건이 열려 있다.
- 법령 인용 오탐과 DB손보 PUA 원문자 결함을 우리와 독립적으로 발견해 고쳤다. 서로 다른
  코드베이스가 같은 문제에 부딪혔다는 상호 검증이다.
- `manifest_to_documents.py`의
  `INSURER_NORM = {'samsunglife': '삼성생명'}`은 우리가 `insurer` 테이블을 근거로 정리한
  문제를 이미 잡아 둔 것이다.
- 중복을 질의 시점에 접는 함수의 존재 자체도 설계가 맞았다는 신호다. 중복이 있다는 사실을
  외면하지 않고 검색 결과에서 제어하고 있다. 키 선택만 더 안전하게 바꾸면 된다.

## 3. 구현 점검 결과

### 3-1. [P0 즉시] PUA 원문자 매핑이 ⑩부터 틀렸다

`preprocessing/clause_detector.py:124`:

```python
_PUA_CIRCLED = {chr(0xF02B1 + i): '①②③④⑤⑥⑦⑧⑨⑩⑪⑫⑬⑭⑮⑯⑰⑱⑲⑳'[i]
                for i in range(20)}
```

이 코드는 `U+F02B1+i`를 `i+1`번째 원문자로 산술 확장한다. 그러나 우리
`data/extracted/*/s4_*` 전량에서는 ⑩·⑪이 한 글리프가 아니었다.

- `U+F02BA`는 1,207회 / 118문서에 나오며 뒤 문자가 1,207회 전부 `\n`이다. 항상 단독 줄이다.
- 표본 60문서의 동시출현 조합은 `(F02BA, F02C3)` 31문서,
  `(F02BA, F02C3, F02C4)` 29문서다. 60문서 전부 `F02BA`와 `F02C3`가 함께 나온다.
- 실제 텍스트는 다음과 같다.

```text
… 위 ⑦의 청약일로 하여 적용합니다.
󰊺
󰋃 피보험자가 단체실손의료보험의 …
```

`󰊺`는 `U+F02BA`, `󰋃`는 `U+F02C3`다. 즉 **⑩은 `U+F02BA + U+F02C3`**,
**⑪은 `U+F02BA + U+F02C4`**로 두 글리프가 겹쳐 그려진다.

| 원본 | 코드 결과 | 실제 |
|---|---|---|
| `U+F02BA` | ⑩ | ⑩의 앞 글리프 |
| `U+F02C3` | **⑲** | ⑩의 뒤 글리프 |
| `U+F02C4` | **⑳** | ⑪의 뒤 글리프 |

정규화 뒤에는 `⑩\n⑲ 피보험자가…`가 된다. `preprocessing/clause_detector.py:102`의
`RE_HANG.match(s)`가 줄머리 ⑲를 항 헤더로 잡아 **없는 제19항을 만들고 본문을 붙인다.**
제10항은 1글자 빈 청크가 된다.

영향 범위는 `U+F02C3` 510회 / 118문서, `U+F02C4` 423회 / 63문서다. 118문서 전량
DB손보다. DB손보가 그쪽 4개사 색인에 포함됐다는 판단은 앞서 밝힌 README 서술에 근거하며,
파일 목록으로는 확인하지 않았다.

**권고:** 1~9만 매핑한다. 10 이상은 변환하지 말고 **남은 값을 세어 기록한다.** 우리 `v5`의
`unresolved_paragraphs`는 전량 3,340건이다. 못 읽은 번호를 남기는 편이 제19항을 지어내는
것보다 안전하다. 이는 [CLAUDE.md](../../CLAUDE.md) 0장의 원칙과 같다.

### 3-2. [P1 다음 재색인 전] 형식 투표가 오탐 필터보다 먼저 일어난다

`preprocessing/clause_detector.py:231-237`:

```python
if doc_style == 'auto':
    style = 'jo' if len(raw_jo) >= len(raw_num) else 'num'   # 오탐 포함 원시 카운트
raw = raw_jo if style == 'jo' else raw_num
accepted, rejected = _filter_sequence(raw)                   # 필터는 그 다음
```

관계법령 부록의 `제N조` 인용이 `raw_jo`에 들어간 상태로 형식 투표를 한다. 인용이 실제
`N.` 헤더보다 많으면 형식을 잘못 고른다.

우리 `v3`도 같은 계열의 결함으로 산출물 35%가 손상됐다
([`2026-08-02_전처리_v4_중간리포트.md`](../reports/2026-08-02_전처리_v4_중간리포트.md) §2).
당시 로직은 `제N조`가 0개일 때만 `N.`으로 넘어갔다. 해당 문서의 줄머리 `제N조` 8개는
전부 법령 인용이었고, 실제 조항은 `1. (제목)` 꼴로 93개였다.

feature-ai1 산출물에서 이 순서 때문에 손상된 문서 수는 **미측정**이다.

**권고:** 두 후보를 각각 필터링한 뒤 비교한다. 점수 차가 작으면 `ambiguous`로 표시해 자동
판정에서 뺀다. 현재 `stats`에는 `style`은 있지만 확신도가 없다.

### 3-3. [P1 다음 재색인 전] 낮은 번호 법령 인용은 시퀀스 필터를 항상 통과한다

`preprocessing/clause_detector.py:261-266`:

```python
if n <= prev:                      # 리셋/동일(특약 경계 등) → 허용
    accepted.append(h); prev = n
elif n - prev <= max_jump:
    ...
else:                              # 큰 점프 → 인용 오탐
    rejected += 1
```

`상법 제651조`처럼 높은 번호는 걸러질 수 있지만, 줄바꿈으로 줄머리에 온
`「의료법」 제3조(의료기관)에서 규정한…` 같은 낮은 번호는 특약 리셋으로 간주돼 통과한다.
우리 `v3`에서 실제로 발생한 사례가 위 중간리포트 §2의 사례다.

`max_jump=15`와 `abs_cap=150`도 고정 임계값이다. [CLAUDE.md](../../CLAUDE.md) 3장의
“딱 떨어지는 숫자는 프로토콜을 의심한다”와 위 중간리포트 §6의 “고정 창·고정 임계값으로
판단했다 — 둘 다 실제 문서에서 무너졌다”는 기록을 다시 적용할 지점이다. feature-ai1에서
낮은 번호 인용이 통과한 개수는 **미측정**이다.

**권고:** 버리지 말고 `statute=true`로 표시해 분리한다. 우리 `v5`에서는 전량 33,257개,
조항의 15.8%가 이렇게 갈렸다. `[법규5] 상법`, `인용법·규정`, `○ 개인정보보호법`처럼
문서가 스스로 표시한 경계를 읽는 방식이다
([`2026-08-02_1000_전처리_v5_2단계_항호청킹_결과.md`](../reports/2026-08-02_1000_전처리_v5_2단계_항호청킹_결과.md) §4).
버리면 무엇을 왜 버렸는지 셀 수 없다.

### 3-4. [P1 다음 재색인 전] 평가셋의 30%가 변별력이 없다

`embedding/2_model_select/gen_questions.py`가 문항을 자동 생성하고,
`embedding/2_model_select/embed_eval.py:79`의 `match()`가 `text_contains`, 즉 키워드 포함으로
정답을 판정한다.

원본 CSV 480행을 재집계한 e5-large의 유형별 결과는 다음과 같다.

| 유형 | 문항 | hit@5 | hit@1 |
|---|---:|---:|---:|
| 필터교차 | 16 | 100% | 100% |
| 필터교차2중 | 8 | 100% | 100% |
| 구어체 | 36 | 92% | 72% |
| 조항지정 | 15 | 87% | 53% |
| 표숫자 | 5 | 80% | 20% |

필터교차 계열 24문항, 전체의 30%는 6모델 중 5모델이 만점이다. 예외는
openai-3-small의 14/16, ko-sroberta의 6/8이다. 메타필터가 `insurer`와 `generation`을
이미 보장하고, 생성기가 정답 후보 3개 이상을 확인한 뒤 만든 문항이라 구조적으로 틀리기 어렵다.

24문항을 뺀 56문항 기준 재계산 결과다.

```text
e5-large     92% → 89%       bge-m3   90% → 86%
ko-sroberta  85% → 82%       openai   85% → 82%
kure-v1      86% → 80%       qwen3    82% → 75%
```

**e5-large 1위는 바뀌지 않는다. 모델 선정 결론은 견고하다.** 다만 kure-v1은 3위에서
5위로 내려가므로 순위표는 정정해야 한다.

**권고:** 정답 판정을 키워드 포함이 아니라 특정 `chunk_id` 일치로 바꾼다. “그 낱말이
들어 있는가”가 아니라 “그 조항을 찾았는가”를 재야 한다. 검색 지표 계약은
[`10_계약_모델_평가.md`](10_계약_모델_평가.md) §1을 따른다.

### 3-5. [P2 개선] 평가 조건 두 가지

#### 평가 코퍼스 규모

평가 코퍼스는 1,433청크인데 실제 색인은 231,270청크로 160배다. README는 문항 수의
소표본 위험은 경고하지만 코퍼스 규모 차이는 언급하지 않는다. 1,433개 중 top-5와
231,270개 중 top-5는 난이도가 다르다.

#### 모델 고유 입력 형식

`embedding/2_model_select/embed_eval.py:52-59`는 e5에 `query:`와 `passage:` 접두사를
붙인다. 올바른 처리다. 반면 `Qwen/Qwen3-Embedding-0.6B`는 쿼리의 권장 instruction
프리픽스를 붙이지 않았다(`embedding/2_model_select/embed_eval.py:63-67`). 따라서 qwen3의
hit@1 51%는 과소평가됐을 **가능성**이 있다. 확정된 결론이 아니며 영향 폭은 **미측정**이다.

**권고:** 실제 231,270청크 조건에서 다시 비교하고, qwen3는 권장 instruction 적용 여부를
구분해 결과를 기록한다.

### 3-6. [P2 개선] 중복 접기 키가 앞 15자다

`embedding/rag_config.py:67-70`:

```python
raw = (m.get("term") or d[:50]).replace(" ", "")
key = (raw[:15], m["insurer"], m["generation"])
if key in seen: continue
```

약관 조항은 서두가 같은 경우가 많다. 앞 15자만 같아도 같은 보험사·세대 안에서 서로 다른
조항이 함께 접힐 수 있다. 실제로 잘못 접힌 조항 수는 **미측정**이다.

다만 이 함수의 존재 자체는 **설계가 맞았다는 신호**다. 우리 `v5` 실측에서 조 단위 내용
중복은 **66.5%**(고유 68,431 / 204,098 · **s6**), 항 단위 중복은 84.4%(s5 측정)다. Chroma는 “내용 1벌 + 수록
N벌” 구조를 만들지 못하므로 질의 시점에 접은 선택은 도구 제약상 합리적이다. 틀린 설계가
아니라 트레이드오프다.

**권고:** 접기 키만 내용 해시로 바꾼다.

### 4-1. [P1 다음 재색인 전] 전처리가 두 벌이다

```text

                                   │     1,367문서 · 조항 204,098 · 항 547,738 · 호 434,484  (s6)
                                   └─→ preprocessing/ (feature-ai1)
                                         chunks_main.jsonl
                                         4개사 · 231,270청크
```

같은 PDF를 서로 다른 코드가 각각 조항으로 자른다. 어느 쪽을 정본으로 둘지는 아직 팀이
결정하지 않았다.

선택지는 전처리를 하나로 합치거나, 두 벌을 유지하되 각 산출물의 용도·계보·정본을 명시하는
것이다. **이 문서는 어느 쪽으로 결정하지 않는다.** 다만 다음 재색인 전에 입력이 어느
전처리에서 왔는지는 고정해야 한다.

### 4-2. [P1 다음 재색인 전] v5에는 있고 그쪽에는 없는 정직성 신호

| 신호 | 우리 v5 실측 | 없으면 |
|---|---|---|
| `statute` | 33,257개 (조항의 15.8%) | `상법 제651조`가 `단체취급 특별약관 제651조`로 인용된다 |
| `paragraph_no_ambiguous` | **8,554개 (조항의 4.2% · s6)** | 한 조에서 항 번호가 재시작해도 확정값처럼 보인다 |
| `unresolved_paragraphs` | 3,340개 | 못 읽은 항 번호를 지어내게 된다 |

이 필드들은 파싱 실패를 감추지 않고 다음 단계에 전달하는 감사 신호다. feature-ai1에서 같은
상태를 별도로 기록한 개수는 **미측정**이다. 재색인 전에 동등한 신호를 메타데이터에 남겨야
한다.

### 4-3. [P1 다음 재색인 전] `citation` 문자열은 식별자가 아니다

우리 `v5` 전량 중 법령 원문 33,257개를 제외한 약관 조항 177,874개를 기준으로 문서 내
충돌을 셌다.

| 식별키 | 충돌 | 영향 문서 |
|---|---:|---:|
| `citation` (`제4조(보상하지 않는 사항)`) | 46,540 | 1,210 (88%) |
| `qualified_no` | 47,362 | 1,201 |
| `section` + `citation` | 24,816 | 1,192 |
| `content_hash` | 3,578 | 544 (40%) |
| `ordinal` | 0 | 0 |

특약마다 조 번호가 1부터 다시 시작하므로 제목을 붙여도 88% 문서에서 겹친다. 그쪽
`chunk_id`에는 `#00042` 같은 일련번호가 있어 **검색 자체는 이미 유일하다.** 문제는 사용자에게
보이는 출처 표기와 LLM이 인용을 되짚는 경로다.

식별자 계약과 주의사항은 이미 [`10_계약_모델_평가.md`](10_계약_모델_평가.md) §2-3에
적혀 있다. 여기서는 반복하지 않는다.

### 4-4. [P1 다음 재색인 전] 항을 별도 행으로 빼지 말 것

우리 `v5` 실측은 다음과 같다.

| | 조 단위 | 항 단위 |
|---|---:|---:|
| 단위 수 | 204,098 | 547,738 |
| 길이 중앙 | 356자 | **127자** |
| p95 | 2,851자 | 656자 |
| 900자 초과 | 22.2% | 2.9% |
| 내용 중복률 | 65.4% | 84.4% |

면책(`exclude`)과 예외(`exception`)를 함께 담은 조항 1,257개 중 432개, 34.4%는 항 경계로
자르면 서로 다른 항으로 갈린다. 고유 약관 조항 64,400을 기준으로
`app/core/domain/kcd_ranges.scan_clause`를 `v5`의 실제 `paragraphs[]` 경계에 적용해 측정했다.

면책 항만 검색되고 `다만 ~는 보상합니다`가 따라오지 않으면 시스템은 “보장 안 됩니다”라고
답할 수 있다. [CLAUDE.md](../../CLAUDE.md) 0장이 막으려는 사고다.

**권고 청킹:** 항 경계에 정렬해 900자까지 묶고 조 머리를 붙여 임베딩한다. 고유 약관 조항
64,400 기준 우리 추산은 154,874행 · 중앙 774자 · p95 900자다(s5 때 낸 추산).
항 낱개는 **s6 기준 547,738행**이고 중앙 127자라 문맥이 부족하며, 조 고정분할은 의미 경계와 무관하다.
★추산 154,874 는 s5 분모로 낸 것이라 s6 로 다시 내야 한다 — 아직 안 했다.
