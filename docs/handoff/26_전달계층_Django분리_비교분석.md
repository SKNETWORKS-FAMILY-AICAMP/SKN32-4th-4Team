## 0. 한 문단 요약

Django 를 **말단 전달 계층(BFF)** 으로만 두고 코어는 FastAPI 그대로 두는 형상을 만들어
**세 기계에서** 실측했다. 홉 하나가 붙는 **고정비는 1.4~3.8ms** 이고,
**실제 판정 경로에서는 +0.9~1.8ms(+2.7~9.1%)** 다 — 사전 기준(10%) 안이다.

★**성능은 이 결정의 근거가 되지 못한다.** 결정은 **무엇을 얻느냐**로 해야 한다 —
세션 보안, 화면·템플릿, Admin.

★**keep-alive 는 플랫폼 문제다** — Linux 루프백 두 대에서는 **끈 쪽이 오히려 빨랐고**
(RTT·TLS 가 없어 연결 비용이 거의 0이라 풀 관리 비용이 더 크다), Windows 에서만
**끄면 6.4배** 느려졌다. 배포 형상(다른 호스트·TLS)이 정해지면 다시 재야 한다.

## 1. ★먼저 — 무엇을 만들었나 (엔드포인트 포팅이 아니다)

처음 계획(v1)은 **엔드포인트를 Django 로 옮기는** 것이었다. 그 계획은 **폐기했다.**
그대로 했으면 FastAPI 가 공짜로 주던 것(pydantic 검증, `response_model` 직렬화, OpenAPI)을
Django 쪽에 **다시 구현**해야 했고, 그 순간 **판정 규약이 두 벌**이 된다.
두 벌이 되면 반드시 어긋나고, 어긋나면 「보장됩니다」를 잘못 말한다(`CLAUDE.md` §0).

지금 형상:

```
브라우저 ──→ Django (전달 계층)  ──→ FastAPI (코어: 검증·판정·검색·인용)
              세션·CSRF·화면            ★같은 프로세스, 같은 코드, 그대로
```

Django 가 하는 일은 **전송 계층의 것뿐**이다:

| 한다 | 절대 안 한다 |
|---|---|
| 세션(HttpOnly 쿠키) · CSRF · 기본 보안 헤더 | 스키마 검증 · 응답 직렬화 |
| 화면 · 정적 자산 · 로그인 흐름 | 도메인 오류 본문 생성 |
| FastAPI 로 **가공 없이** 전달 | 판정 · AI · 검색 |
| `X-Trace-ID` 승계/발급 | `app.core`/`app.workflow`/`app.routers` import |

마지막 줄은 말로만 두지 않고 **AST 검사 테스트**로 고정했다
(`tests/delivery/test_django_import_boundary.py`).

★데이터 스냅샷 지문이 로컬과 **일치**한다(`a20ff3fcc8b450d4…` · 1,355문서) — 값으로 증명된다.

|---|---:|---:|---:|---:|---:|

### 2-5. ★판정 경로 12배 차이 — **네트워크 파일시스템이었다**

| 기계 | 파일시스템 | Python | CPU | 판정 L0 p50 |
|---|---|---|---|---:|
| RunPod | ★**네트워크 FS**(MooseFS `/workspace`) | 3.12 | 128코어 서버 | **253.5 ms** |
| x600 | 로컬 | 3.14 | 12코어 데스크톱 | 20.1 ms |
| 3차 기계 | **로컬 RAID**(`/dev/md0`) | 3.12 | 56코어 서버 | **35.1 ms** |

3차 기계는 RunPod 과 **OS·Python·서버 구성·CPU 종류가 같고 파일시스템만 다르다.**
**253.5 → 35.1 ms, 7.2배.** 로컬 디스크 두 대(20.1 · 35.1)가 같은 자릿수로 모인다.

★**RunPod 의 253ms 는 판정 로직이 아니라 네트워크 FS 지연이었다.**
  그 분모로 낸 「전달 비용이 ±5.3% 로 묻힌다」는 **부풀려진 바닥 위의 수치**다.
  ★단 CPU 도 다르므로(128코어 vs 56코어) FS 가 **유일한** 원인이라고 단정하지는 않는다.
  두 로컬 기계가 모이는 것이 근거다.

## 3. 프레임워크 장단점 — 이 구조에서 실제로 확인된 것

### 3-1. FastAPI 가 코어에 남아야 하는 이유

| | 무엇 | 왜 이 프로젝트에 중요한가 |
|---|---|---|
| ★ | **pydantic 스키마 검증** | 판정 입력이 규약대로인지 **한 곳**에서 본다. 두 벌이 되면 어긋난다 |
| ★ | **`response_model` 직렬화** | 판정 결과의 필드(`verdict`·`reason_code`·`citations`)가 계약대로 나간다 |
| | **OpenAPI 자동 생성** | 프론트·에이전트·MCP 가 같은 문서를 본다 |
| | **async 네이티브** | 검색·LLM 호출이 I/O 대기다 |
| | 의존성 주입 | `app/composition.py` 조립이 라우터와 분리된다 |

### 3-2. Django 가 전달 계층에서 주는 것

| | 무엇 | 대안 대비 |
|---|---|---|
| ★ | **세션 + HttpOnly 쿠키** | FastAPI 에서 직접 만들면 세션 저장소·만료·회전을 손으로 짠다 |
| ★ | **CSRF 기본 제공** | 미들웨어 한 줄. 단 **토큰 발급 경로를 열어야 한다**(§5 ③) |
| | 템플릿 · 정적 자산 | 화면이 늘면 이득이 커진다 |
| | **Admin** | 모델 하나 붙이면 운영 화면이 공짜. ★**아직 POC 안 함 — 실증되지 않은 이득이다** |
| | 성숙한 배포 관행 | `check --deploy` · `collectstatic` |

### 3-3. 대가

| | 무엇 | 크기 |
|---|---|---|
| | 홉 하나 고정비 | **1.4~3.8ms** — 판정 경로 대비 **±5%(RunPod) ~ +9~15%(x600)**. §2-4 |
| | 프로세스·배포 대상 +1 | 컨테이너 1개, 헬스체크 1개 |
| ★ | **CSRF 가 비브라우저 클라이언트를 막는다** | 부하 도구·curl·모바일이 토큰을 먼저 받아야 한다 |
| ★ | **업로드 경로가 따로 깨진다** | §5 ④⑤ |
| | 설정 이원화 위험 | `ALLOWED_HOSTS` 를 `DELIVERY_DJANGO_BASE_URL` 에서 **파생**시켜 막았다 |

## 4. ★WSGI vs ASGI — 가설이 반증됐고 이유가 코드에 있다

계획서 H3 은 *keep-alive 유무가 WSGI/ASGI 선택보다 영향이 크다* 였다.
**세 기계로 보니 「플랫폼에 달렸다」가 답이다.**

`GET /_bench/noop` p50 기준:

| 비교 | RunPod (Linux) | 3차 기계 (Linux) | x600 (Windows) |
|---|---:|---:|---:|
| WSGI ↔ ASGI | ASGI **+0.70 ms** 느림 | ASGI **+1.53 ms** 느림 | ASGI **+0.64 ms** 느림 |
| keep-alive 켬 ↔ 끔 | 끈 쪽 **0.35 ms 빠름** | 끈 쪽 **0.31 ms 빠름** | ★끈 쪽 **12.7 ms 느림** |

★**Linux 두 대가 일치한다** — 루프백에는 RTT 도 TLS 도 없어 연결 비용이 거의 0이고,
  커넥션 풀 관리 비용이 그보다 크다. **Windows 만 반대다.**

**① ASGI 가 느린 것은 두 기계에서 일관된다.** 계획서는 L1-b 를 *ASGI + async HTTP
클라이언트* 로 정의했는데, 지금 패스스루 뷰는 **동기**이고 동기 `httpx.Client` 를 쓴다.
Django ASGI 는 동기 뷰를 **스레드풀로 넘긴다** — async 이득 없이 왕복만 하나 는다.
★**가설이 아직 없는 구현을 전제했다.** 진짜 ASGI 이득을 보려면 뷰를 async 로 다시 써야 한다.

**② ★keep-alive 는 플랫폼 문제다.**

- **Linux 루프백(2대 일치)**: 끈 쪽이 0.3ms 빠르다. 연결 비용이 거의 0이라 풀 관리가 손해다.
- **Windows**: 끄면 판정 경로가 20.1 → 44.4ms 로 **2.2배**. 전달 비용(1.4ms)의 15배다.

★**여기서 내가 두 번 틀렸다.** RunPod 만 보고 「W7 은 쓸모없다」로 읽을 뻔했고,
  x600 만 보고 「반드시 켜 둔다」로 고쳤다. **둘 다 표본 1개짜리 결론이었다.**

### 권고

- **지금 형상(같은 호스트 루프백·Linux)에서는 keep-alive 가 이득이 아니다.**
  ★그러나 **끄지 않는다** — 이 측정이 덮지 못하는 형상(다른 호스트·TLS·Windows)에서는
  지배적 요인이 되고, 켜 두는 쪽이 그 모든 경우에 안전하다. **최악을 기준으로 고른다.**
- WSGI 로 간다. ASGI 는 세 기계 모두에서 느리다(+0.64~1.53ms) —
  패스스루 뷰가 **동기**라 Django ASGI 가 스레드풀로 넘기기 때문이다.
  **뷰를 async 로 바꾼 뒤에** 다시 잰다.

## 4-2. ★H4 — 커넥션 풀 부재가 전달 계층 비용보다 **23배** 크다

계획서 H4: *"커넥션 풀 부재(psycopg)가 전달 계층 비용보다 큰 개선 여지를 갖는다."*
**성립한다. 그것도 크게.**

3차 기계 · PostgreSQL 16 + pgvector 0.6.0 · `GET /v1/cohorts`(PG 읽기) · 동시성1 · 회차5

| 구성 | p50 ms | p50 CI95 | p95 ms | rps |
|---|---:|---|---:|---:|
| 커넥션 풀 있음(기준) | **9.323** | [7.85, 9.55] | 12.745 | 112.2 |
| ★**풀 없음**(직접 연결) | **30.891** | [29.75, 31.30] | 39.171 | 32.2 |

**풀 부재의 대가: +21.6 ms (+231%)** — 구간이 겹치지 않는다.

| 비교 | 크기 |
|---|---:|
| 전달 계층 홉 하나 (판정 경로) | +0.94 ms |
| **커넥션 풀 부재** | **+21.6 ms** |

★**23배다.** 성능을 논한다면 **전달 계층이 아니라 여기를 봐야 한다.**

### 대조군을 어떻게 만들었나 (★코어 코드를 고치지 않았다)

`db/postgres/pool.py` 는 `psycopg_pool` import 가 실패하면 **직접 연결로 폴백**하도록
이미 돼 있다. 그 **기존 경로**를 그대로 타게 하려고 `psycopg_pool` 만 뺀 두 번째 venv 를 썼다.
측정을 위해 제품 코드에 스위치를 넣지 않았다.

★**함정 하나**: 복사한 venv 의 `pip` 은 shebang 이 **원본 venv 의 python** 을 가리킨다
(`#!/workspace/bench/.venv/bin/python3`). 그래서 `.venv_nopool/bin/pip uninstall` 이
**기준군을 지웠다.** `python -m pip` 으로 바꿔 고쳤고, 두 venv 의 `pool_status()` 를
각각 확인해(True / False) 대조가 실제로 성립하는지 값으로 검증했다.

### 이 수치가 말하지 않는 것

- **동시성 1 이다.** 동시성이 오르면 풀의 이득은 더 커진다(연결 수립이 직렬화된다).
- `/v1/cohorts` 는 **테이블이 비어 있다**(n=0). 쿼리 자체가 가벼워
  **연결 비용이 두드러지는** 조건이다 — 무거운 쿼리라면 비율은 낮아진다.
  ★그러나 **절대값 +21.6ms 는 쿼리 무게와 무관한 고정비**다.
- 이 기계는 PostgreSQL 이 **같은 호스트**에 있다. 원격 DB 면 연결 비용이 더 커진다.

## 5. ★실제로 밟은 함정 — 이걸 모르면 같은 데서 넘어진다

전달 계층은 **단위 테스트 38건이 전부 통과하는 상태에서 모든 요청이 실패**하고 있었다.
`RequestFactory`·`django.test.Client` 는 WSGI 환경을 **흉내만 내기** 때문이다.

| | 증상 | 원인 | 소켓 없이 보이나 |
|---|---|---|---|
| ① | 기동 불가 | `ALLOWED_HOSTS` 빈 목록 | ✗ |
| ② | **모든 요청 500** | `Content-Length` 를 그대로 전달 → `LocalProtocolError` | ✗ |
| ③ | **모든 POST 403** | CSRF 토큰 **쿠키를 아무도 발급 안 함** → 토큰을 얻을 방법이 없다 | ✗ |
| ④ | **모든 업로드 500** | CSRF 검사가 multipart 스트림을 먼저 소비 → `RawPostDataException` | ✗ (JSON POST 는 멀쩡) |
| ⑤ | 업로드 상한이 업스트림보다 낮음 | Django 기본 2.5MB < 앱 8~16MB | ✗ |
| ⑥ | 미들웨어가 붙인 헤더 증발 | `items()` 가 업스트림 헤더만 반환 | ✗ (잠복) |

→ [디버그 리포트](../reports/debugs/2026-08-26_전달계층_소켓없이는_안_보이는_결함2종.md)
→ 회귀 테스트 `tests/delivery/test_real_socket_passthrough.py`
  (가짜 업스트림과 Django 를 **실제 소켓**에 띄운다. 고친 것을 되돌려 실패까지 확인했다)

★⑤ 는 성격이 다르다. 전달 계층이 업스트림보다 **엄격한 문지기**가 되면
**도메인이 낸 적 없는 거절**이 사용자에게 간다. 판정 로직은 그런 판단을 한 적이 없는데
사용자에게는 「서비스가 거부했다」로 보인다 — `CLAUDE.md` §0 이 뒤집히는 자리다.

★**교훈 둘**:
1. 전달 계층은 **소켓을 열어야만** 검증된다.
2. **경로마다 본문 종류가 다르면 다른 시험**이다 — P3 통과 검증 5사례(전부 JSON·빈 본문)를
   통과하고도 업로드는 100% 깨져 있었다.

## 6. 배포 형상 — 세 가지와 권고

| | 형상 | 프로세스 | 인증 권위 | 판단 |
|---|---|---|---|---|
| **A** | FastAPI 단독 (현행) | 1 | localStorage JWT | 지금 동작. 세션 보안 약함 |
| **B** | **Django BFF → FastAPI** | +1 | **세션 쿠키 ↔ 서버측 토큰** | ★**권고.** 실무 BFF 표준 |
| **C** | 엣지 프록시가 경로로 가름 | +0 | 애매 — 누가 세션을 쥐나 | 단독으로는 부족. **B 와 조합** 가능 |

### 6-1. B 를 권고하는 이유

성능이 아니다(§2 에서 차이 없음이 확인됐다). **얻는 것** 때문이다:

1. **세션이 HttpOnly 쿠키로 간다** — XSS 노출면이 준다
2. **CSRF 보호가 붙는다**
3. 화면·Admin 이 Django 관행 위에 선다

★단, ①은 **지금 제품 화면에는 해당되지 않는다**(§9 ① 참조). 그래서 B 의 실익은
**앞으로 로그인이 붙을 때** 생긴다.

### 6-2. 되돌릴 수 있어야 한다

`DELIVERY_MODE=direct|django` 하나로 A ↔ B 를 오간다.
★**알 수 없는 값이면 기동이 실패한다** — 조용히 direct 로 떨어지지 않는다.
설치도 분리했다(`requirements/delivery.txt` 는 루트 집계에 없다) — FastAPI 단독으로
돌리는 사람에게 Django 를 강요하지 않는다.

### 6-3. ★아직 안 한 것

- Dockerfile + compose (FastAPI · Django · 엣지 프록시)
- `fastapi[standard]` 추가 후 `fastapi run` 표준화 / Django `collectstatic` · `check --deploy`
- **Django Admin POC** — 모델 1개. ★§3-2 에서 Admin 을 이득으로 적었는데 **아직 실증 안 했다**
- 리버스 프록시 뒤의 `ALLOWED_HOSTS` — 지금은 `DELIVERY_DJANGO_BASE_URL` 에서 파생하므로
  **공개 도메인 뒤에 두면 400 이 난다.** 배포 형상이 정해질 때 명시 목록이 필요하다

## 9. 결론과 다음 결정

**결론**: 전달 계층 분리의 대가는 **홉 하나에 1.4~3.8ms**,
**실제 판정 경로에서는 +0.9~1.8ms** 다.

| 기계 | 판정 L0 p50 | 전달 비용 | 상대 |
|---|---:|---:|---:|
| 3차 기계 (Linux · 로컬 RAID) | 35.1 ms | +0.94 ms | **+2.7%** |
| x600 (Windows · 로컬) | 20.1 ms | +1.82 ms | **+9.1%** |
| RunPod (Linux · 네트워크 FS) | 253.5 ms | −13.3 ms | −5.3% |

세 기계 모두 사전 기준(10%) 안이다. **성능은 이 결정의 근거가 되지 못한다.**
결정은 얻는 것(세션 보안·화면·Admin)으로 한다.

★**단서**: 분모가 작을수록 비율은 커진다. 판정 경로를 앞으로 더 빠르게 만들면
  전달 비용의 비중은 올라간다 — 그때 다시 재야 한다.
