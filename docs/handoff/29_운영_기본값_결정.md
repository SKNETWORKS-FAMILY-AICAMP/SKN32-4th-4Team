# 29. 운영 기본값 — 무엇을 어디에 두나 (결정)

**결정일** 2026-08-27 · **결정** DB 담당(사용자 위임) · **대상** `AUTH`·`OPS`·`PRECHECK`·`OUTCOME` persistence, `CLAUSE_STORE`

전제 자료: [PostgreSQL 런타임 운영성 재점검](../reports/2026-08-24_postgresql_런타임_운영성_재점검.md) §우선순위 1

---

## 결정 1 — **코드 기본값은 바꾸지 않는다** (dev 친화 유지)

```
AUTH_PERSISTENCE=sqlite · OPS_PERSISTENCE=sqlite
PRECHECK_PERSISTENCE=off · OUTCOME_PERSISTENCE=file
CLAUSE_STORE=file
```

### 왜

기본값을 `postgres`/`pg` 로 바꾸면 **PostgreSQL 이 없는 사람은 앱이 아예 안 뜬다.**
지금 이 저장소는 팀 다섯이 각자 기계에서 돌린다. 기본값은 「아무 준비 없이도 도는 값」이어야 한다.

★그리고 재점검 보고서의 1순위도 「코드 기본값을 바꾸라」가 아니라
**「production 환경에서 명시하라」**다. 그 말이 맞다 —
운영 설정은 **배포가 정하는 것**이지 소스가 정할 일이 아니다.

### 대신 하는 것

- 운영 설정은 `.env.example` 의 주석 블록이 **그대로 정본**이다.
- 그 값이 진짜 준비됐는지는 `GET /readyz`(`check_readiness()`)가 판정한다.

---

## 결정 2 — ☠**`PRECHECK_PERSISTENCE=postgres` 는 아직 켜지 않는다** (2026-08-27 재확인 — 원인이 하나 더 있다)

★★**2026-08-27 갱신** — KCD 마스터는 그 뒤 실제로 구해서 x600 DB에 적재했다
(`core.kcd_code` 40,513행). 그런데 **켜서 실측해 보니 여전히 안 된다** — 실제
약관이 매칭되는 판정은 전부 503이다. 원인이 하나 더 있었다:

```
core.kcd_code       = 40,513   (적재 완료)
core.policy_version =      0
core.policy_clause  =      0
core.product        =      0
```

`resolve_policy_reference`/`resolve_clause_reference` 가 이 표들을 찾는데
전부 0행이다. KCD 사전은 막힌 배선 셋 중 하나였을 뿐이고([DB4 승인요청
문서](28_DB4_core원장_적재_승인요청.html)가 이미 이 배선들을 적어 뒀다),
**`core` 를 확정 원장(`confirmed_documents.jsonl`)에서 채우는 적재
파이프라인 자체가 아직 없다** — KCD처럼 "자료를 못 구해서"가 아니라
스크립트가 없다. x600에서 켰다가 되돌렸다 →
[실측 리포트](../reports/debugs/2026-08-27_1215_x600_PRECHECK_PERSISTENCE_켰다가_실제매칭은_전부503_확인후_되돌림.md).

★EC2 도 마찬가지로 이 표들이 채워지기 전에는 켜면 안 된다.

아래는 KCD 부분만 막혀 있던 시점(그 전날)의 기록이라 그대로 둔다 — 이제는
KCD 는 안 막혔고 위 세 표가 막혀 있다는 점이 다르다.

**켜면 모든 판정이 503 이 된다.** 실측(2026-08-26):

```
persist_precheck.py:165  resolve_kcd_reference(...)
→ InfraError: 사고일에 적용되는 KCD code를 찾지 못했습니다 (F32).
```

`core.kcd_code` 가 **0행**이다. 표는 서 있지만 비어 있다.

### 왜 못 채우나

`core.kcd_code` 는 `code` 와 **`name_ko`(NOT NULL)** 를 요구하는데,
**코드 → 질병명 사전을 우리는 갖고 있지 않다**(KCD 마스터, 약 2만 항목).

저장소 전수 검색 결과 — 코드↔이름 쌍을 담은 파일 **없음**.
있는 것은 범위 목록(`kcd_catalog.json` 525개 · 예 `N96~N98`)과 장 분류뿐이고,
그 파일 스스로 「이건 KCD 사전이 아니다」라고 적어 뒀다.

★`name_ko` 를 「(미상)」으로 때우면 `resolve_kcd_reference` 가 그 행을 돌려주고,
**그 값이 판정 원장에 사실로 기록된다.** CLAUDE.md §0 에 정면으로 걸린다. 넣지 않았다.

### 켤 수 있는 조건

통계청 KCD 마스터를 받아 `core.kcd_version` + `core.kcd_code` 에 적재한 뒤.
그때 `readyz` 가 자동으로 통과시킨다.

## 결정 3 — ★`readyz` 가 「표가 비어 있는 것」도 잡게 했다

**앞서는 이 상태에서 `ready: true` 를 냈다.** 스키마·마이그레이션만 봤기 때문이다.
그대로 뒀으면 `.env.example` 을 보고 주석을 푼 사람이
**모든 판정이 죽는 배포**를 「준비됨」으로 믿고 올렸을 것이다.
그리고 503 메시지는 "서비스 의존 시스템을 사용할 수 없습니다" 뿐이라 원인을 못 찾는다.

`PRECHECK_PERSISTENCE=postgres` 일 때 `core.kcd_code` 행수를 세어 `kcd_master` 로 보고한다.

```
ready=False  kcd={'required': True, 'checked': True, 'rows': 0, 'ready': False}
hint: core.kcd_code 가 비어 있습니다 — … KCD 마스터를 적재하거나 PRECHECK_PERSISTENCE=off 로 두세요.
```

★못 셌을 때도 「준비됨」으로 넘기지 않는다 — `checked: False, ready: False` 다.

## 결정 4 — `CLAUSE_STORE=pg` 는 **운영에서 켠다**

실측으로 동작을 확인했다 — 실제 요청에서 인용 3건, `occurrence_id` 가 v2 로 정상 발급.
색인 신선도도 0 이다.

★단 **조건이 하나 붙는다**: `pg` 는 색인이 현행 산출물과 같은 판일 때만 옳다.
`file` 은 산출물을 직접 읽어 늘 현행이지만, `pg` 는 재색인을 안 하면 **낡은 조항을 근거로 낸다.**
그래서 배포 전에 반드시:

```bash
python -m scripts.db.check_index_freshness     # 0 이면 종료코드 0
```

`readyz` 의 `clause_index` 항목도 같은 것을 본다(세대·모델·벡터 유무).
★다만 그건 **필터가 맞는가**이지 **내용이 같은 판인가**가 아니다 — 위 명령이 그걸 본다.

## 정리

| 설정 | 코드 기본값 | 운영 | 지금 켤 수 있나 |
|---|---|---|---|
| `AUTH_PERSISTENCE` | sqlite | postgres | ✅ |
| `OPS_PERSISTENCE` | sqlite | postgres | ✅ |
| `OUTCOME_PERSISTENCE` | file | postgres | ✅ |
| `VERIFIED_COHORT_STORE` | file | postgres | ✅ |
| `CLAUSE_STORE` | file | **pg** | ✅ (재색인 신선도 0 확인 후) |
| `PRECHECK_PERSISTENCE` | off | postgres | ☠**아니다** — KCD는 풀렸으나 `core.policy_version`/`policy_clause`/`product` 적재 파이프라인 대기 |

★이 표를 바꾸려면 `readyz` 를 먼저 통과시켜야 한다. 통과 못 하는 값을 배포에 적으면
서비스가 뜨고 나서 죽는다 — 뜨기 전에 죽는 편이 낫다.
