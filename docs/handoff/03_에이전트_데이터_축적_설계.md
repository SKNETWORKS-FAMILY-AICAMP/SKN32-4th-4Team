## 0. 시나리오

사용자의 **에이전트**가 우리 API를 부른다. 그 에이전트는 이미 가진 것이 있다 —
과거 청구 이력, 다른 데서 받은 판정, 실제 지급 결과. 그걸 우리에게 주기도 한다.

우리는 그걸 쌓아서 **승인율**과 **우리 판정의 사후 검증**에 쓰려 한다.

---

## 1. 제1원칙 — **약관과 같은 급으로 쓰지 않는다**

이게 전부다.

> 남의 에이전트가 "이 건 지급됐어요"라고 말했다고 해서,
> 그걸 근거로 다른 사용자에게 **"보장됩니다"라고 말하면 안 된다.**

약관 조항은 **회사가 공시한 계약 내용**이고, 외부 보고는 **주장**이다.
둘을 같은 인덱스에 넣으면 검색에서 섞이고, 섞이면 인용에서 구분할 수 없다.

```python
class EvidenceTier(str, Enum):
    POLICY_CLAUSE   = "policy_clause"     # 약관 원문 — 유일하게 판정 근거가 된다
    EXTERNAL_REPORT = "external_report"   # 외부 보고 — 참고만
    STATISTICS      = "statistics"        # 집계 — 참고만
```

`precheck.run()` 은 `POLICY_CLAUSE` 만 인용한다. 코드로 강제돼 있다.

## 2. 어떤 문서 형태로 저장하나 — **원본 그대로 + 이벤트 로그**

### 2-1. 받은 것은 손대지 않고 남긴다

```
data/external/submissions/{YYYY-MM}/{client_ref}/{received_at}_{idem_key}.json
```

```json
{
  "received_at": "2026-08-02T14:03:11Z",
  "client_ref": "agent-abc",
  "idempotency_key": "…",
  "payload": { "…클라이언트가 보낸 그대로…" },
  "signature": { "api_key_id": "…", "ip_hash": "…" }
}
```

**왜 원본을 남기나** — 나중에 파싱 규칙이 바뀐다. 정규화한 것만 두면
"그때 뭘 받았나"를 다시 볼 수 없다. 약관 PDF를 원본으로 두는 것과 같은 이유다.

### 2-2. 정규화한 것은 이벤트 로그로

```
data/external/events/{YYYY-MM-DD}.jsonl     (append-only)
```

```json
{"event":"claim_outcome","at":"…","client_ref":"agent-abc",
 "insurer":"DB손해보험","enrolled_on":"20200301","kcd_codes":["F32"],
 "outcome":"denied","verification":"unverified","precheck_trace_id":"744154ed…"}
```

**추가만 한다(append-only).** 수정·삭제하지 않는다 — 통계가 조용히 바뀌면 안 된다.
정정이 필요하면 정정 이벤트를 **뒤에 붙인다.**

## 3. DB에는 어떻게

| 테이블 | 역할 | 현행 ERD |
|---|---|---|
| `external_submission` | 원본 `payload jsonb` + `idempotency_key` UNIQUE | ⚠ **현행 27테이블에 없다**(아래) |
| `claim_outcome` | 정규화된 결과 1행 | → `app.claim` + `app.outcome` 으로 **분리됐다** |
| `evidence_verification` | 검증 이력 (누가·언제·무엇으로) | `app.evidence_verification` (그대로) |

> ★**2026-08-02 확인 — 이 문서가 약속한 "원본 그대로 보존(append-only)"을 담을 테이블이
> 현행 ERD에 없다.** `ops.interaction_log` 는 질의응답용이고 `core` 로 가는 FK가 없다.
> `app.claim`/`outcome` 은 정규화된 결과만 받는다.
> 멱등키는 `ops.interaction_log.source_event_id` 에 `UNIQUE(agent_client_id, source_event_id)` 로
> 잡혀 있으나, **원문 payload 보존은 자리가 없다.**
> [02_ERD_및_스키마.md](02_ERD_및_스키마.md) 확정 전까지 **미해결**로 둔다 —
> 조용히 `interaction_log` 에 밀어넣지 않는다.

### 검증 등급

```
unverified       받기만 했다. 기본값. ★통계에 넣지 않는다
self_reported    본인이 신고했고 신원은 확인됐다
document_backed  지급명세서 등 문서가 붙었다
confirmed        보험사 확인 또는 교차검증 통과
```

**`unverified` 를 승인율에 넣으면 안 된다.**
넣으면 "우리 서비스로 청구하면 90% 나옵니다" 같은 수치가 근거 없이 만들어진다.

## 3-1. ★사람이 계속 검수할 수는 없다 — 확장 경로

지금 설계는 **관리자가 한 건씩 검수해야 `verified` 가 된다.** 규모가 커지면 이건 못 버틴다.
그 사실을 적어 두지 않으면 "사람이 다 본다"가 영구 전제처럼 굳는다.

### 왜 지금은 사람인가 (한시적 이유)

1. **자동화할 대상이 아직 없다.** 실제 코호트는 `n=0` 이다. 0건을 자동 검증하는 파이프라인은 만들 수 없다.
2. **첫 표본이 이후 전부의 기준이 된다.** 초기 수십 건을 사람이 보면서 *"무엇이 검증인가"* 의
   규칙을 뽑아내야 자동화할 규칙이 생긴다. **순서가 반대면 자동화가 무엇을 흉내내는지 모른다.**

### 병목을 정직하게 — 상한을 미리 안다

```
검수 1건 5분 · 하루 2시간 투입  →  하루 24건 · 월 500건 남짓이 상한
```

**월 500건을 넘는 순간 사람 검수는 끝난다.** 그 전에 아래가 붙어야 한다.

### 무엇이 사람을 대체하나 — 등급마다 다르다

★핵심은 **"검증"이 한 덩어리가 아니라는 것**이다. 등급을 쪼개 보면
사람 판단이 꼭 필요한 부분은 생각보다 작다.

| 등급 | 실제로 하는 일 | 자동화 가능성 |
|---|---|---|
| `self_reported` | 신원 확인 | **이미 자동이다** — `agent_client` 인증 + 동의 기록 |
| `document_backed` | 문서가 붙었나, 그 문서가 말이 되나 | **규칙엔진으로 가능** — 해시 중복, OCR 필드 추출, 금액·날짜·보험사·질병코드 내부 정합성 (`consistency_result` 가 이미 그 자리다) |
| `confirmed` | 발행처가 실제로 그렇게 결정했나 | **조회지 판단이 아니다** — 보험사·기관 API 확인. 제휴가 되면 자동화 가능 |
| (나머지) | 위 어디에도 안 걸리는 애매한 건 | **여기만 사람이 본다** |

즉 목표는 *"사람을 없앤다"* 가 아니라 **"사람이 전수가 아니라 예외만 본다"** 이다.

### 확장 순서

```
1단계 (지금)   전수 사람 검수                     n < 500
2단계          자동 정합성 검사 + 이상탐지        → 통과분은 표본 검수(예: 10%)
               사람은 이상 신호 + 표본만 본다
3단계          발행처 API 확인                    → confirmed 자동 승격
4단계          클라이언트 신뢰등급                → 이력 좋은 agent_client 는 표본율 하향
                                                   (단 감사 추적은 100% 유지)
```

### ★스키마는 바뀌지 않는다 — 이게 지금 설계의 값어치다

`evidence_verification` 은 **누가·언제·무엇으로** 검증했는지를 이미 요구한다
(`verification_method NOT NULL`). 검증 주체가 사람이든 규칙엔진이든 API든
**같은 자리에 기록된다.** 자동화는 스키마 변경이 아니라 `verification_method` 값의 추가다.

```
verification_method = admin_review | consistency_rules | issuer_api | cross_submission
```

### ★그러나 정직성 대가가 있다 — 등급을 뭉뚱그리지 않는다

자동 검증은 **사람 검수보다 검증 강도가 낮다.** 이걸 `verified` 하나로 합치면
자동화가 진행될수록 **통계가 조용히 묽어진다.** 그래서 두 가지를 지킨다.

- 코호트를 **`verification_method` 별로 쪼개 볼 수 있어야** 한다
- 화면·응답에 **"무엇으로 검증된 n 인지"** 를 표시한다 —
  "검증 40건"이 아니라 "발행처 확인 12건 · 자동 정합성 28건"

### 하지 않을 것

**LLM 이 지급통지서를 읽고 "검증됨"으로 올리는 것.** 그건 검증이 아니라 추측이다.
LLM 은 **필드를 뽑는 데까지만** 쓰고, 뽑은 값이 맞는지는 규칙·해시·외부 조회가 판단한다.
근거 없는 판정을 막는 것이 이 서비스의 제1원칙이고, 검증 단계에서 그걸 어기면
그 오류가 **통계 전체로 번진다** — 판정 오류보다 범위가 넓다.

## 4. 다시 쓰는 형식 — 세 가지, 각각 다른 급

### 4-1. 승인율 통계 (사용자에게 보여 줌)

```
"이 보험사의 F32 청구 33건 중 지급 26건 (검증된 건만)"
```

조건:
- `verification >= document_backed` 인 것만
- **표본이 작으면 숫자를 보여 주지 않는다** — `n < 30` 이면 "사례가 적습니다"
- 반드시 "실제 결과는 다를 수 있습니다" 를 함께 낸다

### 4-2. 우리 판정의 사후 검증 (내부용)

`precheck_trace_id` 가 붙어 온 보고는 **우리 답과 대조**할 수 있다.

```
우리 판정         실제 결과      해석
unlikely        →  denied     맞았다
unlikely        →  paid       ★틀렸다. 조항 해석을 다시 봐야 한다
needs_expert    →  paid       기권했지만 실제로는 보장됐다. 검색 보강 필요
```

이게 **가장 값어치 있는 쓰임**이다. 정확도를 숫자로 잴 수 있게 된다.

### 4-3. 검색 평가 세트 (모델팀용)

실제 사례를 골든 세트로 만든다. **판정에 직접 쓰지 않는다.**

## 5. ★어떤 RAG 형태가 되나 — **인덱스를 분리한다**

```
인덱스 A  약관 조항        core.clause_chunk.embedding  (content_hash 종속)
          → 판정 근거로 인용된다
          → 필터: policy_version_id 로 **반드시** 가둔다
          → ★인용은 core.policy_clause 를 가리킨다(citeable=true 만)

인덱스 B  외부 사례        external_case.embedding
          → 인용되지 않는다. "비슷한 사례가 있습니다" 로만 쓴다
          → 필터: verification 등급
          → ⚠ **현행 ERD에 이 테이블이 없다.** 위와 같은 미해결 항목이다
```

### 왜 합치면 안 되나

1. **인용이 섞인다.** 답변에 "제9조에 따르면"과 "어떤 사용자 보고에 따르면"이
   같은 출처 목록에 나란히 붙으면 사용자는 구분하지 못한다.
2. **검색 순위가 오염된다.** 사례 문장은 구어체라 사용자 질문과 더 비슷하다.
   같은 인덱스에 두면 **약관 조항을 밀어낸다.**
3. **약관은 버전으로 가둬야 한다.** 사례에는 그런 축이 없다.

### 검색 흐름

```
질문
 ├─ 인덱스 A 검색 (policy_version_id 고정)  → 판정 근거
 └─ 인덱스 B 검색 (선택)                     → "비슷한 사례" 참고 표시

답변 = 판정(A 근거만 인용) + 참고(B, 별도 구역에 "참고 사례"로 표시)
```

**두 구역을 화면에서도 나눈다.** 근거와 참고가 같은 목록에 있으면 안 된다.

## 6. 인증·감사

| 항목 | 방침 |
|---|---|
| 인증 | 클라이언트별 API 키(해시 저장) + scope. 외부 공개 시 OAuth 2.1 |
| scope | `precheck:read` `terms:read` `observations:write` `cohort:read` |
| 멱등성 | 쓰기 요청에 `Idempotency-Key` **필수** |
| 레이트리밋 | `client_id + subject_hash + operation` 기준 |
| 감사로그 | **원문 의료정보 대신 해시.** client, policy_version, clause_ids, rule/model version, verdict, abstain 사유, latency |
| 보존 | 원문 payload는 암호화·별도 보존기간·삭제 가능 |

질병기호는 민감정보다. 로그에 그대로 남기지 않는다.

### v1.1 구현 경계

- 고객 브라우저가 쓰던 `/v1/*`는 UI 비회귀를 위해 유지한다. 이 경로의 `client_ref`는
  **인증된 에이전트 provenance가 아니다.**
- 등록 외부 에이전트는 별도 프로세스 `app.agent_main:agent_app`의
  `/v1/agent/*`만 사용한다. 이 앱에는 고객 정적 파일·합성·관리자 라우터가 실리지 않는다.
- 인증은 `Authorization: Bearer <agent-key>`, 최종 사용자 축은 원문이 아닌 opaque
  `X-Agent-Subject` 헤더다. 서버는 이를 `AGENT_HASH_SECRET` HMAC으로만 저장한다.
- API 키 원문은 생성 시 한 번만 반환하고 `insurance_agent.ops.agent_client`에는 SHA-256만
  저장한다. 키는 서버가 256-bit 난수로 생성하므로 사용자가 정한 저엔트로피 키를 받지 않는다.
- rate limit·멱등 예약·감사 원장은 `insurance_agent` DB에 둔다. `mall_vec` 및
  합성 `insurance_demo`와 물리적으로 분리하며 연결 장애 시 다른 저장소로 폴백하지 않는다.
- 보호 observation도 원문 사례 저장소에 `unverified`로만 들어간다. DB 멱등 예약과 파일 저장이
  하나의 트랜잭션은 아니므로, 처리 중 장애는 실패/5분 stale 재개 후 파일 측 동일 payload 대조로
  복구한다. stale 재예약은 새 `lease_token`을 발급하고 완료·실패 갱신은 compare-and-set으로
  제한해, 늦게 끝난 이전 worker가 새 worker의 결과를 덮지 못한다. 자동 승격은 여전히 하지 않는다.
- 원본 파일은 공개 채널과 `submissions/registered_agent/` 채널을 분리하고, 정규화 이벤트에는
  `ingest_channel`과 안정적인 `submission_id`를 함께 기록한다.
- runtime 역할은 인증 조회·rate/멱등 처리·감사 append에 필요한 최소 권한만 가진다. 클라이언트
  변경과 보존기간 경과 이력 파기는 admin 역할과 `scripts.agent_clients`에서만 수행한다.

## 7. 4주 안에 할 것 / 미룰 것

| 할 것 | 미룰 것 |
|---|---|
| `POST /v1/agent/observations` 보호 접수 + 원본 저장 | 자동 검증 파이프라인(§3-1 2단계 이후) |
| `verification=unverified` 로 쌓기 | 사용자향 승인율 노출 |
| `precheck_trace_id` 대조 리포트(내부) | 사례 임베딩·인덱스 B |
| API key hash+scope·원자적 rate limit·HMAC 감사로그 | OAuth 2.1·원격 MCP/A2A |

**승인율을 사용자에게 보여 주는 것은 검증된 데이터가 쌓인 뒤다.**
지금 보여 주면 근거 없는 숫자가 된다.
