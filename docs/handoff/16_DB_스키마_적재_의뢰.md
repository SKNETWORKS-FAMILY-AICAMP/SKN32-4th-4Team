## 0-1. 보내주신 스키마 점검 (2026-08-03 · 코덱스 교차검증)

DBML 기준 8테이블(`data_subject` · `agent_client` · `agent_client_auth_log` ·
`insurance_product` · `policy_holding` · `coverage_review` · `event` · `session_manager`)을
`001_core.sql` · [ERD v4](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) 와 대조했습니다.

### 잘 된 것 — 그대로 가면 됩니다

- ★**`case` → `coverage_review` 개명.** `CASE` 는 SQL 예약어라 그대로 쓰면 매번 따옴표가 필요합니다.
  ERD 가 `case` 로 적어둔 걸 실제로 부딪혀 보고 고친 것으로 보입니다 — **ERD 쪽을 고치겠습니다**
- ★**`coverage_review.policy_holding_id` 직접 참조** + 주석 *"data_subject 경유 조인 금지"*.
  피보험자에게 계약이 여럿일 때 오배분되는 것을 막습니다. 정확합니다
- `sha256_hash` **전체 64자, 잘라 쓰지 않음** — `sha12` 로 자르다 겪은 문제를 피했습니다
- `UNIQUE (coverage_review_id, sha256_hash)` — 같은 증빙 중복 제출 차단
- `agent_client` 를 *"고객 식별자로 쓰지 않는다"* 고 주석에 명시 — ERD §7-3 과 일치
- `COMMENT` 가 성실합니다

### ★A · `001_core.sql` 과 원장이 이중화됩니다

**저장소에 이미 14테이블이 있습니다**(`db/migrations/postgres/001_core.sql`, 스키마 `core`/`app`/`ops` 분리).

| 보내주신 것 | 이미 있는 것 |
|---|---|
| `insurance_product` (VARCHAR PK · `insurance_company` 문자열) | `core.product` (uuid PK · `insurer_id` FK → **`core.insurer`**) |
| — | **`core.insurer`** — `kind CHECK (general/life)` ★삼성화재/삼성생명 구분 |
| `agent_client` (평평) | ERD 는 `ops.agent_client` (**DDL 에는 아직 없음**) |

SQL 이름 충돌이 아니라 **상품 원장이 두 벌**이 되는 문제입니다.
`core.insurer` 를 안 쓰면 손보/생보 구분이 문자열에 의존합니다.

★그리고 `product_id VARCHAR(50)` 이 **업무 코드**라면 ERD 의 *"불변 대리키. 업무 코드를 PK로 쓰지 않는다"*
에 걸립니다. 무작위 불변 식별자라면 uuid 계약과의 불일치일 뿐입니다 — **어느 쪽인지 알려주세요.**

→ **먼저 정할 것: `001_core.sql` 위에 얹을지, 갈아엎을지.** 지금은 그 결정이 없습니다.

### ★B · 판정 사슬이 통째로 없습니다

```
없음 ▸ assessment · assessment_clause_citation · case_diagnosis
     ▸ evidence_verification · claim · outcome · cohort_stats(뷰)
```

`assessment_clause_citation` 이 없으면 **"판정 근거는 약관 조항뿐"이 구조로 강제되지 않습니다.**

> 상호작용 로그·FAQ·다른 사용자의 답변을 근거로 넣으려면 **FK 가 없어서 못 넣는다.**
> "그러지 말자"는 규칙이 아니라 **넣을 수 없는 구조**다. — [ERD v4 §5](../plans/2026-08-02_0700_ERD_현행_v4_통합.md)

지금은 코드(`EvidenceTier`)로만 막고 있는데 **코드는 고칠 수 있고 FK 는 못 뚫습니다.**
`case_diagnosis`(질병기호 ↔ `core.kcd_code` FK)도 빠져 있습니다.

### ★C · 정합성 검사와 검증 사실을 가르는 구조가 없습니다

`event` 에 `submitted_at` 만 있습니다. **`consistent`(재계산 가능한 검사 결과)와
`verified`(사람이 책임진 불변 사실)를 구분할 수단이 없습니다.**

ERD 는 이 비대칭을 의도적으로 설계했습니다 — *"`consistent` 는 컬럼이고 `verified` 는 행이다"*.
`status` 컬럼을 하나 더 다는 방식이 **아닙니다**. §2·§3 참조.

### D · 어느 약관 판본으로 판정했는지 남지 않습니다

`policy_holding` 에 **`policy_version_id` 가 없습니다.** `product_id` 만으로는
같은 상품의 2019년판/2024년판을 구분하지 못합니다.

> ★**적용 약관 확정의 결과가 여기 저장된다.** 판정 때마다 다시 추론하지 않는다. — ERD §5

### E · `generation_type` 의 `0 = 미상`

```sql
CHECK (generation_type IS NULL OR generation_type BETWEEN 0 AND 5)   -- 0=미상
```

**미상을 숫자 0 으로 모델링**하셨는데, 이미 있는 DDL 은 다르게 갑니다:

```sql
generation             smallint CHECK (generation BETWEEN 1 AND 5),   -- NULL 허용
generation_source      text,
generation_confidence  text CHECK (... IN ('exact','month','unknown'))
```

CLAUDE.md §1 — *"값을 모르면 비워 둔다"*. 그리고 ★**세대는 약관 판본의 속성**이지
개인 계약의 속성이 아닙니다. `policy_holding` 에 두면 같은 상품인데 계약별로 달라질 수 있습니다.

### F · `session_manager`

[ERD v4 §7](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) 확정사항 1번 —
**"`session` 테이블을 만들지 않는다. 세션 흐름은 `ops.interaction_log` 가 받는다."**

`chatbot_count` 도 로그에서 집계로 나옵니다. 컬럼으로 들고 있으면 `UPDATE` 로 통계가 오염됩니다.

### G · 동의 원장이 이미 있는데 컬럼으로 흩어졌습니다

`consent` · `retention_until` · `deleted_at` 이 5개 테이블에 반복됩니다.
그런데 **`001_core.sql` 에 `ops.consent` 가 이미 있습니다.**

문제는 반복 자체가 아니라 **단일 동의 원장과 철회·삭제 전파 수단(FK·트리거·작업)이 안 보이는 것**입니다.
(`retention_until` 은 레코드별로 달라도 됩니다.)

### I · 명명·자료형

| | |
|---|---|
| `TIMESTAMP` / `TIMESTAMPTZ` | 혼용 자체는 결함이 아닙니다. 다만 **인증·제출·감사 같은 절대 시각**에 tz 없는 타입을 쓰면 시간대가 어긋납니다 |
| `event_id` = `{날짜}_{파일명}_{division}_{sha256}` | **파일명에 개인정보가 들어갈 수 있어** 식별자·로그·URL 로 노출될 위험이 있습니다 |
| `sha256_hash VARCHAR(64)` | 길이만으로는 부족합니다 — **16진수 CHECK** 또는 32-byte `bytea` |
| `event` 이름 | 너무 일반적입니다. `audit_log`·도메인 이벤트와 혼동. ERD 는 `evidence` |
| `auth_log ON DELETE SET NULL` | 행은 남지만 **호출 주체 귀속을 잃습니다.** `agent_client` 소프트 삭제가 낫습니다 |

### 남기신 미해결 10건 중 3건 — 답변

**#4 `app.event` 에도 `consistent`/`verified` 가 필요한가 → 불필요합니다.**
MVP §2-③ 의 상태전이는 **지급결과 사후검증**(`app.evidence` → `evidence_verification`)입니다.
사전검토 증빙은 **판정 입력**이지 통계 근거가 아닙니다.
다만 OCR·파싱·무결성 검사 결과와 **원본 계보**는 필요하고,
★**코호트에는 절대 들어가면 안 됩니다.**

**#9 두 `policy_version_id` 중 어느 쪽이 정본인가 → `assessment` 쪽입니다.**
`assessment.policy_version_id` 가 **과거 판정의 불변 스냅샷**이고,
`user_policy_info.policy_version_id` 는 **계약 입력·현재 상태**입니다. 둘은 달라질 수 있습니다.
★단 버전 선택에는 `incident_on` 만으로 부족하고 `enrolled_on`·상품·특약·변경 이력이 함께 필요합니다.

**#10 `incident_on` 기준 매칭 → ★제가 앞서 "인자만 바꾸면 된다"고 한 것은 틀렸습니다.**

```python
# manifest_policy_resolver.resolve() — 실제로 비교하는 것
v.sale_start <= enrolled_on and (not v.sale_end or enrolled_on <= v.sale_end)
```

**`sale_start`/`sale_end`(판매기간)** 를 봅니다. `valid_from`/`valid_to`(적용구간)가 아닙니다.
여기에 `incident_on` 을 넣으면 **사고일을 판매기간에 대조하는 버그**가 됩니다.

올바른 형태:

```
enrolled_on  →  sale_start/sale_end   가입·판매 적합성 확인
incident_on  →  valid_from/valid_to   ★적용 약관 결정
```

`core.policy_version` 에 `valid_from`/`valid_to` 가 이미 있으므로 **DB 기반으로 따로 구현**해야 합니다.
★그리고 *"현행 약관으로 폴백하지 않는다"* 는 그대로 지켜 주세요.

### ★새로 발견한 것 — 버전 교차 인용이 아직 막히지 않습니다

`citeable` 복합 FK 만으로는 **2019년 판정이 2024년 조항을 인용**할 수 있습니다.
`citeable=true` 이기만 하면 통과하기 때문입니다.

**해결이 쉽습니다 — `001_core.sql` 에 전제가 이미 있습니다.**

```sql
-- core.policy_clause
UNIQUE (id, citeable),
UNIQUE (id, policy_version_id),   -- ★이것도 이미 있다
```

그래서 인용 테이블을 이렇게 두면 **버전 교차가 물리적으로 막힙니다**:

```sql
CREATE TABLE app.assessment_clause_citation (
  assessment_id     uuid NOT NULL,
  policy_clause_id  uuid NOT NULL,
  citeable          boolean NOT NULL DEFAULT true CHECK (citeable),
  policy_version_id uuid NOT NULL,                       -- ★추가
  ...
  FOREIGN KEY (policy_clause_id, citeable)
      REFERENCES core.policy_clause (id, citeable),
  FOREIGN KEY (policy_clause_id, policy_version_id)      -- ★추가
      REFERENCES core.policy_clause (id, policy_version_id),
  FOREIGN KEY (assessment_id, policy_version_id)         -- ★추가
      REFERENCES app.assessment (id, policy_version_id)  -- assessment 에 UNIQUE(id, policy_version_id) 필요
);
```

→ **판정이 쓴 버전과 인용 조항의 버전이 다르면 INSERT 자체가 실패**합니다.
`app.assessment` 에 `UNIQUE (id, policy_version_id)` 하나만 더 두면 됩니다.

★`cohort_stats` 도 같은 이유로 `user_policy_info` 의 현재 버전이 아니라
**판정 당시 버전**(`assessment.policy_version_id`)을 그룹키로 써야 합니다.

## 2. C · 반드시 돌아야 하는 한 줄기

[MVP §5](../plans/2026-07-31_1600_MVP_기능선정.md) 가 정한 **데모의 단 하나의 장면**:

```
consistent 제출 → n 그대로   /   verified 처리 → n+1
```

> *"정합성만으론 통계가 안 움직이고, 검증돼야 움직인다"* — **이게 우리가 파는 것**이다.

이 장면이 지나는 테이블:

```
subject → policy_holding → case → case_diagnosis → assessment
                                       ↓
                          assessment_clause_citation → core.policy_clause
                                       ↓
                          claim → outcome → evidence → evidence_verification
                                       ↓
                                  cohort_stats (뷰)
```

★**`claim`·`outcome`·`cohort_stats` 를 후순위로 미루면 이 장면이 안 돕니다.**
실데이터가 0건이라 미루자는 판단이 처음에 있었는데, **합성 데이터(`insurance_demo`)로는 돌아갑니다.**
실제 경로는 `n=0` 으로 두면 됩니다.

### 인수 테스트 — 이 네 줄이 통과해야 완료입니다

```
1. 기준 n
2. consistent 제출 후          → n 그대로
3. 권한 있는 검증 함수로 verified → n+1
4. 같은 건 재처리              → n+1 유지 (멱등)
```

---

## 3. ★하지 말아야 할 것 (코덱스 2라운드)

여기 있는 것들은 **하나만 어겨도 제품 주장이 무너집니다.**

- ❌ `consistent` 를 집계에 넣거나 `verified` 로 간주
- ❌ `CHECK(status IN …)` **만으로** 전이 순서 보장 — 그건 값 검사지 **순서 보장이 아니다**.
  trigger / 전용 함수 / 권한 제한으로 **이전 상태 대비 전이**를 강제
- ❌ 검증 테이블(`evidence_verification`)에 직접 INSERT·UPDATE 권한 부여
- ❌ 합성·실제 `UNION` · 같은 DB에 `is_synthetic` boolean 으로 구분 · FDW·dblink
- ❌ **`cohort_stats` 대신 mock·하드코딩 카운터로 데모** ← 그러면 집계 게이트를 증명 못 한다
- ❌ 합성 seed 를 `insurance_real` 에 넣기
- ❌ 파일·DB **이중 쓰기**, 장애 시 **말없는 파일 fallback**
- ❌ 실제 데이터가 없는데 "실제 통계"로 표시

---

## 4. 전환기의 진실 원천 — 미리 정합니다

파일과 DB 를 동시에 쓰면 **이중 진실**이 생깁니다. 순서를 못박습니다.

```
컷오버 전        파일이 원본
적재 검증 후     DB 가 런타임 원본
그 뒤 파일       재현 가능한 import artifact (원본 아님)
```

★**이중 쓰기 금지 · 조용한 파일 fallback 금지.** DB 가 죽으면 **503 으로 실패**해야 합니다
([`usecases/precheck.py`](../../app/core/usecases/precheck.py) 가 이미 그렇게 갈라 놨습니다 —
`InfraError` 는 올려보내고 "산출물 없음"만 기권).

---

## 5. ★DB 간 FK 는 불가능하다 — 이미 정한 대가

[ERD v4 §2](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) 가 **DB 2개 물리 분리**를 택했고,
그 대가를 정직 기록으로 남겼습니다:

> DB 를 나누면 **약관 코퍼스를 두 벌 유지해야 한다.**
> `assessment_clause_citation` 의 FK 가 **같은 DB 안에 있어야** 강제되기 때문이다.

→ **`core` 를 한 DB 에만 두고 둘이 공유하는 구성은 안 됩니다.** citation FK 가 무력해집니다.
두 DB 에 `core` 를 각각 두고, **기준 데이터 동기화 방법**(reference-data drift 방지)을 정해 주세요.

`assessment_clause_citation` 은 **`core.policy_clause` 하나만 FK** 로 참조해야 합니다.
지금은 코드(`EvidenceTier`)로만 막고 있는데, **코드는 고칠 수 있고 FK 는 못 뚫습니다.**

## 6. `insurance_real` 은 지금 만들지 않습니다

실제 데이터를 받을 합법적 경로가 아직 없습니다. 대신:

- **동일 migration 이 적용되는 빈 DB** 를 CI·데모용으로 만들어
  **`n=0` 과 물리 분리를 검증**합니다
- 영구 인스턴스는 **수집 경로 · 동의/보존 정책 · 검수 책임자**가 생길 때 엽니다
