> 팀에서 같은 질문이 반복해서 나왔다 — *RAG를 몇 개 만드나 / 용어 설명은 별도인가 /

## 1. 인덱스가 둘인 이유 — 등급이 다르다

나누는 기준은 "데이터가 다른가"가 아니라 **"판정 근거로 인용할 수 있는가"** 다.
코드에 enum으로 박혀 있다 ([`precheck_result.py`](../../app/core/domain/precheck_result.py)):

```python
POLICY_CLAUSE   = "policy_clause"     # 약관 원문 — 유일하게 판정 근거가 된다
EXTERNAL_REPORT = "external_report"   # 외부 보고 — 참고만
STATISTICS      = "statistics"        # 집계 — 참고만
```

> 남의 에이전트가 "이 건 지급됐어요"라고 말했다고 해서,
> 그걸 근거로 다른 사용자에게 **"보장됩니다"라고 말하면 안 된다.**
> 약관 조항은 **회사가 공시한 계약 내용**이고, 외부 보고는 **주장**이다.
> — [03_에이전트_데이터_축적_설계.md](03_에이전트_데이터_축적_설계.md) §1

### 왜 필터로 못 막고 인덱스를 나눠야 하나

두 가지다.

1. **인용이 섞인다.** 답변에 "제9조에 따르면"과 "어떤 사용자 보고에 따르면"이
   같은 근거 목록에 나란히 붙으면 사용자는 구분하지 못한다.
2. **검색 순위가 오염될 위험이 있다.** 사례 보고는 **구어체라 사용자 질문과 문장이 비슷**하고,
   약관 조항은 법률체 문어다. 같은 인덱스에 두면 사례가 조항을 밀어낼 수 있다.
   사후 필터로 사례를 빼도 **필요한 조항이 이미 top-k 밖으로 밀린 뒤**라 되살릴 수 없다.

> ★**정직 기록** — 2번의 "밀어낸다"는 아직 **측정하지 못했다.** 인덱스 B의 데이터가 0건이라
> 잴 대상이 없다. 다만 *"사후 필터로는 밀려난 것을 되살릴 수 없다"* 는 구조적 사실이다.
> 가설과 사실을 섞어서 둘 다 단정하면, 검증된 쪽까지 의심받는다.

DB 층에서도 같은 것을 강제한다 — `assessment_clause_citation` 의 FK가 `core.policy_clause`
하나뿐이라, 다른 것을 근거로 넣으려면 **넣을 수 없다**([ERD v4](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) §5).

## 2. 용어 설명이 별도 RAG가 아닌 이유

용어 정의는 결국 **약관 안에 있다**(「제2조 용어의 정의」). 코퍼스가 같으므로 인덱스도 하나다.
두 벌로 두면 어긋났을 때 무엇이 맞는지 판단할 근거가 없어진다
([약관보관형식 결정](../reports/2026-07-31_약관보관형식_결정.md) §3에서 표 CSV를 폐기한 것과 같은 논리).

**대신 유스케이스는 나눈다.** 필터와 출력 계약이 다르기 때문이다.

| | 판정용 | 용어설명용 |
|---|---|---|
| 문서 범위 | 확정된 **약관 버전 하나로 고정** | 전역 |
| 확정 여부 | `confirmed` 만 | 완화 가능 |
| `parse_status` | `ok` 만 | 완화 가능 |
| 출력 | `verdict` 4단 + 근거조항 + 면책조항 + locator | 정의 + 인용 |

### 왜 유스케이스는 꼭 나눠야 하나

챗봇이 *"그래서 저 보장되나요?"* 로 자연스럽게 넘어가는데, **거기서 답하면 규칙엔진을 우회**한다.
약관버전 확정·인용검증·4단 판정을 전부 건너뛴 답이 나간다.

> "이 용어는 이런 뜻입니다"와 "그래서 당신은 보장됩니다"는 다른 유스케이스다.
> — [팀MVP6 구조설계](../plans/2026-07-31_1900_팀MVP6_구조설계.md) §5

★리트리버는 **필터를 명시 인자로 받는다.** 기본값을 느슨하게 두면 용어 경로의 완화된 필터가
판정 경로로 샌다.

## 3. 판정은 확률이 아니다 — 그리고 유사사례로 하지 않는다

이 둘은 **다른 것**이고, 화면에서도 다른 구역이다.

### 판정 — 약관 근거 규칙엔진

날짜·면책기간·특약·한도를 **코드로 계산**한다. LLM에 맡기지 않는다
([MVP 기능선정](../plans/2026-07-31_1600_MVP_기능선정.md) §2-5).

결과는 확률이 아니라 **4단**이다 (스토리보드 컷⑤):

| `verdict` | 화면 표시 | 뜻 |
|---|---|---|
| `likely_covered` | 보장 가능 | 보장 조항 근거가 있다 |
| `needs_documents` | 조건부 확인 필요 | 요양급여 해당 여부 등 확인이 필요하다 |
| `unlikely` | 면책 가능성 | 면책 조항 근거가 있다 |
| `needs_expert` | 전문가 확인 필요 | 근거를 못 댔다 (기권) |

**이진 판정 금지.** 그리고 근거 조항을 못 찾으면 답을 만들지 않고 기권한다 — 이건 오류가 아니라
정상 결과다(HTTP 200 + `abstained=true`).

### 유사사례 통계 — 별개 구역

각 사례가 **모든 조건이 일치하는 것이 아니므로 하나의 확률로 합치지 않는다.** 대신 셋을 함께 낸다.

- **건수**와 **95% 신뢰구간** (점추정 금지 — `"82.5%"` 가 아니라 `"68~91%"`)
- **`match_level`** — 무엇을 완화해서 묶었는지
- 표본 **30건 미만이면 비율 자체를 숨긴다**

★표본이 모자랄 때 **즉석에서 조건을 하나씩 빼지 않는다**(p-hacking). 미리 정의한 roll-up 하나만
허용한다. **약관 버전 roll-up 은 금지** — 세대·개정판을 섞는 것은 표본 부족보다 위험하다
([ERD v4](../plans/2026-08-02_0700_ERD_현행_v4_통합.md) §9-3).

**두 구역을 화면에서 섞지 않는다.** 스토리보드 컷⑤(판정) / 컷⑧(코호트)가 그 형태다.

## 4. 승인율은 모델 학습이 아니다 — 다만 문장까지 LLM이 만들지는 않는다

별도 모델을 학습시키지 않는다. `app.cohort_stats` **집계 뷰**다.

★그런데 **숫자를 문장으로 바꾸는 것은 LLM이 아니라 결정론 코드**가 한다
([`cohort.py`](../../app/core/usecases/cohort.py) `_headline()`).

실제로 나가는 문장:

```
검증된 과거 사례 40건 중 33건 승인 · 7건 부지급
(이 사례들의 승인 비율은 68%~91% 범위로 추정됩니다 · 95% 신뢰구간
 · 본인의 결과를 예측하지 않습니다)
```

문장의 조각마다 이유가 있다.

| 조각 | 빼면 |
|---|---|
| **"과거 사례 중"** | 사용자가 *"내가 82% 확률로 받는다"* 로 읽는다. 신뢰구간은 모수에 대한 진술이지 개인에 대한 것이 아니다 |
| **"68%~91%"** (구간) | 점추정은 팀MVP6가 쓰지 말자고 정한 표현이다 |
| **"본인의 결과를 예측하지 않습니다"** | [MVP §4 비범위](../plans/2026-07-31_1600_MVP_기능선정.md) — *개인 예상 지급액 제시(손해사정 유사행위 소지)* 에 걸린다 |

LLM이 *"F32는 대체로 지급되는 편입니다"* 로 다듬으면 **셋이 한 번에 사라지고, LLM은 그걸
지웠다고 말해주지 않는다.** 코드는 짝을 강제하는 데까지 갔다 — 점추정만 있고 신뢰구간이 없는
응답은 **만들 수 없다**(`__post_init__` 에서 `ValidationErr`).

**LLM은 봉투를 만들고, 편지는 코드가 쓴다.** 질문 해석과 답변 조립에는 LLM을 쓰되,
통계 문장은 그대로 싣는다.

## 5. 역할 구분 — RAG를 만드는 사람과 흐름을 잇는 사람

| | 하는 일 | 담당 | 계약 문서 |
|---|---|---|---|
| **검색(AI 1)** | 인덱스 A 구축·검색. 조항 + 면책조항 함께 반환, locator 제공 | 서유현 | [04](04_계약_AI1_검색.md) |
| **판정·설명(AI 2)** | 규칙 기반 `assess()` + LLM `explain()` | 송채영 | [05](05_계약_AI2_판정.md) |
| **흐름(Agent)** | 위 둘을 **잇고·분기하고·재시도를 통제**한다. 도메인 판단은 안 한다 | 정재희 | [06](06_계약_Agent.md) |
| **백엔드** | DB·API·감사 | 김지혜 | [07](07_계약_백엔드.md) |
| **프론트** | 화면 상태표 | 최연우 | [08](08_계약_프론트.md) |

### 왜 LangChain이 아니라 LangGraph인가

흐름이 **분기하고 되돌아온다.** 개별 파이프라인은 LangChain(LCEL)으로 짜되 **전체는
LangGraph**로 묶는다. 선형 LCEL만으로 불가능하지는 않지만, 분기·순환·상태·재시도를 전부
체인 안에서 관리하면 복잡도가 급격히 올라간다.

되돌아오는 지점이 실제로 있다 — `verify_citations` 가 그렇다
([06](06_계약_Agent.md) §1):

```
verify_citations
  ├─ 통과 → 완료
  ├─ 조항번호 오류 → 허용 목록으로 설명문만 1회 수정   ← 되돌아온다
  ├─ 근거 부족    → 표적 검색 1회                    ← 되돌아온다
  └─ 재시도 초과   → 초안 폐기, abstain(CITATION_UNVERIFIED)
```

저장소에 `langgraph 1.2.8` · `langchain 1.3.12` 가 고정돼 있고,
[`app/workflow/ticket_graph.py`](../../app/workflow/ticket_graph.py) 에 `StateGraph` 사용 선례가 있다.

### 이 역할이 실제로 정하는 것

- 어떤 노드가 어떤 툴을 호출하는지
- 툴 입력·출력 **JSON 스키마**
- **Graph State** 에 어떤 값을 저장하는지 (★질병기호는 민감정보 — 해시로)
- 성공·실패·**재시도 조건** (재시도 2회 초과 금지)
- 툴 호출 결과에 따른 **분기**
- **타임아웃과 fallback**
- 에이전트 간 전달 **메시지 형식**

★**자율 ReAct 루프는 만들지 않는다.** 언제 끝날지 모르고 감사가 안 된다.
★그래프가 `verdict` 를 바꾸지 않는다. AI 2가 정한 것을 그대로 나른다.

## 6. 지금 상태 — ★휘발성 관측 기록

> ⚠ **이 표는 진실의 원천이 아니라 재검증 가능한 관측 기록이다.**
>
> 측정 **17:46 시작 ~ 17:48 종료** · 브랜치 `main` · HEAD `4140cae`
> ★**단일 시점 스냅숏이 아니다.** 여러 세션이 같은 디스크를 동시에 고치고 있어
> 측정 중에도 값이 바뀌었다 (`app/insurance/` 가 16:53 에 있었고 17:46 에 없었다).
> **쓰기 전에 각 행의 확인 명령을 다시 돌려라.**
>
> 앞선 판(14:34)은 3시간 만에 낡아 **용어·코호트를 "없음"으로 잘못 적고 있었다.**
> 낡은 상태표의 해는 정보 오류가 아니라 **중복 구현·진행 중 코드 덮어쓰기**다.

### ★값을 적지 않는다 — 확인 명령을 적는다

이 표의 앞 판은 기능마다 ✅/❌ 를 박았다가 **3시간 만에 두 곳이 틀렸다.**
그래서 **판정값을 쓰지 않는다.** 각 항목을 **직접 확인하는 명령**만 둔다.

**판정 규칙** — `PASS` 기대대로 · `FAIL` 명령은 도는데 결과가 기대와 다름 ·
`UNKNOWN` 명령 자체가 실패(경로 없음·연결 안 됨). ★**`UNKNOWN` 을 `FAIL` 로 읽지 마라.**

| **LangGraph** | `ls -l app/workflow/precheck_graph.py` | 존재.<br>★**`app/insurance/` 가 아니다** — 아래 참조 |

### ★두 가지는 특히 잘못 읽기 쉽다

**1. LangGraph 를 `app/insurance/` 에 다시 만들지 마라.**
구현은 [`app/workflow/precheck_graph.py`](../../app/workflow/precheck_graph.py) 에 있다.
`app/insurance/` 가 없는 것은 **의도된 구조**다. 이 문서의 앞 판이 그 경로를 적어놨는데,
그대로 두면 **중복 구현**이 난다.

**2. `422` 를 미구현으로 오판하지 마라.**
`/v1/cohorts` 는 `code` 가 **필수**다. 없이 부르면 422 가 나오는데 **정상 동작**이다.

★**파일이 있다 ≠ 동작한다.** `grep` 으로 라우터 등록만 보면 import 실패·데이터 형식 불일치를
못 잡는다. 위 명령을 **실제로 실행**하는 형태로 쓴 이유다.

★**산출물의 mtime 은 신선도가 아니다.** `data/glossary/passages.jsonl` 이 있다고 해서
**현재 코드로 만든 것이라는 보장은 없다.** 쓰기 전에 다시 만들거나 생성 명령·입력 해시를 확인해라.

### 확실한 것 — 잘 안 변하는 것만 적는다

- **실제 청구결과가 0건이다.** 실제 코호트는 `n=0`, 화면에는 "미공개"로 나간다.
  합법적으로 받을 경로가 아직 없다
- **확정된 약관 문서가 0건이다.** 사람이 식별을 확정해야 판정에 쓸 수 있다

  ★단, **판정 코드는 이걸 이미 막고 있다.** [`ports/precheck.py`](../../app/core/ports/precheck.py) 의
  `REQUIRE_CONFIRMED` 가 **기본 켜짐**이고 `PRECHECK_ALLOW_UNCONFIRMED=1` 로만 끌 수 있다.
  시연용으로 껐는지는 **런타임 환경변수를 봐야** 안다.

  ★★**게이트를 꺼도 판정 응답(`/v1/prechecks`)의 `warnings` 에는 경고가 안 붙는다.**
  경고는 [`/v1/support-manifest`](../../app/routers/precheck.py) 의 `notes` 에만 있다.
  즉 **판정 응답만 보고는 게이트가 꺼졌는지 알 수 없다.** 확인은
  `curl -s localhost:8000/v1/support-manifest` 의 `require_confirmed_documents` 로 한다

- ★**전처리 "완료"와 품질은 다르다.** 무참조 지표에서 `citation_eligible = false` 가
  **1,197건(87.6%)** 이다.

  ★★이건 **실제 결함률이 아니라 휴리스틱 탐지율**이다. 정답셋이 없어
  **precision/recall 을 모른다.** "87.6% 가 망가졌다"로 읽으면 안 된다 —
  "87.6% 가 확인이 필요하다"이다.
  근거: [무참조 품질지표](../reports/2026-08-02_1600_무참조_품질지표_구성과_코드.md)

## 7. 자주 나온 오해

| 오해 | 사실 |
|---|---|
| "RAG를 3개 만든다" | **2개.** 약관(A) / 외부 청구결과(B). 용어 설명은 A의 유스케이스다 |
| "용어 설명용 데이터를 따로 구성한다" | 코퍼스는 같다. **필터와 출력 계약**만 다르다 |
| "판정은 유사사례를 체크해서 준다" | ★**아니다.** 판정은 약관 조항 근거 규칙엔진이다. 유사사례는 별개 구역이고 판정 근거로 인용되지 않는다 |
| "승인율을 위해 모델을 학습시킨다" | 아니다. DB 집계 뷰다 |
| "집계 결과를 LLM이 자연어로 만들어 준다" | 문장은 **코드가 고정 생성**한다. LLM이 다듬으면 정직성 문구가 사라진다 |
| "LangGraph 담당이 RAG도 만든다" | 아니다. **잇고·분기하고·재시도를 통제**한다. 도메인 판단은 안 한다 |
| "근거를 못 찾으면 에러다" | 아니다. **HTTP 200 + `abstained=true`** 가 정상 결과다 |
