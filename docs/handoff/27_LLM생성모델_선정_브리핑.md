## 2. 2026-08-02 — 왜 애초에 `gemma-4-E4B`였나

[SOTA 모델 조사](../reports/2026-08-02_1500_SOTA_모델_조사_코덱스합의.md) §0·§4·§13 요지:

- 판단 기준은 **"가장 좋은 모델"이 아니라 "12GB 로컬에서 파이프라인 전체(OCR+임베딩+
  리랭커+생성)가 함께 도는 것 중 가장 좋은 것"** — 진료비 내역서가 민감 의료정보라
  원문을 외부로 보낼 수 없다는 제약이 이 기준을 만들었다.
- 8GB급 공개 벤치마크: **Gemma 3 4B(Q4)가 JSON 파싱률 100%·스키마 준수율 87%**로
  Llama 3.2 3B(47~56%)·SmolLM2 1.7B(26%)를 크게 앞섬 → **"3B급은 부족하다, 4B급 유지"**.
- 12GB 재검토(§13-1): OCR·임베딩·리랭커·`Gemma-4-E4B Q4(text only)`를 **전부 GPU 상주**
  시켜도 상주 가중치 합 ~8.8GiB로 여유 있게 들어감 — 이게 `gemma4:e4b`가 채택된 실제 근거다.
- `Qwen3.5-4B BF16`도 후보였지만 순차 로드가 필요해(12.7GiB) 우선순위가 낮았다.
- ★문서 자체가 "2026-08-02 이후 공개·변경된 모델은 모른다"고 명시 — §5·§6의 재조사는
  이 공백을 메우는 작업이었다.

## 3. 2026-08-25/26 — EC2 배포가 왜 이 결정을 흔들었나

- EC2 인스턴스 디스크가 **8GB 고정**(리전/스펙상 확장 불가로 판단, [배포 완료보고](../reports/2026-08-25_1727_dockerize_ec2_배포_완료보고.md) §4b) —
  GGUF 모델(수GB) + 나머지 스택이 안 들어감.
- `llm`·`backup` 서비스를 보류하고 `LLM_PROVIDER=openai`, `OPENAI_MODEL=gpt-4o-mini`
  (기존 기본값)로 잠정 전환해 core 스택(postgres·migrate·customer·admin)만 검증.
- ★**이건 "로컬 Gemma4를 버린다"는 결정이 아니었다** — 인프라 제약으로 인한 임시
  우회였는데, 그 뒤 §4.1~4.8 비교가 전부 OpenAI 계열끼리만 진행되면서 이 사실이
  한동안 리포트에 명시되지 않았다(§4.9에서 사용자 지적으로 바로잡음).
