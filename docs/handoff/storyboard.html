팀 비서단 · 2026-08-02 · 사람 화면 · 에이전트 JSON 2트랙 · 9컷
근거: app/schemas/precheck.py(실제 계약) · 06_계약_Agent.md · 08_계약_프론트.md · MVP 기능선정 §5·§6

왜 2트랙인가 — 화면만 그리면 우리 주장을 증명하지 못한다 MVP 기능선정 §6: "AI 에이전트가 화면 없이 직접 쓴다는 것이 이 프로젝트의 포지셔닝 전체이고, 그 주장의 유일한 증거가 에이전트 경로다. 증거 없는 포지셔닝은 발표에서 X."

그래서 같은 9컷을 두 표면으로 그린다. 사람은 화면을 보고, 에이전트는 JSON을 받는다. 둘은 같은 유스케이스(precheck.run())를 부르며 로직을 두 벌 만들지 않는다.

# 다른 기권 사유
#  document_not_reliable  parse_status != ok
#  citation_unverified    인용 검증 실패 → 초안 폐기

절대 하면 안 되는 것
  • needs_expert 를 "보장 안 됨"으로 표시 — 전혀 다른 뜻이다
  • needs_documents 를 "보장"으로 표시 — 조건이 있다
  • 면책 목록에 없다는 것을 "보장됩니다"로 표시 — 보장은 '보상하는 사항' 조항이 정한다
  • 기권을 5xx 로 내보내기 — 에이전트가 재시도 루프를 돈다
사람 트랙 주의 — 회색으로 흐리게 처리하면 "실패"로 읽힌다. 다른 판정과 크기·대비를 같게 둔다.
에이전트 트랙 주의 — abstained 를 안 보고 verdict 만 읽는 클라이언트가 반드시 생긴다. 그래서 reason_code 를 항상 채우고 스키마 리소스(insurance://schemas/precheck-v1)에 명시한다.

절대 규칙 — 두 구역을 같은 목록에 합치지 않는다. UNION 하는 뷰·쿼리·엔드포인트를 만들지 않는다. "승인율 82.5%"라고 쓰지 않고 "40건 중 33건 승인"과 경고를 함께 쓴다. 생존 편향은 사후 보정이 불가능한 구조적 편향이라 숫자로 고칠 수 없고 말로 밝혀야 한다.
★에이전트에게 data_source 를 생략하지 않는다. 사람은 화면의 DEMO 배지를 보지만, 에이전트는 필드를 안 보면 합성 수치를 실제로 오해해 자기 사용자에게 전달한다.
★왜 "승인 확률"로 표시하지 않나 — 이유 셋
  • 빈도는 사실, 확률은 예측이다. "40건 중 33건"은 과거 사실이지만 "82% 확률로 승인"은 예측이고, 우리 표본으로는 못 받친다
  • 개인 확률은 비범위다. MVP §4 — "개인 예상 지급액 제시(손해사정 유사행위 소지) · 과거 분포만 표시"
  • 확률로 말하면 편향이 숫자 안으로 숨는다. 빈도로 말하면 편향 경고가 숫자 바깥에 남는다
★그래서 문구에 주어를 박는다. "승인 비율 68%~91%" 라고만 쓰면 사용자는 "내가 그 확률로 받는다" 로 읽는다 — 신뢰구간은 모수(과거 사례들의 비율) 에 대한 진술이지 개인에 대한 것이 아니다.

구조로 강제된다 — 집계 뷰가 evidence_verification 을 조인하므로 unverified 상태로는 통계에 들어갈 수 없다.
★외부 에이전트가 준 사례는 판정 근거가 아니다(tier="external_report"). 통계·사후검증에만 쓰고 약관 조항과 같은 인덱스에 넣지 않는다. precheck_trace_id 가 있으면 우리 판정과 실제 결과를 대조할 수 있다 — 이게 이 제품의 학습 고리다.
★"사람이 검수한다"는 영구 전제가 아니다 — 확장 경로 지금은 관리자가 한 건씩 본다. 규모가 커지면 이건 못 버틴다. 적어 두지 않으면 "사람이 다 본다"가 영구 전제처럼 굳는다.
병목 상한을 미리 안다 — 1건 5분 · 하루 2시간이면 하루 24건 · 월 500건 남짓이 한계다.
★핵심은 "검증"이 한 덩어리가 아니라는 것이다. 등급을 쪼개면 사람 판단이 꼭 필요한 부분은 생각보다 작다.

★스키마는 바뀌지 않는다 — verification_method NOT NULL 이 이미 "누가·무엇으로"를 요구한다. 검증 주체가 사람이든 규칙엔진이든 API든 같은 자리에 기록된다. 자동화는 스키마 변경이 아니라 값의 추가다: admin_review | consistency_rules | issuer_api | cross_submission
★대가 — 등급을 뭉뚱그리지 않는다. 자동 검증은 사람 검수보다 강도가 낮다. verified 하나로 합치면 자동화가 진행될수록 통계가 조용히 묽어진다. 그래서 코호트를 verification_method 별로 쪼개 보고, 화면에는 "검증 40건"이 아니라 "발행처 확인 12건 · 자동 정합성 28건" 으로 쓴다.
하지 않을 것 — LLM 이 지급통지서를 읽고 "검증됨"으로 올리는 것. 그건 검증이 아니라 추측이다. LLM 은 필드를 뽑는 데까지만 쓰고, 맞는지는 규칙·해시·외부 조회가 판단한다. 검증 단계의 오류는 판정 오류보다 범위가 넓다 — 통계 전체로 번진다. 자세한 것은 03_에이전트_데이터_축적_설계.md §3-1.

4. 시연 시나리오

같은 케이스를 두 번 보여준다
  1. 사람으로 — 웹 화면에서 ①→⑨ 를 끝까지 한 번
  2. 에이전트로 — 보호 REST 계약에 맞는 curl/외부 HTTP client 로 같은 케이스를 JSON으로. 같은 verdict·같은 citations 가 나오는 것을 나란히 띄운다
  3. 기권 케이스 — 근거 없는 질병기호로 needs_expert + 200
  4. 증빙 제출 — 제출해도 n 이 안 움직이고, 검수 후 n+1
★2번이 포지셔닝을 증명하는 유일한 장면이다. 화면만 보여주면 약관 챗봇으로 보인다.

5. 범위를 줄여야 한다면

줄이는 순서 ① 지원범위 화면 축소 → ③ 되묻기를 단일 상품 고정으로 → ② 처방전 업로드를 직접 입력만으로 → MCP 4종을 REST + llms.txt 만으로

⑤ ⑥ ⑧ ⑨ 와 에이전트 트랙 자체는 줄이지 않는다. 앞의 넷은 정직성 장치이고, 에이전트 트랙은 포지셔닝의 증거다. 빼면 남는 것은 약관 챗봇이다.

6. 확인 방법

백엔드·테스트 통과만으로 "완료"라 하지 않는다

  • 에이전트 트랙 — curl 또는 외부 HTTP client 로 응답 JSON 원문을 확인한다. OpenAPI 문서(/docs)만 보고 넘어가지 않는다
  • ★needs_expert 는 실제 기권 케이스로 띄워 본다 — 정상 케이스만 보면 이 화면·이 응답은 끝까지 안 보인다
