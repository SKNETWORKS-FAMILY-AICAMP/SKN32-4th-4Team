# A2A 를 넣을 것인가 — 판단 기록

2026-08-02 · 코덱스 2차 검토(팀 반론 반영)

---

## 0. 결론

**A2A 프로토콜은 필수가 아니다.** 다만 팀 반론의 **문제의식은 타당하다.**

> 팀이 원하는 것: "여러 에이전트가 접속하고 그걸 관리한다"
> 그걸 주는 것: **API 키 + 클라이언트 레지스트리 + 데모 에이전트**
> A2A 프로토콜은 **그 위에 얹는 별개 층**이다

우선순위:

```
1순위  API 키 + 클라이언트 레지스트리 + 감사      ← 이게 "에이전트 관리"다
2순위  데모용 에이전트 (REST + MCP 클라이언트)     ← 시연에 필요
3순위  MCP 서버 (도구 3개)                        ← 표준 도구 노출
4순위  A2A 얇은 어댑터                            ← 발표 차별화가 필요할 때만, 3~5일 timebox
```

---

## 1. 팀 반론과 그에 대한 답

> "접속하는 유저들이 판정 자료를 공유하는 상황이다.
>  여러 에이전트가 접속하고 그걸 관리해야 한다."

**맞다.** 그런데 그 요구는 A2A 프로토콜이 아니라 **클라이언트 관리**가 푼다.

| 필요한 것 | A2A 가 주나? | 실제로 필요한 것 |
|---|---|---|
| 에이전트 등록·식별 | ❌ | `agent_client` 테이블 |
| 권한 구분 | ❌ | scope (`precheck:read` 등) |
| 사용량 제한 | ❌ | 레이트리밋 |
| 누가 뭘 했나 | ❌ | 감사 로그 |
| 판정 자료 받기 | ❌ | `POST /v1/observations` (이미 있다) |
| **표준 방식으로 기능 발견** | ✅ | Agent Card |
| **다른 A2A 클라이언트와 연동** | ✅ | A2A 바인딩 |

**A2A 를 넣어도 위 다섯 개는 그대로 따로 만들어야 한다.**
즉 "여러 에이전트 관리" 문제는 A2A 로 풀리지 않는다.

---

## 2. 구분 기준 — MCP 냐 A2A 냐

| | MCP | A2A |
|---|---|---|
| 관계 | agent → **tool** | agent ↔ **agent** |
| 상호작용 | 부르고 즉답 받음 | 장기·상태형 협업 |
| 필요 조건 | 도구를 노출하면 됨 | Task 수명주기, 협상, 위임 |

**우리 판정은 즉답이다**(규칙 기반, 수백 ms). 장시간 비동기가 아니고,
추가 자료를 여러 번 협상하지도 않는다. → **MCP 가 맞는 추상화**다.

A2A 가 필요해지는 시점:
- 판정이 오래 걸려 polling/cancel 이 필요할 때
- 자료를 여러 번 주고받으며 협상할 때
- 다른 독립 보험·의료 에이전트에 작업을 **위임**할 때

지금은 셋 다 아니다.

---

## 3. 테스트용 에이전트 — **A2A 와 별개다**

팀이 "테스트용 에이전트도 우리 구성에 둬야 한다"고 한 것은 맞다.
그런데 그건 **클라이언트를 하나 만드는 일**이지 서버 프로토콜을 세우는 일이 아니다.

```
외부 REST client(curl/팀별 client)  REST 로 우리를 부르는 외부 에이전트
scripts/mcp_smoke.py                현행 보험 MCP stdio 왕복 검증
```

이 둘이면 시연에서 "에이전트가 우리 서비스를 쓴다"를 보여줄 수 있다.
A2A 서버 없이도 된다.

---

## 4. 기존 `app/routers/a2a.py` 는 A2A 가 아니다

```
GET  /agents     커머스 시절 가짜 전문 에이전트 목록
POST /message    커스텀 형식
```

표준 A2A 가 요구하는 것이 없다:
- `/.well-known/agent-card.json`
- 표준 Agent Card 형식
- 표준 Message/Part 구조
- 요청별 권한 검사

**"이미 A2A 가 있다"고 간주하면 안 된다.** 이름만 같은 잔재다.

---

## 5. 넣는다면 — 최소 구성

3~5 개발일 timebox. 그 이상이면 자른다.

| 넣는다 | 뺀다 |
|---|---|
| `/.well-known/agent-card.json` | streaming |
| skill **하나만**: `coverage-precheck` | push notification |
| HTTP+JSON 바인딩 | Task 영속화·취소 |
| 직접 Message 응답 (Task 없음) | 서명된 카드 |
| 표준 오류 형식 | 멀티테넌시 |

### 구조 — 로직을 두 벌 만들지 않는다

```
외부 에이전트
   ├─ REST   POST /v1/prechecks    ← 정본
   ├─ MCP    insurance_precheck    ← 어댑터
   └─ A2A    coverage-precheck     ← 어댑터 (선택)
                    ↓
          precheck.run()  동일한 application service
```

A2A 어댑터도 **내부 HTTP 자기호출이 아니라 같은 서비스를 직접 부른다.**

### Agent Card 와 support-manifest 는 합치지 않는다

| | 답하는 질문 |
|---|---|
| Agent Card | "어떤 인터페이스와 skill 을 제공하는가" |
| `/v1/support-manifest` | "어느 보험사·세대·기간을 실제로 판정할 수 있는가" |

서로 다른 계약이다.

## 6. 얻는 것과 잃는 것

**얻는 것**
- 표준 Agent Card 로 기능 발견
- 다른 A2A SDK/클라이언트와 연동 가능성
- 발표 소재: "REST 전용이 아니라 A2A 원격 에이전트로도 노출된다"

시연 장면:
> 외부 에이전트가 well-known 카드 조회 → `coverage-precheck` skill 발견
> → A2A 메시지 전송 → 내부 판정 실행 → 근거와 `trace_id` 가 담긴 응답

**잃는 것**
- REST/OpenAPI/MCP/A2A **네 겹의 인터페이스**
- 입력 검증·오류·인증·버전 관리의 중복
- 판정 DTO 를 A2A Message/Part 로 다시 감싸는 비용
- SDK·사양 변경 리스크
- 발표 직전 통합 테스트 표면 증가
- **"A2A 를 썼지만 실제로는 REST 한 번 호출"이라는 과장 인상**

마지막 항목이 특히 위험하다. 발표에서 지적당하기 쉽다.

---

## 7. 그래서 이렇게 한다

```
1주  API 키 + 클라이언트 레지스트리 + 감사        ★ "에이전트 관리"의 실체
2주  데모 에이전트 (REST)  +  판정 수직 슬라이스
3주  MCP 서버 (도구 3개)  +  observations 접수
4주  평가·보안·시연
       └ 여유가 있고 발표 차별화가 필요하면 A2A 어댑터 3~5일 timebox
```

**A2A 는 "있으면 좋은 것"이지 "없으면 안 되는 것"이 아니다.**
그리고 공식 A2A SDK 클라이언트와 왕복 테스트가 통과할 때만
"A2A 호환"이라고 발표한다. 그 전에는 말하지 않는다.
