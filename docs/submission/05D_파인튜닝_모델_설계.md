### 0-1. ★2026-08-05 개정 — **합성 파일럿을 돌림**

## 1. 목적과 비범위

### 1-1. 파인튜닝이 **고칠 수 있는 것**

생성 단계의 **형식·태도 문제**다.

| 문제 | 예 |
|---|---|
| 근거 밖 문장을 덧붙임 | 검색 근거에 없는 "보통 이런 경우는…" |
| 기권해야 할 때 답해 버림 | 근거 0건인데 그럴듯한 설명 생성 |
| 인용을 문장에 연결하지 않음 | 근거는 있는데 어느 주장의 근거인지 안 밝힘 |
| 출력 schema 위반 | `verdict` 를 자유문장으로 씀 |

### 1-2. ★파인튜닝이 **고칠 수 없는 것** — 이게 더 중요하다

RAG 오류의 대부분은 생성 이전에 발생하고, **생성 모델을 학습시켜도 사라지지 않는다.**

| 실패 | 왜 파인튜닝으로 안 되나 |
|---|---|
| **검색이 조항을 못 찾음** | 후보에 없는 것을 생성 모델이 만들어 낼 수 없다(만들면 그게 환각이다) |
| **잘못된 판본을 골랐음** | 판본 확정은 `policy_version` 조회 문제다 |
| **표의 행·열이 깨졌음** | 전처리 문제다. 학습으로 복원하면 **그럴듯하게 틀린 값**이 생긴다 |
| **약관 자체에 없음** | 없는 것은 없다. 기권이 정답이다 |

★**"OCR 불일치를 생성 LLM 이 상식적으로 교정하게 한다"는 절대 하지 않는다.**
불일치는 교정 대상이 아니라 **기권 대상**이다.

### 1-3. 그래서 착수 조건을 먼저 정한다

아래 넷을 **모두** 만족하기 전에는 시작하지 않는다.

1. 승인된 `질의–근거–답변` 데이터 **≥ 3,000건**
2. 보험사·세대·판정상태별 **holdout 분리**, 동일 문서 문장이 train/test 에 중복되지 않음
3. 답변의 **모든 주장**에 citation 이 연결되고 **이중 검수** 통과
4. base RAG 대비 **근거성 · 기권 정확도 · 인용 정확도를 동시에** 개선

**현재 충족 상태**

| 조건 | 지금 | 판정 |
|---|---|---|
| 1. 승인 QA ≥ 3,000 | 승인 OCR facts 850 · 승인 QA 쌍 **0** | ❌ |
| 2. holdout 분리 | 검색 평가셋 417 은 있으나 **생성용 아님** | ❌ |
| 3. 이중 검수 | 프로세스 미정의 | ❌ |
| 4. 동시 개선 증명 | baseline 측정 자체가 없음 | ❌ |

→ **제대로 된 파인튜닝도 착수 불가.** 이 문서는 조건이 맞을 때를 대비한 테스트런에 가까움

> 즉, 이건 「**완전 합성** 데이터로 파이프라인 시험」
> 승인 QA 는 그대로 **0건**이고, 합성 데이터로 학습한 어댑터의 정확도는
> **품질 근거가 될 수 없다.** "파인튜닝했다" X

### 3-2-1. ★**어떻게 3,000건을 얻나** — 획득 계획 (2026-08-26 · 코덱스 검토 반영)

사용자 요구는 *"기계 처리를 최대한 하고 사람 작업을 최소화"* 였다.
그 방향으로 안을 세워 코덱스에 반박을 요청했고, **내가 세운 축소 장치 두 개가 폐기됐다.**

#### ★먼저 — 폐기된 것 두 개

| 내가 세운 안 | 판정 | 왜 |
|---|---|---|
| **「이중 기계 심판이 일치하면 자동 승인」** | ☠**폐기** | NLI 심판이 **같은 검색 결과를 본다.** 누락 근거·잘못된 판본·공통 인용 오류를 **둘이 같이 놓친다.** 일치는 승인이 아니라 「1인 검수로 충분」의 근거로만 쓴다 |
| **「층화 표본으로 오류율 재고 낮은 층은 층 단위 승인」** | ☠**폐기** | 표본이 통과해도 **개별 건의 인용이 맞다는 보장이 없다.** 판정 근거가 되는 데이터라 건별 확인이 필요하다 |

★**그래서 결론이 뒤집혔다** — **3,000건 전부가 최소 1회 사람을 거친다.**
줄일 수 있는 것은 **건수가 아니라 건당 시간**이다.

|---|---:|---|---|
| **A** 승인 조항 QA | 1,800 | ★**`retrieval_probes.json` 의 `exclusion_queries` 212건**에서 시작(`query`+`gold_ids`+`sha12` 가 이미 짝지어져 있다) → 부족분은 확정문서×KCD 로 `/v1/prechecks` 배치 | 확정 1,353문서 · `page_probes` 1,880 |
| **B** OCR facts QA | 600 | 승인 850 facts × 질의 템플릿 (표 값·locator 보유) | facts 850 · 청크 75 |
| **C** 기권 hard negative | 600 | 판결·금감원 골든셋 **114건(사람 검토 완료)** + 지식갭 35 + 결손 주입 4종 | ↓ |

★**A 를 「문서 × KCD 무차별 조합」으로 만들지 않는다**(코덱스 지적). 그러면 **오답 라벨**이 생긴다.
기존 212쌍처럼 **정답 조항이 확인된 것**에서 시작한다.

★**C 의 결손 주입은 「조건 제거」만으로 부족하다.** 근거를 지웠을 때
**대체 근거가 정말 없는지**까지 검사해야 한다 — 다른 조항이 답을 갖고 있으면 그건 기권 정답이 아니다.

```
결손 4종:  근거 0건        → no_evidence
           상품 3개 겹침    → ambiguous_product
           parse_status≠ok → document_not_reliable
           인용 ID 교체     → citation_unverified
```

#### ★★학습 입력 설계 — 규칙엔진 상한 문제의 해답

내가 물은 것: *"규칙엔진 출력을 초안으로 쓰면 SFT 가 「LLM 이 규칙엔진을 흉내내게」 만드는 것 아닌가."*

**답: 맞다. 그래서 LLM 에게 `verdict` 를 맞히게 하지 않는다.**

```jsonc
// 입력에 **판정 결과를 같이 넣는다**
{ "context": {...}, "question": "...", "evidence": [...],
  "engine_verdict": "needs_documents",        // ← 규칙엔진이 이미 정한 것
  "engine_reason_code": "exception_applies",
  "engine_citations": ["eb778…/보통약관/제4조#6dcb03bc"] }

// 출력은 **설명만**
{ "message": "면책의 예외에 해당합니다. 요양급여 해당 여부 등 조건을 확인해야 합니다.",
  "citations": ["eb778…/보통약관/제4조#6dcb03bc"] }
```

★**질문만 보고 `verdict` 를 맞히게 학습시키면 규칙엔진의 불완전한 복제품이 된다.**
판정은 규칙엔진이, LLM 은 **설명**이 — 05C §2-3 의 역할 분리를 학습 형식에서도 지킨다.
그러면 「품질 상한이 규칙엔진」인 것이 **결함이 아니라 설계**가 된다.

#### 사람이 하는 것 — 비용 실측 기반 추정

기준선은 추정이 아니라 **실측**이다. 2026-08-26 에 5명이 끝낸 600건 라벨링의
`reviewed_at` 타임스탬프에서 **건당 43.2초 · 실작업 7.2시간**이 나왔다
(→ [24_팀원_배분가능_작업목록.md §1-1](../handoff/24_팀원_배분가능_작업목록.md)).

★그 600건은 **선택지 고르기**였고 QA 검수는 *"이 근거가 이 주장을 받치나"* 를 읽어야 한다.
**2~3배로 잡는다** — 코덱스도 이 배수가 타당하다고 봤다.

| | 값 |
|---|---|
| 건당 | 86.4 ~ 129.6초 |
| 3,000건 총량 | **72 ~ 108 인시** |
| 5명 병렬 | **1인 14.4 ~ 21.6시간** |
| 재검 큐(불일치·저신뢰·수정발생) | **20% = 600건** 용량으로 준비 |

★B(승인 fact 강조 표시)와 명백한 C 는 더 빠를 가능성이 크지만 **파일럿 전에는 할인하지 않는다.**

#### 층화 — 축을 전면 교차하지 않는다

`12개사 × 5세대 × 4 verdict × 10 reason_code × 3축` 을 다 교차하면 **희소층만 양산된다.**
**축별 오류 원인**을 1차 층으로 삼는다.

| 축 | 1차 층 |
|---|---|
| A | `verdict × reason_code` (종속이면 희소 셀은 합친다) |
| B | `fact 종류 × 표 파싱 상태` |
| C | 결손 4종 각각 |

보험사 12곳·세대 1~5 는 **층이 아니라 각 층 안의 커버리지 할당**으로 둔다.

★**층당 30건은 탐색용 최소, 60건은 운영 판단 최소.**
오류 **0/60 이어도 95% 상한이 약 5%** 다. 1% 미만을 주장하려면 **0/300** 이 필요하다 —
표본으로 「안전하다」고 말할 때 이 수를 함께 적는다.

#### 순서 — 파일럿 300건 먼저

```
1단계  파일럿 300건 (세 축 동시)   A 180 · B 60 · C 60
         A 는 기존 exclusion 212쌍에서 · C 는 결손 4종 × 15건
         ★60건은 블라인드 이중 검수(사람 간 일치율 측정용)
         ↓ 통과 기준
         · 치명적 출처·판본·교차문서 인용 오류  **0건**
         · 중대 라벨 오류                      **≤ 2%**
         · 사람 간 일치율                      **≥ 90%**
         ↓
2단계  본생산  **B → C → A**
         B 로 locator·화면을 안정화 → C 로 무폴백 기권을 검증
         → 가장 비싸고 위험한 A 를 300~500건 배치로
```

★**A 를 마지막에 둔다.** 가장 많고(1,800) 가장 판단이 무겁다.
앞의 둘로 화면과 기준을 다듬은 뒤에 들어가야 재작업이 없다.

#### 검수 화면 요구사항

600건 화면이 43.2초/건을 낸 이유를 살린다 — **한 화면, 한 키 입력.**

| 항상 보인다 | 기본은 숨긴다 |
|---|---|
| 질문 · 최종 답변/verdict | NLI 심판 결과 ★**결정 전에는 숨긴다** |
| **강조된 조항/표 셀 + 앞뒤 문맥** | 장황한 생성 근거 · 원시 JSON |
| 문서명 · 세대 · `sha12` · 쪽 · 조항 ID · `parse_status` | 관련 없는 조항 |

★**기계 의견을 먼저 보여주면 사람이 그것을 따라 찍는다**(15번 문서에서 같은 이유로
자동값을 후보 파일에서 뺐다). 결정한 뒤에 펼쳐 보게 한다.

필수: `[A]승인 [E]수정 [N]기권 [R]반려` 단축키 · 사유 단축키 · 다음 항목 자동 이동 ·
**즉시 자동저장** · Undo · 작업 잠금(동시 검수 충돌 방지) · 감사로그 · **중단 후 정확한 위치 복귀**.

> ★이 절은 **계획이지 실적이 아니다.** 2026-08-26 기준 승인 QA 는 여전히 **0건**이다.

### 3-3. ★제외 — 넣으면 안 되는 것

| 제외 대상 | 왜 |
|---|---|
| 미승인 candidate facts (8,622건) | 사람이 승인하지 않았다. 학습하면 승인 게이트가 무의미해진다 |
| 다른 판본이 섞인 근거 | 판본이 다르면 정답이 다르다 |
| 생성만 있고 검수 없는 데이터 | 모델 출력을 모델에 다시 먹이면 오류가 증폭된다 |
| `tier != POLICY_CLAUSE` 인 근거 | 외부 리포트·통계는 판정 근거가 될 수 없다 |
| `parse_status != "ok"` 문서 | 판정에 못 쓰는 데이터로 학습하지 않는다 |

### 3-4. ★분할 — 랜덤 70/15/15 를 쓰지 않는다

같은 약관 조항이 **최대 170개 문서에 그대로 실린다**(중복률 66.5%).
행 단위로 랜덤 분할하면 **train 의 문장이 test 에 그대로 들어가** 성능이 부풀려진다.

```
분할 키 = (document_sha256, product_line)   ← 문서·상품계열 단위로 통째로 나눈다
  train 70%   valid 15%   test 15%

추가 검사 (분할 후 반드시)
  ① content_hash 교집합 = 0        (같은 조항 내용이 양쪽에 없다)
  ② 보험사 12곳이 test 에 모두 존재
  ③ 세대 1~5 가 test 에 모두 존재
  ④ 기권 사례(C) 비율이 train/test 에서 ±3%p 이내
  ⑤ seed 고정 (42) · 분할 결과 SHA-256 을 manifest 에 기록
```

★①이 0 이 아니면 누수가 있는 것 => **학습을 시작하지 않는다.**

## 4. QLoRA 설정 — 못 박을 수 있는 값

★**초기값이다.** pilot 측정 전에는 이 값이 최적이라고 주장하지 않는다(§4-3).

### 4-1. 양자화 · 어댑터

```yaml
quantization:
  load_in_4bit: true
  bnb_4bit_quant_type: nf4          # ★fp4 아님. 정규분포 가중치에 nf4 가 맞다
  bnb_4bit_use_double_quant: true   # 양자화 상수까지 양자화 — 약 0.4bit/param 절약
  bnb_4bit_compute_dtype: bfloat16  # ★fp16 아님. 학습 중 overflow 회피

lora:
  r: 16
  lora_alpha: 32                    # alpha/r = 2.0
  lora_dropout: 0.05
  bias: none
  task_type: CAUSAL_LM
  target_modules: [q_proj, k_proj, v_proj, o_proj]
```

> ★★**이 `target_modules` 를 그대로 쓰면 학습이 시작되지 않는다** (2026-08-04 확인).
>
> ```
> ValueError: Target module Gemma4ClippableLinear(
>   (linear): Linear4bit(in_features=768, out_features=768, bias=False)
> ) is not supported.
> ```
>
> **원인은 비전 타워다.** E4B 는 멀티모달이라 이미지 인코더에도 같은 이름의
> q/k/v/o 가 있고, **그쪽만** `Gemma4ClippableLinear` 로 감싸여 있다
> (오류의 `in_features=768` 도 언어모델이 아니라 비전 인코더 차원이다).
> 이름으로만 매칭하면 그것까지 잡혀 **실행 전체가 죽는다.**
>
> 언어모델의 q/k/v/o 는 평범한 `Linear4bit` 다 — 비전·오디오 타워를 빼면
> 위 목록이 **그대로 동작한다**(실측: 대상 132개 = 33층 × 4,
> 이름은 `model.language_model.layers.*.self_attn.q_proj` 로 `.linear` 접미사가 없다).
> 빼기 전에는 대상이 100개였고 그중 앞자리가 `model.vision_tower.…` 였다.
> → [결함 리포트 D2](../reports/debugs/2026-08-04_2250_파인튜닝_착수_전_결함3건.md)

★`target_modules` 를 **attention 4개로 시작**한다. MLP(`gate/up/down`)까지 넣으면
학습 파라미터가 2~3배가 되고 VRAM·시간이 늘지만, 우리 과제(형식·기권 태도)는
**표현 학습이 아니라 행동 학습**이라 attention 만으로 충분한지 먼저 본다.
부족하면 그때 넓힌다 — 넓히는 실험은 §7 의 ablation 에 넣는다.

### 4-2. 학습 스케줄

```yaml
max_seq_length: 2048              # 근거 3~5건 + 질의 + 출력이 들어가는 길이
per_device_train_batch_size: 1
gradient_accumulation_steps: 16   # 유효 배치 16
gradient_checkpointing: true      # ★VRAM ↔ 속도 교환. 12GB 에서 필수
learning_rate: 2.0e-4
lr_scheduler_type: cosine
warmup_ratio: 0.03
num_train_epochs: 2               # ★3,000건 규모에서 3 이상은 과적합 위험
weight_decay: 0.0
max_grad_norm: 0.3
optim: paged_adamw_8bit           # 12GB 에서 optimizer state 압박 완화
seed: 42
```

★**epoch 를 2 로 둔다.** 3,000건은 작다. 작은 데이터에 오래 돌리면
**기권 문구를 통째로 외워** 근거가 있는 상황에서도 기권하게 된다.

### 4-3. ★pilot 전에는 확정할 수 없는 것

| 항목 | 왜 못 박을 수 없나 |
|---|---|
| peak VRAM | E4B 는 per-layer embedding 구조라 공개 파라미터 수로 환산이 안 맞는다 |
| step 당 시간 · 총 학습 시간 | 커널·드라이버·시퀀스 분포에 따라 달라진다 |
| 안전한 최대 `max_seq_length` | 2048 이 OOM 없이 도는지는 측정해야 안다 |
| 최종 분할 건수 | 데이터가 아직 0건이다 |
| **성능 향상 폭** | ★baseline 조차 측정하지 않았다 |

**pilot 절차**: 데이터 200건 · 50 step 으로 먼저 돌려 peak VRAM · step/s 를 재고,
그 값으로 `max_seq_length` 와 `gradient_accumulation_steps` 를 확정한다.

처리량 **-21%**. 이 비용은 05D 어디에도 적혀 있지 않았다.

## 5. VRAM 예산 (RTX 4070 SUPER 12GB) — ★추정

```
① 4-bit 베이스 가중치      = 파라미터수 × 0.5 byte × (1 + double-quant 오버헤드)
② LoRA 파라미터            = r × (d_in + d_out) × 대상모듈수 × 층수
③ optimizer state          = ② × 2 (paged AdamW 8bit 기준)
④ 활성값(activations)      = f(batch, seq_len, hidden, 층수) ÷ gradient_checkpointing
⑤ 단편화·CUDA 컨텍스트 여유 = 총합의 10~15%
```

| 구성 요소 | 추정 | 확실도 |
|---|---|---|
| ① 베이스 (E4B · NF4 · double quant) | 2.5~3.0 GiB | 중 — 공식 Q4 GGUF 텍스트 5.15GB 를 기준으로 역산 |
| ② + ③ LoRA + optimizer (r=16 · q/k/v/o) | 0.3~0.6 GiB | 중 |
| ④ 활성값 (seq 2048 · batch 1 · checkpointing on) | 1.5~2.5 GiB | **낮음** ← pilot 필요 |
| ⑤ 여유 | 0.6~0.9 GiB | — |
| **합** | **약 5~7 GiB** | ★**틀렸다** — 실측 peak allocated **15.38 GiB**(§4-5) |

> ★★**이 표에 빠진 항목이 있다** (2026-08-05 실측).
> `prepare_model_for_kbit_training()` 이 비양자화 파라미터를 **float32 로 업캐스트**하는데,
> E4B 의 per-layer embedding 에서 그 한 번이 **10.50 GiB** 를 요구했다.
>
> ```
> torch.OutOfMemoryError: Tried to allocate 10.50 GiB
>   peft/utils/other.py:202   param.data = param.data.to(torch.float32)
> ```
>
> compute dtype 이 이미 bf16 이라 이 업캐스트는 **불필요하다.**
> `gradient_checkpointing_enable()` + `enable_input_require_grads()` 로 대체하고 나서야
> seq 2048 학습이 돌았다. 위 ①~⑤ 다섯 항목만 세면 이 비용이 통째로 빠진다.

★**이 표는 실측이 아니다.** `model_registry.yaml` 의 `memory_peak_mb` 는 아직 `null` 이다.
학습을 시작할 때 pilot 로그의 `torch.cuda.max_memory_allocated()` 값을 여기 채워 넣는다.

> ★2026-08-04 파일럿 시도에서도 **채우지 못했다**(§4-4). GPU 경합 상태의 OOM 이라
> 그 숫자를 여기 적으면 거짓이 된다. `null` 로 둔다.
>
> 다만 한 가지는 관찰됐다 — **비전 타워를 LoRA 대상에서 빼는 것만으로 GPU 점유가
> 11,938 → 9,112 MiB 로 내려갔다.** 위 표 ①~⑤ 는 **텍스트 경로만** 계산한 값이라
> 멀티모달 가중치(비전 타워·projector)를 빠뜨리고 있을 가능성이 있다.
> 05C §6 이 "공식 Q4 GGUF 는 텍스트 가중치만 5.15GB, 멀티모달 projector 가 추가 992MB"
> 라고 이미 지적한 것과 같은 종류의 누락이다. 재측정 때 확인한다.

★**학습 중에는 OCR·검색·리랭커를 GPU 에서 내린다.** 05C §6 의 「전부 상주」 예산은
**추론 기준**이고 학습과 동시에 성립하지 않는다.

## 7. 평가 프로토콜

### 7-1. baseline 을 **먼저** 고정한다

```
baseline = 같은 검색·리랭크·게이트 + 파인튜닝 안 한 Gemma-4-E4B
```

★**검색 경로를 함께 바꾸지 않는다.** 둘을 같이 바꾸면 무엇이 기여했는지 알 수 없다.

### 7-2. 지표 — 넷을 **동시에** 본다

| 지표 | 정의 | 합격 기준(안) |
|---|---|---|
| **citation precision** | 인용한 조항이 실제로 그 주장을 지지하는 비율 | baseline **이상**, 하락 0 |
| **groundedness** | 답변의 각 주장이 제공된 근거로 검증되는 비율 | baseline 대비 **+5%p 이상** |
| **abstention precision / recall** | 기권해야 할 때 기권했나 / 기권하지 말아야 할 때 안 했나 | recall **≥ 0.95**, precision 하락 0 |
| **schema validity** | 출력이 `PrecheckResult` 스키마를 만족하는 비율 | **100%** (제약 디코딩이므로) |

★**하나라도 회귀하면 채택하지 않는다.** 특히 `abstention recall` 은 안전 지표다 —
여기가 떨어지면 "모르는데 답하는" 모델이 된 것이고, 다른 지표가 올라도 **실패**다.

### 7-3. 층별로 본다 — 평균만 보지 않는다

```
보험사 12곳별 · 세대 1~5별 · verdict 4단별
→ ★최저 구간이 baseline 보다 나쁘면 평균이 올라도 채택하지 않는다
```

한 보험사에서만 좋아지고 다른 곳이 나빠지면 그건 개선이 아니라 **편향**이다.

### 7-4. 표본이 작으면 구간으로 말한다

test 가 수백 건 규모라면 점추정을 단정하지 않는다.
**paired bootstrap 10,000회 · 95% 신뢰구간**을 붙인다(리랭커 평가와 같은 방식).
구간이 0 을 걸치면 **"차이를 확인하지 못했다"** 라고 적는다 — "같다"가 아니다.

## 8. 재현과 롤백

### 8-1. 재현에 필요한 것 (manifest 로 고정)

```
베이스 모델 repo + revision           bb3b92e6…
학습 데이터 SHA-256                   (분할 후 train/valid/test 각각)
분할 seed                             42
QLoRA 설정 파일 SHA-256
라이브러리 버전                       transformers · peft · bitsandbytes · torch

평가 결과 JSON SHA-256

```

경로에 버전을 박아 **덮어쓰지 않고 공존**시킨다.

### 8-2. 배포 게이트

```
pilot → 학습 → 평가(§7) → ★사람 검수 → model_registry 에 새 프로필 추가
                                          artifact_sha256 · verified_at 채움

```

★`artifact_sha256` 이나 `verified_at` 이 비어 있으면 **배포하지 않는다.**
지금 `local_gemma4_e4b` 가 그 상태이며, 그래서 "승인된 모델"이라고 부르지 않는다.

### 8-3. 롤백

adapter 방식이라 되돌리기가 싸다.

```
1. .env 의 LLM_PROVIDER / LOCAL_MODEL 을 base 프로필로 되돌린다
2. adapter 를 로드하지 않는다 (베이스 가중치는 애초에 안 바뀌었다)
3. 판정 결과는 영향받지 않는다 — ★판정은 규칙엔진과 인용 게이트가 하고
   LLM 은 설명만 생성하기 때문이다(05C §2-3)
```

★**이 마지막 줄이 이 설계의 안전장치다.** 생성 모델이 나빠져도 **잘못된 보장 판정으로 이어지지 않는다.**

| 3 | **12GB 예산에 안 들어간다** | 학습 peak **15.38 GiB**. §2 가 QLoRA 를 고른 근거("12GB 단일 GPU 에서 가능한 유일한 선택")가 **이 설정 그대로는 성립하지 않는다** |
| 4 | **배포 게이트를 못 넘는다** | §8-2 는 `artifact_sha256`·`verified_at` 이 비면 배포 금지다. §1-3 착수 조건 넷이 **전부 미충족**이라 애초에 후보가 아니다 |

**추가로, 붙일 자리도 없다.** 현행 서빙은 `llama-cpp-python` + Q4 GGUF 다(05C §2).
이번 어댑터는 HF transformers 4bit 경로에서 만들어졌다.
붙이려면 **런타임을 바꿔야 하고**, 그 비용은 위 어디에도 세지 않았다.

**그럼 이번 작업에서 남는 것은 무엇인가.** 셋이다.

1. **설계가 실행 가능하다는 확인** — 데이터 생성 → §3-4 분할 검사 → QLoRA → 어댑터 →
   제약 디코딩 없이도 스키마 준수까지 끊기지 않고 돈다.
2. **설계서의 오류 4건** — §12-1 의 revision·target_modules·VRAM 표·seq_len.
   승인 QA 가 모여 진짜 학습에 들어갈 때 **이 넷은 이미 해결된 상태로 시작**한다.
3. **비용의 크기** — 학습 20.8분/60step·15.38 GiB, 추론 토큰당 +27%.
   다음 판단은 이 숫자 위에서 한다.

### 12-4. 다시 시도한다면 무엇을 바꾸나

| 바꿀 것 | 근거 |
|---|---|
| `max_seq_length` 2048 → **1792** | 실측 최대 1,788. 활성값이 준다 |
| `prepare_model_for_kbit_training()` **제거** | fp32 업캐스트 10.50 GiB. compute dtype 이 이미 bf16 이다 |
| `target_modules` 에서 **비전·오디오 타워 제외** | 텍스트 판정 설명에 이미지 인코더는 필요 없다 |
| 분할을 **`content_hash` 연결성분 단위**로 | 실데이터에서 §3-4 ①을 통과하는 유일한 방법 |
| 평가에 **OOD 합성셋** 추가 | "외웠나 배웠나"를 가른다. 지금은 갈리지 않는다 |
| 지연 비교는 **출력 토큰 수를 고정**하고 | 어댑터 비용과 출력 길이를 분리해야 한다 |
