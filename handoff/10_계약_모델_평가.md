## 0. 먼저 — 지금까지 한 일에 대한 평가

**파이프라인은 잘 만들었다.** 특히 이 셋은 그대로 간다.

- `rag_config.py` 단일 출처 + e5 접두사 자동 부착 (직접 `encode` 금지) — 조용한 성능 저하를 구조로 막았다

## 1. ★채점 지표 — 이걸로 잰다

### 지금 채점이 못 잡는 것

```
채점 = 출처를 표기했는가?  +  거부 표현이 있는가?
```

이 둘은 아래를 **통과시킨다**:

> 틀린 조항을 인용하면서 **"보장됩니다"** 라고 답한 경우 → 출처가 붙어 있으므로 **O**

우리 서비스에서 가장 위험한 실패가 정확히 채점망을 빠져나간다.

### 생성 지표 5개 (계약)

**새로 정하는 것이 아니다.** [`05_계약_AI2_판정.md`](05_계약_AI2_판정.md) §5에 이미 확정돼 있고,
원안은 `docs/reports/2026-08-01_판정_정직성_인용검증_설계.md` §4다.
**모델팀 파이프라인이 이 계약을 아직 반영하지 않았다** — 그게 이 문서의 존재 이유다.

| 지표 | 정의 | 방향 |
|---|---|---|
| **인용 정합률** | 인용한 조항 중 **넘겨준 근거에 실재하는** 비율 | 높을수록 좋음 |
| **근거 초과율** | 근거에 없는 내용을 답에 포함한 비율 | 낮을수록 좋음 |
| **적절한 기권율** | 근거가 부족할 때 `unknown` 을 낸 비율 | 높을수록 좋음 |
| **과잉 기권율** | 근거가 충분한데 `unknown` 을 낸 비율 | 낮을수록 좋음 |
| **스키마 준수율** | 구조화 출력을 형식대로 낸 비율 | 높을수록 좋음 |

★**모델 선정 기준은 "지시를 잘 따르는가"가 아니라 "검사에 걸리는가"다.**
지시 준수는 프롬프트·질문마다 달라져 측정이 애매하다. 위 5개는 **코드로 검증된다.**

### 검색 지표 4개 (계약)

hit@1 / hit@5 / MRR 은 **모델 비교용으로는 유지하되, 서비스 품질 지표로 쓰지 않는다.**
보장 판정에는 보장조항 + 면책 + 정의 + 특약 + 대기기간 + 한도가 **함께** 필요하기 때문이다.

| 지표 | 정의 |
|---|---|
| **근거세트 recall** | 판정에 필요한 조항 **집합**이 top-k 에 다 들어왔는가 |
| ★**면책 누락률** | 정답에 면책조항이 필요한데 top-k 에 없는 비율 |
| **오판본 혼입률** | 다른 보험사·다른 세대 조항이 근거에 섞인 비율 |
| **기권 가능성** | 근거가 없을 때 빈 결과를 내는가 (억지로 채우지 않는가) |

> `README_EMBEDDING.md` §11에 **부수 이슈**로 적힌
> *"긍정형 질문 ↔ 면책 조항 매칭 약함"("비만도 보장되나요?" → 보상하지 않는 사항을 못 찾음)* 은
> 주변 이슈가 아니라 **이 서비스의 핵심 위험**이다.
> `docs/plans/2026-07-31_1900_팀MVP6_구조설계.md` §2-1 — **"조항만 주면 안 된다. 면책조항을 함께 반환한다."**
> **핵심 테스트군으로 승격한다.**

## 2. 인용 검증 — ★새로 만들 것이 없다. 이미 저장소에 있다

### 2-0. ★경로 주의 — 계약서 `05` 의 import 경로가 틀렸다

[`05_계약_AI2_판정.md`](05_계약_AI2_판정.md) §3은 `app.insurance.citation_guard` 라고 적었는데
**그 모듈은 없다**(`ModuleNotFoundError`). 실제 위치는 아래다. 실측 확인했다.

```python
from app.core.domain.citation_guard import EvidenceClause, verify   # ← 실제 경로
```

| 계약서 표기 | 실제 |
|---|---|
| `app/insurance/citation_guard.py` | **`app/core/domain/citation_guard.py`** |
| `app/insurance/kcd.py` | `app/core/domain/kcd_ranges.py` |
| `app/insurance/precheck.py` | `app/core/usecases/precheck.py` |
| `app/insurance/assess.py` | **아직 없음** (송채영 작업분) |

테스트는 `tests/test_citation_guard.py` 에 이미 있고 올바른 경로를 쓴다.
**`05` 를 고치거나 모듈을 옮기거나 — 둘 중 하나를 정해야 한다.**

### 2-1. 구조화 출력 형식 (계약서 `05` §4 그대로)

자유 텍스트는 검증할 수 없다. 형태를 고정한다.

```json
{
  "verdict": "likely_covered | unlikely | needs_documents | needs_expert",
  "cited_clauses": ["보통약관/제9조", "특별약관/제3조"],
  "quotes": { "보통약관/제9조": "실제 원문에서 따온 문장" },
  "reason": "사람이 읽을 설명"
}
```

### ★`verdict` 값 주의 — 계약서 `05`·`08` 이 틀렸다

**실제 코드**(`app/core/domain/insurance.py` 의 `Verdict`)는 아래 4값이다.

| 값 | 뜻 |
|---|---|
| `likely_covered` | 보장 조항 근거가 있다 |
| `unlikely` | 면책 조항 근거가 있다 |
| `needs_documents` | 조건부 — 요양급여 해당 여부 등 확인이 필요하다 |
| `needs_expert` | ★근거가 부족하다. 사람이 봐야 한다 — **정상 결과** |

[`05`](05_계약_AI2_판정.md) §4 와 [`08`](08_계약_프론트.md) §1 은
`covered / conditional / not_covered / unknown` 으로 적혀 있는데 **그 값은 코드에 없다.**
`app/schemas/precheck.py` 주석이 그 경위를 남겨 두었다 —
*"처음에 그 4값을 여기 새로 만들었다가 도메인에 이미 `Verdict` 가 있는 것을 뒤늦게 알았다."*
**도메인 4단이 정본이다.** 이진 판정을 만들지 않는다는 원칙이 값 자체에 박혀 있다.

- 기권 여부는 별도 필드 **`abstained: bool`** 로 나간다. `verdict` 만 보고 판단하지 않는다
- `needs_expert` 는 **정상 답이다.** 부끄러운 답이 아니다
- `cited_clauses` 가 비어 있으면 `likely_covered`/`unlikely` 를 낼 수 없다

### 2-2. 인용 검증을 평가 하네스에 붙인다

`verify()` 가 이미 세 가지를 검사한다 — 인용 조항 실재(**폐기**) · `제N조` 미선언(경고) ·
인용문이 원문의 실제 일부인지(경고).

```python
r = verify(cited_clauses=out.cited_clauses,
           evidence=[EvidenceClause(qualified_no=c.qualified_no, text=c.text) for c in bundle.clauses],
           answer_text=out.reason, quotes=out.quotes)
```

**평가에서 할 일은 이걸 호출해 `r.ok` 비율을 집계하는 것뿐이다** — 그게 인용 정합률이다.
`rag_llm_eval.py` 의 자동 채점을 여기에 연결하면 §1의 지표 5개 중 3개가 바로 나온다.

**프롬프트를 무시하는 모델이라도 이 검사는 통과하지 못한다.**
"제9조에 따르면…"이라고 지어내면 제9조가 근거에 없으므로 답이 폐기된다.

### 2-3. ★조항 식별자 주의 — `qualified_no` 만으로는 유일하지 않다

전처리 산출물 실측: `qualified_no` 문서내 중복이 s2 62,477건 / **s4 에도 31,085건** 남아 있다.
특별약관마다 조 번호가 1부터 다시 시작하기 때문이다.

```
식별키 = (policy_version, section, clause_no)      ← 이 셋을 함께 써야 유일해진다
```

`docs/handoff/02_ERD_및_스키마.md` 의 **`core.policy_clause`** 가 이 키를 쥔다
(구 이름 `clause_occurrence`). ★식별키는 `UNIQUE(document_extraction_id, ordinal)` 이고
**`qualified_no` 는 유일하지 않다** — 문서 내 중복 31,085건. 평가셋 키를 `qualified_no` 로 잡으면
서로 다른 조항이 같은 키가 된다.
**대조를 `제N조` 문자열로만 하면 다른 특약의 제9조를 통과시킨다.**

## 3. 평가셋 규칙

### 3-1. 사전 동결

**문항은 결과를 보기 전에 확정하고 잠근다.** S5(고객센터 번호)를 결과 확인 후 무효 처리한 것은
올바른 판단이었지만, 그 방식이 반복되면 **사후 해석**이 된다. 문항 확정 시점에
사전 검색으로 실재 여부를 확인하고, 그 이후에는 빼지 않는다.

### 3-2. 표본 크기를 정직하게 말한다

- 6문항 스모크에서 S5가 무효면 **유효 5문항**이다. 여기서 "품질 대등", "faithfulness 실증",
  "sLLM 티어링 근거"는 도출되지 않는다.
- 30문항도 12개사 × 상품 × 판본 × 특약 기준으로는 **보험사당 2.5문항**이다.
- 위험 사례 30건에서 오류 0건이어도 **실제 오류율 95% 상한은 약 10%** 다(rule-of-three).
  "보장됩니다"의 오탐률을 주장하기엔 너무 넓다.

### 3-3. 층화 + 위험군 (계약)

| 군 | 최소 | 내용 |
|---|---|---|
| 답있음 | 20 | 보험사·세대 층화 |
| 답없음 | 5 | **사전 검색으로 실재 없음 확인** (S5 교훈) |
| 용어 | 5 | 정상 용어에서 선별 |
| ★**위험군** | **추가** | 긍정질문↔면책 · 이중부정 · 표/각주 · 복수 특약 · **판본 불명** · 계약정보 부족 · 상충 조항 |

위험군이 핵심이다. 나머지는 잘 나와도 서비스가 안전하다는 뜻이 아니다.

### 3-4. 채점 프로토콜

사람 채점은 **사전 rubric · 블라인드 · 2인 독립 · 불일치 조정 · 원문 페이지 확인**으로 한다.
CSV 원문을 읽는 것 자체는 옳지만, 기준 없이 읽으면 모델 선호가 개입한다.

## 4. 검색과 생성을 분리해 기록한다

S2(삼성 면책사항)에서 두 모델 모두 거부한 건에 대한 해석:

| 층 | 판정 |
|---|---|
| 생성기 | **정상** — 부실한 근거로 추측하지 않았다 |
| 시스템(end-to-end) | **실패** — 답할 수 있는 약관 질문에 답하지 못했다 |

**두 줄을 다 적어야 한다.** "LLM은 올바르게 행동했다"만 적으면 검색 실패가 가려진다.

같은 이유로, **두 모델의 O/X 패턴이 6문항 전부 같았다**는 관찰의 결론은
"두 모델이 대등하다"가 아니라 **"현재 실험이 두 모델을 구분할 능력이 없다"** 이다.
공통 retriever 가 병목이면 생성 모델 차이는 가려진다.

## 5. 색인 입력 계약 — 재색인 전에 맞출 것

### 5-1. 입력은 s4 산출물로 통일한다

```
data/structured/{보험사}/s4_pymupdf-1.28.0/{sha12}.clauses.json
```

s2 대비 개선폭(전수 실측):

| 지표 | s2 | s4 |
|---|---:|---:|
| `qualified_no` 문서내 중복 | 62,477 | **31,085** |
| 20,000자 초과 조항 | 897 | **391** |
| `sale_start` 없음 | 421 | **4** |

★S2 실패 원인으로 지목한 `'보상하지 않는 사항)'` 같은 **조각 청크가 정확히 s2 결함의 산물**이다.
s2 위에서 재색인하면 같은 실패를 더 큰 규모로 재생산한다.

### 5-2. 계보를 표기한다

색인 메타에 **원본 sha → s버전 → 청크 ID → 컬렉션 버전**을 남긴다.
지금은 `policy_e5` 가 어느 전처리 산출물에서 왔는지 저장소에서 확인할 수 없다
(`chunks_main.jsonl` 이 저장소에 없다).

### 5-3. "재색인 전후 비교"는 그대로는 성립하지 않는다

조항 경계가 바뀌므로 **정답 청크 ID가 깨진다.** gold 를 **원문 페이지·의미 단위 기준으로
재정합**한 뒤 비교해야 한다. S2를 검증 지표로 지정한 발상은 좋으나 재정합이 전제다.

### 5-4. 판정에 쓸 수 없는 것은 색인 단계에서 표시한다

| 표시 | 처리 |
|---|---|
| `parse_status != "ok"` | 검색엔 쓰되 **판정 근거로는 안 씀** |
| `chunk_type == "page_fallback"` | 〃 |
| `date_confidence == "unknown"` | **"어느 시점 약관인지 확인 불가"** 로 답한다 |

s4 실측: `ok` 1,240 (91%) · `suspect` 108 (8%) · `no_clause_heads` 19 (1%)

### 5-5. 분모를 맞춘다

`PDF 1,858건` 은 저장소의 어느 값과도 일치하지 않는다.

```
물리 파일 1,690 · 고유 sha 1,367 · 매니페스트 1,765 · 격리 336 · s4 산출물 1,367
```

현재 색인이 **4개사 기준**이면 벤치·스모크 결과는 4개사 범위의 탐색 결과이고,
**12개사로 일반화할 수 없다.** 문서에 그렇게 적는다.

## 6. ★외부 전송 경계 — 모델 선정보다 앞선다

티어링안 *"무거운 판단은 GPT-4.1, 가벼운 기능은 Qwen3"* 는
**진료비 내역서·처방전을 외부 API로 보내는 구조**를 함의한다.

임베딩을 로컬 e5로 고른 이유가 *"민감정보 외부 전송 없음"* 이었는데, 생성 단계에서 뒤집힌다.
`docs/plans/2026-07-31_1600_MVP_기능선정.md` §3(최소 개인정보 통제)·§4(비범위)에 걸린다.

**먼저 정할 것 — 무엇을 외부로 보내는가.**

| 경계안 | 외부 모델 사용 |
|---|---|
| 마스킹된 질문 + 약관 조항만 전송 (원문 의료자료 미전송) | 가능 |
| 진료비 내역서·처방전 원문 전송 | **불가** |

이건 4축(정확도·속도·비용·보안) 중 하나가 아니라 **선행 제약**이다.
경계를 정하기 전에는 티어링 결론을 내지 않는다.

| "GPT-4.1과 Qwen3 품질 대등" | "6문항(유효 5)에서 **차이를 관측하지 못함**. 구분력 부족" |
| "faithfulness 실증" | "distractor 1건에 속지 않음. 일반화 근거 아님" |
| "sLLM 티어링 근거 확보" | "티어링은 **외부 전송 경계 확정 후** 판단" |
| "PDF 1,858건" | 분모 정의 병기 (물리/고유/매니페스트 중 무엇인지) |

## 8. 하지 않을 것

- 자동 채점 결과를 **품질 점수**라고 부르지 않는다 (형식 검사다)
- 결과를 본 뒤 문항을 빼지 않는다
- 필터(`insurer`/`generation`)를 정답으로 준 평가 수치를 **실사용 성능으로 말하지 않는다**
  — 사용자는 자기 약관 세대를 모른다
- 검색이 못 찾은 것을 **"LLM이 잘 거부했다"로만 기록하지 않는다**
- 근거 없이 `likely_covered`/`unlikely` 를 내지 않는다. `needs_expert` 가 정상 답이다
